Java 8 LTS

The release that reshaped how Java code is written. Lambda expressions, the Streams API, and default methods brought functional-style programming into the language itself, while Optional, the new java.time API, and CompletableFuture fixed three of Java's longest-standing API pain points in one release. This is where this guide's Java 9–26 story begins.

⚠ Migration watch-outs (7 → 8).
  • PermGen removed — -XX:PermSize/-XX:MaxPermSize are now silently ignored (no error) in favor of Metaspace, which grows in native memory. Full story → JVM Memory & GC deep-dive.
  • DocLint checks Javadoc comments strictly by default — malformed HTML in doc comments that javac used to ignore can now fail a build.
  • Default methods + multiple interfaces: implementing two interfaces that declare the same default method signature is a compile error unless your class overrides it — rare, but a real new failure mode that didn't exist in 7.
  • Nashorn replaces Rhino as the bundled JavaScript engine — scripts relying on Rhino-specific behavior may need adjustment.

1 · Language features

Lambda expressions

Why it matters: passing behavior around used to mean an anonymous class — four lines of ceremony to express one line of logic. Lambdas make the behavior itself the value.

Before — anonymous class
Comparator<String> byLength = new Comparator<String>() {
  @Override
  public int compare(String a, String b) {
    return Integer.compare(a.length(), b.length());
  }
};
button.addActionListener(new ActionListener() {
  public void actionPerformed(ActionEvent e) {
    System.out.println("clicked");
  }
});
After — lambda
Comparator<String> byLength = (a, b) -> Integer.compare(a.length(), b.length());
button.addActionListener(e -> System.out.println("clicked"));

Functional interfaces — java.util.function

Why it matters: a lambda needs a target type — an interface with exactly one abstract method. Java 8 shipped a standard library of them so you rarely need to declare your own.

Function<Integer, Integer> square = x -> x * x;      // T -> R
Predicate<Integer>         isEven = x -> x % 2 == 0;  // T -> boolean
Supplier<String>           sup    = () -> "value";    // () -> T
Consumer<String>           con    = System.out::println; // T -> void
BiFunction<Integer,Integer,Integer> add = (a, b) -> a + b;

System.out.println(square.apply(5));      // 25 — verified
// mark your own with @FunctionalInterface for a compiler check:
@FunctionalInterface
interface Greeter { String greet(String name); }

Method references

Before — a lambda that just forwards
names.forEach(s -> System.out.println(s));
list.stream().map(s -> s.toUpperCase());
After — four forms of ::
names.forEach(System.out::println);       // instance method on a particular object
list.stream().map(String::toUpperCase);   // instance method, unbound receiver
list.stream().map(Integer::parseInt);     // static method
list.stream().map(Order::new);            // constructor reference

Default & static methods on interfaces

Why it matters: before 8, adding any method to a published interface broke every existing implementer. Default methods let an interface evolve without breaking anyone.

Before — adding a method breaks every implementer
interface Greeter {
  String greet(String name);
  // adding greetLoudly() here breaks every class that implements Greeter
}
After — default method, source-compatible
interface Greeter {
  String greet(String name);
  default String greetLoudly(String name) {   // existing implementers unaffected
    return greet(name).toUpperCase();
  }
  static Greeter simple() {                    // static methods too
    return name -> "Hello, " + name;
  }
}
// verified: Greeter.simple().greetLoudly("Ada") -> "HELLO, ADA"

This is exactly the mechanism that let Collection/Map grow forEach, stream(), removeIf and more without breaking every existing collection implementation ever written — see §2.

Repeating annotations & type annotations

Before — a wrapper array annotation, always
@Schedules({ @Schedule(day="Mon"), @Schedule(day="Fri") })
class Job {}
After — repeat it directly
@Retention(RetentionPolicy.RUNTIME)
@Repeatable(Schedules.class)   // still needs a container annotation declared...
@interface Schedule { String day(); }

@Schedule(day = "Mon")
@Schedule(day = "Fri")          // ...but you write this at the use site
class Job {}
// Job.class.getAnnotationsByType(Schedule.class) -> [Mon, Fri] — verified
Gotcha, verified: forgetting @Retention(RetentionPolicy.RUNTIME) on the annotation means getAnnotationsByType silently returns an empty array at runtime — no error, just missing data.

Type annotations (JSR 308) let annotations appear anywhere a type is used, not just on declarations — List<@NonNull String> — mainly consumed by external static-analysis tools like Checker Framework rather than the JDK itself.

2 · New & updated APIs

The Streams API

Why it matters: filtering, transforming and aggregating collections in bulk, declaratively, instead of a mutable-accumulator for loop every time.

Before
List<String> names = new ArrayList<>();
for (Employee e : employees) {
  if (e.salary() > 50_000) names.add(e.name().toUpperCase());
}
Collections.sort(names);
After — Streams
List<String> names = employees.stream()
    .filter(e -> e.salary() > 50_000)
    .map(e -> e.name().toUpperCase())
    .sorted()
    .collect(Collectors.toList());

Streams are deep enough to earn their own page — creating streams, every intermediate/terminal operation, reduce's three overloads, the full Collectors catalogue, custom collectors, and parallel streams → Stream API complete guide.

Optional<T>

Before — null checks, or a silent NPE later
User user = findUser(id);         // might return null
if (user != null) {
  String name = user.getName();
  System.out.println(name);
} else {
  System.out.println("unknown");
}
After — the absence is in the type
Optional<User> user = findUser(id);
System.out.println(
    user.map(User::getName).orElse("unknown"));
// verified: opt.map(String::length).orElse(0)

The java.time API (JSR-310)

Why it matters: the old java.util.Date/Calendar were mutable, not thread-safe, had months indexed from zero, and threw checked exceptions for basic parsing — widely regarded as one of Java's worst original API designs. java.time replaces all of it.

Before — mutable, zero-indexed months, unsafe
Calendar cal = Calendar.getInstance();
cal.set(2014, Calendar.MARCH, 18);   // MARCH is month 2, not 3 — a classic bug source
cal.add(Calendar.DAY_OF_MONTH, 10);
Date result = cal.getTime();
SimpleDateFormat fmt = new SimpleDateFormat("yyyy-MM-dd");  // NOT thread-safe
System.out.println(fmt.format(result));
After — immutable, readable, thread-safe
LocalDate date = LocalDate.of(2014, Month.MARCH, 18);
LocalDate result = date.plusDays(10);
System.out.println(result.format(DateTimeFormatter.ISO_LOCAL_DATE));
// verified: "2014-03-28"

Duration.ofMinutes(90);              // amount of time, machine-precision
Period.ofMonths(3);                  // amount of time, human/calendar terms
Instant.now();                       // a point on the machine timeline (UTC)
ZonedDateTime.now(ZoneId.of("Asia/Kolkata"));   // time zone aware

CompletableFuture

Before — plain Future, no composition
Future<String> f = executor.submit(() -> fetch());
String result = f.get();          // blocks; can't chain another async step
String upper = result.toUpperCase();  // has to happen after the blocking get()
After — composable, non-blocking chains
CompletableFuture<String> cf = CompletableFuture
    .supplyAsync(() -> fetch())          // fetch() returns "async result!"
    .thenApply(String::toUpperCase)
    .exceptionally(ex -> "fallback");
System.out.println(cf.get());   // verified real output: "ASYNC RESULT!"

Collection default methods, Base64, and more

Before
for (Map.Entry<String,Integer> e : scores.entrySet()) {
  System.out.println(e.getKey() + "=" + e.getValue());
}
Integer old = scores.get("Ada");
scores.put("Ada", old == null ? 5 : old + 5);

for (Iterator<Integer> it = nums.iterator(); it.hasNext(); ) {
  if (it.next() % 2 == 0) it.remove();
}

String encoded = new sun.misc.BASE64Encoder().encode("hi".getBytes());  // internal, unsupported API
After
scores.forEach((k, v) -> System.out.println(k + "=" + v));   // Map default method
scores.merge("Ada", 5, Integer::sum);                          // add-or-update in one call
scores.computeIfAbsent("Bob", k -> 0);
// verified: {Bob=0, Ada=95}

nums.removeIf(n -> n % 2 == 0);      // Collection default method
nums.replaceAll(n -> n * 10);
// verified: [10, 30, 50]

String encoded = Base64.getEncoder().encodeToString("hi".getBytes());
// verified: "aGk="  — a real, public, supported API at last

int[] arr = {5,3,1,4,2};
Arrays.parallelSort(arr);             // verified: [1, 2, 3, 4, 5]
// StringJoiner — build delimited strings without a manual loop
StringJoiner sj = new StringJoiner(", ", "[", "]");
sj.add("a").add("b").add("c");
System.out.println(sj);   // verified: "[a, b, c]"

3 · Tooling

  • Nashorn — a new, faster JavaScript engine replacing Rhino, invoked from the command line or embedded via javax.script: 
    jjs
jjs> print("hello from Nashorn")
    (Nashorn itself was later deprecated in 11 and removed in 15 — see Java 11.)
  • DocLint — javac now validates Javadoc comment syntax by default; run javadoc -Xdoclint:none to suppress it while migrating an old codebase.
  • Compact Profiles — three subsets of the full JRE (compact1/2/3) for constrained/embedded devices, letting you target less than the full platform footprint.
  • Access to parameter names at runtime — compile with -parameters and reflect on real parameter names instead of arg0, arg1 — the foundation frameworks like Spring rely on for parameter-name-based binding.

4 · JVM / performance / other

  • PermGen removed; Metaspace introduced JEP 122 — class metadata moved out of the heap into native memory that grows automatically. The long-standing OutOfMemoryError: PermGen space became OutOfMemoryError: Metaspace instead, now bounded by -XX:MaxMetaspaceSize rather than a fixed heap region. Full story → JVM Memory & GC deep-dive.
  • HashMap collision handling with balanced trees JEP 180 — when many keys land in the same bucket (pathological hashing, or hostile input), that bucket converts from a linked list to a tree, turning a potential O(n) worst case into O(log n).
  • Reduce cache contention JEP 142 — the @Contended annotation pads a field to its own cache line, avoiding false sharing between threads on multi-core hardware.
  • AES intrinsics JEP 164 — hardware AES instructions used automatically where available, meaningfully speeding up encryption.
  • Small VM JEP 148 and a large batch of security/crypto updates (TLS SNI, stronger password-based encryption, PKCS#11 on 64-bit Windows) rounded out the release.

5 · Summary cheat-sheet

Java 8 in one glance

  • Lambdas: (a, b) -> a + b; method refs: String::toUpperCase
  • Functional interfaces: Function / Predicate / Supplier / Consumer / BiFunction
  • Interfaces: default and static methods
  • Streams: collection.stream().filter().map().collect() → full guide
  • Optional: Optional<T> — absence is part of the type
  • Time: LocalDate / LocalDateTime / Duration / Period / Instant replace Date/Calendar
  • Async: CompletableFuture — composable, non-blocking chains
  • Collections: forEach / removeIf / merge / computeIfAbsent (default methods)
  • Also new: Base64, StringJoiner, Arrays.parallelSort, repeating annotations
  • JVM: PermGen → Metaspace → deep dive
