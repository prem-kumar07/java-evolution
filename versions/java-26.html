1 · Language features

Prepare to Make final Mean Final JEP 500

Why it matters: part of the "integrity by default" effort. Historically, libraries could mutate final fields via deep reflection (setAccessible), which silently broke the one guarantee final was supposed to give — and blocked the JIT from treating final fields as true constants. Java 26 begins warning so a future release can enforce it.

Before — silently allowed
Field f = obj.getClass().getDeclaredField("id");
f.setAccessible(true);
f.setInt(obj, 999);      // mutates a final field — worked
After (Java 26)
// same code now emits a warning; a future release
// will throw. Opt back in per-module only if needed:
//   --enable-final-field-mutation=<module>

Primitive types in patterns, instanceof & switch Preview (4th) JEP 530

Why it matters: extends pattern matching to primitives, so numeric type-narrowing no longer needs error-prone manual casts and range checks.

Before — manual cast & range check
Object o = 42;
if (o instanceof Integer) {
  int i = (Integer) o;
  if (i == (int) i) use(i);           // "fits" check by hand
} else if (o instanceof Double) {
  double d = (Double) o;
  use(d);
}
After (preview, Java 26)
switch (o) {
  case int i    -> use(i);
  case double d -> use(d);
  default       -> {}
}
// safe range check, no manual arithmetic:
if (bigValue instanceof int i) { use(i); }  // only matches if it fits exactly

Structured concurrency Preview (6th) JEP 525

Why it matters: approaching final after six previews — treats a group of concurrent subtasks as one unit, so a failure in one cancels the rest instead of leaking threads.

Java 26 Refinements: This release continues to polish the new Joiner API introduced in Java 25. Key changes include adding an onTimeout() hook for custom cleanup, changing Joiner.allSuccessfulOrThrow() to return a List<T> instead of a Stream<T>, and renaming the "any" joiner to Joiner.anySuccessfulOrThrow().

See the structured concurrency deep-dive for the full StructuredTaskScope API and worked examples.

2 · New & updated APIs

HTTP/3 for the HTTP Client

Why it matters: the java.net.http.HttpClient (standardised in Java 11) now speaks HTTP/3 (QUIC over UDP) — faster connection setup and better behaviour on lossy/mobile networks, with the exact same request/response API you already use.

Before — HTTP/1.1 or /2
HttpClient client = HttpClient.newBuilder()
    .version(HttpClient.Version.HTTP_2)
    .build();
HttpResponse<String> res = client.send(req, BodyHandlers.ofString());
After (Java 26)
HttpClient client = HttpClient.newBuilder()
    .version(HttpClient.Version.HTTP_3)
    .build();
HttpResponse<String> res = client.send(req, BodyHandlers.ofString());
// same call site — only the transport changes

Lazy Constants Preview (2nd) JEP 526

Why it matters: the feature previewed as "Stable Values" in Java 25, now renamed. A safe primitive for compute-once, thread-safe lazy initialisation that the JIT can fold like a real constant — replacing the classic (and easy to get subtly wrong) double-checked-locking idiom.

Before — double-checked locking
private volatile Config config;
Config get() {
  Config c = config;
  if (c == null) {
    synchronized (this) {
      c = config;
      if (c == null) config = c = loadConfig();
    }
  }
  return c;
}
After (preview, Java 26)
private final LazyConstant<Config> config = LazyConstant.of(this::loadConfig);
Config get() {
  return config.get();   // computed at most once, then treated as constant
}

Error handling — failure doesn't stick. Straight from the LazyConstant Javadoc: "If the computing function throws, the throwable is relayed to the caller and the lazy constant remains uninitialized; a subsequent call to get() may then attempt the computation again." No wrapping, no caching of the failure — every failed get() is a fresh attempt:

LazyConstant<String> risky = LazyConstant.of(() -> {
  attempts++;
  if (attempts < 3) throw new RuntimeException("transient failure #" + attempts);
  return "success on attempt " + attempts;
});

for (int i = 1; i <= 4; i++) {
  try {
    System.out.println("call " + i + ": got \"" + risky.get() + "\"");
  } catch (RuntimeException e) {
    System.out.println("call " + i + ": threw " + e.getMessage());
  }
}
// verified real output:
// call 1: threw transient failure #1
// call 2: threw transient failure #2
// call 3: got "success on attempt 3"
// call 4: got "success on attempt 3"      <- 4th call reuses the successful result, doesn't recompute
A computing function that returns null also counts as failure — verified: it throws NullPointerException at that get() call, and, same rule as above, the constant stays uninitialized. "Hence, a lazy constant can never hold a null value."

Cycle detection. If the computing function — directly, or indirectly through another LazyConstant — ends up calling get() on the very constant it's computing, that's a real bug (there's no value yet to return), and the JDK catches it immediately rather than deadlocking or recursing forever:

class A {
  static final LazyConstant<B> b = LazyConstant.of(B::new);
  A() { b.get(); }   // needs a B before A can finish constructing
}
class B {
  static final LazyConstant<A> a = LazyConstant.of(A::new);
  B() { a.get(); }   // needs an A before B can finish constructing — cycle
}

new A();
// verified real output:
// java.lang.IllegalStateException: Recursive invocation of a LazyConstant's computing function
The same exception fires for the simplest possible case too — a LazyConstant whose own computing function calls its own get() — verified. This is the built-in safety net double-checked locking never had: hand-rolled DCL with a genuine self-referential dependency just deadlocks or infinite-loops instead of failing fast.

Identity, not value, equality. Two separate LazyConstants that end up holding the exact same content are still not equal — verified against the actual Javadoc wording: "equals compares the identity of this lazy constant and obj... two distinct lazy constants with the same contents are not equal." hashCode() is the identity hash. Crucially, none of equals/hashCode/toString ever trigger initialization — calling them is always safe, even on a constant you never intend to compute:

LazyConstant<String> a = LazyConstant.of(() -> "same value");
LazyConstant<String> b = LazyConstant.of(() -> "same value");
a.get(); b.get();   // both now hold "same value"

a.equals(b);   // verified: false — same content, different instances
a.equals(a);   // verified: true  — same instance

Where it's applicable. Documented and verified working in both static fields and instance fields (the two forms this page already shows); as a plain Supplier<T> under the hood, it composes with anything that takes one. The whole point of holding it in a final field is what makes JIT constant-folding possible in the first place — a non-final field defeats that.

Lazy collections — List.ofLazy & Map.ofLazy Preview (2nd) JEP 526

Yes — same preview as LazyConstant, same JEP 526, same flag. These aren't a separate feature riding along; they're part of the same preview API surface. Verified directly against javac's own error message when the flag is left off: 
$ javac PreviewCheck.java
PreviewCheck.java:5: error: <E>ofLazy(int,IntFunction<? extends E>) is a preview API and is disabled by default.
    List<Integer> squares = List.ofLazy(3, i -> i * i);
                                ^
  (use --enable-preview to enable preview APIs)
It doesn't stop at compile time either — a class file compiled with the flag still refuses to run without it, verified: 
$ java -cp . PreviewCheck
Error: LinkageError occurred while loading main class PreviewCheck
	java.lang.UnsupportedClassVersionError: Preview features are not enabled for PreviewCheck
	(class file version 70.65535). Try running with '--enable-preview'
Same rule as every other example on this page: compile and run with --release 26 --enable-preview, or it doesn't work at all.

Why it matters: the same "compute once, on first access" idea as LazyConstant, scaled to a whole collection — each element gets its own independent lazy constant under the hood, computed the first time that index or key is touched, not when the collection itself is created.

List.ofLazy(int size, IntFunction<E> computingFunction) — an unmodifiable list of a fixed size, each element computed from its index on first access:

List<Integer> squares = List.ofLazy(5, i -> expensiveSquare(i));

squares.get(3);   // computeCalls: 0 -> 1 (computed now, not at list-creation time)
squares.get(3);   // computeCalls stays at 1 — cached, not recomputed
squares.get(1);   // computeCalls: 1 -> 2 (a different index, computed independently)
squares.set(0, 100);   // verified: throws UnsupportedOperationException — it's unmodifiable
Verified real output (with a counter inside expensiveSquare): 
list created, computeCalls so far = 0
squares.get(3) = 9, computeCalls = 1
squares.get(3) again = 9, computeCalls = 1
squares.get(1) = 1, computeCalls = 2
set() rejected: unmodifiable, as documented

Map.ofLazy(Set<K> keys, Function<K,V> computingFunction) — same idea keyed by an explicit, fixed key set instead of an index range:

Set<Locale> supported = Set.of(Locale.US, Locale.FRANCE, Locale.GERMANY);
Map<Locale, String> bundles = Map.ofLazy(supported, loc -> loadResourceBundle(loc));

bundles.get(Locale.US);       // computed now, on first access
bundles.get(Locale.US);       // cached, not recomputed
bundles.get(Locale.JAPAN);    // JAPAN was never in the declared key set — returns null, no crash
Verified real output: 
bundles.get(US) = bundle-for-en_US, computeCalls = 1
bundles.get(US) again = bundle-for-en_US, computeCalls = 1
bundles.get(FRANCE) = bundle-for-fr_FR, computeCalls = 2
bundles.get(JAPAN) = null, computeCalls = 2
bundles.containsKey(JAPAN) = false
Verified on this JDK 26 build: List.ofLazy/Map.ofLazy exist (both preview along with LazyConstant itself), but Set.ofLazy does not yet — javap java.util.Set shows no such method here. It's planned for a future release, not this one.

PEM encodings of cryptographic objects Preview (2nd) JEP 524

Why it matters: read/write keys & certificates in the standard PEM text format (-----BEGIN...-----) directly — no hand-rolled Base64/DER parsing, no third-party library just to save a key to a .pem file.

Before — manual Base64 + DER wrapping
byte[] der = privateKey.getEncoded();          // raw DER bytes
String b64 = Base64.getMimeEncoder(64, new byte[]{'\n'}).encodeToString(der);
String pem = "-----BEGIN PRIVATE KEY-----\n" + b64 +
             "\n-----END PRIVATE KEY-----\n";   // easy to get the wrapping wrong
After (preview, Java 26)
PEMEncoder encoder = PEMEncoder.of();
String pem = encoder.encodeToString(privateKey);   // correct PEM, every time

PEMDecoder decoder = PEMDecoder.of();
PrivateKey decoded = decoder.decode(pem, PrivateKey.class);
// verified: round-trips byte-for-byte identical to the original key

Vector API 11th incubator JEP 529

Why it matters: explicit SIMD (Single Instruction, Multiple Data) — process several array elements in one CPU instruction instead of one at a time. Still incubating pending Project Valhalla (value types), which will let it reach full native speed.

import jdk.incubator.vector.*;

static final VectorSpecies<Integer> SPECIES = IntVector.SPECIES_PREFERRED;

int[] a = {1, 2, 3, 4, 5, 6, 7, 8};
int[] b = {10, 20, 30, 40, 50, 60, 70, 80};
int[] result = new int[a.length];

int i = 0, upperBound = SPECIES.loopBound(a.length);
for (; i < upperBound; i += SPECIES.length()) {
  var va = IntVector.fromArray(SPECIES, a, i);
  var vb = IntVector.fromArray(SPECIES, b, i);
  va.add(vb).intoArray(result, i);         // adds SPECIES.length() ints at once
}
for (; i < a.length; i++) result[i] = a[i] + b[i];   // scalar tail

// verified: result = [11, 22, 33, 44, 55, 66, 77, 88]; SIMD lane width = 4 on this CPU
// run with:  java --add-modules jdk.incubator.vector Demo.java

3 · Tooling

Ahead-of-Time Object Caching with Any GC JEP 516

Why it matters: Project Leyden's AOT cache (pre-warmed classes and heap objects) was previously tied to specific collectors; now it works regardless of the garbage collector you choose, so more applications get the faster-startup benefit without giving up their GC of choice.

// training run — records what the app touches at startup
java -XX:AOTCacheOutput=app.aot -XX:+UseZGC -jar app.jar --record-run

// production run — reuses the cache, works with the GC you actually want
java -XX:AOTCache=app.aot -XX:+UseZGC -jar app.jar

Full lineage (CDS → AppCDS → AOT Cache), verified GC-mismatch behavior, and measured startup-time numbers → AOT Cache deep-dive.

4 · JVM / performance / other

  • G1: improved throughput by reducing synchronization JEP 522 — less internal locking overhead in the default collector, meaning better throughput with no config changes for most apps.
  • Applet API removed Removed — the last of the applet era is gone (deprecated back in Java 17). Any lingering java.applet.* usage now fails to compile.

5 · Summary cheat-sheet

Java 26 in one glance

  • HTTP/3: .version(HttpClient.Version.HTTP_3) — same API, faster transport
  • Integrity: "final means final" — deep reflection on final fields now warns
  • Startup: AOT object caching works with any GC (Project Leyden)
  • Perf: faster G1 (less synchronization); Applet API removed
  • Preview: primitive patterns (4th), structured concurrency (6th), lazy constants (2nd), PEM encodings (2nd)
  • LazyConstant: failed get() retries next call (not cached); recursive get() throws IllegalStateException; equals is identity-only; null content is never allowed.
  • Lazy collections: List.ofLazy(size, IntFunction), Map.ofLazy(keys, Function) — per-element lazy constants; no Set.ofLazy yet.
