Set up your machine

Quick start & tooling

Install one or more JDKs, switch between them, and learn the fastest ways to try features — JShell, single-file programs, preview features and incubator modules.

1 · Install a JDK

Pick a build of OpenJDK. Any of these give you the same language; they differ in support/branding:

  • Eclipse Temurin (Adoptium) — the popular community default.
  • Oracle JDK — Oracle's build.
  • Amazon Corretto, Azul Zulu, Microsoft / Liberica — vendor builds, often with extras.

Verify what you have:

java -version      # runtime version
javac -version     # compiler version
java --list-modules | head   # JDK modules available

2 · Install & switch between versions

You will want several JDKs installed at once (e.g. 17, 21, 25). Use a version manager.

SDKMAN! (macOS / Linux / WSL) — recommended

curl -s "https://get.sdkman.io" | bash        # install SDKMAN
sdk list java                                  # see available builds
sdk install java 25-tem                        # install Temurin 25
sdk install java 21.0.5-tem
sdk use java 25-tem        # switch for THIS shell only
sdk default java 21.0.5-tem   # set the global default

jenv (per-directory switching)

brew install jenv
jenv add /Library/Java/JavaVirtualMachines/temurin-25.jdk/Contents/Home
jenv global 21       # default
jenv local 25        # pin THIS project (writes .java-version)

Homebrew (macOS)

brew install openjdk@25 openjdk@21 openjdk@17

Manual — set JAVA_HOME

macOS / Linux (bash/zsh)
export JAVA_HOME=$(/usr/libexec/java_home -v 25)
export PATH="$JAVA_HOME/bin:$PATH"
# Linux: JAVA_HOME=/usr/lib/jvm/temurin-25
Windows (PowerShell)
$env:JAVA_HOME = "C:\Program Files\Java\jdk-25"
$env:Path = "$env:JAVA_HOME\bin;" + $env:Path

3 · JShell — the Java REPL Added in 9

The fastest way to try a snippet without a class, main, or compile step.

jshell                    # start the REPL
jshell> var xs = List.of(1, 2, 3)
xs ==> [1, 2, 3]
jshell> xs.stream().mapToInt(i -> i).sum()
$2 ==> 6
jshell> /exit

# useful commands
jshell> /vars      /methods     /imports     /list
jshell> /save mysession.jsh    # save your session
jshell --enable-preview        # REPL with preview features on
Tip. Pipe a script in: jshell myscript.jsh, or feed stdin with echo 'System.out.println("hi")' | jshell -.

4 · Run a single source file — no compile step Added in 11

Since Java 11 (JEP 330) you can run a .java file directly; the JDK compiles it in memory.

Before — compile then run
// Hello.java
public class Hello {
  public static void main(String[] a) {
    System.out.println("Hi");
  }
}
// terminal:
javac Hello.java   // -> Hello.class
java Hello
After — run directly
// Hello.java  (same file)
java Hello.java    // compiles + runs in one step

// pass args after the file name:
java Hello.java arg1 arg2

Multi-file source programs Added in 22

JEP 458 extended this: if the file you launch references other .java files in the same source tree, they are compiled on demand too — no build tool for small programs.

java Main.java     # also compiles Helper.java, model/User.java, ... as needed

Shebang scripts

Make a Java file executable like a shell script (the file need not end in .java):

#!/usr/bin/env java --source 25
public class App {
  public static void main(String[] a) { System.out.println("script!"); }
}
// then:  chmod +x app  &&  ./app

5 · Try preview language features

A preview feature is a finished-but-not-permanent language/VM feature. You must opt in at both compile and run time, and pass --release matching your JDK. Examples in this guide that are still preview show a Preview badge.

Compile with preview
javac --release 25 --enable-preview Demo.java
Run with preview
java --enable-preview Demo

# single-file shortcut (compile+run together):
java --enable-preview --source 25 Demo.java
Gotcha. A class file compiled with --enable-preview is tied to that exact JDK version and refuses to run on any other. Preview APIs/syntax can change or be removed in the next release — never ship them to production.

6 · Try incubator modules

An incubator module is a non-final API (a whole library, e.g. the Vector API) shipped under a jdk.incubator.* module. You add the module rather than flip a preview flag.

// compile & run code that uses jdk.incubator.vector
javac --add-modules jdk.incubator.vector Simd.java
java  --add-modules jdk.incubator.vector Simd

// see all incubator modules in your JDK:
java --list-modules | grep incubator

September 2017

Java 9

The big structural release: the module system (JPMS) reorganised the JDK itself. Alongside it came JShell, collection factory methods, a reactive Flow API, CompletableFuture timeouts, the Stack-Walking API and many smaller language tidy-ups.

ModulesJPMS — modular JDK (~90 modules)
JShellofficial REPL
List.of()immutable collection factories
Flowreactive streams
jlinkcustom runtime images
⚠ Migration watch-outs (8 → 9).
  • Strong encapsulation of JDK internals — reflective access to sun.*/internal APIs now warns (and later fails). Run jdeps --jdk-internals your.jar first.
  • Split packages are illegal on the module path — two JARs sharing a package break.
  • _ is no longer a valid identifier.
  • New version string (9, not 1.9) — regexes that parsed 1.x break.
  • Applet API and several GC flag combinations deprecated.

1 · Language features

Private methods in interfaces

Why it matters: Java 8 gave interfaces default methods, but there was no way to share logic between them without exposing it. private (and private static) interface methods fix that.

Before (Java 8)
interface Logger {
  default void info(String m)  { log("INFO", m); }
  default void error(String m) { log("ERROR", m); }
  // shared helper is forced to be public
  default void log(String lvl, String m) {
    System.out.println(lvl + ": " + m);
  }
}
After (Java 9)
interface Logger {
  default void info(String m)  { log("INFO", m); }
  default void error(String m) { log("ERROR", m); }
  private void log(String lvl, String m) {   // hidden helper
    System.out.println(lvl + ": " + m);
  }
}

Try-with-resources on effectively-final variables

Why it matters: removes a pointless extra variable when the resource already exists.

Before
// must declare a fresh variable inside the ()
BufferedReader reader = openReader();
try (BufferedReader r = reader) {
  return r.readLine();
}
After (Java 9)
BufferedReader reader = openReader();   // effectively final
try (reader) {                          // use it directly
  return reader.readLine();
}

Enhanced @Deprecated

Why it matters: deprecation can now state when and whether removal is planned, so tools and readers know how urgent it is.

Before
@Deprecated
public void oldApi() { }    // deprecated... since when? removed when?
After (Java 9)
@Deprecated(since = "9", forRemoval = true)
public void oldApi() { }    // compilers warn louder for forRemoval

Small clean-ups: diamond on anonymous classes · @SafeVarargs on private methods · _ banned

Callable<String> c = new Callable<>() { ... };     // diamond now allowed here
@SafeVarargs private void f(List<String>... xs) { }  // allowed on private methods
int _ = 3;   // COMPILE ERROR: '_' is now reserved (for future language use)

2 · New & updated APIs

Immutable collection factory methods

Why it matters: creating small immutable collections was verbose and error-prone.

Before
List<String> list = Collections.unmodifiableList(
    Arrays.asList("a", "b", "c"));
Map<String,Integer> m = new HashMap<>();
m.put("a", 1); m.put("b", 2);
m = Collections.unmodifiableMap(m);
After
List<String>  list = List.of("a", "b", "c");
Set<String>   set  = Set.of("a", "b");
Map<String,Integer> m = Map.of("a", 1, "b", 2);
// immutable, null-hostile, compact

Stream additions: takeWhile, dropWhile, ofNullable, ranged iterate

Before
// "take the leading run < 5" — no clean way
list.stream()
    .filter(x -> x < 5)   // keeps ALL <5, not just the leading run
    .collect(toList());
After (Java 9)
list.stream().takeWhile(x -> x < 5).toList();   // leading run only
list.stream().dropWhile(x -> x < 5).toList();   // skip leading run
Stream.ofNullable(maybeNull);                    // 0- or 1-element stream
Stream.iterate(1, n -> n < 100, n -> n * 2);     // for-style with predicate

New Collectors: filtering & flatMapping

Why it matters: filter/flatten inside a downstream collector (e.g. within a groupingBy), which plain filter can't do without dropping empty groups.

Before — filter drops empty groups
Map<Dept, List<Employee>> m = employees.stream()
    .filter(e -> e.salary() > 100_000)          // dept with none disappears
    .collect(groupingBy(Employee::dept));
After (Java 9)
Map<Dept, List<Employee>> m = employees.stream()
    .collect(groupingBy(Employee::dept,
             filtering(e -> e.salary() > 100_000, toList())));
// every dept kept; empty list where none match

Optional: ifPresentOrElse, or, stream

Before
if (opt.isPresent()) use(opt.get());
else handleEmpty();

List<User> users = new ArrayList<>();
for (Optional<User> o : optionals)
  o.ifPresent(users::add);
After (Java 9)
opt.ifPresentOrElse(this::use, this::handleEmpty);
Optional<User> u = primary.or(() -> fallbackLookup());   // lazy fallback
List<User> users = optionals.stream()
    .flatMap(Optional::stream).toList();                 // drop empties

CompletableFuture: timeouts & delays

Why it matters: before Java 9 you needed an external scheduler to time out an async task.

Before
// bolt on a timeout with a separate scheduler... fiddly
CompletableFuture<String> f = callAsync();
scheduler.schedule(() -> f.completeExceptionally(
    new TimeoutException()), 2, SECONDS);
After (Java 9)
CompletableFuture<String> f = callAsync()
    .orTimeout(2, SECONDS)                    // fail if too slow
    .completeOnTimeout("default", 2, SECONDS);// or fall back to a value
CompletableFuture.delayedExecutor(1, SECONDS);// delayed execution

Stack-Walking API

Why it matters: a lazy, efficient way to inspect the call stack, replacing the costly Throwable.getStackTrace() trick.

Before
// build a whole throwable just to read the caller
StackTraceElement[] st = new Throwable().getStackTrace();
String caller = st[1].getClassName();
After (Java 9)
Class<?> caller = StackWalker
    .getInstance(StackWalker.Option.RETAIN_CLASS_REFERENCE)
    .walk(s -> s.skip(1).findFirst()
                .map(StackWalker.StackFrame::getDeclaringClass)
                .orElseThrow());   // lazy, no full trace built

Reactive Streams — java.util.concurrent.Flow

Why it matters: standard interfaces (Publisher, Subscriber, Processor, Subscription) for back-pressured async streams, so libraries like RxJava/Reactor can interoperate.

Process API — inspect & control OS processes

ProcessHandle self = ProcessHandle.current();
System.out.println(self.pid());
ProcessHandle.allProcesses()
    .filter(p -> p.info().command().isPresent())
    .forEach(p -> System.out.println(p.pid() + " " + p.info().command().get()));

1 · Language features

var — local-variable type inference Added in 10

Why it matters: drops the redundant left-hand type when it's obvious from the initializer. It's still static typing — no runtime cost.

Before
Map<String, List<Integer>> scores =
    new HashMap<String, List<Integer>>();
for (Map.Entry<String, List<Integer>> e : scores.entrySet()) { }
After (Java 10)
var scores = new HashMap<String, List<Integer>>();
for (var e : scores.entrySet()) { }   // type inferred

Full rules → var deep-dive.

var in lambda parameters Added in 11

Why it matters: lets you put annotations/modifiers on inferred lambda parameters.

Before — no place for the annotation
map.forEach((k, v) -> use(k, v));
// can't annotate k or v
After (Java 11)
map.forEach((@NonNull var k, @NonNull var v) -> use(k, v));

Nest-based access control Added in 11

Why it matters: nested and outer classes can access each other's private members directly. Before, javac generated synthetic bridge methods to fake it; now the JVM understands "nests" natively (also fixes some reflection quirks).

2 · New & updated APIs

Standard HTTP Client — java.net.http

Why it matters: a modern client with HTTP/2, WebSocket and async support, replacing the clunky HttpURLConnection (incubated in 9, standard in 11).

Before — HttpURLConnection
URL url = new URL("https://api.example.com");
HttpURLConnection c = (HttpURLConnection) url.openConnection();
c.setRequestMethod("GET");
try (var in = new BufferedReader(
        new InputStreamReader(c.getInputStream()))) {
  String body = in.lines().collect(joining("\n"));
}
After — HttpClient
HttpClient client = HttpClient.newHttpClient();
HttpRequest req = HttpRequest.newBuilder()
    .uri(URI.create("https://api.example.com")).build();
HttpResponse<String> res =
    client.send(req, BodyHandlers.ofString());
String body = res.body();
// async: client.sendAsync(req, BodyHandlers.ofString())
//              .thenApply(HttpResponse::body);

New String methods

Before — hand-rolled helpers
boolean blank = s.trim().isEmpty();
String bar = String.join("", Collections.nCopies(20, "="));
for (String line : text.split("\\R")) process(line);
After (Java 11)
boolean blank = s.isBlank();
String bar = "=".repeat(20);
text.lines().forEach(this::process);
" hi ".strip();   // Unicode-aware (trim() is ASCII-only)

Files: read/write a whole string in one call

Before
byte[] bytes = Files.readAllBytes(path);
String text = new String(bytes, StandardCharsets.UTF_8);
Files.write(path, text.getBytes(StandardCharsets.UTF_8));
After (Java 11)
String text = Files.readString(path);
Files.writeString(path, text);

1 · Language features

Switch expressions Final in 14

Why it matters: switch can return a value, uses arrow labels (no fall-through), and yield for blocks — eliminating a whole class of break bugs.

Before — statement, fall-through, mutable var
int days;
switch (month) {
  case JAN: case MAR: case MAY:
    days = 31; break;
  case FEB:
    days = 28; break;
  default:
    days = 30;
}
After — expression
int days = switch (month) {
  case JAN, MAR, MAY -> 31;
  case FEB           -> 28;
  default            -> 30;
};   // exhaustive, no break, single assignment

Records Final in 16

Why it matters: immutable data carriers with generated constructor, accessors, equals/hashCode/toString.

Before — ~40 lines
public final class Point {
  private final int x, y;
  public Point(int x, int y){this.x=x;this.y=y;}
  public int x(){return x;} public int y(){return y;}
  public boolean equals(Object o){ /* ... */ }
  public int hashCode(){ /* ... */ }
  public String toString(){ /* ... */ }
}
After
public record Point(int x, int y) { }

var — local-variable type inference Java 10

var lets the compiler infer a local variable's type from its initializer. It is syntactic sugar, not dynamic typing — the variable still has one fixed, static type; you simply don't write it out.

0runtime cost — pure compile-time
localsonly (+ lambda params in 11)

The problem it solves Long generic type names had to be written twice — once on the left, once on the right — (Map<String, List<Customer>> m = new HashMap<…>()), adding noise without adding information. var removes the redundant left-hand type when it's obvious from the initializer, without any change to runtime behaviour or performance.

3 · Where you cannot use it

var x;                 // ✗ no initializer — nothing to infer
var y = null;          // ✗ null has no type
var f = () -> 42;      // ✗ lambda needs a target type
var arr = { 1, 2, 3 }; // ✗ array initializer needs a type
public var field = 1;  // ✗ fields cannot use var
var method() { }       // ✗ return types cannot use var
void m(var p) { }      // ✗ method parameters cannot use var

var is local variables only — never fields, method parameters, or return types.

4 · Rules & gotchas

  • Inferred type = the initializer's type, which may be more specific than you want: 
    var list = new ArrayList<String>();   // type is ArrayList<String>, not List<String>
    Declare the interface type explicitly if that matters.
  • Diamond + var: var m = new HashMap<>(); infers HashMap<Object,Object> — usually not intended. Put the type args on the right: var m = new HashMap<String,Integer>();
  • var is not a keyword — it's a reserved type name, so existing variables/methods named var still compile. You just can't name a class var.
  • No effect on generics inference elsewhere — it only names the local.

5 · var vs Object

Object — erases the type
Object o = "hello";
o.length();      // ✗ compile error — only Object methods available
var — keeps the precise type
var s = "hello";
s.length();      // ✓ s is a String, all String methods available

They're completely different: var preserves the exact static type; Object throws it away.

The problem it solves "Data classes" (DTOs, value objects, tuples) were almost all boilerplate — and hand-written equals/hashCode are easy to get subtly wrong (forget a field and you get silent bugs). Records make that boilerplate automatic and correct, and clearly signal intent: this type is just its data.

1 · What is a record?

You write the shape of the data in the header — the record components — and that's it. The record is implicitly final, its fields are final, and it carries no hidden state beyond those components.

Legacy — a hand-written value class
public final class Point {
  private final int x, y;
  public Point(int x, int y) { this.x = x; this.y = y; }
  public int x() { return x; }
  public int y() { return y; }
  @Override public boolean equals(Object o) {
    if (!(o instanceof Point p)) return false;
    return x == p.x && y == p.y;
  }
  @Override public int hashCode() { return Objects.hash(x, y); }
  @Override public String toString() {
    return "Point[x=" + x + ", y=" + y + "]";
  }
}
Record — same thing
public record Point(int x, int y) { }
Easy way to think about it: a record is to a data class what enum is to a set of constants — a special, purpose-built shorthand the compiler fills in for you.

2 · What the compiler generates

  • Canonical constructor taking all components in order.
  • Accessors named exactly like the component: x(), y().
  • equals/hashCode comparing all components by value.
  • toString like Point[x=1, y=2].
  • A private final field per component; the class extends java.lang.Record and is final.

3 · Customising records

Compact canonical constructor — validate / normalise

Omit the parameter list and the field assignments; write only the checks. The fields are assigned for you afterwards.

Legacy — validation in a full constructor
public Range(int lo, int hi) {
  if (lo > hi) throw new IllegalArgumentException();
  this.lo = lo;
  this.hi = hi;
}
Record — compact constructor
public record Range(int lo, int hi) {
  public Range {                       // no params, no assignments
    if (lo > hi) throw new IllegalArgumentException();
  }
}

Extra members that are allowed

public record Point(int x, int y) {
  static final Point ORIGIN = new Point(0, 0);     // static fields: OK
  public Point(int v) { this(v, v); }              // extra constructors: OK (must delegate)
  public double distanceTo(Point o) {              // instance methods: OK
    return Math.hypot(x - o.x, y - o.y);
  }
  public static Point of(int x, int y) {           // static factory: OK
    return new Point(x, y);
  }
}
Not allowed: extra instance fields (all state must be a component), and you cannot extend another class (records already extend Record). You can implements interfaces.

4 · Immutability & defensive copies

Records are shallowly immutable: the component references can't change, but if a component is itself mutable (a List, array, Date), callers can still mutate what it points to. Copy in the compact constructor for real immutability.

Leaky — shares the caller's list
public record Team(String name, List<String> members) { }

var list = new ArrayList<>(List.of("Ada"));
var team = new Team("A", list);
list.add("Bob");             // 😱 mutates the record's list too
Safe — defensive copy
public record Team(String name, List<String> members) {
  public Team {
    members = List.copyOf(members);   // immutable snapshot
  }
}
// now external mutation of the original list has no effect

7 · Serialization

Records serialize based on their components, and deserialization goes through the canonical constructor — so your validation runs on the way in. That's a real safety improvement over normal serialization, which bypasses constructors.

public record Money(String currency, long cents) implements Serializable {
  public Money {                       // runs on deserialize too
    if (cents < 0) throw new IllegalArgumentException("negative");
  }
}

Sealed classes & interfaces Final in Java 17

A sealed type declares exactly which classes may extend or implement it. That gives you a closed, known set of subtypes — the foundation for exhaustive pattern matching and for modelling "a value is one of a fixed set of shapes".

closedknown subtype set
0default needed in switch
compile-timeexhaustiveness check
3subtype modes: final / sealed / non-sealed
Java 17final (preview in 15)
The problem it solves Before, a type was either final (no subtypes) or completely open (anyone, anywhere could subclass). There was no way to say "these three types and no others", so the compiler could never know a hierarchy was complete — every switch needed a default and could silently miss a newly added case at runtime. Sealed types close the hierarchy so the compiler can reason about it.

1 · What & why

Legacy — open hierarchy, compiler can't help
public abstract class Shape { }
// Any code anywhere can do:  class Blob extends Shape {}
// so every switch over Shape must have a default and
// can silently miss new subtypes → runtime surprises.
Sealed — the set is fixed and known
public sealed interface Shape
    permits Circle, Square, Rectangle { }

public record Circle(double r)              implements Shape { }
public record Square(double side)           implements Shape { }
public record Rectangle(double w, double h) implements Shape { }

2 · The three choices each subtype must make

Every permitted subtype must declare how its own hierarchy continues — this keeps the whole tree closed and intentional.

ModifierMeaning
finalLeaf — cannot be extended further.
sealedContinues the closed hierarchy with its own permits.
non-sealedDeliberately re-opens the type to unrestricted extension.

3 · Rules

  • Permitted subtypes must be accessible to the sealed type and, unless in the same source file, in the same module (same package for the unnamed module).
  • permits is optional if all subtypes live in the same file — the compiler infers the list: 
    sealed interface Expr { }              // permits inferred below
record Num(int v) implements Expr { }
record Add(Expr l, Expr r) implements Expr { }
  • Every permitted subtype must directly extend/implement the sealed type.
  • Records are implicitly final, so they slot into permits lists perfectly.

4 · The payoff: exhaustive switch

Because the compiler knows every subtype, a switch needs no default. Add a new subtype later and every non-exhaustive switch fails to compile — a compile-time to-do list instead of a production incident.

Legacy — default + runtime failure
double area(Shape s) {
  if (s instanceof Circle c)  return Math.PI*c.r()*c.r();
  if (s instanceof Square sq) return sq.side()*sq.side();
  // forgot Rectangle...
  throw new IllegalStateException("unknown shape");  // 💥 at runtime
}
Sealed — exhaustive, checked at compile time
double area(Shape s) {
  return switch (s) {                 // no default
    case Circle c    -> Math.PI * c.r() * c.r();
    case Square sq   -> sq.side() * sq.side();
    case Rectangle r -> r.w() * r.h();
  };
  // add a new Shape → this won't compile until you handle it
}

5 · Sealed + records = algebraic data types

The killer combination: model a closed set of cases as sealed records, then switch over them with destructuring. This is the modern, type-safe replacement for the Visitor pattern.

Legacy — Visitor pattern (lots of ceremony)
interface Node { <R> R accept(Visitor<R> v); }
interface Visitor<R> { R visitNum(Num n); R visitAdd(Add a); }
final class Num implements Node {
  final int v; Num(int v){this.v=v;}
  public <R> R accept(Visitor<R> v){ return v.visitNum(this); }
}
// ...Add, plus a Visitor impl per operation. Verbose.
Sealed records + switch
sealed interface Node permits Num, Add {}
record Num(int v)          implements Node {}
record Add(Node l, Node r) implements Node {}

int eval(Node n) {
  return switch (n) {
    case Num(int v)          -> v;
    case Add(Node l, Node r) -> eval(l) + eval(r);
  };
}

2 · Switch expressions Java 14

Legacy — statement, break, fall-through
int num;

  case MON: case TUE: case WED:
  case THU: case FRI:
    num = 5; break;          // forget break → bug
  case SAT: case SUN:

}
Switch expression
int num = switch (day) {
  case MON, TUE, WED, THU, FRI -> 5;
  case SAT, SUN                -> 2;
};   // arrow: no fall-through; exhaustive over the enum

  default  -> 0;
};

3 · Pattern matching for instanceof Java 16

Legacy
if (o instanceof String) {
  String s = (String) o;      // repeat the type + cast
  if (s.length() > 3) use(s);
}
Pattern
if (o instanceof String s && s.length() > 3) {
  use(s);                     // s bound where the test is true
}

Flow scoping: the binding is in scope exactly where the pattern is known to have matched — including after an early return:

if (!(o instanceof String s)) return;
// we only reach here if it matched, so s is in scope:
System.out.println(s.length());

4 · Pattern matching for switch + guards Java 21

Legacy — instanceof ladder
String describe;
if (o instanceof Integer i && i < 0) describe = "negative";
else if (o instanceof Integer i)     describe = "int " + i;
else if (o instanceof String s)      describe = "str " + s;
else if (o == null)                  describe = "null";
else                                 describe = "other";
Switch with patterns + guards
String describe = switch (o) {
  case null                   -> "null";      // null is a case
  case Integer i when i < 0    -> "negative";  // guard with 'when'
  case Integer i              -> "int " + i;
  case String s               -> "str " + s;
  default                     -> "other";
};
  • Guards use when. The first matching label wins, so order matters.
  • null only matches if you add case null (or case null, default); otherwise a null selector throws NPE, as before.
  • Over a sealed type or enum the switch is exhaustive — no default needed.

8 · Dominance & exhaustiveness

  • Dominance: a broader pattern can't precede a narrower one — the compiler rejects the unreachable case. Put case Integer i when … before the plain case Integer i.
  • Exhaustiveness: over a sealed type/enum the compiler verifies all cases are covered. Guarded (when) cases don't count toward covering a subtype, so keep an unguarded fallback for that type.
  • Null: add case null to handle null in-switch instead of guarding before.

Mixing arrow & colon labelsNot allowed in the same switch — pick one style.

2 · Indentation — incidental vs essential whitespace

The compiler finds the line with the least leading whitespace (the closing """ counts) and strips that common margin from every line. So you can indent the block to match your code without that indentation ending up in the string.

        one
          two
        """;
// → "one\n  two\n"   (8-space margin removed; the extra 2 before "two" kept)

1 · What is a virtual thread?

A normal Java thread (a platform thread) is a thin wrapper around an operating-system thread. OS threads are expensive: each reserves ~1 MB of stack, and switching between them means a trip into the kernel. So you can realistically only have a few thousand — which is why we hide them behind thread pools and try never to block them.

A virtual thread is not tied to an OS thread. Its stack lives on the Java heap, and the JVM runs many virtual threads on a small pool of real OS threads, parking a virtual thread whenever it blocks and reusing the OS thread for someone else. A virtual thread costs a few hundred bytes, so you can have millions.

Easy analogy. Platform threads are like giving every restaurant customer their own private chef (expensive, you run out fast). Virtual threads are like a few chefs serving a huge dining room: while one order waits in the oven (blocked on I/O), the chef cooks someone else's dish. Same chefs, far more customers served.

3 · Architecture & how it works

Three pieces make virtual threads work:

  • Carrier threads — a small pool of real OS threads (a dedicated ForkJoinPool, sized to CPU cores by default) that actually execute code.
  • The JVM scheduler — decides which virtual thread runs on which carrier.
  • Continuations — the low-level mechanism that lets a virtual thread's call stack be captured to the heap and resumed later. This is what makes "pause here, come back later" possible without an OS thread.

The key verbs are mount and unmount: a virtual thread is mounted on a carrier while running, and unmounts (its stack is copied to the heap) the instant it blocks. The freed carrier immediately runs another virtual thread. When the blocking call finishes, the virtual thread is re-mounted — possibly on a different carrier.

4 · Creating virtual threads

Four ways, from lowest to highest level:

// (a) Fire-and-forget, unnamed
Thread t = Thread.startVirtualThread(() -> doWork());
t.join();

// (b) Builder — name, uncaught handler, not-yet-started
Thread t2 = Thread.ofVirtual()
    .name("worker-", 0)          // worker-0, worker-1, ...
    .start(() -> doWork());

// (c) A ThreadFactory (plug into existing APIs)
ThreadFactory factory = Thread.ofVirtual().factory();

// (d) The recommended way for many tasks — an executor
try (var exec = Executors.newVirtualThreadPerTaskExecutor()) {

7 · Pinning (and the JDK 24 fix)

Pinning is when a virtual thread cannot unmount even though it's blocked, so it holds its carrier hostage. Enough pinned threads and the carrier pool starves — you lose the whole benefit.

In Java 21–23 the two causes were:

  1. Blocking inside a synchronized block or method.
  2. Calling a native method / foreign function while blocked.

Java 24 (JEP 491) removed the synchronized cause entirely — the big one. Native-call pinning remains but is rare in application code.

Pins the carrier (JDK 21–23)
private final Object lock = new Object();

Result read() {
  synchronized (lock) {        // VT can't unmount here...
    return jdbc.query(sql);    // ...and this call BLOCKS → pinned
  }
}
Does not pin
private final ReentrantLock lock = new ReentrantLock();

Result read() {
  lock.lock();                 // VT can unmount while holding it
  try {
    return jdbc.query(sql);    // blocks cheaply
  } finally { lock.unlock(); }
}

8 · Relationship with structured concurrency

Virtual threads make it cheap to run each subtask on its own thread. Structured concurrency gives those subtasks a parent scope so they start together and are joined or cancelled together — no leaks, clear error handling. Think: virtual threads are the cheap workers; structured concurrency is the manager that owns them.

Raw virtual-thread executor — manual coordination
try (var ex = Executors.newVirtualThreadPerTaskExecutor()) {
  var uf = ex.submit(() -> loadUser(id));
  var of = ex.submit(() -> loadOrders(id));
  // if loadUser fails, loadOrders keeps running (waste);
  // cancellation is on you.
  return new Page(uf.get(), of.get());
}
Structured concurrency — one unit of work
try (var scope = StructuredTaskScope.open()) {   // Java 25 API
  var user   = scope.fork(() -> loadUser(id));
  var orders = scope.fork(() -> loadOrders(id));
  scope.join();                 // fail-fast: one error cancels siblings
  return new Page(user.get(), orders.get());
}

9 · Relationship with scoped values

ThreadLocal was tolerable when threads were few and pooled. With millions of virtual threads, per-thread copies add up and the usual "set in a pool thread and forget to clear it" bugs get worse. Scoped values are the intended companion: immutable, automatically unbound at the end of a scope, and inherited by forked subtasks.

ThreadLocal — mutable, must clean up
static final ThreadLocal<User> CUR = new ThreadLocal<>();
CUR.set(user);
try { handle(); } finally { CUR.remove(); }   // leak if forgotten
ScopedValue — immutable, self-cleaning
static final ScopedValue<User> CUR = ScopedValue.newInstance();
ScopedValue.where(CUR, user).run(() -> handle());  // auto-unbound
// deeper code: CUR.get()

11 · Virtual threads vs WebFlux / reactive

  Map<String, Future<Integer>> results = urls.stream()
      .collect(toMap(u -> u, u -> exec.submit(() -> status(http, u))));

  results.forEach((url, f) -> {
    try { System.out.println(url + " → " + f.get()); }
    catch (Exception e) { System.out.println(url + " → ERROR"); }
  });
}   // all 10,000 checks run concurrently; limited only by the network

1 · The problem with raw futures

Legacy — unstructured, leak-prone
Future<User>  u = pool.submit(() -> findUser(id));
Future<Order> o = pool.submit(() -> fetchOrder(id));
try {
  return new Response(u.get(), o.get());
  // if findUser throws, fetchOrder keeps running (leak);
  // if the caller is interrupted, both may be orphaned.
} catch (Exception e) {
  u.cancel(true); o.cancel(true);   // did you remember both?
  throw e;
}
Structured — one scope, one unit
try (var scope = StructuredTaskScope.open()) {   // Java 25 API
  var user  = scope.fork(() -> findUser(id));
  var order = scope.fork(() -> fetchOrder(id));

  scope.join();          // wait for all; first failure cancels the rest
  return new Response(user.get(), order.get());
}   // on exit, every subtask is guaranteed done

2 · The scope model

  • No leaks: try-with-resources can't exit until all forked subtasks finish/cancel.
  • Short-circuit: one failure cancels the siblings — no waiting on work you'll discard.
  • Clear hierarchy: observability tools show the real parent→child task tree.
  • Cheap: each subtask runs on its own virtual thread.

3 · Basic usage

Response handle(String id) throws Exception {
  try (var scope = StructuredTaskScope.open()) {
    var user   = scope.fork(() -> findUser(id));    // returns a Subtask<User>
    var orders = scope.fork(() -> fetchOrders(id));

    scope.join();                    // MUST join before reading results
    return new Response(user.get(), orders.get());
  }
}

4 · Joiners — choosing the completion policy

A Joiner decides when join() returns and how results/errors combine.

All must succeed (fail-fast)

  scope.fork(() -> a());
  scope.fork(() -> b());

}

  scope.fork(() -> mirror1());
  scope.fork(() -> mirror2());

}

Worked example — aggregate a product page with a 2s SLA

Legacy — futures, manual timeout & cancel
var pool = Executors.newFixedThreadPool(3);

  var pf = pool.submit(() -> productSvc.get(id));
  var rf = pool.submit(() -> reviewSvc.list(id));
  var sf = pool.submit(() -> stockSvc.check(id));
  // enforce a 2s budget across three gets... by hand
  var page = new ProductPage(
      pf.get(2, SECONDS), rf.get(2, SECONDS), sf.get(2, SECONDS));
  return page;

  // cancel whatever is still running — easy to miss one
  throw e;
} finally { pool.shutdownNow(); }
Structured concurrency
try (var scope = StructuredTaskScope.open(
        Joiner.allSuccessfulOrThrow(),
        cf -> cf.withTimeout(Duration.ofSeconds(2)))) {

  var product = scope.fork(() -> productSvc.get(id));
  var reviews = scope.fork(() -> reviewSvc.list(id));
  var stock   = scope.fork(() -> stockSvc.check(id));

  scope.join();   // 2s budget for the whole group; failures cancel siblings
  return new ProductPage(product.get(), reviews.get(), stock.get());
}

9 · Cheat sheet

Structured concurrency in one glance

  • try (var scope = StructuredTaskScope.open(joiner)) { scope.fork(...); scope.join(); }
  • Joiners: allSuccessfulOrThrow, anySuccessfulResultOrThrow, custom.
  • Read subtask.get() only after join().
  • All subtasks complete or are cancelled before the block exits — no leaks.
  • One virtual thread per subtask; add withTimeout for a group deadline.

Stream Gatherers Final in Java 24

A Gatherer is a custom intermediate stream operation — the long-missing counterpart to a custom Collector. Where collect ends a stream, gather transforms it mid-pipeline: windowing, running totals, dedup-by-key, bounded-concurrency mapping and more.

The problem it solves Streams shipped with a fixed set of intermediate ops (map, filter, limit…). Anything stateful across elements — sliding windows, running averages, "stop after N distinct", batching — meant leaving the stream for manual loops. Collector let you customise the end; Gatherer finally lets you customise the middle.

3 · Anatomy of a gatherer

A gatherer has up to four parts. Only the integrator is required.

4 · Writing your own — "distinct by key"

Legacy — stateful lambda hack (fragile)
Set<String> seen = ConcurrentHashMap.newKeySet();
var out = people.stream()
    .filter(p -> seen.add(p.city()))   // side-effecting filter 😬
    .toList();
Reusable gatherer
static <T,K> Gatherer<T,?,T> distinctBy(Function<T,K> key) {
  return Gatherer.ofSequential(
    HashSet::new,                             // initializer
    (seen, item, downstream) -> {             // integrator
      if (seen.add(key.apply(item)))
        return downstream.push(item);         // emit first per key
      return true;                            // true = keep going
    });
}
var out = people.stream().gather(distinctBy(Person::city)).toList();

Returning false from the integrator short-circuits the upstream — that's how a gatherer can implement limit-like behaviour.

5 · mapConcurrent — bounded parallel I/O in a stream

Backed by virtual threads, it runs up to N mappings at once and preserves encounter order — ideal for concurrent I/O without a thread pool.

Legacy — executor + futures + ordering

    .map(u -> pool.submit(() -> fetch(u)))
    .toList();
var bodies = futures.stream().map(f -> get(f)).toList();
pool.shutdown();
Gatherer
var bodies = urls.stream()
    .gather(Gatherers.mapConcurrent(10, this::fetch))
    .toList();   // ≤10 in flight, order preserved

3 · Off-heap memory: Arena & MemorySegment

Legacy — ByteBuffer / Unsafe
ByteBuffer buf = ByteBuffer.allocateDirect(16)
    .order(ByteOrder.nativeOrder());
buf.putInt(0, 42);
int v = buf.getInt(0);
// no explicit lifetime; freed whenever the GC/cleaner gets to it
Arena + MemorySegment
try (Arena arena = Arena.ofConfined()) {
  MemorySegment seg = arena.allocate(ValueLayout.JAVA_INT, 4);
  seg.setAtIndex(ValueLayout.JAVA_INT, 0, 42);
  int v = seg.getAtIndex(ValueLayout.JAVA_INT, 0);
}   // memory released deterministically here

Arena controls lifetime & sharing: ofConfined() (one thread, cheapest), ofShared() (many threads), ofAuto() (GC-managed), global() (never freed). Access after an arena closes throws instead of corrupting memory.

4 · Calling native functions

// call C's  size_t strlen(const char *s);
Linker linker = Linker.nativeLinker();
SymbolLookup std = linker.defaultLookup();

MethodHandle strlen = linker.downcallHandle(
    std.find("strlen").orElseThrow(),
    FunctionDescriptor.of(ValueLayout.JAVA_LONG,     // return: size_t
                          ValueLayout.ADDRESS));     // arg: char*

try (Arena arena = Arena.ofConfined()) {
  MemorySegment cString = arena.allocateUtf8String("hello");
  long len = (long) strlen.invoke(cString);          // → 5
}

6 · jextract — generate bindings automatically

For real libraries you rarely hand-write handles. The jextract tool reads a C header and generates ready-to-use Java bindings:

7 · Native-access restrictions

Because native calls can crash the VM, they're a restricted operation. Enable them explicitly:

java --enable-native-access=com.myapp   -jar app.jar   # a module
java --enable-native-access=ALL-UNNAMED -jar app.jar   # classpath apps
// without it you get warnings now, errors later
