Set up your machine

Quick start & tooling

Install one or more JDKs, switch between them, and learn the fastest ways to try features — JShell, single-file programs, preview features and incubator modules.

1 · Install a JDK

Pick a build of OpenJDK. Any of these give you the same language; they differ in support/branding:

  • Eclipse Temurin (Adoptium) — the popular community default.
  • Oracle JDK — Oracle's build.
  • Amazon Corretto, Azul Zulu, Microsoft / Liberica — vendor builds, often with extras.

Verify what you have:

java -version      # runtime version
javac -version     # compiler version
java --list-modules | head   # JDK modules available

2 · Install & switch between versions

You will want several JDKs installed at once (e.g. 17, 21, 25). Use a version manager.

SDKMAN! (macOS / Linux / WSL) — recommended

curl -s "https://get.sdkman.io" | bash        # install SDKMAN
sdk list java                                  # see available builds
sdk install java 25-tem                        # install Temurin 25
sdk install java 21.0.5-tem
sdk use java 25-tem        # switch for THIS shell only
sdk default java 21.0.5-tem   # set the global default

jenv (per-directory switching)

brew install jenv
jenv add /Library/Java/JavaVirtualMachines/temurin-25.jdk/Contents/Home
jenv global 21       # default
jenv local 25        # pin THIS project (writes .java-version)

Homebrew (macOS)

brew install openjdk@25 openjdk@21 openjdk@17

Manual — set JAVA_HOME

macOS / Linux (bash/zsh)
export JAVA_HOME=$(/usr/libexec/java_home -v 25)
export PATH="$JAVA_HOME/bin:$PATH"
# Linux: JAVA_HOME=/usr/lib/jvm/temurin-25
Windows (PowerShell)
$env:JAVA_HOME = "C:\Program Files\Java\jdk-25"
$env:Path = "$env:JAVA_HOME\bin;" + $env:Path

3 · JShell — the Java REPL Added in 9

See the JShell deep-dive for advanced shortcuts, variables, and commands.

The fastest way to try a snippet without a class, main, or compile step.

jshell                    # start the REPL
jshell> var xs = List.of(1, 2, 3)
xs ==> [1, 2, 3]
jshell> xs.stream().mapToInt(i -> i).sum()
$2 ==> 6
jshell> /exit

# useful commands
jshell> /vars      /methods     /imports     /list
jshell> /save mysession.jsh    # save your session
jshell --enable-preview        # REPL with preview features on
Tip. Pipe a script in: jshell myscript.jsh, or feed stdin with echo 'System.out.println("hi")' | jshell -.

4 · Run a single source file — no compile step Added in 11

Since Java 11 (JEP 330) you can run a .java file directly; the JDK compiles it in memory.

Before — compile then run
// Hello.java
public class Hello {
  public static void main(String[] a) {
    System.out.println("Hi");
  }
}
// terminal:
javac Hello.java   // -> Hello.class
java Hello
After — run directly
// Hello.java  (same file)
java Hello.java    // compiles + runs in one step

// pass args after the file name:
java Hello.java arg1 arg2

Multi-file source programs Added in 22

JEP 458 extended this: if the file you launch references other .java files in the same source tree, they are compiled on demand too — no build tool for small programs.

java Main.java     # also compiles Helper.java, model/User.java, ... as needed

Shebang scripts

Make a Java file executable like a shell script (the file need not end in .java):

#!/usr/bin/env java --source 25
public class App {
  public static void main(String[] a) { System.out.println("script!"); }
}
// then:  chmod +x app  &&  ./app

5 · Try preview language features

A preview feature is a finished-but-not-permanent language/VM feature. You must opt in at both compile and run time, and pass --release matching your JDK. Examples in this guide that are still preview show a Preview badge.

Compile with preview
javac --release 25 --enable-preview Demo.java
Run with preview
java --enable-preview Demo

# single-file shortcut (compile+run together):
java --enable-preview --source 25 Demo.java
Gotcha. A class file compiled with --enable-preview is tied to that exact JDK version and refuses to run on any other. Preview APIs/syntax can change or be removed in the next release — never ship them to production.

6 · Try incubator modules

An incubator module is a non-final API (a whole library, e.g. the Vector API) shipped under a jdk.incubator.* module. You add the module rather than flip a preview flag.

// compile & run code that uses jdk.incubator.vector
javac --add-modules jdk.incubator.vector Simd.java
java  --add-modules jdk.incubator.vector Simd

// see all incubator modules in your JDK:

March 2014 · LTS

Java 8 LTS

The release that reshaped how Java code is written. Lambda expressions, the Streams API, and default methods brought functional-style programming into the language itself, while Optional, the new java.time API, and CompletableFuture fixed three of Java's longest-standing API pain points in one release. This is where this guide's Java 9–26 story begins.

⚠ Migration watch-outs (7 → 8).
  • PermGen removed — -XX:PermSize/-XX:MaxPermSize are now silently ignored (no error) in favor of Metaspace, which grows in native memory. Full story → JVM Memory & GC deep-dive.
  • DocLint checks Javadoc comments strictly by default — malformed HTML in doc comments that javac used to ignore can now fail a build.
  • Default methods + multiple interfaces: implementing two interfaces that declare the same default method signature is a compile error unless your class overrides it — rare, but a real new failure mode that didn't exist in 7.
  • Nashorn replaces Rhino as the bundled JavaScript engine — scripts relying on Rhino-specific behavior may need adjustment.

1 · Language features

Lambda expressions

Why it matters: passing behavior around used to mean an anonymous class — four lines of ceremony to express one line of logic. Lambdas make the behavior itself the value.

Before — anonymous class
Comparator<String> byLength = new Comparator<String>() {
  @Override
  public int compare(String a, String b) {
    return Integer.compare(a.length(), b.length());
  }
};
button.addActionListener(new ActionListener() {
  public void actionPerformed(ActionEvent e) {
    System.out.println("clicked");
  }
});
After — lambda
Comparator<String> byLength = (a, b) -> Integer.compare(a.length(), b.length());
button.addActionListener(e -> System.out.println("clicked"));

Functional interfaces — java.util.function

Why it matters: a lambda needs a target type — an interface with exactly one abstract method. Java 8 shipped a standard library of them so you rarely need to declare your own.

Function<Integer, Integer> square = x -> x * x;      // T -> R
Predicate<Integer>         isEven = x -> x % 2 == 0;  // T -> boolean
Supplier<String>           sup    = () -> "value";    // () -> T
Consumer<String>           con    = System.out::println; // T -> void
BiFunction<Integer,Integer,Integer> add = (a, b) -> a + b;

System.out.println(square.apply(5));      // 25 — verified
// mark your own with @FunctionalInterface for a compiler check:
@FunctionalInterface
interface Greeter { String greet(String name); }

Method references

Before — a lambda that just forwards
names.forEach(s -> System.out.println(s));
list.stream().map(s -> s.toUpperCase());
After — four forms of ::
names.forEach(System.out::println);       // instance method on a particular object
list.stream().map(String::toUpperCase);   // instance method, unbound receiver
list.stream().map(Integer::parseInt);     // static method
list.stream().map(Order::new);            // constructor reference

Default & static methods on interfaces

Why it matters: before 8, adding any method to a published interface broke every existing implementer. Default methods let an interface evolve without breaking anyone.

Before — adding a method breaks every implementer
interface Greeter {
  String greet(String name);
  // adding greetLoudly() here breaks every class that implements Greeter
}
After — default method, source-compatible
interface Greeter {
  String greet(String name);
  default String greetLoudly(String name) {   // existing implementers unaffected
    return greet(name).toUpperCase();
  }
  static Greeter simple() {                    // static methods too
    return name -> "Hello, " + name;
  }
}
// verified: Greeter.simple().greetLoudly("Ada") -> "HELLO, ADA"

This is exactly the mechanism that let Collection/Map grow forEach, stream(), removeIf and more without breaking every existing collection implementation ever written — see §2.

Repeating annotations & type annotations

Before — a wrapper array annotation, always
@Schedules({ @Schedule(day="Mon"), @Schedule(day="Fri") })
class Job {}
After — repeat it directly
@Retention(RetentionPolicy.RUNTIME)
@Repeatable(Schedules.class)   // still needs a container annotation declared...
@interface Schedule { String day(); }

@Schedule(day = "Mon")
@Schedule(day = "Fri")          // ...but you write this at the use site
class Job {}
// Job.class.getAnnotationsByType(Schedule.class) -> [Mon, Fri] — verified
Gotcha, verified: forgetting @Retention(RetentionPolicy.RUNTIME) on the annotation means getAnnotationsByType silently returns an empty array at runtime — no error, just missing data.

Type annotations (JSR 308) let annotations appear anywhere a type is used, not just on declarations — List<@NonNull String> — mainly consumed by external static-analysis tools like Checker Framework rather than the JDK itself.

2 · New & updated APIs

The Streams API

Why it matters: filtering, transforming and aggregating collections in bulk, declaratively, instead of a mutable-accumulator for loop every time.

Before
List<String> names = new ArrayList<>();
for (Employee e : employees) {
  if (e.salary() > 50_000) names.add(e.name().toUpperCase());
}
Collections.sort(names);
After — Streams
List<String> names = employees.stream()
    .filter(e -> e.salary() > 50_000)
    .map(e -> e.name().toUpperCase())
    .sorted()
    .collect(Collectors.toList());

Streams are deep enough to earn their own page — creating streams, every intermediate/terminal operation, reduce's three overloads, the full Collectors catalogue, custom collectors, and parallel streams → Stream API complete guide.

Optional<T>

Before — null checks, or a silent NPE later
User user = findUser(id);         // might return null
if (user != null) {
  String name = user.getName();
  System.out.println(name);
} else {
  System.out.println("unknown");
}
After — the absence is in the type
Optional<User> user = findUser(id);
System.out.println(
    user.map(User::getName).orElse("unknown"));
// verified: opt.map(String::length).orElse(0)

The java.time API (JSR-310)

Why it matters: the old java.util.Date/Calendar were mutable, not thread-safe, had months indexed from zero, and threw checked exceptions for basic parsing — widely regarded as one of Java's worst original API designs. java.time replaces all of it.

Before — mutable, zero-indexed months, unsafe
Calendar cal = Calendar.getInstance();
cal.set(2014, Calendar.MARCH, 18);   // MARCH is month 2, not 3 — a classic bug source
cal.add(Calendar.DAY_OF_MONTH, 10);
Date result = cal.getTime();
SimpleDateFormat fmt = new SimpleDateFormat("yyyy-MM-dd");  // NOT thread-safe
System.out.println(fmt.format(result));
After — immutable, readable, thread-safe
LocalDate date = LocalDate.of(2014, Month.MARCH, 18);
LocalDate result = date.plusDays(10);
System.out.println(result.format(DateTimeFormatter.ISO_LOCAL_DATE));
// verified: "2014-03-28"

Duration.ofMinutes(90);              // amount of time, machine-precision
Period.ofMonths(3);                  // amount of time, human/calendar terms
Instant.now();                       // a point on the machine timeline (UTC)
ZonedDateTime.now(ZoneId.of("Asia/Kolkata"));   // time zone aware

CompletableFuture

Before — plain Future, no composition
Future<String> f = executor.submit(() -> fetch());
String result = f.get();          // blocks; can't chain another async step
String upper = result.toUpperCase();  // has to happen after the blocking get()
After — composable, non-blocking chains
CompletableFuture<String> cf = CompletableFuture
    .supplyAsync(() -> fetch())          // fetch() returns "async result!"
    .thenApply(String::toUpperCase)
    .exceptionally(ex -> "fallback");
System.out.println(cf.get());   // verified real output: "ASYNC RESULT!"

Collection default methods, Base64, and more

Before
for (Map.Entry<String,Integer> e : scores.entrySet()) {
  System.out.println(e.getKey() + "=" + e.getValue());
}
Integer old = scores.get("Ada");
scores.put("Ada", old == null ? 5 : old + 5);

for (Iterator<Integer> it = nums.iterator(); it.hasNext(); ) {
  if (it.next() % 2 == 0) it.remove();
}

String encoded = new sun.misc.BASE64Encoder().encode("hi".getBytes());  // internal, unsupported API
After
scores.forEach((k, v) -> System.out.println(k + "=" + v));   // Map default method
scores.merge("Ada", 5, Integer::sum);                          // add-or-update in one call
scores.computeIfAbsent("Bob", k -> 0);
// verified: {Bob=0, Ada=95}

nums.removeIf(n -> n % 2 == 0);      // Collection default method
nums.replaceAll(n -> n * 10);
// verified: [10, 30, 50]

String encoded = Base64.getEncoder().encodeToString("hi".getBytes());
// verified: "aGk="  — a real, public, supported API at last

int[] arr = {5,3,1,4,2};
Arrays.parallelSort(arr);             // verified: [1, 2, 3, 4, 5]
// StringJoiner — build delimited strings without a manual loop
StringJoiner sj = new StringJoiner(", ", "[", "]");
sj.add("a").add("b").add("c");
System.out.println(sj);   // verified: "[a, b, c]"

  • Nashorn — a new, faster JavaScript engine replacing Rhino, invoked from the command line or embedded via javax.script:

4 · JVM / performance / other

  • PermGen removed; Metaspace introduced JEP 122 — class metadata moved out of the heap into native memory that grows automatically. The long-standing OutOfMemoryError: PermGen space became OutOfMemoryError: Metaspace instead, now bounded by -XX:MaxMetaspaceSize rather than a fixed heap region. Full story → JVM Memory & GC deep-dive.
  • HashMap collision handling with balanced trees JEP 180 — when many keys land in the same bucket (pathological hashing, or hostile input), that bucket converts from a linked list to a tree, turning a potential O(n) worst case into O(log n).
  • Reduce cache contention JEP 142 — the @Contended annotation pads a field to its own cache line, avoiding false sharing between threads on multi-core hardware.
  • AES intrinsics JEP 164 — hardware AES instructions used automatically where available, meaningfully speeding up encryption.
  • Small VM JEP 148 and a large batch of security/crypto updates (TLS SNI, stronger password-based encryption, PKCS#11 on 64-bit Windows) rounded out the release.

1 · Language features

Private methods in interfaces

Why it matters: Java 8 gave interfaces default methods, but there was no way to share logic between them without exposing it. private (and private static) interface methods fix that.

Before (Java 8)
interface Logger {
  default void info(String m)  { log("INFO", m); }
  default void error(String m) { log("ERROR", m); }
  // shared helper is forced to be public
  default void log(String lvl, String m) {
    System.out.println(lvl + ": " + m);
  }
}
After (Java 9)
interface Logger {
  default void info(String m)  { log("INFO", m); }
  default void error(String m) { log("ERROR", m); }
  private void log(String lvl, String m) {   // hidden helper
    System.out.println(lvl + ": " + m);
  }
}

Try-with-resources on effectively-final variables

Why it matters: removes a pointless extra variable when the resource already exists.

Before
// must declare a fresh variable inside the ()
BufferedReader reader = openReader();
try (BufferedReader r = reader) {
  return r.readLine();
}
After (Java 9)
BufferedReader reader = openReader();   // effectively final
try (reader) {                          // use it directly
  return reader.readLine();
}

Enhanced @Deprecated

Why it matters: deprecation can now state when and whether removal is planned, so tools and readers know how urgent it is.

Before
@Deprecated
public void oldApi() { }    // deprecated... since when? removed when?
After (Java 9)
@Deprecated(since = "9", forRemoval = true)
public void oldApi() { }    // compilers warn louder for forRemoval

Small clean-ups: diamond on anonymous classes · @SafeVarargs on private methods · _ banned

Callable<String> c = new Callable<>() { ... };     // diamond now allowed here
@SafeVarargs private void f(List<String>... xs) { }  // allowed on private methods
int _ = 3;   // COMPILE ERROR: '_' is now reserved (for future language use)

2 · New & updated APIs

Immutable collection factory methods JEP 269

Why it matters: creating small immutable collections was verbose and error-prone.

Before
List<String> list = Collections.unmodifiableList(
    Arrays.asList("a", "b", "c"));
Map<String,Integer> m = new HashMap<>();
m.put("a", 1); m.put("b", 2);
m = Collections.unmodifiableMap(m);
After
List<String>  list = List.of("a", "b", "c");
Set<String>   set  = Set.of("a", "b");
Map<String,Integer> m = Map.of("a", 1, "b", 2);
// immutable, null-hostile, compact

Stream additions: takeWhile, dropWhile, ofNullable, ranged iterate

Before
// "take the leading run < 5" — no clean way
list.stream()
    .filter(x -> x < 5)   // keeps ALL <5, not just the leading run
    .collect(Collectors.toList());
After (Java 9)
list.stream().takeWhile(x -> x < 5).collect(Collectors.toList());   // leading run only (use .toList() on Java 16+)
list.stream().dropWhile(x -> x < 5).collect(Collectors.toList());   // skip leading run   (use .toList() on Java 16+)
Stream.ofNullable(maybeNull);                    // 0- or 1-element stream
Stream.iterate(1, n -> n < 100, n -> n * 2);     // for-style with predicate

New Collectors: filtering & flatMapping

Why it matters: filter/flatten inside a downstream collector (e.g. within a groupingBy), which plain filter can't do without dropping empty groups.

Before — filter drops empty groups
Map<Dept, List<Employee>> m = employees.stream()
    .filter(e -> e.salary() > 100_000)          // dept with none disappears
    .collect(groupingBy(Employee::dept));
After (Java 9)
Map<Dept, List<Employee>> m = employees.stream()
    .collect(groupingBy(Employee::dept,
             filtering(e -> e.salary() > 100_000, toList())));
// every dept kept; empty list where none match

Optional: ifPresentOrElse, or, stream

Before
if (opt.isPresent()) use(opt.get());
else handleEmpty();

List<User> users = new ArrayList<>();
for (Optional<User> o : optionals)
  o.ifPresent(users::add);
After (Java 9)
opt.ifPresentOrElse(this::use, this::handleEmpty);
Optional<User> u = primary.or(() -> fallbackLookup());   // lazy fallback
List<User> users = optionals.stream()
    .flatMap(Optional::stream).collect(Collectors.toList());   // drop empties (use .toList() on Java 16+)

CompletableFuture: timeouts & delays

Why it matters: before Java 9 you needed an external scheduler to time out an async task.

Before
// bolt on a timeout with a separate scheduler... fiddly
CompletableFuture<String> f = callAsync();
scheduler.schedule(() -> f.completeExceptionally(
    new TimeoutException()), 2, SECONDS);
After (Java 9)
CompletableFuture<String> f = callAsync()
    .orTimeout(2, SECONDS)                    // fail if too slow
    .completeOnTimeout("default", 2, SECONDS);// or fall back to a value
CompletableFuture.delayedExecutor(1, SECONDS);// delayed execution

Stack-Walking API

Why it matters: a lazy, efficient way to inspect the call stack, replacing the costly Throwable.getStackTrace() trick.

Before
// build a whole throwable just to read the caller
StackTraceElement[] st = new Throwable().getStackTrace();
String caller = st[1].getClassName();
After (Java 9)
Class<?> caller = StackWalker
    .getInstance(StackWalker.Option.RETAIN_CLASS_REFERENCE)
    .walk(s -> s.skip(1).findFirst()

Reactive Streams — java.util.concurrent.Flow JEP 266

Why it matters: before Java 9, "reactive" libraries (RxJava, Reactor, Akka Streams) each had their own incompatible Publisher/Subscriber interfaces — you couldn't connect one library's stream to another's. Flow standardises the four interfaces so any compliant library can interoperate, with built-in back-pressure (the subscriber controls how many items it's ready for, so a fast producer can't overwhelm a slow consumer).

try (SubmissionPublisher publisher = new SubmissionPublisher<>()) {  // Note: 'var' requires Java 10+
  publisher.subscribe(new Flow.Subscriber<Integer>() {
    private Flow.Subscription subscription;
    public void onSubscribe(Flow.Subscription s) {
      subscription = s;
      s.request(Long.MAX_VALUE);        // "I'm ready for everything"
    }
    public void onNext(Integer item)  { System.out.println("got: " + item); }
    public void onError(Throwable t)  { t.printStackTrace(); }
    public void onComplete()          { System.out.println("done"); }
  });
  publisher.submit(1);
  publisher.submit(2);
  publisher.submit(3);
}   // closing the publisher signals onComplete() to subscribers
// prints: got: 1 / got: 2 / got: 3 / done   (verified output)

SubmissionPublisher is the JDK's own ready-made Publisher — you don't need a third-party library to try Flow.

Generics

Generics let types be parameters, the same way method parameters let values be parameters. Box<T> is one class that works for Box<String>, Box<Integer>, or any type — with the compiler checking every use, and zero runtime cost.

1 · Why generics — before & after

Before generics (pre-Java 5) — casts everywhere
List names = new ArrayList();     // holds Object
names.add("Ada");
names.add(42);                    // compiles fine — no error yet!

String s = (String) names.get(0); // manual cast, could fail
String s2 = (String) names.get(1); // ClassCastException AT RUNTIME, far from the bug
After — the compiler catches it immediately
List<String> names = new ArrayList<>();
names.add("Ada");
names.add(42);                    // COMPILE ERROR right here — caught immediately

String s = names.get(0);          // no cast needed at all

Three concrete benefits, straight from Oracle's own generics tutorial: stronger compile-time checks, elimination of casts, and the ability to write one algorithm that works across many types safely.

2 · Generic classes & methods

A non-generic box — only safe with Object
public class Box {
  private Object content;
  public void set(Object content) { this.content = content; }
  public Object get() { return content; }
}
Box b = new Box();
b.set("hello");
String s = (String) b.get();   // cast required, and nothing stops b.set(42)
A generic box — one class, every type, type-safe
public class Box<T> {
  private T content;
  public void set(T content) { this.content = content; }
  public T get() { return content; }
}
Box<String> b = new Box<>();
b.set("hello");
String s = b.get();            // no cast; b.set(42) would not compile

Generic methods — the type parameter belongs to the method, not the class

3 · Type inference & the diamond

Before Java 7 — repeat the type on both sides
Map<String, List<String>> map = new HashMap<String, List<String>>();
The diamond <> — let the compiler infer it
Map<String, List<String>> map = new HashMap<>();
// the compiler infers <String, List<String>> from the declared variable type
Gotcha: new HashMap() with no diamond at all uses the raw type — you lose type checking silently (an unchecked-conversion warning, not an error). Always use either the full parameterization or the empty diamond <>, never bare new HashMap() when assigning to a parameterized variable.

4 · Bounded, multiple, and recursive bounds

By default a type parameter accepts anything. extends narrows it to a specific hierarchy — and despite the keyword, it also means "implements" for interfaces.

// simple bound: T must be a Number (or subtype)
static double sumOf(List<? extends Number> nums) { ... }

// multiple bounds: at most ONE class, then any number of interfaces —
// the class (if any) must be listed first
static <T extends Number & Comparable<T>> T max(T a, T b) {
  return a.compareTo(b) >= 0 ? a : b;
}
// verified: max(3, 7) -> 7

// recursive bound: T must be comparable to itself — this is exactly
// how Collections.max() and Comparable-based sorting are declared in the JDK
  // Using PECS (Producer Extends, Consumer Super) for maximum compatibility
static <T extends Comparable<? super T>> T maxOf(T a, T b) {
  return a.compareTo(b) >= 0 ? a : b;
}
// verified: maxOf("apple", "banana") -> "banana"
Recursive bounds look strange the first time (T extends Comparable<T> — "T is comparable to itself") but they're everywhere in the JDK once you know to look: Enum<E extends Enum<E>> is declared exactly this way.

5 · Wildcards & PECS

A wildcard (?) represents an unknown type — used at the call site, not in a declaration, when you need flexibility a plain type parameter can't give you.

Too restrictive — only accepts List<Number> exactly
static double sum(List<Number> nums) { ... }
sum(List.of(1, 2, 3));       // ✗ compile error — List<Integer> is NOT a List<Number>
Upper-bounded wildcard — accepts any subtype
static double sum(List<? extends Number> nums) {
  double total = 0;
  for (Number n : nums) total += n.doubleValue();   // read-only access as Number
  return total;
}
sum(List.of(1, 2, 3));        // ✓ works — verified: 6.0
sum(List.of(1.5, 2.5));       // ✓ works — verified: 4.0
// lower-bounded wildcard: write Integers into anything that can hold them
static void addIntegers(List<? super Integer> list) {
  list.add(1);
  list.add(2);
}
List<Number> dest = new ArrayList<>();
addIntegers(dest);             // verified: dest == [1, 2]

// unbounded wildcard: List — you can read as Object, but can only WRITE null
List<?> unknown = List.of(1, 2, 3);
Object o = unknown.get(0);     // fine — verified
// unknown.add("x");           // would NOT compile — the element type is truly unknown

6 · Type erasure — verified with real bytecode

Generics are a compile-time feature. The compiler checks your types, then erases them: T becomes Object (or its first bound), and inserts casts where needed to keep the illusion of type safety at runtime.

class Node<T> { T data; void setData(T data) { this.data = data; } }

// after erasure, the compiler actually generates:
class Node { Object data; void setData(Object data) { this.data = data; } }

Bridge methods — verified with real javap output

Erasure creates a real, observable side effect when a subclass narrows a generic method's type. Here's the exact scenario, run and disassembled for real:

class Node<T> {
  T data;
  Node(T data) { this.data = data; }
  void setData(T data) { System.out.println("Node.setData"); this.data = data; }
}
class MyNode extends Node<Integer> {
  MyNode(Integer data) { super(data); }
  @Override void setData(Integer data) {           // looks like an override...
    System.out.println("MyNode.setData");
    super.setData(data);
  }
}

MyNode mn = new MyNode(5);
Node n = mn;              // raw type reference
n.setData("Hello");       // compiles (with an unchecked warning) — erased to setData(Object)
Verified real output: 
Exception in thread "main" java.lang.ClassCastException:
  class java.lang.String cannot be cast to class java.lang.Integer
    at MyNode.setData(BridgeDemo.java:12)
    at BridgeDemo.main(BridgeDemo.java:24)
After erasure, Node.setData(T) becomes Node.setData(Object) — so MyNode.setData(Integer) no longer overrides it by signature. To preserve polymorphism, the compiler silently generates a synthetic bridge method. Verified with javap -p MyNode: 
void setData(java.lang.Integer);   // your real method
void setData(java.lang.Object);    // compiler-generated bridge — casts, then delegates
The bridge method is what actually gets called, casts its argument to Integer, and that cast is where the ClassCastException is thrown — not inside your code at all.
Looking ahead — Project Valhalla: Valhalla aims to bring primitive specialization for generics to Java, enabling List<int> instead of List<Integer> without boxing overhead. This would fundamentally change the erasure model for specialized types and is expected to ship in a future Java LTS.

7 · What you cannot do with generics

All seven of these are direct, real consequences of erasure — verified against Oracle's own "Restrictions on Generics" reference.

RestrictionWhy (and the workaround)
Cannot instantiate with primitives: Pair<int, char>Only reference types — use Pair<Integer, Character> (autoboxed).
Cannot create an instance of a type parameter: new T()The compiler can't know what T is at runtime. Workaround: pass a Supplier<T> or a Class<T> and use reflection.
Cannot declare static fields of a type parameterA static field is shared by all instances, but each instantiation could have a different T — there's no single answer for what type it would be.
Cannot use instanceof or cast against a parameterized type: x instanceof List<String>Erased at runtime — the JVM can't tell List<Integer> from List<String>. You can check x instanceof List<?> instead.
Cannot create arrays of a parameterized type: new List<String>[10]Arrays check their element type at runtime (ArrayStoreException); erasure would silently defeat that safety check, so it's forbidden outright.
A generic class cannot extend ThrowableException types must be resolvable at both compile and catch time — erasure would make catch clauses ambiguous.

Clarification: Under JLS §8.1.2, it is a compile-time error if a generic class directly or indirectly subclasses Throwable. You cannot define class MyException<T> extends RuntimeException. However, type parameters are allowed in a method's throws clause (e.g., <T extends Throwable> void doIt() throws T).

Cannot overload two methods that erase to the same signaturevoid m(List<String> x) and void m(List<Integer> x) both erase to m(List) — a duplicate-method compile error.

Generics in one glance

  • class Box<T> { T value; } — one type parameter, works for any reference type.
  • Naming: E element, K/V key/value, N number, T type.
  • Diamond: new HashMap<>() — never bare new HashMap() when the variable is parameterized.
  • Bounds: <T extends Number>; multiple: <T extends Number & Comparable<T>> (class first).
  • PECS: ? extends to read (producer), ? super to write (consumer).
  • Erasure: T → Object/bound at compile time — zero runtime cost, but no runtime type info either.
  • Can't: new T(), static fields of T, instanceof List<String>, arrays of parameterized types, extend Throwable generically.

Advanced Generics Topics

  • Wildcard Capture: When the compiler internally infers a specific but unknown type from a wildcard type (?) during type checking.
  • Heap Pollution & @SafeVarargs: Situations where parameterized types lose their type safety, often related to varargs. The @SafeVarargs annotation suppresses unchecked warnings for varargs parameters.
  • Intersection Types: Declaring a type that must satisfy multiple bounds (e.g., <T extends Serializable & Comparable<T>>).
  • Super Type Tokens (e.g., TypeReference<T>): A pattern to retain generic type information at runtime, circumventing type erasure.

2 · Class — the entry point

Every reflective operation starts from a java.lang.Class instance. There are four ways to get one:

String s = "hello";
Class<?> c1 = s.getClass();              // (a) from an instance
Class<?> c2 = String.class;              // (b) the class literal — no instance needed
Class<?> c3 = Class.forName("java.lang.String");  // (c) by fully-qualified name (throws checked exception)
Class<?> c4 = int[].class;                // (d) even array/primitive types have a Class

Note on constructors: none of the classes in java.lang.reflect have public constructors — you always reach them through methods on Class.

4 · Modifiers

Class.getModifiers() (and the same method on Field/Method/Constructor via the Member interface) returns an int where each bit represents one modifier. Decode it with the Modifier helper class rather than bit-twiddling yourself:

int mods = String.class.getModifiers();
System.out.println(Modifier.isPublic(mods));    // true
System.out.println(Modifier.isFinal(mods));     // true — String really is final
System.out.println(Modifier.toString(mods));    // "public final"
Not every modifier your code sees in Modifier covers newer keywords — sealed and non-sealed are not represented in java.lang.reflect.Modifier (verified from dev.java's own reflection tutorial). Use Class.isSealed() and Class.getPermittedSubclasses() instead.

8 · Arrays

Arrays are a special case: Array.getLength() exists because array length isn't part of the type, only the instance.

Object arr = Array.newInstance(int.class, 5);   // like new int[5]
Array.set(arr, 0, 42);
System.out.println(Array.get(arr, 0));           // verified: 42
System.out.println(Array.getLength(arr));        // verified: 5
System.out.println(arr.getClass().isArray());    // true
System.out.println(arr.getClass().getComponentType());  // int
Verified precision rule: Array.setFloat() with a boxed Float throws IllegalArgumentException. Array.setInt() into a long[] works (no precision lost widening int→long); the reverse (setLong into an int[]) is illegal — narrowing would lose data.

9 · Enums & records

11 · Dynamic proxies

Why it matters: a dynamic proxy creates a real, working implementation of one or more interfaces at runtime, with no class file for it ever written by you — every method call is routed through one handler. This is exactly how Spring AOP, mocking frameworks, and lazy-load proxies in Hibernate work.

interface Greeter { String greet(String name); }

Greeter proxy = (Greeter) Proxy.newProxyInstance(
    Greeter.class.getClassLoader(),
    new Class<?>[]{ Greeter.class },
    (Object p, Method method, Object[] args) -> {
      System.out.println("before calling " + method.getName());
      String result = "Hello, " + args[0];
      System.out.println("after calling " + method.getName());
      return result;
    });

System.out.println(proxy.greet("Ada"));
// verified real output:
//   before calling greet
//   after calling greet
//   Hello, Ada
System.out.println(Proxy.isProxyClass(proxy.getClass()));   // verified: true
Limitation: java.lang.reflect.Proxy can only proxy interfaces, not concrete classes — for that, frameworks like CGLIB or ByteBuddy generate real subclasses on the fly instead.

12 · Real patterns: interceptors & dependency injection

Two complete, working examples adapted from dev.java's own Reflection API tutorial — the kind of code that sits inside Java EE/Jakarta EE and enterprise frameworks. Every line below was compiled and run for real before being written here.

Pattern A — a method interceptor driven by an annotation

The idea: instead of calling a service method directly, you route the call through an interceptor first. The interceptor gets the raw Method, the target object, and the arguments — it can validate them, change them, decide whether to call the real method at all, and transform the result before returning it. (A production version of this would use dynamic proxies so the call site looks like an ordinary method call; here we build the mechanism by hand so every step is visible.)

Step 1 — the interceptor contract and the annotation that selects it:

interface Interceptor<T, R> {
  R intercept(Method method, T target, Object[] args) throws Exception;
}

@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.METHOD)
@interface Intercepted {
  Class<? extends Interceptor> value();   // which interceptor handles this method
}

Step 2 — a service, with one method marked for interception and one left alone:

public class SomeInterceptedService {
  @Intercepted(MessageInterceptor.class)
  public String message(String text) { return text; }
}

public class SomeNonInterceptedService {
  public String message(String text) { return text; }   // no annotation -> called directly
}

Step 3 — the interceptor itself. It validates the arguments, reflectively invokes the real method to get the underlying result, then decorates it:

public class MessageInterceptor implements Interceptor<SomeInterceptedService, String> {
  public String intercept(Method method, SomeInterceptedService target, Object[] args) throws Exception {
    if (args.length != 1 || !(args[0] instanceof String)) {
      throw new IllegalArgumentException("expected exactly one String argument");
    }
    String result = (String) method.invoke(target, args);   // call the REAL method
    return result + " [was intercepted]";                    // then decorate the result
  }
}

Step 4 — the "runtime": locate the method, check for the annotation, and either run the interceptor or call the method as normal:

class ServiceFactory {
  @SuppressWarnings("unchecked")
  static <T> Object invoke(Class<T> serviceClass, String methodName, Object... args) throws Exception {
    T service = serviceClass.getDeclaredConstructor().newInstance();
    Class<?>[] types = Arrays.stream(args).map(a -> a == null ? Object.class : a.getClass()).toArray(Class[]::new);
    Method method = serviceClass.getDeclaredMethod(methodName, types);

    if (method.isAnnotationPresent(Intercepted.class)) {
      Intercepted meta = method.getAnnotation(Intercepted.class);
      Interceptor<T, Object> interceptor =
          (Interceptor<T, Object>) meta.value().getDeclaredConstructor().newInstance();
      return interceptor.intercept(method, service, args);   // routed through the interceptor
    } else {
      return method.invoke(service, args);                    // called directly, no interception
    }
  }
}

Object r1 = ServiceFactory.invoke(SomeInterceptedService.class, "message", "Hello");
Object r2 = ServiceFactory.invoke(SomeNonInterceptedService.class, "message", "Hello");
System.out.println(r1);   // verified real output: "Hello [was intercepted]"
System.out.println(r2);   // verified real output: "Hello"
Verified gotcha the original tutorial calls out explicitly: ServiceFactory.invoke builds the parameter types from each argument's runtime class. If the target method were declared as message(CharSequence text) instead of message(String text), looking it up with getDeclaredMethod("message", String.class) throws NoSuchMethodException — verified — even though a String genuinely is a CharSequence. Reflective method lookup matches the exact declared parameter type, never a supertype.

Pattern B — a dependency-injection framework with singletons

The idea, in three layers: (1) a factory that builds objects reflectively instead of you calling new, (2) a @Singleton annotation so some beans are built once and reused, (3) an @Inject annotation so the factory can wire one bean's dependencies into another automatically.

Layer 1 — the basic factory. Give it a class and constructor arguments, get an instance back:

class BeanFactory {
  static <T> T getInstanceOf(Class<T> beanClass, Object... args) throws ReflectiveOperationException {
    Class<?>[] types = Arrays.stream(args).map(a -> a == null ? Object.class : a.getClass()).toArray(Class[]::new);
    Constructor<T> constructor = beanClass.getConstructor(types);   // exact-type match, see §7
    return constructor.newInstance(args);
  }
}
Verified gotcha (the same rule from §7, and the DI framework hits it immediately): getConstructor() only finds public constructors on public types. A package-private bean class throws NoSuchMethodException even though the constructor is right there in getDeclaredConstructors() — every bean class in these examples needs to be public.

Layer 2 — add @Singleton. A thread-safe registry backed by ConcurrentHashMap, with the construction logic pulled into a private helper so it isn't duplicated:

@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.TYPE)
@interface Singleton {}

class BeanFactory {
  private static final ConcurrentMap<Class<?>, Object> registry = new ConcurrentHashMap<>();

  @SuppressWarnings("unchecked")
  static <T> T getInstanceOf(Class<T> beanClass, Object... args) throws ReflectiveOperationException {
    if (beanClass.isAnnotationPresent(Singleton.class)) {
      Object existing = registry.get(beanClass);
      if (existing != null) return (T) existing;

      T candidate = instantiateBeanClass(beanClass, args);
      registry.putIfAbsent(beanClass, candidate);   // atomic — no explicit synchronization needed
      return (T) registry.get(beanClass);            // there IS a winner, but it might not be "candidate"
      // if two threads raced here, both built an instance, but only one is stored — read it back
      // via get() rather than returning "candidate", or you could return the LOSING instance
    }
    return instantiateBeanClass(beanClass, args);
  }

  private static <T> T instantiateBeanClass(Class<T> beanClass, Object... args) throws ReflectiveOperationException {
    Class<?>[] types = Arrays.stream(args).map(a -> a == null ? Object.class : a.getClass()).toArray(Class[]::new);
    Constructor<T> constructor = beanClass.getConstructor(types);
    return constructor.newInstance(args);
  }
}

Layer 3 — add @Inject. After constructing a bean, scan its fields for @Inject and fill each one in — recursively through getInstanceOf, so an injected field that's itself @Singleton correctly reuses the shared instance:

@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.FIELD)
@interface Inject {}

// instantiateBeanClass grows one more step at the end:
private static <T> T instantiateBeanClass(Class<T> beanClass, Object... args) throws ReflectiveOperationException {
  Class<?>[] types = Arrays.stream(args).map(a -> a == null ? Object.class : a.getClass()).toArray(Class[]::new);
  Constructor<T> constructor = beanClass.getConstructor(types);
  T bean = constructor.newInstance(args);

  for (Field field : beanClass.getDeclaredFields()) {           // every field, any visibility
    if (field.isAnnotationPresent(Inject.class)) {
      field.setAccessible(true);                                 // always — even if it were public
      // Note: Real DI frameworks register 'bean' early here to prevent circular dependency StackOverflows
      Object value = getInstanceOf(field.getType());              // recursive — respects @Singleton
      field.set(bean, value);
    }
  }
  return bean;
}

Putting all three layers together:

@Singleton
public class DBService {
  public DBService() { System.out.println("DBService instance created"); }
  String query() { return "some data"; }
}

public class MyApplication {
  @Inject
  private DBService dbService;    // BeanFactory fills this in — no setter, no constructor arg
  void run() { System.out.println("result = " + dbService.query()); }
}

MyApplication app = BeanFactory.getInstanceOf(MyApplication.class);
app.run();
// verified real output:
//   DBService instance created
//   result = some data

DBService a = BeanFactory.getInstanceOf(DBService.class);
DBService b = BeanFactory.getInstanceOf(DBService.class);
System.out.println(a == b);
// verified real output: true — and "DBService instance created" printed only ONCE across
// all three getInstanceOf calls total, proving the singleton was genuinely reused

13 · setAccessible & the module system

Since Java 9's module system (see Modules deep-dive), calling setAccessible(true) on a private member of a module you don't own only works if that module opens the package to you — either explicitly or via --add-opens on the command line. This is exactly why upgrading old reflection-heavy code to Java 9+ often throws InaccessibleObjectException until the right module is opened.

16 · Cheat sheet

Reflection in one glance

  • Entry point: obj.getClass(), Type.class, or Class.forName(name).
  • getDeclared* = this class only, includes private. get* (no "Declared") = inherited, public only.
  • setAccessible(true) before touching a private field/method/constructor.
  • Method.invoke throws InvocationTargetException (unwrap with getCause()), plus IllegalAccessException and IllegalArgumentException.
  • Constructor.newInstance throws the same, plus InstantiationException.
  • Proxy.newProxyInstance — implement an interface at runtime, one handler for every call.
  • Records refuse field mutation even via reflection; enums can't gain new constants at runtime.
  • Java 9+: reflecting into another module needs that module to opens the package.
  • Prefer normal code when you can — reflection is slower and bypasses compile-time checks.

7 · Type annotations & pluggable type systems

Type annotations (Java 8, ElementType.TYPE_USE) exist to support pluggable type checkers — the JDK itself doesn't interpret them, but a separate tool (like the University of Washington's Checker Framework) can read them and flag violations before you ever run the code.

@NonNull String name;                    // a pluggable checker can now verify this never gets null
List<@NonNull String> names;            // annotate a generic type argument
myGraph.add((@Interned Node) n);          // annotate a cast

Without a checker plugged into the build, these compile as plain metadata with zero enforcement — the checking is opt-in tooling, not a language guarantee.

8 · Repeating annotations, verified

Before Java 8, applying the "same" annotation twice needed an explicit wrapper array annotation written at every use site. @Repeatable hides that wrapper.

Before Java 8 — manual container, always
@interface Schedules { Schedule[] value(); }
@interface Schedule { String day(); }

@Schedules({ @Schedule(day="Mon"), @Schedule(day="Fri") })  // wrapper visible every time
class Job {}
Java 8+ — repeat it directly
@Retention(RetentionPolicy.RUNTIME)
@interface Schedules { Schedule[] value(); }   // 1. still need the container...

@Retention(RetentionPolicy.RUNTIME)
@Repeatable(Schedules.class)                    // 2. ...but point @Repeatable at it
@interface Schedule { String day(); }

@Schedule(day = "Mon")
@Schedule(day = "Fri")                          // no wrapper at the use site
class Job {}

Job.class.getAnnotationsByType(Schedule.class); // verified: [day=Mon, day=Fri]
The container annotation is real and still generated by the compiler behind the scenes — getAnnotation(Schedule.class) (singular) still only finds one match or throws ambiguity; use getAnnotationsByType(Schedule.class) (plural) to get every repeat.

13 · Cheat sheet

Annotations in one glance

  • public @interface Name { String value(); int x() default 1; } — an annotation is a special interface.
  • Retention: SOURCE (compiler only) → CLASS (default, in bytecode) → RUNTIME (reflectable). Forgetting RUNTIME fails silently.
  • Target: restrict legal placements with @Target(ElementType...).
  • Repeatable: @Repeatable(Container.class) on the annotation + a container with an array value(); read repeats with getAnnotationsByType.
  • Inherited: class declarations only, not interfaces/methods/fields.
  • Type annotations (TYPE_USE) are inert without a pluggable checker reading them.
  • Annotations do nothing by themselves — something (compiler, reflection, a processor) has to read them.

Advanced Annotation Topics

  • Permitted attribute types: Annotations can only have attributes of primitive types, String, Class, enums, annotations, and 1-dimensional arrays of these types.
  • Prohibition of null default values: Annotation attributes cannot have null as a valid default value.
  • Interface Annotation Inheritance: Annotations on interfaces are generally not inherited by classes implementing them, unlike annotations on superclasses (when marked with @Inherited).
  • @Generated: Added in Java 9 to javax.annotation.processing to mark code generated by tools.

var — local-variable type inference Java 10

var lets the compiler infer a local variable's type from its initializer. It is syntactic sugar, not dynamic typing — the variable still has one fixed, static type; you simply don't write it out.

3 · Where you cannot use it

var x;                 // ✗ no initializer — nothing to infer
var y = null;          // ✗ null has no type
var f = () -> 42;      // ✗ lambda needs a target type
var arr = { 1, 2, 3 }; // ✗ array initializer needs a type
var arr2[] = new int[3]; // ✗ 'var' is not allowed as an array element type

var is local variables only — never fields, method parameters, or return types. It also can't use the legacy C-style array bracket suffix (var arr[]) even though int arr[] is legal Java — always use var arr = new int[3]; instead.

4 · Rules & gotchas

  • Inferred type = the initializer's type, which may be more specific than you want: 
    var list = new ArrayList<String>();   // type is ArrayList<String>, not List<String>
    Declare the interface type explicitly if that matters.
  • Diamond + var: var m = new HashMap<>(); infers HashMap<Object,Object> — usually not intended. Put the type args on the right: var m = new HashMap<String,Integer>();
  • var is not a keyword — it's a reserved type name, so existing variables/methods named var still compile. You just can't name a class var.
  • No effect on generics inference elsewhere — it only names the local.

Intersection-type trap: var x = condition ? "hello" : 42; infers an intersection type (Serializable & Comparable<?>), not Object. This can surprise readers. Always annotate such variables with an explicit comment or use an explicit type when the inferred type is a non-obvious intersection.

5 · var vs Object

Object — erases the type
Object o = "hello";
o.length();      // ✗ compile error — only Object methods available
var — keeps the precise type
var s = "hello";
s.length();      // ✓ s is a String, all String methods available

They're completely different: var preserves the exact static type; Object throws it away.

7 · var in pattern matching

The same var keyword shows up inside record patterns (Java 21) to bind a destructured component without repeating its type — the compiler infers each component's type from the record's declaration, not from an initializer this time.

Records Final in Java 16

A record is a concise, immutable, transparent carrier for a fixed set of values. You declare the components; the compiler generates the constructor, accessors, equals, hashCode and toString — correctly, every time.

Records make that boilerplate automatic and correct, and clearly signal intent: this type is just its data.

1 · What is a record?

You write the shape of the data in the header — the record components — and that's it. The record is implicitly final, its fields are final, and it carries no hidden state beyond those components.

Legacy — a hand-written value class
public final class Point {
  private final int x, y;
  public Point(int x, int y) { this.x = x; this.y = y; }
  public int x() { return x; }
  public int y() { return y; }
  @Override public boolean equals(Object o) {
    if (!(o instanceof Point p)) return false;
    return x == p.x && y == p.y;
  }
  @Override public int hashCode() { return Objects.hash(x, y); }
  @Override public String toString() {
    return "Point[x=" + x + ", y=" + y + "]";
  }
}
Record — same thing
public record Point(int x, int y) { }
Easy way to think about it: a record is to a data class what enum is to a set of constants — a special, purpose-built shorthand the compiler fills in for you.

2 · What the compiler generates

  • Canonical constructor taking all components in order.
  • Accessors named exactly like the component: x(), y().
  • equals/hashCode comparing all components by value.
  • toString like Point[x=1, y=2].
  • A private final field per component; the class extends java.lang.Record and is final.

3 · Customising records

Compact canonical constructor — validate / normalise

Omit the parameter list and the field assignments; write only the checks. The fields are assigned for you afterwards.

Legacy — validation in a full constructor
public Range(int lo, int hi) {
  if (lo > hi) throw new IllegalArgumentException();
  this.lo = lo;
  this.hi = hi;
}
Record — compact constructor
public record Range(int lo, int hi) {
  public Range {                       // no params, no assignments
    if (lo > hi) throw new IllegalArgumentException();
  }
}

Extra members that are allowed

public record Point(int x, int y) {
  static final Point ORIGIN = new Point(0, 0);     // static fields: OK
  public Point(int v) { this(v, v); }              // extra constructors: OK (must delegate)
  public double distanceTo(Point o) {              // instance methods: OK
    return Math.hypot(x - o.x, y - o.y);
  }
  public static Point of(int x, int y) {           // static factory: OK
    return new Point(x, y);
  }
}
Not allowed: extra instance fields (all state must be a component), and you cannot extend another class (records already extend Record). You can implements interfaces.

Generic records & local records

Records can take type parameters like any other type, and — since they're just a kind of class — can be declared locally inside a method, scoped to exactly where you need a throwaway data shape:

record Pair<A, B>(A first, B second) {}
var p = new Pair<>("x", 42);
System.out.println(p);   // Pair[first=x, second=42] — verified

List<Order> topByScore(List<Order> orders) {
  record Scored(Order order, double score) {}   // local record — only exists in this method
  return orders.stream()
      .map(o -> new Scored(o, rank(o)))
      .sorted(Comparator.comparingDouble(Scored::score).reversed())
      .map(Scored::order)
      .toList();
}

4 · Immutability & defensive copies

Records are shallowly immutable: the component references can't change, but if a component is itself mutable (a List, array, Date), callers can still mutate what it points to. Copy in the compact constructor for real immutability.

Leaky — shares the caller's list
public record Team(String name, List<String> members) { }

var list = new ArrayList<>(List.of("Ada"));
var team = new Team("A", list);
list.add("Bob");             // 😱 mutates the record's list too
Safe — defensive copy
public record Team(String name, List<String> members) {
  public Team {
    members = List.copyOf(members);   // immutable snapshot
  }
}
// now external mutation of the original list has no effect

5 · Comparing two records

Because the compiler generates equals from the components (§2), comparing two records is usually just .equals() — but there are a few things worth knowing exactly.

== vs .equals() — verified

== — are they the same object?
var p1 = new Point(1, 2);
var p2 = new Point(1, 2);          // a SEPARATE instance, same data
System.out.println(p1 == p2);      // verified: false
.equals() — do they hold the same data?
System.out.println(p1.equals(p2)); // verified: true
// this is exactly why records exist: two different instances with the
// same component values are equal, with zero hand-written code
Always use .equals() for records, never == (except deliberately checking object identity) — == compares references, so two records built separately from identical data are ==-unequal but .equals()-equal.

Nested records — equality recurses correctly, verified

record Point(int x, int y) {}
record Line(Point start, Point end) {}   // a record made of records

var l1 = new Line(new Point(0, 0), new Point(3, 4));
var l2 = new Line(new Point(0, 0), new Point(3, 4));   // separately built, same values
var l3 = new Line(new Point(0, 0), new Point(3, 5));   // one coordinate differs

System.out.println(l1.equals(l2));   // verified: true  — compares Point-by-Point
System.out.println(l1.equals(l3));   // verified: false — the nested difference is detected

Line's generated equals calls Point's generated equals on each component — no extra work needed, it composes automatically.

The one exception: if a component is an array rather than another record, equality does not recurse the way you'd expect — see the verified array-component gotcha in §9 Pitfalls, and the two working fixes right below.

If a record contains an array — two working fixes, verified

The generated equals/hashCode/toString treat an array component by identity, exactly like Object[] would — because arrays themselves never overrode those methods to compare contents. There are two real fixes.

Broken — verified
record BytesDefault(byte[] data) {}

var d1 = new BytesDefault(new byte[]{1, 2, 3});
var d2 = new BytesDefault(new byte[]{1, 2, 3});   // same content, different array object

d1.equals(d2);   // verified: false
d1.toString();   // verified: "BytesDefault[data=[B@6356695f]" — identity hash, not content
Fix 1 — override with Arrays.equals/hashCode
record BytesFixed(byte[] data) {
  @Override
  public boolean equals(Object o) {
    if (this == o) return true;
    if (!(o instanceof BytesFixed other)) return false;
    return Arrays.equals(data, other.data);
  }
  @Override
  public int hashCode() { return Arrays.hashCode(data); }
  @Override
  public String toString() { return "BytesFixed[data=" + Arrays.toString(data) + "]"; }
}

var f1 = new BytesFixed(new byte[]{1, 2, 3});
var f2 = new BytesFixed(new byte[]{1, 2, 3});
f1.equals(f2);   // verified: true
f1.toString();   // verified: "BytesFixed[data=[1, 2, 3]]"

Fix 2 — the simpler option: don't use an array at all. A List already compares by content, so switching the component type sidesteps the whole problem:

record BytesAsList(List<Byte> data) {}

var l1 = new BytesAsList(List.of((byte) 1, (byte) 2, (byte) 3));
var l2 = new BytesAsList(List.of((byte) 1, (byte) 2, (byte) 3));
l1.equals(l2);   // verified: true — no overrides needed
l1.toString();   // verified: "BytesAsList[data=[1, 2, 3]]"
Prefer Fix 2 when you can. It's less code, and you get correct equals/hashCode/toString for free, the same way every other record component does. Reach for Fix 1 (manual Arrays.equals) only when you're specifically constrained to an array type — e.g. matching an existing array-based API, or avoiding boxing overhead for a primitive array in a performance-sensitive path.

Sorting records — they have no natural order by default

A record does not automatically implement Comparable — equals is generated, but ordering is something only you can define, since the compiler doesn't know which component (if any) should drive the sort. Use Comparator.comparing:

List<Point> points = new ArrayList<>(List.of(
    new Point(3, 1), new Point(1, 9), new Point(2, 5)));

points.sort(Comparator.comparingInt(Point::x));
// verified: [Point[x=1, y=9], Point[x=2, y=5], Point[x=3, y=1]]

// multi-key sort: age ascending, ties broken by name
record Person(String name, int age) {}
List<Person> people = new ArrayList<>(List.of(
    new Person("Bob", 30), new Person("Ada", 30), new Person("Cy", 25)));

people.sort(Comparator.comparingInt(Person::age).thenComparing(Person::name));
// verified: [Person[name=Cy, age=25], Person[name=Ada, age=30], Person[name=Bob, age=30]]

If a record genuinely has one obvious natural order, you can make it explicit by implementing Comparable yourself — records can implement interfaces (§3):

record Money(long cents) implements Comparable<Money> {
  public int compareTo(Money other) { return Long.compare(cents, other.cents); }
}

6 · Records + pattern matching

Records were co-designed with pattern matching: because their shape is transparent, they can be destructured directly (record patterns, Java 21).

Legacy — accessor soup
if (obj instanceof Line l) {
  Point a = l.start(), b = l.end();
  int x1 = a.x(), y1 = a.y();
  int x2 = b.x(), y2 = b.y();
}
Record patterns
if (obj instanceof Line(Point(var x1, var y1),
                        Point(var x2, var y2))) {
  // all four bound at once
}
// Sealed + records + switch = type-safe "algebraic data types"
sealed interface Expr permits Num, Add {}
record Num(int v)            implements Expr {}
record Add(Expr l, Expr r)   implements Expr {}

int eval(Expr e) {
  return switch (e) {
    case Num(int v)          -> v;
    case Add(Expr l, Expr r) -> eval(l) + eval(r);
  };   // exhaustive — no default needed
}

The record-vs-enum choice comes down to one question: is the set of values fixed and known at compile time? Days of the week, HTTP methods, and status codes are enums — there will only ever be exactly those constants. (Enums can carry fields too — MONDAY(1), TUESDAY(2) — but every constant is still one specific, pre-declared singleton, never a fresh instance built from runtime data.)
If a type is mostly data and immutable, reach for a record. If it needs mutability, inheritance, or lots of behaviour, use a class. Records largely remove the need for Lombok's @Value/@Data on Java 16+.

8 · Serialization

Records serialize based on their components, and deserialization goes through the canonical constructor — so your validation runs on the way in. That's a real safety improvement over normal serialization, which bypasses constructors.

public record Money(String currency, long cents) implements Serializable {
  public Money {                       // runs on deserialize too
    if (cents < 0) throw new IllegalArgumentException("negative");
  }
}

Note: Records are not serializable by default. The class must explicitly declare implements java.io.Serializable. The guarantee that deserialization routes through the canonical constructor only applies when serialization is enabled.

Sealed classes & interfaces Final in Java 17

A sealed type declares exactly which classes may extend or implement it. That gives you a closed, known set of subtypes — the foundation for exhaustive pattern matching and for modelling "a value is one of a fixed set of shapes".

The problem it solves Before, a type was either final (no subtypes) or completely open (anyone, anywhere could subclass). There was no way to say "these three types and no others", so the compiler could never know a hierarchy was complete — every switch needed a default and could silently miss a newly added case at runtime. Sealed types close the hierarchy so the compiler can reason about it.

1 · What & why

Legacy — open hierarchy, compiler can't help

// Any code anywhere can do:  class Blob extends Shape {}
// so every switch over Shape must have a default and
// can silently miss new subtypes → runtime surprises.
Sealed — the set is fixed and known

    permits Circle, Square, Rectangle { }

public record Circle(double r)              implements Shape { }
public record Square(double side)           implements Shape { }
public record Rectangle(double w, double h) implements Shape { }

2 · The three choices each subtype must make

Every permitted subtype must declare how its own hierarchy continues — this keeps the whole tree closed and intentional.

ModifierMeaning
finalLeaf — cannot be extended further.

non-sealedDeliberately re-opens the type to unrestricted extension.

3 · Rules

  • Permitted subtypes must be accessible to the sealed type and, unless in the same source file, in the same module (same package for the unnamed module).
  • permits is optional if all subtypes live in the same file — the compiler infers the list: 
    sealed interface Expr { }              // permits inferred below
record Num(int v) implements Expr { }
record Add(Expr l, Expr r) implements Expr { }
  • Every permitted subtype must directly extend/implement the sealed type.
  • Records are implicitly final, so they slot into permits lists perfectly.
  • Enums work too — an enum with constant bodies is implicitly sealed (otherwise implicitly final), so it satisfies a sealed interface's requirement with no extra modifier, and mixes with record subtypes in the same hierarchy: 
    sealed interface Status permits Active, Suspended, Closed {}
enum Active     implements Status { INSTANCE }
enum Suspended  implements Status { INSTANCE }
record Closed(String reason) implements Status {}

String describe(Status s) {
  return switch (s) {                          // exhaustive — verified
    case Active a       -> "active";
    case Suspended sp    -> "suspended";
    case Closed(var why) -> "closed: " + why;
  };
}
Requires Java 21+ — Record deconstruction patterns in switch (JEP 440, final in Java 21). Sealed classes themselves are available since Java 17 (JEP 409), but deconstruction syntax inside switch requires Java 21.
Forget a modifier and the compiler tells you exactly what's missing — verified real error: 
sealed interface Shape permits Circle {}

4 · The payoff: exhaustive switch

Because the compiler knows every subtype, a switch needs no default. Add a new subtype later and every non-exhaustive switch fails to compile — a compile-time to-do list instead of a production incident.

Legacy — default + runtime failure
double area(Shape s) {
  if (s instanceof Circle c)  return Math.PI*c.r()*c.r();
  if (s instanceof Square sq) return sq.side()*sq.side();
  // forgot Rectangle...
  throw new IllegalStateException("unknown shape");  // 💥 at runtime
}
Sealed — exhaustive, checked at compile time
double area(Shape s) {
  return switch (s) {                 // no default
    case Circle c    -> Math.PI * c.r() * c.r();
    case Square sq   -> sq.side() * sq.side();
    case Rectangle r -> r.w() * r.h();
  };
  // add a new Shape → this won't compile until you handle it
}

5 · Sealed + records = algebraic data types

The killer combination: model a closed set of cases as sealed records, then switch over them with destructuring. This is the modern, type-safe replacement for the Visitor pattern.

Legacy — Visitor pattern (lots of ceremony)
interface Node { <R> R accept(Visitor<R> v); }
interface Visitor<R> { R visitNum(Num n); R visitAdd(Add a); }
final class Num implements Node {
  final int v; Num(int v){this.v=v;}
  public <R> R accept(Visitor<R> v){ return v.visitNum(this); }
}
// ...Add, plus a Visitor impl per operation. Verbose.
Sealed records + switch
sealed interface Node permits Num, Add {}
record Num(int v)          implements Node {}
record Add(Node l, Node r) implements Node {}

int eval(Node n) {
  return switch (n) {
    case Num(int v)          -> v;
    case Add(Node l, Node r) -> eval(l) + eval(r);
  };
}

4 · Pattern matching for switch + guards Java 21 JEP 441

Previewed in Java 17 (JEP 406), 18 (JEP 420), 19 (JEP 427), 20 (JEP 433), finalized in Java 21 (JEP 441).

Legacy — instanceof ladder
String describe;
if (o instanceof Integer i && i < 0) describe = "negative";
else if (o instanceof Integer i)     describe = "int " + i;
else if (o instanceof String s)      describe = "str " + s;
else if (o == null)                  describe = "null";
else                                 describe = "other";
Switch with patterns + guards
String describe = switch (o) {
  case null                   -> "null";      // null is a case
  case Integer i when i < 0    -> "negative";  // guard with 'when'
  case Integer i              -> "int " + i;
  case String s               -> "str " + s;
  default                     -> "other";
};
  • Guards use when. The first matching label wins, so order matters.
  • null only matches if you add case null (or case null, default); otherwise a null selector throws NPE, as before.
  • Over a sealed type or enum the switch is exhaustive — no default needed.

8 · Switch statements, not just expressions

Every example so far has been a switch expression (it produces a value with ->). Patterns work exactly the same way in a switch statement — you just don't assign the result. Exhaustiveness over a sealed type still applies, and default is still unnecessary:

sealed interface Shape permits Circle, Square {}
record Circle(double r) implements Shape {}
record Square(double side) implements Shape {}

void printArea(Shape s) {
  switch (s) {                       // statement — no assignment, no yield
    case Circle c  -> System.out.println("circle: " + Math.PI * c.r() * c.r());
    case Square sq -> System.out.println("square: " + sq.side() * sq.side());
    // exhaustive over the sealed type — verified: still no default needed
  }
}

Use the expression form when you're computing a value; use the statement form for side effects (logging, dispatching, printing) — the pattern syntax itself doesn't change.

9 · Record patterns & generics

Record patterns support generic record types, but with a real restriction worth knowing: you can only give an explicit type argument when it doesn't require an unsound narrowing. Where a regular cast would just produce an "unchecked" warning, a record pattern refuses outright.

✗ Doesn't compile — unsound narrowing
record Box<T>(T value) {}

String describe(Box<?> box) {
  return switch (box) {
    case Box<String>(var s) -> "string: " + s;   // ✗ compile error, verified:
    // "Box<CAP#1> cannot be safely cast to Box<String>"
  };
}
✓ Two ways that actually work
// (a) omit the type argument — let it be inferred/erased safely
String describe(Box<?> box) {
  return switch (box) {
    case Box(var v) -> "box of: " + v;    // v is Object; verified, works for any T
  };
}

// (b) give a type argument only when the selector ALREADY has that exact type
String describeExact(Box<String> box) {
  return switch (box) {
    case Box<String>(var s) -> "string: " + s;   // verified: fine, no narrowing needed
  };
}

In practice: omit the generic type argument in a record pattern unless the selector's static type is already exactly that parameterization — it's simpler and always compiles.

10 · Dominance & exhaustiveness

  • Dominance: a broader pattern can't precede a narrower one — the compiler rejects the unreachable case. Put case Integer i when … before the plain case Integer i.
  • Exhaustiveness: over a sealed type/enum the compiler verifies all cases are covered. Guarded (when) cases don't count toward covering a subtype, so keep an unguarded fallback for that type.
  • Null: add case null to handle null in-switch instead of guarding before.

The Java Platform Module System (JPMS) Java 9

A module is a named, self-describing group of packages that declares what it needs (requires) and what it exposes (exports). It adds strong encapsulation and reliable configuration on top of the old flat classpath.

~90modules the JDK is split into
strongencapsulation (hidden = truly hidden)
startupmissing deps fail early, not deep in a run
jlinkship only the modules you use
Java 9introduced (Project Jigsaw)
The problem it solves The classpath is a flat bag of JARs: every public class is reachable by everyone ("nothing is really private"), missing or duplicate JARs blow up deep into a run ("JAR hell"), and you always ship the whole JRE. Modules make dependencies explicit and checked at startup, let libraries hide internals, and let tools assemble a minimal runtime.
On this page 1. What & why 2. module-info.java 3. Directives 4. A module graph 5. exports vs opens 5b. open module — open everything 6. Classpath vs module path 7. Services (ServiceLoader) 8. Migration & escape hatches 9. Tooling: jlink, jdeps 10. Pitfalls 11. Real-world use cases 12. Cheat sheet

1 · What & why

  • Strong encapsulation — packages you don't export are hidden, even from reflection.
  • Reliable configuration — missing/duplicate/cyclic dependencies are caught at startup.
  • A scalable platform — the JDK is ~90 modules, so jlink can ship only what you use.

2 · A module in one file: module-info.java

// src/com.myapp/module-info.java
module com.myapp {
  requires java.net.http;            // I depend on this module
  requires transitive com.mylib;     // and my consumers get com.mylib too

  exports com.myapp.api;             // this package is public API
  exports com.myapp.internal to com.myapp.tests;   // qualified export

  uses    com.myapp.spi.Plugin;                     // I consume this service
  provides com.myapp.spi.Plugin
      with com.myapp.plugins.DefaultPlugin;          // I provide an implementation

  opens   com.myapp.model;           // allow deep reflection (frameworks)
}

5 · exports vs opens — the key distinction

exports
exports com.myapp.api;
// Compile against & call public types normally.
// Deep reflection (setAccessible on privates) is STILL blocked.
opens
opens com.myapp.model;
// Reflection frameworks (Jackson, Hibernate, Spring)
// can access members at runtime.
// No compile-time access to non-public types.

opens com.myapp.model to com.fasterxml.jackson.databind;
// qualified opens — only THAT module gets deep reflection,
// everyone else is still blocked

The dreaded error: If you use a reflection-based library (like Gson, Jackson, or Spring) to inspect a class in a module that is not opened, Java will throw a strict exception at runtime instead of silently failing:

java.lang.reflect.InaccessibleObjectException: 
  Unable to make field private java.lang.String com.myapp.model.User.name 
  accessible: module com.myapp does not "opens com.myapp.model" to unnamed module...

To fix this, you must either add an opens directive to your module-info.java or use the --add-opens command-line escape hatch.

5b · open module — opening everything at once

Why it matters: writing opens on every single package that a reflection-heavy framework (Spring, Hibernate, Jackson) might touch gets tedious fast — and it's easy to miss one. Prefixing the whole module declaration with open opens every package in it to deep reflection at once, while exports still controls what's compile-time visible.

Opening each package individually
module com.acme.app {
  requires spring.core;
  exports com.acme.app.api;
  opens com.acme.app.model;
  opens com.acme.app.entities;
  opens com.acme.app.config;   // forget one and Spring throws
                                // InaccessibleObjectException at runtime
}
One open module declaration
open module com.acme.app {
  requires spring.core;
  exports com.acme.app.api;   // exports still applies — this is compile-time API
  // every package in this module is open to reflection — verified:
  // Class.getDeclaredField(...).setAccessible(true) works from anywhere
}

This is exactly why many Spring Boot / Jakarta EE applications declare their main module as open module — those frameworks reflectively construct and inject into almost every class, and enumerating every package individually isn't worth the ceremony for an application module (as opposed to a published library, where you'd want the tighter, explicit package-by-package opens).

7 · Services (ServiceLoader) — complete example

Modules formalise the plugin pattern. Instead of hard-coding dependencies on implementation classes, a module provides an implementation, another uses the interface, and the JVM's ServiceLoader wires them together at runtime. This completely replaces the old META-INF/services text files.

Step 1: The API module (defines the contract)

// module-info.java
module com.myapp.api {
  exports com.myapp.spi;
}

// com/myapp/spi/Plugin.java
package com.myapp.spi;
public interface Plugin {
    void run();
}

Step 2: The Provider module (implements the contract)

// module-info.java
module com.acme.impl {
  requires com.myapp.api;
  // We do NOT export the implementation package! It remains hidden.
  provides com.myapp.spi.Plugin with com.acme.impl.FancyPlugin; 
}

// com/acme/impl/FancyPlugin.java
package com.acme.impl;
import com.myapp.spi.Plugin;
public class FancyPlugin implements Plugin {
    public void run() { System.out.println("Running fancy plugin!"); }
}

Step 3: The Consumer module (uses the contract)

// module-info.java
module com.myapp.app {
  requires com.myapp.api;
  uses com.myapp.spi.Plugin; // Declares intent to load this service
}

// com/myapp/app/Main.java
package com.myapp.app;
import com.myapp.spi.Plugin;
import java.util.ServiceLoader;

public class Main {
    public static void main(String[] args) {
        // The JVM automatically discovers FancyPlugin on the module path!
        // Notice: we do NOT require com.acme.impl anywhere.
        Iterable<Plugin> plugins = ServiceLoader.load(Plugin.class);
        for (Plugin p : plugins) {
            p.run(); 
        }
    }
}

9 · Tooling: jdeps, jlink, and jpackage

The module system enabled the creation of three powerful tools that completely change how Java apps are distributed: you no longer tell users to "install Java"; you just hand them an installer.

1. jdeps (Dependency Analysis)

Scans your JARs to find exactly which JDK modules your code actually requires, and flags any illegal usage of internal JDK APIs (like sun.misc.Unsafe).

# What JDK modules does my app need? (Output might be: java.base, java.desktop)
jdeps --module-path libs -summary my-app.jar

# Am I using any hidden/removed JDK internal APIs?
jdeps --jdk-internals my-app.jar

2. jlink (Custom Runtime Generator)

Why ship a 250MB JRE if your app only uses java.base? jlink strips away unused JDK modules (like Swing or CORBA) to build a minimal, custom JVM just for your app.

# Create a tiny custom JVM containing only your app's required modules
jlink --module-path $JAVA_HOME/jmods:./libs \
      --add-modules java.base,com.myapp \
      --strip-debug --no-man-pages --no-header-files --compress zip-9 \
      --output my-custom-jre
# Result: my-custom-jre/bin/java is a fully functional, ~30MB runtime!

3. jpackage (Native Installer Builder) Java 16

Takes your JARs and your custom jlink runtime, and wraps them into a native installer (.exe, .dmg, .deb). The user just double-clicks the installer — they don't even know it's a Java app.

# Build a Windows MSI installer (must be run on Windows)
jpackage --type msi \
         --name "MyApp" \
         --input ./libs \
         --main-jar my-app.jar \
         --main-class com.myapp.Main \
         --runtime-image ./my-custom-jre \
         --win-shortcut --win-menu

The Stream API Java 8

A Stream is a pipeline of operations over a sequence of data — you declare what to do (filter, transform, aggregate) instead of writing the loop yourself. Every example on this page is written to be pasted into a file and run as-is.

1 · Mental model & creating streams

A pipeline is always source → zero or more intermediate ops → one terminal op. Intermediate ops (map, filter...) are lazy — they just describe the pipeline. Nothing executes until a terminal op (collect, forEach, reduce...) pulls elements through it.

Creating a stream — every common source

Legacy — manual loops per source
List<String> out = new ArrayList<>();
for (String s : list) out.add(s.toUpperCase());

int[] arr = {1, 2, 3};
int sum = 0;
for (int x : arr) sum += x;

List<String> lines = new ArrayList<>();
try (var r = Files.newBufferedReader(path)) {
  String line;
  while ((line = r.readLine()) != null) lines.add(line);
}
Streams — one shape for every source
list.stream();                       // from a Collection
Stream.of("a", "b", "c");             // from varargs
Arrays.stream(new int[]{1, 2, 3});    // from an array -> IntStream
Stream.generate(Math::random);        // infinite; must limit()
Stream.iterate(1, n -> n * 2);         // infinite; must limit() or use bounded form
IntStream.range(0, 10);                // 0..9
IntStream.rangeClosed(1, 10);          // 1..10
Files.lines(path);                     // lazy, one line per element (try-with-resources!)
map.entrySet().stream();               // from a Map
A stream can only be consumed once. Calling a terminal operation twice on the same stream throws IllegalStateException. Re-create it from the source (or wrap creation in a Supplier<Stream<T>>) if you need to run the pipeline again.

Multi-key sorting with Comparator chaining

Sorting by more than one field is where Comparator's static/default methods (comparing, thenComparing, reversed) pay off — no manual compareTo chains.

4 · reduce() — identity, accumulator, combiner

reduce is the most general terminal operation — it folds a stream down to one value. It comes in three overloads, and the difference between them is exactly the part most people find confusing: what happens to the combiner in parallel.

4.1 · One-arg — no identity, returns Optional

Optional<Integer> max = Stream.of(3, 1, 4, 1, 5).reduce(Integer::max);
// empty stream -> Optional.empty() (no identity to fall back on)

4.2 · Two-arg — identity + accumulator, same type

Legacy — manual loop
int sum = 0;
for (int n : numbers) sum += n;
reduce(identity, accumulator)
int sum = numbers.stream().reduce(0, Integer::sum);
// identity = 0 (returned for an empty stream, and the starting value)
// accumulator = (partial, next) -> partial + next

4.3 · Three-arg — identity + accumulator + combiner, different types

Use this when the accumulated type (U) differs from the element type (T) — e.g. reducing a stream of Strings down to a total int length. This is the only form that lets U != T, and it's the one that makes parallel execution correct.

List<String> words = List.of("foo", "bars", "bazzz");   // lengths: 3, 4, 5

int totalLen = words.stream().reduce(
    0,                                    // identity: U (int)
    (partial, word) -> partial + word.length(),   // accumulator: (U, T) -> U
    Integer::sum                          // combiner: (U, U) -> U
);
// totalLen == 12

Why the combiner exists — sequential vs parallel

Common mistake: writing a 3-arg reduce where the combiner doesn't correctly represent "merge two partial results of the accumulation" — e.g. a combiner with side effects, or one that isn't associative. It'll work by luck sequentially and produce wrong answers only when run in parallel.

5 · Collectors, in depth

Collectors is a factory of ready-made terminal strategies for collect(...) — from a plain list to a fully grouped, aggregated report.

5.1 · The basics — toList, toSet, toMap, joining

Legacy
List<String> names = new ArrayList<>();
for (Employee e : emps) names.add(e.name());
StringBuilder sb = new StringBuilder();
for (int i = 0; i < names.size(); i++) {
  sb.append(names.get(i));
  if (i < names.size() - 1) sb.append(", ");
}
Collectors
List<String> names = emps.stream().map(Employee::name).toList();
String csv = emps.stream().map(Employee::name).collect(joining(", "));
String csv2 = emps.stream().map(Employee::name).collect(joining(", ", "[", "]"));  // "[Ada, Bob]"

Map<String, Double> salaryByName = emps.stream()
    .collect(toMap(Employee::name, Employee::salary));
// duplicate keys THROW by default — see 5.2 for the fix

5.2 · toMap with a merge function — handling duplicate keys

// two employees could share a department; keep the HIGHEST salary per dept
Map<String, Double> maxSalaryByDept = emps.stream()
    .collect(toMap(Employee::dept, Employee::salary, Double::max));
// toMap(keyFn, valueFn, mergeFn) — mergeFn resolves collisions instead of throwing

5.3 · groupingBy — the workhorse

Groups elements by a classifier function. Pair it with a downstream collector to do more than just collect the raw group into a list.

// simplest form: group into List<Employee> per dept
Map<String, List<Employee>> byDept = emps.stream()
    .collect(groupingBy(Employee::dept));

// + downstream collector: average salary per dept, instead of the raw list
Map<String, Double> avgByDept = emps.stream()
    .collect(groupingBy(Employee::dept, averagingDouble(Employee::salary)));

// + a Map supplier: sorted keys via TreeMap instead of HashMap
Map<String, Double> avgByDeptSorted = emps.stream()
    .collect(groupingBy(Employee::dept, TreeMap::new, averagingDouble(Employee::salary)));

// nesting groupingBy inside groupingBy: dept -> salary-bucket -> names
Map<String, Map<Boolean, List<String>>> nested = emps.stream()
    .collect(groupingBy(Employee::dept,
             groupingBy(e -> e.salary() > 70_000,
             mapping(Employee::name, toList()))));
// verified: {Sales={false=[Cy, Dee]}, Eng={true=[Ada, Bob]}}
// the downstream collector of one groupingBy can be another groupingBy —
// this is how you build a two-level report in a single pass

5.4 · partitioningBy — grouping by true/false

Map<Boolean, List<Employee>> highLow = emps.stream()
    .collect(partitioningBy(e -> e.salary() > 80_000));
List<Employee> highEarners = highLow.get(true);
// always has BOTH keys present, even if one group is empty

5.5 · Numeric downstream collectors

long total   = emps.stream().collect(counting());                          // same as .count()
double sum   = emps.stream().collect(summingDouble(Employee::salary));
double avg   = emps.stream().collect(averagingDouble(Employee::salary));
DoubleSummaryStatistics stats = emps.stream()
    .collect(summarizingDouble(Employee::salary));
// stats.getMin() / getMax() / getAverage() / getSum() / getCount() — all in one pass

5.6 · teeing — two collectors, one pass 12

Why it matters: without teeing, computing "sum AND count" in one pass meant either two separate stream traversals or a hand-rolled combined accumulator.

Legacy — two passes over the stream
double sum = emps.stream().mapToDouble(Employee::salary).sum();
long count = emps.stream().count();
String stats = "sum=" + sum + " count=" + count;
teeing — one pass
String stats = emps.stream().collect(teeing(
    summingDouble(Employee::salary),
    counting(),
    (sum, count) -> "sum=" + sum + " count=" + count));
// "sum=425000.0 count=5"

Key property: teeing() performs a single pass over the stream, branching each element into two independent sub-collectors simultaneously — not two sequential passes. This makes it efficient for combined aggregations like (sum + count) or (min + max) without iterating the source twice.

6 · Writing a custom Collector

A Collector<T, A, R> has the same four moving parts as a Gatherer, but they build a single final result instead of emitting elements downstream.

Legacy — build a joined string by hand
StringJoiner sj = new StringJoiner(", ", "[", "]");
for (Employee e : emps) sj.add(e.name());
String joined = sj.toString();
// works, but isn't a reusable, composable Collector
Custom Collector.of — reusable & composable
Collector<Employee, StringJoiner, String> joinNames = Collector.of(
    () -> new StringJoiner(", ", "[", "]"),   // supplier
    (sj, e) -> sj.add(e.name()),              // accumulator
    StringJoiner::merge,                      // combiner (parallel streams)
    StringJoiner::toString);                  // finisher

String joined = emps.stream().collect(joinNames);
// "[Ada, Bob, Cy, Dee, Eve]" — and joinNames can be reused anywhere

StringJoiner already has a merge method built for exactly this purpose — a nice illustration of how the combiner should genuinely represent "merge two partial containers".

7 · Primitive streams — avoiding boxing

IntStream, LongStream, DoubleStream avoid boxing every element into an Integer/Long/Double — faster, and come with numeric-only operations like sum() and summaryStatistics().

Legacy — boxed, manual sum
List<Integer> nums = List.of(1, 2, 3, 4, 5);
int sum = 0;
for (int n : nums) sum += n;   // unboxing on every read
IntStream — unboxed, built-in sum
int sum = IntStream.rangeClosed(1, 5).sum();
IntSummaryStatistics stats = emps.stream()
    .mapToInt(e -> (int) e.salary())
    .summaryStatistics();
// stats.getMin() / getMax() / getAverage() — no manual loop
Stream<Integer> boxedAgain = IntStream.range(0, 5).boxed();   // back to Integer if needed

Convert with mapToInt/mapToLong/mapToDouble (object → primitive) and .boxed() (primitive → object).

Custom thread pool (advanced, use sparingly)

Parallel streams always use the shared common ForkJoinPool — sized to your CPU count and shared with everything else in the JVM that uses it. To isolate a parallel stream in its own pool (e.g. to avoid starving other parallel work), submit the whole pipeline as a task:

ForkJoinPool customPool = new ForkJoinPool(4);
long result = customPool.submit(() ->
    hugeList.parallelStream().filter(Item::isExpensive).count()
).get();
customPool.shutdown();

9 · Putting it all together — a sales report

A single pipeline combining groupingBy, a downstream collector, sorting, and a LinkedHashMap to preserve that order — the kind of thing Stream API replaces a whole page of manual code for.

    new Sale("East", "Widget", 200),

             (a, b) -> a, LinkedHashMap::new));   // (a,b)->a: unused, keys are unique here

1 · What is a virtual thread?

A normal Java thread (a platform thread) is a thin wrapper around an operating-system thread. OS threads are expensive: each reserves ~1 MB of stack, and switching between them means a trip into the kernel. So you can realistically only have a few thousand — which is why we hide them behind thread pools and try never to block them.

A virtual thread is not tied to an OS thread. Its stack lives on the Java heap, and the JVM runs many virtual threads on a small pool of real OS threads, parking a virtual thread whenever it blocks and reusing the OS thread for someone else. A virtual thread costs a few hundred bytes, so you can have millions.

Easy analogy. Platform threads are like giving every restaurant customer their own private chef (expensive, you run out fast). Virtual threads are like a few chefs serving a huge dining room: while one order waits in the oven (blocked on I/O), the chef cooks someone else's dish. Same chefs, far more customers served.

3 · Architecture & how it works

Three pieces make virtual threads work:

  • Carrier threads — a small pool of real OS threads (a dedicated ForkJoinPool, sized to CPU cores by default) that actually execute code.
  • The JVM scheduler — decides which virtual thread runs on which carrier.
  • Continuations — the low-level mechanism that lets a virtual thread's call stack be captured to the heap and resumed later. This is what makes "pause here, come back later" possible without an OS thread.

The key verbs are mount and unmount: a virtual thread is mounted on a carrier while running, and unmounts (its stack is copied to the heap) the instant it blocks. The freed carrier immediately runs another virtual thread. When the blocking call finishes, the virtual thread is re-mounted — possibly on a different carrier.

4 · Creating virtual threads

Four ways, from lowest to highest level:

// (a) Fire-and-forget, unnamed
Thread t = Thread.startVirtualThread(() -> doWork());
t.join();

// (b) Builder — name, uncaught handler, not-yet-started
Thread t2 = Thread.ofVirtual()
    .name("worker-", 0)          // worker-0, worker-1, ...
    .start(() -> doWork());

// (c) A ThreadFactory (plug into existing APIs)
ThreadFactory factory = Thread.ofVirtual().factory();

// (d) The recommended way for many tasks — an executor
try (var exec = Executors.newVirtualThreadPerTaskExecutor()) {
  Future<String> f = exec.submit(() -> fetch());
  System.out.println(f.get());
}

// For comparison, an explicit platform thread:
Thread p = Thread.ofPlatform().name("io").start(() -> doWork());

Thread.ofVirtual().unstarted(task) — creates but does not start the thread; useful when you need to configure additional properties (e.g., name, uncaught-exception handler) before starting.

Check at runtime: Thread.currentThread().isVirtual() returns true inside a virtual thread.

5 · Executors & task fan-out

7 · Pinning (and the JDK 24 fix)

Pinning is when a virtual thread cannot unmount even though it's blocked, so it holds its carrier hostage. Enough pinned threads and the carrier pool starves — you lose the whole benefit.

In Java 21–23 the two causes were:

  1. Blocking inside a synchronized block or method.
  2. Calling a native method / foreign function while blocked.

Java 24 JEP 491 removed the synchronized cause entirely — the big one. Native-call pinning remains but is rare in application code.

Pins the carrier (JDK 21–23)
private final Object lock = new Object();

Result read() {
  synchronized (lock) {        // VT can't unmount here...
    return jdbc.query(sql);    // ...and this call BLOCKS → pinned
  }
}
Does not pin
private final ReentrantLock lock = new ReentrantLock();

Result read() {
  lock.lock();                 // VT can unmount while holding it
  try {
    return jdbc.query(sql);    // blocks cheaply
  } finally { lock.unlock(); }
}

8 · Relationship with structured concurrency

Virtual threads make it cheap to run each subtask on its own thread. Structured concurrency gives those subtasks a parent scope so they start together and are joined or cancelled together — no leaks, clear error handling. Think: virtual threads are the cheap workers; structured concurrency is the manager that owns them.

Raw virtual-thread executor — manual coordination
try (var ex = Executors.newVirtualThreadPerTaskExecutor()) {
  var uf = ex.submit(() -> loadUser(id));
  var of = ex.submit(() -> loadOrders(id));
  // if loadUser fails, loadOrders keeps running (waste);
  // cancellation is on you.
  return new Page(uf.get(), of.get());
}
Structured concurrency — one unit of work
try (var scope = StructuredTaskScope.open()) {   // Java 25 API
  var user   = scope.fork(() -> loadUser(id));
  var orders = scope.fork(() -> loadOrders(id));
  scope.join();                 // fail-fast: one error cancels siblings
  return new Page(user.get(), orders.get());
}

9 · Relationship with scoped values

ThreadLocal was tolerable when threads were few and pooled. With millions of virtual threads, per-thread copies add up and the usual "set in a pool thread and forget to clear it" bugs get worse. Scoped values are the intended companion: immutable, automatically unbound at the end of a scope, and inherited by forked subtasks.

ThreadLocal — mutable, must clean up
static final ThreadLocal<User> CUR = new ThreadLocal<>();
CUR.set(user);
try { handle(); } finally { CUR.remove(); }   // leak if forgotten
ScopedValue — immutable, self-cleaning
static final ScopedValue<User> CUR = ScopedValue.newInstance();
ScopedValue.where(CUR, user).run(() -> handle());  // auto-unbound
// deeper code: CUR.get()

11 · Virtual threads vs WebFlux / reactive

Before virtual threads, the only way to serve huge concurrency on the JVM without a thread per request was reactive programming (Project Reactor / Spring WebFlux, RxJava). It works, but it's a different, harder programming model: everything becomes Mono/Flux, stack traces are cryptic, and debugging is painful. Virtual threads deliver similar scalability while letting you keep ordinary imperative, blocking code.

14 · Migration guide

  1. Get on Java 21+ (ideally 24+/25). 24+ removes synchronized pinning — a big reason to prefer it.
  2. Switch task execution to per-task virtual threads. Replace newFixedThreadPool(n) used for I/O with newVirtualThreadPerTaskExecutor(). Leave CPU-bound pools alone.
  3. Hunt for pinning. Run with -Djdk.tracePinnedThreads=full (21–23) or watch the JFR pinned event; swap hot synchronized+I/O for ReentrantLock.
  4. Replace ThreadLocal context (request/user/tenant) with scoped values.
  5. Right-size downstream pools & add back-pressure. The bottleneck moves from threads to DB connections / API limits — cap them with a Semaphore.
  6. Group related subtasks with structured concurrency for clean cancellation and error handling.
  7. Framework flip: Spring Boot 3.2+ → spring.threads.virtual.enabled=true. Then load-test.

    try { System.out.println(url + " → " + f.get()); }
    catch (Exception e) { System.out.println(url + " → ERROR"); }

Virtual Thread Invariants

Virtual threads are managed by the JVM and have a few strict invariants compared to platform threads:

  • Always Daemon: Virtual threads are always daemon threads. They will not keep the JVM alive if all non-daemon platform threads terminate.
  • Fixed Priority: The priority of a virtual thread is always Thread.NORM_PRIORITY. It cannot be changed.
  • No ThreadGroup: Virtual threads cannot be added to a custom ThreadGroup. They all belong to a single system thread group.

1 · The problem with raw futures

Legacy — unstructured, leak-prone
Future<User>  u = pool.submit(() -> findUser(id));
Future<Order> o = pool.submit(() -> fetchOrder(id));
try {
  return new Response(u.get(), o.get());
  // if findUser throws, fetchOrder keeps running (leak);
  // if the caller is interrupted, both may be orphaned.
} catch (Exception e) {
  u.cancel(true); o.cancel(true);   // did you remember both?
  throw e;
}
Structured — one scope, one unit
try (var scope = StructuredTaskScope.open()) {   // Java 25 API
  var user  = scope.fork(() -> findUser(id));
  var order = scope.fork(() -> fetchOrder(id));

  scope.join();          // wait for all; first failure cancels the rest
  return new Response(user.get(), order.get());
}   // on exit, every subtask is guaranteed done

2 · The scope model

  • No leaks: try-with-resources can't exit until all forked subtasks finish/cancel.
  • Short-circuit: one failure cancels the siblings — no waiting on work you'll discard.
  • Clear hierarchy: observability tools show the real parent→child task tree.
  • Cheap: each subtask runs on its own virtual thread.

3 · Basic usage

Response handle(String id) throws Exception {
  try (var scope = StructuredTaskScope.open()) {
    var user   = scope.fork(() -> findUser(id));    // returns a Subtask<User>
    var orders = scope.fork(() -> fetchOrders(id));

    scope.join();                    // MUST join before reading results
    return new Response(user.get(), orders.get());
  }
}

Every Subtask also exposes its outcome via .state() — a Subtask.State enum (SUCCESS, FAILED, or UNAVAILABLE if cancelled before starting) — verified, useful when a Joiner deliberately tolerates partial failure and you want to know which subtasks actually completed:

System.out.println("user subtask state: " + user.state());   // e.g. SUCCESS

4 · Joiners — choosing the completion policy

A Joiner decides when join() returns and how results/errors combine.

All must succeed (fail-fast)
try (var scope = StructuredTaskScope.open(
        Joiner.<String>allSuccessfulOrThrow())) {
  scope.fork(() -> a());
  scope.fork(() -> b());
  var all = scope.join();   // Stream of subtasks, all OK
}
Race — first success wins
try (var scope = StructuredTaskScope.open(
        Joiner.<String>anySuccessfulOrThrow())) {
  scope.fork(() -> mirror1());
  scope.fork(() -> mirror2());
  String fastest = scope.join();   // others cancelled
}

2 · The 5 built-in gatherers, in detail

java.util.stream.Gatherers ships five ready-made gatherers. Each is a small, precise tool — know their edge cases and you rarely need a custom one.

2.1 · windowFixed(n) — non-overlapping batches

Behaviour: groups elements into consecutive, non-overlapping chunks of size n. The last window may be shorter if the stream doesn't divide evenly — nothing is dropped.

Stream.of(1,2,3,4,5,6,7,8).gather(Gatherers.windowFixed(3)).toList();
// [[1, 2, 3], [4, 5, 6], [7, 8]]     ← last window has only 2 elements
Memory note: for efficiency, windows may be allocated eagerly, so very large window sizes on huge streams can use significant memory — size windows for your data, not "big for safety".

2.2 · windowSliding(n) — overlapping windows

Behaviour: a moving window of size n that advances one element at a time — every window after the first shares n-1 elements with its predecessor.

Stream.of(1,2,3,4).gather(Gatherers.windowSliding(2)).toList();
// [[1, 2], [2, 3], [3, 4]]     ← 3 windows from 4 elements (n - windowSize + 1)

2.3 · scan(seed, accumulator) — running (prefix) accumulation

Behaviour: starts from a seed value, then for each input element applies the accumulator to (current value, element) and emits the new running value — one output per input, the seed itself is never emitted separately.

Stream.of(1,2,3,4).gather(Gatherers.scan(() -> 0, Integer::sum)).toList();
// [1, 3, 6, 10]      ← running sum after consuming each element
Stream.of(1,2,3).gather(Gatherers.scan(() -> "", (acc, n) -> acc + n)).toList();
// ["1", "12", "123"]  ← running string concatenation

2.4 · fold(seed, folder) — reduce to exactly one element

Behaviour: like scan, but only the final accumulated value is emitted — always exactly one output element, unlike a plain reduce this works even when the operation is inherently order-dependent (no combiner needed).

Optional<String> result = Stream.of(1,2,3,4,5,6,7,8,9)
    .gather(Gatherers.fold(() -> "", (acc, n) -> acc + n))
    .findFirst();
// Optional["123456789"]

fold vs reduce: fold emits exactly one final element after the entire stream is consumed, and supports an arbitrary accumulator type R that differs from the element type T. Stream.reduce() returns an Optional and requires the accumulated type to match the element type. Use fold when you need type transformation during accumulation.

2.5 · mapConcurrent(n, mapper) — bounded concurrent mapping

Behaviour: maps up to n elements concurrently (backed by virtual threads), while still emitting results in original encounter order. Full breakdown → §6.

var bodies = urls.stream()
    .gather(Gatherers.mapConcurrent(10, this::fetch))
    .toList();   // ≤10 in flight, order preserved

Implementation note: mapConcurrent(n, fn) internally runs tasks on virtual threads, bounded by a semaphore of size n. It reorders outputs to match input encounter order regardless of task completion order, making it safe and deterministic for I/O-bound operations.

3 · Anatomy of a gatherer

A gatherer has up to four parts. Only the integrator is required.

4 · Writing your own

4.1 · "Distinct by key"

Legacy — stateful lambda hack (fragile)
Set<String> seen = ConcurrentHashMap.newKeySet();
var out = people.stream()
    .filter(p -> seen.add(p.city()))   // side-effecting filter 😬
    .toList();
Reusable gatherer
static <T,K> Gatherer<T,?,T> distinctBy(Function<T,K> key) {
  return Gatherer.ofSequential(
    HashSet::new,                             // initializer
    (seen, item, downstream) -> {             // integrator
      if (seen.add(key.apply(item)))
        return downstream.push(item);         // emit first per key
      return true;                            // true = keep going
    });
}
var out = people.stream().gather(distinctBy(Person::city)).toList();

Returning false from the integrator short-circuits the upstream — that's how a gatherer can implement limit-like behaviour.

4.2 · "Group consecutive equal elements" (run-length grouping)

A gatherer that tracks the previous element to decide whether to start a new group — something Collectors.groupingBy can't express, because it groups by key across the whole stream, not by adjacency.

static <T> Gatherer<T,?,List<T>> groupRuns() {
  return Gatherer.<T, List<T>, List<T>>ofSequential(
    ArrayList::new,                                    // initializer: current run
    (run, item, downstream) -> {                       // integrator
      if (!run.isEmpty() && !run.get(run.size() - 1).equals(item)) {
        if (!downstream.push(List.copyOf(run))) return false;
        run.clear();
      }
      run.add(item);
      return true;
    },
    (run, downstream) -> {                              // finisher: flush the last run
      if (!run.isEmpty()) downstream.push(List.copyOf(run));
    });
}

Stream.of("A","A","B","B","B","A","C")
    .gather(groupRuns())
    .toList();
// [[A, A], [B, B, B], [A], [C]]
Why this needed a finisher: the very last run is still sitting in state when the stream runs out of elements — only the finisher gets a chance to flush it.

5 · Composing gatherers with andThen

Gatherers chain like any intermediate operation — either by calling .gather() twice, or by fusing two gatherers into one reusable unit with andThen.

Two separate .gather()/.map() steps, repeated everywhere
var result = readings.stream()
    .gather(Gatherers.windowFixed(3))     // batch into 3s
    .map(GathererCompose::average)        // average each batch
    .toList();
// every pipeline that needs this has to repeat both lines
Fused into one named, reusable Gatherer
// turn a plain mapping function into a (stateless) Gatherer
static <T, R> Gatherer<T, ?, R> mapping(Function<T, R> f) {
  return Gatherer.ofSequential((state, element, downstream) -> downstream.push(f.apply(element)));
}

// fuse "batch into 3s" + "average each batch" into one Gatherer
Gatherer<Reading, ?, Double> batchAverage =
    Gatherers.<Reading>windowFixed(3).andThen(mapping(GathererCompose::average));

var result = readings.stream().gather(batchAverage).toList();
// readings 1..7  →  [2.0, 5.0, 7.0]

andThen is most valuable when you want to name and reuse a multi-step transformation (e.g. "batch, then average, then rate-limit") across several pipelines, instead of repeating the same chain of .gather().map() calls everywhere.

Advanced Gatherer Concepts

Greedy vs Non-Greedy Integrators

A Gatherer's integrator can be greedy (always returning true to request more elements) or non-greedy (returning false to short-circuit). Non-greedy integrators allow gatherers to act like limit() or takeWhile(), stopping upstream processing early once their specific condition is met.

Gatherer.Downstream

The Gatherer.Downstream interface is how an integrator or finisher pushes elements to the next stage in the pipeline. It is intentionally simple, consisting primarily of the push(T element) method. You must check its return value: if it returns false, the downstream no longer accepts elements, and your gatherer should gracefully stop.

Parallel Gatherer Support

To support parallel execution, a Gatherer needs a combiner. If your Gatherer is stateful and cannot be safely merged across threads, use Gatherer.ofSequential(...). If the state is mergeable, you supply a combiner function just like in a Collector, allowing the parallel stream framework to split the work and merge the partial states.

5b · Modeling C structs with MemoryLayout.structLayout

Why it matters: most real native APIs pass structs, not just scalars. A StructLayout describes the C struct's field order/types, and a VarHandle derived from it gives you named, typed field access — no manual offset arithmetic.

Legacy — manual byte offsets
// struct Point { int x; int y; };  — computing offsets by hand

buf.putInt(4, 20);   // y at offset 4 — one typo here and you corrupt data

StructLayout point = MemoryLayout.structLayout(
    JAVA_INT.withName("x"),
    JAVA_INT.withName("y"));

VarHandle yHandle = point.varHandle(MemoryLayout.PathElement.groupElement("y"));

try (Arena arena = Arena.ofConfined()) {
  MemorySegment seg = arena.allocate(point);
  xHandle.set(seg, 0L, 10);
  yHandle.set(seg, 0L, 20);
  System.out.println(xHandle.get(seg, 0L) + "," + yHandle.get(seg, 0L));   // "10,20"

7 · Native-access restrictions

Because native calls can crash the VM, they're a restricted operation. Enable them explicitly:

8 · Full runnable example — sort a native array with libc's qsort

Everything above in one program you can actually run: off-heap memory, a downcall into C, and an upcall callback from C back into Java — no jextract, no build tool, no dependencies. It calls the C standard library's qsort to sort an array, using a comparator written in Java as the callback.

Requirements: JDK 22 or later (FFM is final, no --enable-preview needed). Works on macOS and Linux out of the box (libc's qsort is always loaded). On Windows, run it under WSL.
// NativeQsortDemo.java
// A complete, runnable Foreign Function & Memory API example.
// It sorts an int[] by calling C's qsort() — with a Java method as the comparator.
import java.lang.foreign.*;
import java.lang.invoke.MethodHandle;
import java.lang.invoke.MethodHandles;
import java.util.Arrays;

import static java.lang.foreign.ValueLayout.*;

public class NativeQsortDemo {

    // qsort() calls this for every comparison. Each MemorySegment points at
    // one int inside the native array (ADDRESS.withTargetLayout(JAVA_INT)
    // below tells the runtime the pointer targets a 4-byte int, so .get() works).
    static int compare(MemorySegment a, MemorySegment b) {
        int x = a.get(JAVA_INT, 0);
        int y = b.get(JAVA_INT, 0);
        return Integer.compare(x, y);
    }

    public static void main(String[] args) throws Throwable {
        Linker linker = Linker.nativeLinker();

        // 1. Describe C's qsort and get a downcall handle for it:
        //    void qsort(void *base, size_t nmemb, size_t size,
        //               int (*compar)(const void *, const void *));
        MethodHandle qsort = linker.downcallHandle(
            linker.defaultLookup().find("qsort").orElseThrow(),
            FunctionDescriptor.ofVoid(ADDRESS, JAVA_LONG, JAVA_LONG, ADDRESS));

        // 2. Turn our Java `compare` method into a native function pointer.
        FunctionDescriptor comparDesc = FunctionDescriptor.of(JAVA_INT,
            ADDRESS.withTargetLayout(JAVA_INT),
            ADDRESS.withTargetLayout(JAVA_INT));
        MethodHandle comparHandle = MethodHandles.lookup().findStatic(
            NativeQsortDemo.class, "compare", comparDesc.toMethodType());

        try (Arena arena = Arena.ofConfined()) {
            MemorySegment comparFunc = linker.upcallStub(comparHandle, comparDesc, arena);

            // 3. Copy a Java array into off-heap memory that C can operate on.
            int[] data = { 9, 3, 7, 1, 8, 2, 6, 4, 5, 0 };
            MemorySegment nativeArray = arena.allocateFrom(JAVA_INT, data);

            // 4. Call native qsort. It sorts nativeArray IN PLACE, calling our
            //    Java `compare` method every time it needs to compare two elements.
            qsort.invokeExact(nativeArray, (long) data.length, JAVA_INT.byteSize(), comparFunc);

            // 5. Copy the sorted off-heap array back into a plain Java array.
            int[] sorted = nativeArray.toArray(JAVA_INT);

            System.out.println("Before: " + Arrays.toString(data));
            System.out.println("After:  " + Arrays.toString(sorted));
        }   // arena closes here — native memory is freed deterministically
    }
}

2 · The Java Memory Model

Multiple threads reading and writing the heap raises a question the type system can't answer: if thread A writes a field, when is thread B guaranteed to see it? The Java Memory Model (JLS Chapter 17) answers this with one core relationship: happens-before.

"If one action happens-before another, then the first is visible to and ordered before the second." — JLS §17.4.5, verified from the current spec

What creates a happens-before edge

Program order within one thread always happens-before itself, but across threads you need one of these — verified straight from JLS §17.4.4 (synchronizes-with):

  • An unlock on a monitor happens-before every subsequent lock on that same monitor.
  • A write to a volatile field happens-before every subsequent read of that field.
  • Starting a thread happens-before the first action inside it; a thread's last action happens-before code that observes it via join() or isAlive().
  • Writing a default value (0/null/false) to every field of an object happens-before any action in the program — fields are never "uninitialized garbage" in Java.
  • The completion of a constructor for an object with final fields happens-before any read of those fields (the "freeze" action — see §2e below).
  • An action that interrupts a thread (t.interrupt()) happens-before the point where the target detects the interrupt (InterruptedException / Thread.interrupted()).
  • Happens-before is transitive: if A hb B and B hb C, then A hb C.

Concrete reordering example — why this matters

Without a happens-before edge the compiler/CPU may freely reorder independent writes. Consider two shared variables x and y initially 0:

// Thread 1           // Thread 2
x = 1;                int r1 = y;
y = 1;                int r2 = x;
// Surprisingly legal result: r1 == 1 AND r2 == 0
// Thread 1 reordered y=1 before x=1; Thread 2 saw the reordered state

Making y volatile would prevent this: the write y = 1 would carry a memory barrier that forces x = 1 to be visible before y's write completes.

Verified: a real visibility bug, and the one-word fix

Without a happens-before edge, the compiler and JIT are free to assume a field never changes and cache it — this is not theoretical. Run this yourself:

Without volatile — hangs forever, verified
public class VisibilityDemo {
  static boolean stopRequested = false;   // plain field

  public static void main(String[] args) throws Exception {
    Thread worker = new Thread(() -> {
      while (!stopRequested) { /* spin */ }
      System.out.println("worker stopped");
    });
    worker.start();
    Thread.sleep(1000);
    stopRequested = true;              // main thread's write...
    worker.join(3000);
    System.out.println(worker.isAlive()
        ? "worker STILL RUNNING after 3s"   // ...never seen by worker
        : "worker exited normally");

}

// the JIT hoisted the field read out of the loop — no happens-before edge exists

Advanced JMM: Instruction Reordering & the "As-If-Serial" Illusion

To maximize performance, the compiler, JIT, and CPU are legally allowed to reorder your instructions (e.g., delaying a memory write or hoisting a read) as long as single-threaded execution isn't broken (the "as-if-serial" guarantee). But across threads, this breaks instantly without a happens-before edge.

Advanced JMM: The Double-Checked Locking Bug

The classic Singleton lazy-initialization pattern is the most famous victim of instruction reordering. Without volatile, this code is fatally broken:

public class Singleton {
  private static Singleton instance; // BUG: missing 'volatile'
  public static Singleton getInstance() {
    if (instance == null) {
      synchronized (Singleton.class) {
        if (instance == null) instance = new Singleton(); // The danger zone
      }
    }
    return instance;
  }
}

Why it fails: The JVM performs three steps for new Singleton(): (1) allocate memory, (2) initialize the object (call constructor), and (3) assign the reference to instance. The JMM allows the CPU to reorder these as 1 → 3 → 2. Another thread calling getInstance() could see instance != null (step 3) and return a partially initialized object because the constructor hasn't finished yet (step 2)!
The Fix: Adding volatile to instance establishes a memory barrier. It strictly prevents the write of the reference from being reordered ahead of the object's initialization.

Advanced JMM: final Field Semantics (Initialization Safety)

The JMM provides a special guarantee for final fields. At the end of a constructor, the JMM issues a "freeze" action on all final fields. This creates a happens-before relationship ensuring that any thread that sees the object reference will always see the fully initialized values of those final fields.

  • No Locks Needed: You don't need volatile or synchronized to safely read a final field across threads.
  • The Catch (No Leaking): This guarantee is completely voided if you let the this reference "escape" during construction (e.g., publishing this to a listener or a static field inside the constructor). If this escapes, other threads might see the object before the freeze action occurs.

Advanced JMM: Safe Publication Patterns

"Publication" means making an object reference visible to another thread. Unsafe publication is the #1 source of subtle concurrency bugs — thread B sees the reference but reads partially initialized fields. The JMM defines exactly four safe ways to publish an object:

Safe Publication TechniqueHow it works
static initializerJVM class-loading guarantees the object is fully initialized before any thread can access it. Simplest and safest.
volatile fieldWriting the reference to a volatile field establishes a happens-before edge — all prior writes (including the constructor) are visible to readers.
final fieldThe JMM "freeze" action (§2e) guarantees visibility of final fields without any synchronization — the basis of safe immutable objects.
synchronized / LockAcquiring a lock that was released by the publishing thread creates a happens-before edge. Also applies to concurrent collections (ConcurrentHashMap.put, BlockingQueue.offer).
The Initialization-on-Demand Holder idiom — the preferred lazy singleton in modern Java: 
public class Registry {
  private static class Holder { // Loaded only on first call to getInstance()
    static final Registry INSTANCE = new Registry();
  }
  public static Registry getInstance() { return Holder.INSTANCE; }
}
// Thread-safe, lazy, no volatile needed — relies on JVM class-loading guarantee.

4 · How garbage collection actually works

A collector needs to answer one question — is this object still reachable? — then act on the answer. Every collector on this page is built from combinations of these phases:

PhaseWhat it does
MarkWalk the object graph from GC roots (stack frames, static fields, JNI handles) and mark everything reachable.
SweepReclaim memory occupied by anything not marked.
CompactSlide live objects together to eliminate fragmentation, so large contiguous allocations stay possible.
Evacuate / copyCopy live objects out of the region being collected into a fresh one — compaction and reclamation in one step (G1, ZGC, Shenandoah all do this).

The other axis is who does the work, and does the application keep running while they do it:

  • Stop-the-world (STW): application threads are paused for the phase. Serial and Parallel do almost everything this way.
  • Parallel: multiple GC threads work simultaneously during a stop-the-world pause — shortens the pause, doesn't remove it.
  • Concurrent: GC threads run alongside application threads with only brief STW pauses for bookkeeping — this is what makes G1, ZGC and Shenandoah low-pause.

Minor GC collects the young generation only (fast, frequent). Major GC collects the old generation. A Full GC collects the entire heap — the one you actually want to avoid, since it's typically the longest stop-the-world pause a JVM will take.

5 · The collectors, one by one

Serial — -XX:+UseSerialGC

One thread does everything, stop-the-world. Verified default choice on small/single-CPU machines. Best for tiny heaps, containers, and CLI tools where startup and footprint matter more than pause time.

Parallel (the "throughput" collector) — -XX:+UseParallelGC

Same generational design as Serial, but multiple threads split the STW work. Oracle's own guide: on machines with 8+ hardware threads, it uses roughly 5/8 of them as GC threads by default. Best for batch jobs and throughput-sensitive workloads that can tolerate occasional pauses.

CMS (Concurrent Mark Sweep) — Removed in 14 JEP 363

The first mainstream concurrent, low-pause collector. Deprecated in Java 9, removed in Java 14 — G1 replaced it entirely. If you inherit code with -XX:+UseConcMarkSweepGC, it won't even start on a modern JDK; migrate to G1.

G1 (Garbage-First) — default, -XX:+UseG1GC JEP 248

Default since Java 9. Verified from Oracle's own docs: "generational, incremental, parallel, mostly concurrent, stop-the-world, and evacuating." Splits the heap into equal-sized regions (not one contiguous young/old block) and prioritizes collecting the regions with the most garbage first — hence the name. Full deep dive → §7.

ZGC (Z Garbage Collector) — -XX:+UseZGC

A scalable, low-latency concurrent collector. Verified from Oracle's docs: pause times independent of heap size, "without stopping application threads for more than a millisecond," scales from a few hundred MB to 16 TB. Verified: as of JDK 24, ZGC is generational by default JEP 474 — the old -XX:+ZGenerational and non-generational ZGC have been removed entirely JEP 490.

Shenandoah — -XX:+UseShenandoahGC

Verified from the OpenJDK wiki: "the low pause time garbage collector... pause times are no longer directly proportional to the size of the heap. Garbage collecting a 200 GB heap or a 2 GB heap should have the similar low pause behavior." A Red Hat-led alternative to ZGC with a similar goal, using concurrent compaction rather than ZGC's colored-pointer approach.

Oracle JDK note: JEP 189 was merged into OpenJDK 12, but Oracle JDK did not include Shenandoah until Java 17. If using Oracle-branded JDK builds (not OpenJDK), Shenandoah is available starting from Java 17.

Epsilon (No-Op) — -XX:+UnlockExperimentalVMOptions -XX:+UseEpsilonGC

Allocates memory and never collects it. Verified: it requires unlocking experimental options first, or the JVM refuses to start with a clear error. Useful for performance-testing allocation cost with GC removed from the equation, ultra-short-lived jobs, and memory-pressure testing (it will happily run until it hits -Xmx and then throw OOM).

11 · Advanced concepts

ConceptWhat it means
TLAB (Thread-Local Allocation Buffer)Each thread gets a private chunk of Eden to allocate from without synchronizing with other threads — this is why object allocation in Java is typically faster than a generic malloc.
Escape analysisThe JIT can prove an object never "escapes" a method (no reference survives it) and may allocate it on the stack or in registers instead of the heap — entirely a JIT decision, not something your code controls or can force.
SafepointA point where every thread's state is consistent enough to pause it — the JVM brings all threads to a safepoint before a stop-the-world GC phase can begin.
Card markingInstead of rescanning the whole old generation to find references into the young generation, the JVM marks small "cards" of memory that were written to, so a minor GC only rechecks those.
Compressed oopsOn 64-bit JVMs with heaps under ~32GB, object references are stored as 32-bit offsets instead of full 64-bit pointers — halves reference size, is on by default (-XX:+UseCompressedOops).
Colored pointers (ZGC)ZGC steals unused bits in a 64-bit pointer to store GC metadata directly in the reference, letting it relocate objects concurrently without a separate forwarding table.

12 · Pitfalls

PitfallReality
Catching OutOfMemoryError and immediately logging/concatenating a stringVerified real bug: if the offending reference is still held, the heap is still full — building the log string can throw a second, uncaught OOM. Release the reference (leak = null;) before doing anything else in the catch block.
Static collections / listener registries that only growThe #1 real-world "memory leak" in Java — nothing is technically unreachable, so the GC (correctly) never frees it. Always pair a registration with a matching removal.
"GC overhead limit exceeded"The JVM detected it's spending >98% of time collecting for <2% heap recovered — not a bug, a real signal to raise -Xmx or fix a leak.
Assuming a bigger heap is always betterBigger heaps mean longer full-GC pauses on STW collectors. Pick a collector suited to your latency budget first, then size the heap.
Tuning young-generation size manually with G1Oracle's own guidance: avoid -Xmn/-XX:NewRatio with G1 — fixing the young size overrides and disables G1's pause-time control entirely.
Expecting System.gc() to force a GCIt's only a hint — the JVM is free to ignore it, and often does under production flags.

JVM memory & GC in one glance

  • Memory areas: heap (GC'd) + metaspace (shared) + stack/PC/native-stack (per-thread, not GC'd).

  • Collectors: Serial (simple) → Parallel (throughput) → G1 (default, balanced) → ZGC/Shenandoah (lowest latency) → Epsilon (none, benchmarking).
  • See it live: -Xlog:gc, jstat -gcutil <pid>, jcmd <pid> GC.heap_info.
  • Verified gotcha: release references before logging inside an OutOfMemoryError catch block.
  • Never manually tune G1's young size — it disables pause-time control.

The hierarchy of references (Soft, Weak, Phantom) helps manage object lifecycle. The java.lang.ref.Cleaner API is the modern, safer alternative to overriding Object.finalize(), allowing cleanup actions after objects become phantom reachable.

False sharing occurs when independent variables share a cache line, causing cache invalidation overhead. The @jdk.internal.vm.annotation.Contended annotation pads fields or classes to isolate them in separate cache lines, improving concurrent performance.

The AOT Cache

The Ahead-of-Time (AOT) Cache is Project Leyden's answer to a simple observation: most applications start up the same way every time, so the JVM shouldn't have to rediscover that from scratch on every single run. It records what happened during one "training" run and replays it instantly on every later run. Every command on this page was actually run before being written down — including a real ~50% startup-time improvement, measured locally.

The problem it solves Verified straight from JEP 483's own motivation: on every startup the JVM scans JAR files, parses thousands of class files, loads and links them (verifying bytecode, resolving symbolic references, instantiating lambda objects), then runs every class's static initializers. This is necessary dynamism that gives Java its expressive power — but it's paid for again, identically, on every single JVM start. The AOT cache shifts that repeated cost from every run to one training run.

2 · Basic: your first AOT cache, verified

This is the exact example from JEP 483 itself — a program that looks trivial but, because it touches the Stream API, causes roughly 600 JDK classes to be read, parsed, loaded, and linked.

// HelloStream.java
import java.util.*;
import java.util.stream.*;

public class HelloStream {
    public static void main(String... args) {
        var words = List.of("hello", "fuzzy", "world");
        var greeting = words.stream()
            .filter(w -> !w.contains("z"))
            .collect(Collectors.joining(", "));
        System.out.println(greeting);   // hello, world
    }
}
Requires JDK 24 or later. The examples on this page were run against JDK 26; JEP 483 itself landed in JDK 24, so everything except §5–§6 (any-GC support, method profiling) works from 24 onward too.

4 · How it works — modes & the auto fallback

Verified from Oracle's official java launcher tool specification — -XX:AOTMode has five values, and understanding auto (the default) explains a lot of AOT cache behavior you'll see in practice:

ModeBehavior
auto (default)If AOTCacheOutput is set → training run. Else if a cache can be loaded → production run using it. Else → runs normally with no cache, no error.
recordTraining phase — gathers statistics into a configuration file.
createAssembly phase — reads the configuration, writes the cache. Does not run your app.
onProduction phase, but fails fast: if the cache can't be loaded, print an error and exit immediately.
offNo AOT cache, full stop — all other AOT options are ignored.
Why this matters: -XX:AOTCache=app.aot alone implies AOTMode=auto. That's why a cache that fails to load doesn't crash your application — verified in §5 below. Use -XX:AOTMode=on only as a deliberate, fail-fast debugging aid to confirm your command line is actually compatible with the cache.

5 · Advanced: AOT cache with any garbage collector

Before JEP 516 (Java 26), the AOT cache's format was tied to specific GC assumptions, which made it incompatible with ZGC. Here's both sides of that, verified.

Verified failure — cache trained under one GC, used under another

// cache created with DEFAULT settings (G1, the default collector)
java -XX:AOTCacheOutput=app.aot -cp . HelloStream

// then run under ZGC — a genuine mismatch
java -XX:+UseZGC -XX:AOTCache=app.aot -cp . HelloStream
# verified real output:
# [warning][aot] Unable to use AOT cache.
# The saved state of UseCompressedOops and UseCompressedClassPointers is
#   different from runtime, CDS will be disabled.
# [error][aot] Loading static archive failed.
# hello, world          <- the program still ran correctly! (see §4: this is the "auto" fallback)
Verified: this does not crash. Because -XX:AOTCache= implies AOTMode=auto, the JVM logs a warning, discards the incompatible cache, and runs normally without it. Your application keeps working — it just doesn't get the speed-up that run.

Verified success — consistent GC across training and production

// train, create, AND run — all three with the SAME GC flag
java -XX:+UseZGC -XX:AOTMode=record -XX:AOTConfiguration=app-zgc.aotconf -cp . HelloStream
java -XX:+UseZGC -XX:AOTMode=create -XX:AOTConfiguration=app-zgc.aotconf -XX:AOTCache=app-zgc.aot -cp .
java -XX:+UseZGC -Xlog:aot -XX:AOTCache=app-zgc.aot -cp . HelloStream
# verified real output:
# hello, world
# [info][aot] trying to map app-zgc.aot
# [info][aot] Opened AOT cache app-zgc.aot.
# [info][aot] The AOT cache was created with UseCompressedOops = 0, ...

The rule this demonstrates: the AOT cache is tied to the JVM configuration active when it was built — same GC, same compressed-oops setting, same major options — throughout training, creation, and production. Match them, and JEP 516 makes ZGC (and every other collector) work exactly as smoothly as G1.

6 · Advanced: AOT method profiling (warmup)

Verified from JEP 515's own motivation: the AOT cache in JDK 24 sped up startup (getting classes ready), but a JVM also needs time to warm up — the JIT compiler needs to see a method run many times before it's confident enough to compile it to fast native code. JEP 515 extends the AOT cache to carry method-execution profiles from the training run, so the JIT can start making good compilation decisions from the very first request instead of relearning from zero.

// no new commands needed — profiling piggybacks on the same AOT cache commands from §2/§3
java -XX:AOTCacheOutput=app.aot -cp . com.example.App     // profiles captured during THIS training run too
java -XX:AOTCache=app.aot -cp . com.example.App           // JIT has profile data from the first request
This is a genuine "free" upgrade: if you're already using the AOT cache commands from §2–§3 on JDK 25+, method profiling is captured and used automatically — there's no separate flag to remember. The effect is on warmup curve (how quickly the app reaches peak throughput), which is harder to demonstrate in a one-line example than the very visible startup-time numbers in §2.

8 · How to train your JVM (Oracle's own guidance)

Verified, quoted directly from JEP 483's "How to train your JVM" section — the advice is short and concrete:

  • The best training run is a production run. When that's impractical (servers that open real network connections, write real logs), build a synthetic training run that resembles production as closely as possible — Oracle's suggestion: add a dedicated com.example.AppTrainer main class that drives your real main class against a temporary log directory, a local network config, and a mocked database.
  • To optimize startup time, make the training run load the same classes a real production run loads at startup — check with -verbose:class or the JFR jdk.ClassLoad event.
  • To minimize cache size, avoid loading classes in training that production never uses — don't drive training with a heavyweight test framework's own class graph.
  • A crashed training run produces no cache (verified from JEP 350's non-goals) — dynamic archiving only completes if the JVM exits normally.
