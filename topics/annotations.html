Annotations

An annotation is structured metadata attached to code — read by the compiler, by build tools, or at runtime via reflection. @Override, @Deprecated, and every @Entity/@Autowired/@Test you've ever typed are the same mechanism: a tiny, checked piece of data riding along with your code.

The problem it solves Frameworks used to rely on naming conventions or separate XML config files to attach metadata to code — getXxx() means "getter," a line in hibernate.xml means "this column maps to this field." Both are disconnected from the code they describe and easy to let go stale. Annotations put the metadata directly on the declaration, checked by the compiler, and readable by anything that cares — no separate file, no convention to remember.

1 · The format of an annotation

@Override                              // no elements
void run() { }

@SuppressWarnings("unchecked")         // one element named "value" — the name can be omitted
List list = new ArrayList();

@RequestMapping(path = "/users", method = "GET")   // named elements, several
public List<User> users() { ... }

@Author(name = "Ada")
@Ebook(title = "...")                  // multiple different annotations, stacked
public class Chapter1 { }

An annotation's type is either predefined by the JDK (java.lang / java.lang.annotation) or one you declare yourself — syntactically it looks like an interface, prefixed with @.

2 · Where annotations can be used

Originally (before Java 8) annotations could only sit on declarations — classes, fields, methods, parameters. Java 8 added type annotations: anywhere a type is used, not just declared.

@Deprecated                              // on a declaration (classic)
class OldApi {}

new @Interned MyObject();                // on a class instance creation
myString = (@NonNull String) obj;         // on a cast
class Warning extends @Localized Message {}   // in an implements/extends clause
void m() throws @Critical IOException {}      // on a thrown exception type

3 · Declaring your own annotation type

Before — a comment nobody enforces
/*
 * @author Ada
 * @reviewed true
 */
public class Widget { ... }
// nothing checks this is filled in, nothing can read it at runtime
After — a real, checked, queryable annotation
public @interface ClassPreamble {
  String author();
  String date();
  int currentRevision() default 1;      // elements can have defaults
  String[] reviewers() default {};      // and array types
}

@ClassPreamble(
    author = "Ada",
    date = "2024-01-01",
    reviewers = {"Bob", "Cy"}
)
public class Widget { ... }
To make a custom annotation show up in generated Javadoc, add @Documented to its own declaration (see §5) — by default, annotations are invisible to Javadoc.

4 · Predefined annotations

AnnotationWhat it does
@OverrideTells the compiler this must override a superclass method — a typo in the signature becomes a compile error instead of a silently-new method.
@DeprecatedWarns on use. @Deprecated(since="9", forRemoval=true) (Java 9+) says exactly when and whether it's actually going away.
@SuppressWarnings("...")Silences specific compiler warning categories: unchecked, deprecation, removal, preview.
@SafeVarargsAsserts a varargs method doesn't do anything unsafe with its varargs array — suppresses the unchecked-varargs warning.
@FunctionalInterfaceDocuments intent and gets the compiler to verify the interface really has exactly one abstract method.

5 · Meta-annotations — annotations about annotations

Meta-annotationControls
@RetentionHow long the annotation survives: SOURCE, CLASS, or RUNTIME — see §6.
@TargetWhich kinds of declarations/uses it's legal on — see the full list below.
@DocumentedInclude it in generated Javadoc.
@InheritedA subclass "sees" its superclass's annotation too — class declarations only, verified below.
@RepeatableAllows the same annotation to be applied more than once — see §8.

@Target — every ElementType, verified from the JLS/JDK

ElementType.TYPE              // class, interface, enum, record, annotation type
ElementType.FIELD             // fields (and enum constants)
ElementType.METHOD
ElementType.PARAMETER
ElementType.CONSTRUCTOR
ElementType.LOCAL_VARIABLE
ElementType.ANNOTATION_TYPE   // another annotation's declaration
ElementType.PACKAGE
ElementType.TYPE_PARAMETER    // e.g. <@NonEmpty T>          (Java 8+)
ElementType.TYPE_USE          // any type USE — casts, new, throws  (Java 8+)
ElementType.MODULE            // a module-info.java declaration     (Java 9+)
ElementType.RECORD_COMPONENT  // a record's component               (Java 16+)

@Inherited — verified real behavior

@Retention(RetentionPolicy.RUNTIME)
@Inherited
@interface Auditable {}

@Retention(RetentionPolicy.RUNTIME)
@interface NotInherited {}

@Auditable @NotInherited
class Base {}
class Derived extends Base {}     // declares NEITHER annotation itself

Derived.class.isAnnotationPresent(Auditable.class);     // verified: true
Derived.class.isAnnotationPresent(NotInherited.class);  // verified: false
Only works on class declarations. @Inherited has no effect on interfaces, methods, or fields — a common source of "why isn't my annotation inherited" confusion.

6 · Retention, verified with a real difference

PolicySurvives toUse for
SOURCECompiler only — gone from the .class file@Override, @SuppressWarnings — pure compile-time checks
CLASSThe .class file, but not loaded into the JVM at runtimeBytecode-level tools (default if you omit @Retention — easy to forget)
RUNTIMEFully available via reflection while the program runsAnything a framework needs to read with getAnnotation(...)
Missing RUNTIME retention — silently invisible
@interface Cached {}   // no @Retention at all -> defaults to CLASS

@Cached
class Service {}
Service.class.isAnnotationPresent(Cached.class);   // false — NOT an error, just silently wrong
Explicit RUNTIME retention — works
@Retention(RetentionPolicy.RUNTIME)
@interface Cached {}

@Cached
class Service {}
Service.class.isAnnotationPresent(Cached.class);   // true
If you're ever writing a custom annotation meant to be read at runtime, @Retention(RetentionPolicy.RUNTIME) is not optional — its absence fails silently (no compiler warning, no exception; reflection just returns empty/false).

7 · Type annotations & pluggable type systems

Type annotations (Java 8, ElementType.TYPE_USE) exist to support pluggable type checkers — the JDK itself doesn't interpret them, but a separate tool (like the University of Washington's Checker Framework) can read them and flag violations before you ever run the code.

@NonNull String name;                    // a pluggable checker can now verify this never gets null
List<@NonNull String> names;            // annotate a generic type argument
myGraph.add((@Interned Node) n);          // annotate a cast

Without a checker plugged into the build, these compile as plain metadata with zero enforcement — the checking is opt-in tooling, not a language guarantee.

8 · Repeating annotations, verified

Before Java 8, applying the "same" annotation twice needed an explicit wrapper array annotation written at every use site. @Repeatable hides that wrapper.

Before Java 8 — manual container, always
@interface Schedules { Schedule[] value(); }
@interface Schedule { String day(); }

@Schedules({ @Schedule(day="Mon"), @Schedule(day="Fri") })  // wrapper visible every time
class Job {}
Java 8+ — repeat it directly
@Retention(RetentionPolicy.RUNTIME)
@interface Schedules { Schedule[] value(); }   // 1. still need the container...

@Retention(RetentionPolicy.RUNTIME)
@Repeatable(Schedules.class)                    // 2. ...but point @Repeatable at it
@interface Schedule { String day(); }

@Schedule(day = "Mon")
@Schedule(day = "Fri")                          // no wrapper at the use site
class Job {}

Job.class.getAnnotationsByType(Schedule.class); // verified: [day=Mon, day=Fri]
The container annotation is real and still generated by the compiler behind the scenes — getAnnotation(Schedule.class) (singular) still only finds one match or throws ambiguity; use getAnnotationsByType(Schedule.class) (plural) to get every repeat.

9 · Reading annotations at runtime

Full API surface — isAnnotationPresent, getAnnotation, getAnnotationsByType, and the declared-vs-inherited distinction — is covered in the Reflection deep-dive. The short version:

@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.METHOD)
@interface Cached { int ttlSeconds() default 60; }

class Service {
  @Cached(ttlSeconds = 30)
  public String fetch() { return "data"; }
}

Method fetch = Service.class.getMethod("fetch");
fetch.isAnnotationPresent(Cached.class);    // verified: true
fetch.getAnnotation(Cached.class).ttlSeconds();   // verified: 30

10 · Compile-time annotation processing

Why it matters: some annotations aren't meant to be read at runtime at all — they drive code generation during compilation. This is how Lombok generates getters, Dagger generates dependency-injection code, and MapStruct generates mapper implementations — all with zero runtime reflection cost.

// the processor's shape (compiles against javax.annotation.processing):
@SupportedAnnotationTypes("com.example.GenerateBuilder")
@SupportedSourceVersion(SourceVersion.RELEASE_21)
public class BuilderProcessor extends AbstractProcessor {
  @Override
  public boolean process(Set<? extends TypeElement> annotations, RoundEnvironment env) {
    for (Element e : env.getElementsAnnotatedWith(GenerateBuilder.class)) {
      // inspect e, then use a Filer/JavaFileObject to write a new .java source file
    }
    return true;
  }
}
// registered via META-INF/services/javax.annotation.processing.Processor,
// then javac discovers and runs it automatically during compilation
This is a genuinely deep sub-topic with its own tooling (the Filer API, JavaPoet for generating source text, incremental-compilation concerns) — treat this section as the map, not the full territory, if you're about to build a processor of your own.

11 · Pitfalls

PitfallReality
Forgetting @Retention(RUNTIME)Verified: fails silently — no error, reflection just never finds it. The single most common custom-annotation bug.
Assuming @Inherited works on interfaces/methodsVerified: it only affects class declarations.
Using getAnnotation() on a @Repeatable typeOnly returns one (or throws, depending on JDK version) — use getAnnotationsByType() for repeats.
Expecting type annotations to do something on their ownThey're inert metadata until a pluggable checker or processor reads them — the JDK doesn't enforce @NonNull by itself.
Applying an annotation without a matching @TargetCompile error if you try to put a method-only annotation on a field — a real, immediate safety net, not silent.

13 · Cheat sheet

Annotations in one glance

  • public @interface Name { String value(); int x() default 1; } — an annotation is a special interface.
  • Retention: SOURCE (compiler only) → CLASS (default, in bytecode) → RUNTIME (reflectable). Forgetting RUNTIME fails silently.
  • Target: restrict legal placements with @Target(ElementType...).
  • Repeatable: @Repeatable(Container.class) on the annotation + a container with an array value(); read repeats with getAnnotationsByType.
  • Inherited: class declarations only, not interfaces/methods/fields.
  • Type annotations (TYPE_USE) are inert without a pluggable checker reading them.
  • Annotations do nothing by themselves — something (compiler, reflection, a processor) has to read them.
