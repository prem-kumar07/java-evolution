Annotations

An annotation is structured metadata attached to code — read by the compiler, by build tools, or at runtime via reflection. @Override, @Deprecated, and every @Entity/@Autowired/@Test you've ever typed are the same mechanism: a tiny, checked piece of data riding along with your code.

The problem it solves Frameworks used to rely on naming conventions or separate XML config files to attach metadata to code — getXxx() means "getter," a line in hibernate.xml means "this column maps to this field." Both are disconnected from the code they describe and easy to let go stale. Annotations put the metadata directly on the declaration, checked by the compiler, and readable by anything that cares — no separate file, no convention to remember.

1 · The format of an annotation

@Override                              // no elements
void run() { }

@SuppressWarnings("unchecked")         // one element named "value" — the name can be omitted
List list = new ArrayList();

@RequestMapping(path = "/users", method = "GET")   // named elements, several
public List<User> users() { ... }

@Author(name = "Ada")
@Ebook(title = "...")                  // multiple different annotations, stacked
public class Chapter1 { }

An annotation's type is either predefined by the JDK (java.lang / java.lang.annotation) or one you declare yourself — syntactically it looks like an interface, prefixed with @.

2 · Where annotations can be used

Originally (before Java 8) annotations could only sit on declarations — classes, fields, methods, parameters. Java 8 added type annotations: anywhere a type is used, not just declared.

@Deprecated                              // on a declaration (classic)
class OldApi {}

new @Interned MyObject();                // on a class instance creation
myString = (@NonNull String) obj;         // on a cast
class Warning extends @Localized Message {}   // in an implements/extends clause
void m() throws @Critical IOException {}      // on a thrown exception type

3 · Declaring your own annotation type

Before — a comment nobody enforces
/*
 * @author Ada
 * @reviewed true
 */
public class Widget { ... }
// nothing checks this is filled in, nothing can read it at runtime
After — a real, checked, queryable annotation
public @interface ClassPreamble {
  String author();
  String date();
  int currentRevision() default 1;      // elements can have defaults
  String[] reviewers() default {};      // and array types
}

@ClassPreamble(
    author = "Ada",
    date = "2024-01-01",
    reviewers = {"Bob", "Cy"}
)
public class Widget { ... }
To make a custom annotation show up in generated Javadoc, add @Documented to its own declaration (see §5) — by default, annotations are invisible to Javadoc.

Element declaration rules

An annotation is always declared with @interface, never plain interface. Each element inside it is written exactly like an abstract method — no parameters, no throws, no generic type parameters — and its return type is the type callers must supply a value for:

public @interface ClassPreamble {
  String author();                     // required — caller MUST supply author = "..."
  int currentRevision() default 1;     // optional — has a default, caller may omit it
}

Legal element types are deliberately narrow — only what fits into a .class file's constant pool, checked at compile time:

AllowedNot allowed
primitives (int, boolean, …), String, Class<?>, enum types, other annotation types, and 1-dimensional arrays of any of theseArbitrary objects, generic types, multi-dimensional arrays — and null can never be a default value, even for String/Class elements
The value() shorthand: if an annotation has exactly one element and it's named value(), callers can drop the name entirely — @SuppressWarnings("unchecked") is short for @SuppressWarnings(value = "unchecked"). The moment there's more than one element (or the single element isn't named value), every element needs an explicit name: @RequestMapping(path = "/users", method = "GET").

4 · Predefined annotations

AnnotationWhat it does
@OverrideTells the compiler this must override a superclass method — a typo in the signature becomes a compile error instead of a silently-new method.
@DeprecatedWarns on use. @Deprecated(since="9", forRemoval=true) (Java 9+) says exactly when and whether it's actually going away.
@SuppressWarnings("...")Silences specific compiler warning categories: unchecked, deprecation, removal, preview.
@SafeVarargsAsserts a varargs method doesn't do anything unsafe with its varargs array — suppresses the unchecked-varargs warning. JEP 213 (Milling Project Coin, Java 9) allowed this on private methods.
@FunctionalInterfaceDocuments intent and gets the compiler to verify the interface really has exactly one abstract method.

5 · Meta-annotations — annotations about annotations

Meta-annotationControls
@RetentionHow long the annotation survives: SOURCE, CLASS, or RUNTIME — see §6.
@TargetWhich kinds of declarations/uses it's legal on — see the full list below.
@DocumentedInclude it in generated Javadoc.

Common pitfall: @Documented is absent by default. Custom annotations do not appear in generated Javadoc unless @Documented is explicitly added to the annotation declaration. This is a frequent oversight when writing annotation-based APIs.

@InheritedA subclass "sees" its superclass's annotation too — class declarations only, verified below.
@RepeatableAllows the same annotation to be applied more than once — see §8.

@Target — every ElementType, verified from the JLS/JDK

ElementType.RECORD_COMPONENT  // a record's component               (Java 16+)

@Inherited — verified real behavior

@Retention(RetentionPolicy.RUNTIME)
@Inherited
@interface Auditable {}

@Retention(RetentionPolicy.RUNTIME)
@interface NotInherited {}

@Auditable @NotInherited
class Base {}
class Derived extends Base {}     // declares NEITHER annotation itself

Derived.class.isAnnotationPresent(Auditable.class);     // verified: true
Derived.class.isAnnotationPresent(NotInherited.class);  // verified: false
Only works on class declarations. @Inherited has no effect on interfaces, methods, or fields — a common source of "why isn't my annotation inherited" confusion.

6 · Retention, verified with a real difference

PolicySurvives toUse for
SOURCECompiler only — gone from the .class file@Override, @SuppressWarnings — pure compile-time checks
CLASSThe .class file, but not loaded into the JVM at runtimeBytecode-level tools (default if you omit @Retention — easy to forget)
RUNTIMEFully available via reflection while the program runsAnything a framework needs to read with getAnnotation(...)
Missing RUNTIME retention — silently invisible
@interface Cached {}   // no @Retention at all -> defaults to CLASS

@Cached
class Service {}
Service.class.isAnnotationPresent(Cached.class);   // false — NOT an error, just silently wrong
Explicit RUNTIME retention — works
@Retention(RetentionPolicy.RUNTIME)
@interface Cached {}

@Cached
class Service {}
Service.class.isAnnotationPresent(Cached.class);   // true
If you're ever writing a custom annotation meant to be read at runtime, @Retention(RetentionPolicy.RUNTIME) is not optional — its absence fails silently (no compiler warning, no exception; reflection just returns empty/false).

7 · Type annotations & pluggable type systems

Type annotations (Java 8, ElementType.TYPE_USE) exist to support pluggable type checkers — the JDK itself doesn't interpret them, but a separate tool (like the University of Washington's Checker Framework) can read them and flag violations before you ever run the code.

@NonNull String name;                    // a pluggable checker can now verify this never gets null
List<@NonNull String> names;            // annotate a generic type argument
myGraph.add((@Interned Node) n);          // annotate a cast

Without a checker plugged into the build, these compile as plain metadata with zero enforcement — the checking is opt-in tooling, not a language guarantee.

8 · Repeating annotations, verified

Before Java 8, applying the "same" annotation twice needed an explicit wrapper array annotation written at every use site. @Repeatable hides that wrapper.

Before Java 8 — manual container, always
@interface Schedules { Schedule[] value(); }
@interface Schedule { String day(); }

@Schedules({ @Schedule(day="Mon"), @Schedule(day="Fri") })  // wrapper visible every time
class Job {}
Java 8+ — repeat it directly
@Retention(RetentionPolicy.RUNTIME)
@interface Schedules { Schedule[] value(); }   // 1. still need the container...

@Retention(RetentionPolicy.RUNTIME)
@Repeatable(Schedules.class)                    // 2. ...but point @Repeatable at it
@interface Schedule { String day(); }

@Schedule(day = "Mon")
@Schedule(day = "Fri")                          // no wrapper at the use site
class Job {}

Job.class.getAnnotationsByType(Schedule.class); // verified: [day=Mon, day=Fri]
The container annotation is real and still generated by the compiler behind the scenes — getAnnotation(Schedule.class) (singular) still only finds one match or throws ambiguity; use getAnnotationsByType(Schedule.class) (plural) to get every repeat.

9 · Reading annotations at runtime

Full API surface — isAnnotationPresent, getAnnotation, getAnnotationsByType, and the declared-vs-inherited distinction — is covered in the Reflection deep-dive. The short version:

@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.METHOD)
@interface Cached { int ttlSeconds() default 60; }

class Service {
  @Cached(ttlSeconds = 30)
  public String fetch() { return "data"; }
}

Method fetch = Service.class.getMethod("fetch");
fetch.isAnnotationPresent(Cached.class);    // verified: true
fetch.getAnnotation(Cached.class).ttlSeconds();   // verified: 30

10 · Compile-time annotation processing

Why it matters: some annotations aren't meant to be read at runtime at all — they drive code generation during compilation. This is how Lombok generates getters, Dagger generates dependency-injection code, and MapStruct generates mapper implementations — all with zero runtime reflection cost.

@SupportedAnnotationTypes("com.example.GenerateBuilder")
@SupportedSourceVersion(SourceVersion.RELEASE_21)
public class BuilderProcessor extends AbstractProcessor {
  @Override
  public boolean process(Set<? extends TypeElement> annotations, RoundEnvironment env) {
    for (Element e : env.getElementsAnnotatedWith(GenerateBuilder.class)) {
      // inspect e, then use a Filer/JavaFileObject to write a new .java source file
    }
    return true;
  }
}
// registered via META-INF/services/javax.annotation.processing.Processor,
// then javac discovers and runs it automatically during compilation
This is a genuinely deep sub-topic with its own tooling (the Filer API, JavaPoet for generating source text, incremental-compilation concerns) — treat this section as the map, not the full territory, if you're about to build a processor of your own.

11 · Pitfalls

PitfallReality
Forgetting @Retention(RUNTIME)Verified: fails silently — no error, reflection just never finds it. The single most common custom-annotation bug.
Assuming @Inherited works on interfaces/methodsVerified: it only affects class declarations.
Using getAnnotation() on a @Repeatable typeOnly returns one (or throws, depending on JDK version) — use getAnnotationsByType() for repeats.
Expecting type annotations to do something on their ownThey're inert metadata until a pluggable checker or processor reads them — the JDK doesn't enforce @NonNull by itself.
Applying an annotation without a matching @TargetCompile error if you try to put a method-only annotation on a field — a real, immediate safety net, not silent.

13 · Five complete examples, basic to advanced

Every example on this page so far is a fragment. These five are complete, compiling programs — each one was actually run to produce the output shown — going from a five-minute pattern to the same compile-time code generation trick Lombok and Dagger use.

Example 1 — Basic: method logging with a dynamic proxy

The smallest useful pattern: mark specific interface methods, then have an InvocationHandler check for the marker before deciding whether to log. This is the same shape as Spring's @Transactional/@Async — an annotation that triggers cross-cutting behavior around a call, without the method itself knowing about it.

@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.METHOD)
@interface Loggable {}

interface Calculator {
  @Loggable
  int add(int a, int b);
  int subtract(int a, int b);      // not annotated — stays silent
}

class CalculatorImpl implements Calculator {
  public int add(int a, int b) { return a + b; }
  public int subtract(int a, int b) { return a - b; }
}

class LoggingHandler implements InvocationHandler {
  private final Object target;
  LoggingHandler(Object target) { this.target = target; }

  public Object invoke(Object proxy, Method method, Object[] args) throws Throwable {
    boolean log = method.isAnnotationPresent(Loggable.class);
    if (log) System.out.println("-> " + method.getName() + Arrays.toString(args));
    Object result = method.invoke(target, args);
    if (log) System.out.println("<- " + result);
    return result;
  }
}

Calculator calc = (Calculator) Proxy.newProxyInstance(
    Calculator.class.getClassLoader(),
    new Class<?>[] { Calculator.class },
    new LoggingHandler(new CalculatorImpl()));
calc.add(2, 3);
calc.subtract(5, 1);

// verified output:
// -> add[2, 3]
// <- 5
// (subtract prints nothing)

Example 2 — Basic/intermediate: a bean-validation mini-framework

This is the mechanism behind Jakarta Bean Validation's @NotBlank/@Min: walk an object's fields with reflection, and let each annotation carry its own rule data.

@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.FIELD)
@interface NotBlank {}

@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.FIELD)
@interface Min { int value(); }

class User {
  @NotBlank String name;
  @Min(18) int age;
  User(String name, int age) { this.name = name; this.age = age; }
}

class Validator {
  static List<String> validate(Object obj) throws IllegalAccessException {
    List<String> errors = new ArrayList<>();
    for (Field f : obj.getClass().getDeclaredFields()) {
      f.setAccessible(true);
      if (f.isAnnotationPresent(NotBlank.class)) {
        Object value = f.get(obj);
        if (value == null || value.toString().isBlank())
          errors.add(f.getName() + " must not be blank");
      }
      if (f.isAnnotationPresent(Min.class)) {
        int min = f.getAnnotation(Min.class).value();
        if (f.getInt(obj) < min)
          errors.add(f.getName() + " must be >= " + min);
      }
    }
    return errors;
  }
}

Validator.validate(new User("Ada", 30));   // verified: []
Validator.validate(new User("", 12));      // verified: [name must not be blank, age must be >= 18]

Example 3 — Intermediate: a tiny dependency-injection container

@Inject/@Autowired demystified: a container is just a Map<Class, Object> and a loop that reflects over annotated fields and fills them in.

@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.FIELD)
@interface Inject {}

interface PaymentGateway { String charge(int cents); }

class StripeGateway implements PaymentGateway {
  public String charge(int cents) { return "charged " + cents + " via Stripe"; }
}

class CheckoutService {
  @Inject PaymentGateway gateway;
  String checkout(int cents) { return gateway.charge(cents); }
}

class MiniContainer {
  private final Map<Class<?>, Object> registry = new HashMap<>();
  <T> void register(Class<T> type, T instance) { registry.put(type, instance); }

  <T> T create(Class<T> type) throws Exception {
    T instance = type.getDeclaredConstructor().newInstance();
    for (Field f : type.getDeclaredFields()) {
      if (f.isAnnotationPresent(Inject.class)) {
        f.setAccessible(true);
        f.set(instance, registry.get(f.getType()));   // wire the dependency in by type
      }
    }
    return instance;
  }
}

MiniContainer container = new MiniContainer();
container.register(PaymentGateway.class, new StripeGateway());
CheckoutService checkout = container.create(CheckoutService.class);
checkout.checkout(2500);   // verified: "charged 2500 via Stripe"

Example 4 — Intermediate/advanced: a mini ORM (@Entity/@Column → SQL)

Hibernate's field mapping starts here: annotations describe how a class corresponds to a table, and a generator turns any annotated instance into SQL without either side hand-writing the mapping.

@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.TYPE)
@interface Entity { String table(); }

@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.FIELD)
@interface Column { String name(); }

@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.FIELD)
@interface Id {}

@Entity(table = "users")
class UserRow {
  @Id @Column(name = "id") int id;
  @Column(name = "full_name") String name;
  @Column(name = "email") String email;

  UserRow(int id, String name, String email) {
    this.id = id; this.name = name; this.email = email;
  }
}

class SqlGenerator {
  static String insertStatement(Object entity) throws IllegalAccessException {
    Class<?> type = entity.getClass();
    Entity table = type.getAnnotation(Entity.class);
    if (table == null) throw new IllegalArgumentException(type + " is not @Entity");

    List<String> columns = new ArrayList<>();
    List<String> values = new ArrayList<>();
    for (Field f : type.getDeclaredFields()) {
      Column col = f.getAnnotation(Column.class);
      if (col == null) continue;
      f.setAccessible(true);
      columns.add(col.name());
      Object v = f.get(entity);
      values.add(v instanceof String ? "'" + v + "'" : String.valueOf(v));
    }
    return "INSERT INTO " + table.table() + " (" + String.join(", ", columns)
         + ") VALUES (" + String.join(", ", values) + ")";
  }
}

SqlGenerator.insertStatement(new UserRow(1, "Ada Lovelace", "ada@example.com"));
// verified: INSERT INTO users (id, full_name, email) VALUES (1, 'Ada Lovelace', 'ada@example.com')

Example 5 — Advanced: compile-time code generation (the Lombok/Dagger trick)

This is the full version of the sketch in §10 — a real @GenerateBuilder annotation processor that writes a new .java source file during compilation. Four pieces, compiled and run in order.

1. The marker annotation — SOURCE retention, because nothing needs it after javac is done:

package demo;

@Target(ElementType.TYPE)
@Retention(RetentionPolicy.SOURCE)
public @interface GenerateBuilder {}

2. The processor — for every @GenerateBuilder class, writes a sibling XxxBuilder class with one setter per field:

package demo;

@SupportedAnnotationTypes("demo.GenerateBuilder")
@SupportedSourceVersion(SourceVersion.RELEASE_21)
public class BuilderProcessor extends AbstractProcessor {
  @Override
  public boolean process(Set<? extends TypeElement> annotations, RoundEnvironment roundEnv) {
    for (Element e : roundEnv.getElementsAnnotatedWith(GenerateBuilder.class)) {
      TypeElement classElement = (TypeElement) e;
      String className = classElement.getSimpleName().toString();
      String packageName = processingEnv.getElementUtils()
          .getPackageOf(classElement).getQualifiedName().toString();
      String builderName = className + "Builder";

      try (PrintWriter out = new PrintWriter(
          processingEnv.getFiler().createSourceFile(packageName + "." + builderName).openWriter())) {
        out.println("package " + packageName + ";");
        out.println("public class " + builderName + " {");
        out.println("  private final " + className + " instance = new " + className + "();");
        for (Element field : classElement.getEnclosedElements()) {
          if (field.getKind() != ElementKind.FIELD) continue;
          String name = field.getSimpleName().toString();
          String type = field.asType().toString();
          out.println("  public " + builderName + " " + name + "(" + type + " value) {");
          out.println("    instance." + name + " = value;");
          out.println("    return this;");
          out.println("  }");
        }
        out.println("  public " + className + " build() { return instance; }");
        out.println("}");
      } catch (Exception ex) {
        processingEnv.getMessager().printMessage(Diagnostic.Kind.ERROR, "Failed to generate builder: " + ex);
      }
    }
    return true;
  }
}
// registered in META-INF/services/javax.annotation.processing.Processor
// with a single line: demo.BuilderProcessor

3. The annotated class — no builder written by hand:

package demo;

@GenerateBuilder
public class Product {
  String name;
  double price;

  @Override
  public String toString() { return name + " ($" + price + ")"; }
}

4. Code that uses the generated class — ProductBuilder doesn't exist anywhere in this source tree; javac generates it during compilation and then compiles this file against it in the same pass:

package demo;

public class Main {
  public static void main(String[] args) {
    Product p = new ProductBuilder().name("Widget").price(9.99).build();
    System.out.println(p);
  }
}
// verified generated source (demo/ProductBuilder.java):
//   package demo;
//   public class ProductBuilder {
//     private final Product instance = new Product();
//     public ProductBuilder name(java.lang.String value) { instance.name = value; return this; }
//     public ProductBuilder price(double value) { instance.price = value; return this; }
//     public Product build() { return instance; }
//   }
// verified output: Widget ($9.99)
Compiling this requires two passes: first compile GenerateBuilder and BuilderProcessor on their own, then compile Product/Main with javac -processorpath <dir-with-compiled-processor> ... — a processor can't process the same compilation unit it's part of.

14 · Cheat sheet

Annotations in one glance

  • public @interface Name { String value(); int x() default 1; } — an annotation is a special interface.
  • Retention: SOURCE (compiler only) → CLASS (default, in bytecode) → RUNTIME (reflectable). Forgetting RUNTIME fails silently.
  • Target: restrict legal placements with @Target(ElementType...).
  • Repeatable: @Repeatable(Container.class) on the annotation + a container with an array value(); read repeats with getAnnotationsByType.
  • Inherited: class declarations only, not interfaces/methods/fields.
  • Type annotations (TYPE_USE) are inert without a pluggable checker reading them.
  • Annotations do nothing by themselves — something (compiler, reflection, a processor) has to read them.

Advanced Annotation Topics

  • Interface Annotation Inheritance: Annotations on interfaces are generally not inherited by classes implementing them, unlike annotations on superclasses (when marked with @Inherited).
  • @Generated: Added in Java 9 to javax.annotation.processing to mark code generated by tools.
