Structured concurrency Preview

Structured concurrency treats a group of related subtasks as a single unit of work. They start together inside a scope, and the scope guarantees they all finish — or are all cancelled — before the block exits. No leaked threads, clear error propagation, honest task trees.

Preview6th preview in Java 26
The problem it solves Firing off subtasks with a raw ExecutorService + Futures is unstructured: if one task fails, siblings keep running (wasted work / leaks), cancellation is manual and easy to botch, and there's no relationship between parent and child in stack traces or thread dumps. Structured concurrency gives those subtasks a lifetime bound to a lexical scope — like try-with-resources, but for concurrency.
Still a preview feature (5th preview in Java 25, 6th in 26). Compile/run with --enable-preview. The API here is the reworked Java 25 shape; earlier releases used ShutdownOnFailure/ShutdownOnSuccess (see Evolution).

1 · The problem with raw futures

Legacy — unstructured, leak-prone
Future<User>  u = pool.submit(() -> findUser(id));
Future<Order> o = pool.submit(() -> fetchOrder(id));
try {
  return new Response(u.get(), o.get());
  // if findUser throws, fetchOrder keeps running (leak);
  // if the caller is interrupted, both may be orphaned.
} catch (Exception e) {
  u.cancel(true); o.cancel(true);   // did you remember both?
  throw e;
}
Structured — one scope, one unit
try (var scope = StructuredTaskScope.open()) {   // Java 25 API
  var user  = scope.fork(() -> findUser(id));
  var order = scope.fork(() -> fetchOrder(id));

  scope.join();          // wait for all; first failure cancels the rest
  return new Response(user.get(), order.get());
}   // on exit, every subtask is guaranteed done

2 · The scope model

  • No leaks: try-with-resources can't exit until all forked subtasks finish/cancel.
  • Short-circuit: one failure cancels the siblings — no waiting on work you'll discard.
  • Clear hierarchy: observability tools show the real parent→child task tree.
  • Cheap: each subtask runs on its own virtual thread.

3 · Basic usage

Response handle(String id) throws Exception {
  try (var scope = StructuredTaskScope.open()) {
    var user   = scope.fork(() -> findUser(id));    // returns a Subtask<User>
    var orders = scope.fork(() -> fetchOrders(id));

    scope.join();                    // MUST join before reading results
    return new Response(user.get(), orders.get());
  }
}

Every Subtask also exposes its outcome via .state() — a Subtask.State enum (SUCCESS, FAILED, or UNAVAILABLE if cancelled before starting) — verified, useful when a Joiner deliberately tolerates partial failure and you want to know which subtasks actually completed:

System.out.println("user subtask state: " + user.state());   // e.g. SUCCESS

4 · Joiners — choosing the completion policy

A Joiner decides when join() returns and how results/errors combine.

All must succeed (fail-fast)
try (var scope = StructuredTaskScope.open(
        Joiner.<String>allSuccessfulOrThrow())) {
  scope.fork(() -> a());
  scope.fork(() -> b());
  var all = scope.join();   // Stream of subtasks, all OK
}
Race — first success wins
try (var scope = StructuredTaskScope.open(
        Joiner.<String>anySuccessfulResultOrThrow())) {
  scope.fork(() -> mirror1());
  scope.fork(() -> mirror2());
  String fastest = scope.join();   // others cancelled
}

5 · Deadlines & cancellation

try (var scope = StructuredTaskScope.open(
        Joiner.allSuccessfulOrThrow(),
        cf -> cf.withTimeout(Duration.ofSeconds(2)))) {   // whole-group deadline
  scope.fork(() -> slowCall());
  scope.join();   // throws if the deadline passes; subtasks cancelled
}

6 · With virtual threads & scoped values

Structured concurrency is the "manager" for cheap virtual threads, and scoped values bound in the enclosing scope are visible to every forked subtask — the clean way to pass request context into concurrent work.

ScopedValue.where(CURRENT_USER, user).run(() -> {
  try (var scope = StructuredTaskScope.open()) {
    scope.fork(() -> loadProfile());   // sees CURRENT_USER.get() == user
    scope.fork(() -> loadOrders());    // also sees it
    scope.join();
  }
});

7 · If you're on Java 21–24

The Joiner-based API shown above is the Java 25 rework (JEP 505). If you're on 21–24 LTS-adjacent previews, you'll see (and may still maintain) the older shape based on ShutdownOnFailure/ShutdownOnSuccess subclasses instead of a Joiner parameter. Both compile and run — this is what changed:

Java 21–24 preview — ShutdownOnFailure
try (var scope = new StructuredTaskScope.ShutdownOnFailure()) {
  var sa = scope.fork(() -> a());
  var sb = scope.fork(() -> b());
  scope.join();            // wait for all or first failure
  scope.throwIfFailed();   // rethrow if any subtask failed
  System.out.println(sa.get() + sb.get());
}   // verified: compiles & runs with --enable-preview --source 21
Java 25+ — Joiner
try (var scope = StructuredTaskScope.open(Joiner.allSuccessfulOrThrow())) {
  var sa = scope.fork(() -> a());
  var sb = scope.fork(() -> b());
  scope.join();             // throwing IS the failure signal — no separate throwIfFailed()
  System.out.println(sa.get() + sb.get());
}

The concept — fork, join, fail-fast, no leaks — never changed across any preview. Only the surface API was reworked once, in 25, to make the completion policy pluggable via Joiner instead of baked into a fixed set of scope subclasses.

Worked example — aggregate a product page with a 2s SLA

Legacy — futures, manual timeout & cancel
var pool = Executors.newFixedThreadPool(3);
try {
  var pf = pool.submit(() -> productSvc.get(id));
  var rf = pool.submit(() -> reviewSvc.list(id));
  var sf = pool.submit(() -> stockSvc.check(id));
  // enforce a 2s budget across three gets... by hand
  var page = new ProductPage(
      pf.get(2, SECONDS), rf.get(2, SECONDS), sf.get(2, SECONDS));
  return page;
} catch (Exception e) {
  // cancel whatever is still running — easy to miss one
  throw e;
} finally { pool.shutdownNow(); }
Structured concurrency
try (var scope = StructuredTaskScope.open(
        Joiner.allSuccessfulOrThrow(),
        cf -> cf.withTimeout(Duration.ofSeconds(2)))) {

  var product = scope.fork(() -> productSvc.get(id));
  var reviews = scope.fork(() -> reviewSvc.list(id));
  var stock   = scope.fork(() -> stockSvc.check(id));

  scope.join();   // 2s budget for the whole group; failures cancel siblings
  return new ProductPage(product.get(), reviews.get(), stock.get());
}

10 · Cheat sheet

Structured concurrency in one glance

  • try (var scope = StructuredTaskScope.open(joiner)) { scope.fork(...); scope.join(); }
  • Joiners: allSuccessfulOrThrow, anySuccessfulResultOrThrow, custom.
  • Read subtask.get() only after join().
  • All subtasks complete or are cancelled before the block exits — no leaks.
  • One virtual thread per subtask; add withTimeout for a group deadline.
  • Combine with scoped values to pass context; needs --enable-preview.

⚠ Breaking API change between Java 21–24 and Java 25+. The Java 21–24 preview used new StructuredTaskScope.ShutdownOnFailure() (subclass instantiation) with explicit scope.throwIfFailed(). Java 25+ replaces this with StructuredTaskScope.open(Joiner.allSuccessfulOrThrow()) where join() itself throws. These APIs are incompatible — upgrading from Java 21–24 to Java 25 requires refactoring any code using the old subclass-based API.

Advanced Topics

StructuredTaskScope.Config

In the new Java 25+ API, scopes can be customized via StructuredTaskScope.Config. You can set timeouts and thread factories directly on the configuration, providing a cleaner way to apply constraints without subclassing.

The Joiner API Surface

The Joiner interface introduced in Java 25+ allows writing custom completion policies. A Joiner defines how to accumulate results and short-circuit when a condition is met, bringing flexibility similar to the Stream API's Collector.

Structural Confinement Rule

Structured tasks enforce strict structural confinement. A child subtask cannot outlive the lexical scope of its parent StructuredTaskScope. If a parent exits its scope while subtasks are still running, those subtasks are automatically cancelled (interrupted), preventing orphaned threads.
