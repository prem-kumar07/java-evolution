Structured concurrency Preview

Structured concurrency treats a group of related subtasks as a single unit of work. They start together inside a scope, and the scope guarantees they all finish — or are all cancelled — before the block exits. No leaked threads, clear error propagation, honest task trees.

fail-fastone error cancels siblings
1 VTper subtask (cheap)

Preview6th preview in Java 26
The problem it solves Firing off subtasks with a raw ExecutorService + Futures is unstructured: if one task fails, siblings keep running (wasted work / leaks), cancellation is manual and easy to botch, and there's no relationship between parent and child in stack traces or thread dumps. Structured concurrency gives those subtasks a lifetime bound to a lexical scope — like try-with-resources, but for concurrency.
Still a preview feature (5th preview in Java 25, 6th in 26). Compile/run with --enable-preview. The API here is the reworked Java 25 shape; earlier releases used ShutdownOnFailure/ShutdownOnSuccess (see Evolution).

1 · The problem with raw futures

Legacy — unstructured, leak-prone
Future<User>  u = pool.submit(() -> findUser(id));
Future<Order> o = pool.submit(() -> fetchOrder(id));
try {
  return new Response(u.get(), o.get());
  // if findUser throws, fetchOrder keeps running (leak);
  // if the caller is interrupted, both may be orphaned.
} catch (Exception e) {
  u.cancel(true); o.cancel(true);   // did you remember both?
  throw e;
}
Structured — one scope, one unit
try (var scope = StructuredTaskScope.open()) {   // Java 25 API
  var user  = scope.fork(() -> findUser(id));
  var order = scope.fork(() -> fetchOrder(id));

  scope.join();          // wait for all; first failure cancels the rest
  return new Response(user.get(), order.get());
}   // on exit, every subtask is guaranteed done

2 · The scope model

  • No leaks: try-with-resources can't exit until all forked subtasks finish/cancel.
  • Short-circuit: one failure cancels the siblings — no waiting on work you'll discard.
  • Clear hierarchy: observability tools show the real parent→child task tree.
  • Cheap: each subtask runs on its own virtual thread.

3 · Basic usage

Response handle(String id) throws Exception {
  try (var scope = StructuredTaskScope.open()) {
    var user   = scope.fork(() -> findUser(id));    // returns a Subtask<User>
    var orders = scope.fork(() -> fetchOrders(id));

    scope.join();                    // MUST join before reading results
    return new Response(user.get(), orders.get());
  }
}

Every Subtask also exposes its outcome via .state() — a Subtask.State enum (SUCCESS, FAILED, or UNAVAILABLE if cancelled before starting) — verified, useful when a Joiner deliberately tolerates partial failure and you want to know which subtasks actually completed:

System.out.println("user subtask state: " + user.state());   // e.g. SUCCESS

4 · Joiners — choosing the completion policy

A Joiner decides when join() returns and how results/errors combine. Every factory method and behavior below is verified directly against a real JDK 26 install — both by reading java.util.concurrent.StructuredTaskScope.Joiner's own javap output and by actually running each one.

All must succeed (fail-fast)
try (var scope = StructuredTaskScope.open(
        Joiner.<String>allSuccessfulOrThrow())) {
  scope.fork(() -> a());
  scope.fork(() -> b());
  List<String> all = scope.join();   // verified: List, in fork order — NOT a Stream, NOT Subtasks
}
Race — first success wins
try (var scope = StructuredTaskScope.open(
        Joiner.<String>anySuccessfulOrThrow())) {
  scope.fork(() -> mirror1());
  scope.fork(() -> mirror2());
  String fastest = scope.join();   // others cancelled
}
Verified, and worth being precise about: allSuccessfulOrThrow() returns a List<T> of the actual results, in fork order — confirmed with results.getClass().getSimpleName() reporting ListN, and the values themselves being [a, b], not Subtask wrappers. This is the reworked Java 26 shape (JEP 525) — Java 25 returned a Stream<T> of the same result values instead; it was never a stream of Subtask objects at any point.

4.1 · All five built-in Joiner factories

The doc examples on this page (and most tutorials) only ever show the first two. There are five — confirmed by listing Joiner's actual static methods on a real JDK 26:

FactoryReturnsBehavior
allSuccessfulOrThrow()Joiner<T, List<T>> Cancels the scope and throws on the first failure. On success, result() is a List<T> of every result, in fork order. Use when every subtask returns the same type.
anySuccessfulOrThrow()Joiner<T, T> Returns the first successful result; throws only if every subtask fails (or NoSuchElementException if none were forked at all). Renamed from anySuccessfulResultOrThrow() in Java 25 — Java 26.
awaitAllSuccessfulOrThrow()Joiner<T, Void> Same fail-fast cancellation as allSuccessfulOrThrow, but doesn't collect results — result() is always null. Use when subtasks return different types and you'll read each one individually off its own Subtask handle.
awaitAll()Joiner<T, Void> Waits for every subtask, does not cancel on failure, never throws from a subtask failure. For side-effecting subtasks (a socket-accept loop forking a handler per connection) where you don't want one bad connection to cancel the rest.
allUntil(Predicate<Subtask<T>>) Joiner<T, List<Subtask<T>>> General-purpose: your predicate runs on every completing subtask and returns true to cancel the scope early. result() is the list of all subtasks (some may be UNAVAILABLE if cancelled before finishing) — the building block the other four are conceptually shorthand for.

The three most people never see, verified:

// awaitAllSuccessfulOrThrow — different result types per subtask, read individually
try (var scope = StructuredTaskScope.open(Joiner.<Object>awaitAllSuccessfulOrThrow())) {
  Subtask<String> s1 = scope.fork(() -> "string result");
  Subtask<Integer> s2 = scope.fork(() -> 42);
  scope.join();   // verified: returns null
  use(s1.get(), s2.get());   // both readable after join(), regardless of the Void result
}

// awaitAll — a failing subtask does NOT cancel its siblings or throw
try (var scope = StructuredTaskScope.open(Joiner.<String>awaitAll())) {
  Subtask<String> ok  = scope.fork(() -> "ok");
  Subtask<String> bad = scope.fork(() -> { throw new RuntimeException("boom"); });
  scope.join();   // verified: returns normally even though 'bad' failed
  // ok.state() == SUCCESS, bad.state() == FAILED — check individually, nothing throws for you
}

// allUntil — cancel the scope after 2 failures, but still see every subtask's outcome
Predicate<Subtask<String>> cancelAfterTwoFailures = new Predicate<>() {
  final AtomicInteger failed = new AtomicInteger();
  public boolean test(Subtask<String> s) {
    return s.state() == Subtask.State.FAILED && failed.incrementAndGet() >= 2;
  }
};
try (var scope = StructuredTaskScope.open(Joiner.allUntil(cancelAfterTwoFailures))) {
  scope.fork(() -> { throw new RuntimeException("fail1"); });
  scope.fork(() -> { throw new RuntimeException("fail2"); });
  scope.fork(() -> { Thread.sleep(200); return "would succeed but likely cancelled"; });
  List<Subtask<String>> all = scope.join();   // 3 subtasks: 2 FAILED, 1 UNAVAILABLE (cancelled)
}
Verified real output for all three above, in order: 
awaitAllSuccessfulOrThrow -> join() returned: null, but subtasks still readable: s1=string result s2=42
awaitAll -> join() returned normally; ok.state()=SUCCESS bad.state()=FAILED
allUntil -> total=3 failed=2 unavailable=1

4.2 · The Joiner interface — what you implement for a custom one

Every factory in §4.1 is really just a pre-built implementation of this four-method interface — confirmed with javap -p 'java.util.concurrent.StructuredTaskScope$Joiner' against a real JDK 26:

MethodCalled whenReturn/throw means
boolean onFork(Subtask<T>)Before a subtask's thread is even created — synchronously, on the scope-owner thread.Returning true cancels the scope immediately (verified: a 3rd fork() call can cancel the scope from inside onFork itself, before that subtask ever runs). Default: always false.
boolean onComplete(Subtask<T>)After a subtask finishes (success or failure) — not called if the scope was already cancelled. May be called concurrently from multiple subtask threads at once — your implementation must be thread-safe.Returning true cancels the scope. Default: always false.
void onTimeout() Java 26From join(), only if the scope was opened with a timeout and it expires. New in this version — see §4.4 below.Default implementation throws (see the exact exception type in §4.4 — it's not the class you'd guess).
R result() throws ThrowableOnce, by join(), after every subtask has completed or the scope was cancelled.Whatever it returns is join()'s return value. Whatever it throws comes back out of join() wrapped in StructuredTaskScope.FailedException — verified below.
try (var scope = StructuredTaskScope.open(Joiner.<String>allSuccessfulOrThrow())) {
  scope.fork(() -> { throw new IllegalStateException("subtask blew up"); });
  scope.join();
} catch (StructuredTaskScope.FailedException e) {
  // verified: e.getCause() is the ORIGINAL IllegalStateException, unwrapped one level
  System.out.println(e.getCause().getClass().getSimpleName() + ": " + e.getCause().getMessage());
}
// verified real output: IllegalStateException: subtask blew up
Oracle's own design guidance, worth repeating: create a new Joiner instance for every scope — never share or reuse one across scopes — and keep "business logic" out of it. A Joiner decides when to stop and what shape the result takes; what to actually do with that result belongs at the call site, same separation of concerns as a stream Collector.

4.3 · Writing your own Joiner — complete example

A "best-effort" policy — collect whatever succeeded, silently drop whatever failed, never cancel early, never throw. None of the five built-ins do this; it takes about ten real lines:

import java.util.concurrent.StructuredTaskScope.Joiner;
import java.util.concurrent.StructuredTaskScope.Subtask;
import java.util.*;

public class BestEffortJoiner<T> implements Joiner<T, List<T>> {
  private final List<T> results = Collections.synchronizedList(new ArrayList<>());

  @Override
  public boolean onComplete(Subtask<T> subtask) {
    if (subtask.state() == Subtask.State.SUCCESS) {
      results.add(subtask.get());
    }
    return false;   // never cancel — let every subtask finish, succeed or fail
  }

  @Override
  public List<T> result() {
    return List.copyOf(results);
  }
}
try (var scope = StructuredTaskScope.open(new BestEffortJoiner<String>())) {
  scope.fork(() -> "service-A ok");
  scope.fork(() -> { throw new RuntimeException("service-B down"); });
  scope.fork(() -> "service-C ok");

  List<String> best = scope.join();   // never throws — failures are just dropped
  System.out.println("best-effort results: " + best);
}
Verified real output — two of three services answered, the third's failure never surfaces at all: 
best-effort results: [service-A ok, service-C ok]
onComplete uses Collections.synchronizedList deliberately — the Javadoc is explicit that onComplete "may be invoked concurrently, as multiple subtasks can complete at the same time," and may even run concurrently with the scope-owner thread's own call to onFork or onTimeout. A plain ArrayList here would be a real, if intermittent, data race.

4.4 · onTimeout() — new in Java 26, and a naming trap to know about

Java 26 JEP 525 added onTimeout() specifically for joiners that want to do something other than throw when a deadline expires — the default implementation throws, but a custom one can swallow it and hand back partial results instead. Verified, comparing default vs. overridden behavior on the exact same timeout:

// DEFAULT onTimeout() — not overridden
try (var scope = StructuredTaskScope.open(
    Joiner.<String>allSuccessfulOrThrow(), cf -> cf.withTimeout(Duration.ofMillis(100)))) {
  scope.fork(() -> { Thread.sleep(500); return "too slow"; });
  scope.join();
} catch (Throwable e) {
  System.out.println(e.getClass().getName());   // verified below — read this carefully
}
Verified real output — and it's not the class you'd expect: 
java.util.concurrent.StructuredTaskScope$TimeoutException
That's StructuredTaskScope.TimeoutException — a small, final, unchecked (extends RuntimeException) nested class the JDK 26 preview added, confirmed via javap. It is a completely different class from the familiar java.util.concurrent.TimeoutException (a checked Exception, decades old, used by Future.get(timeout) and friends) — same simple name, wrong catch clause silently misses it if you're not careful, since neither is a subtype of the other.

Overriding onTimeout() replaces that default throw entirely — here, returning whatever succeeded before the deadline instead of failing the whole group:

public class TimeoutHookJoiner<T> implements Joiner<T, List<T>> {
  private final List<T> results = Collections.synchronizedList(new ArrayList<>());

  @Override
  public boolean onComplete(Subtask<T> subtask) {
    if (subtask.state() == Subtask.State.SUCCESS) results.add(subtask.get());
    return false;
  }

  @Override
  public void onTimeout() {
    // deliberately do nothing (and don't throw) — swallow the deadline instead of failing
  }

  @Override
  public List<T> result() { return List.copyOf(results); }
}

try (var scope = StructuredTaskScope.open(
    new TimeoutHookJoiner<String>(), cf -> cf.withTimeout(Duration.ofMillis(100)))) {
  scope.fork(() -> "fast, finishes before deadline");
  scope.fork(() -> { Thread.sleep(500); return "slow, never makes it"; });

  List<String> results = scope.join();   // does NOT throw — onTimeout swallowed it
  System.out.println("join() returned normally: " + results);
}
Verified real output: 
join() returned normally: [fast, finishes before deadline]

6 · With virtual threads & scoped values

Structured concurrency is the "manager" for cheap virtual threads, and scoped values bound in the enclosing scope are visible to every forked subtask — the clean way to pass request context into concurrent work.

ScopedValue.where(CURRENT_USER, user).run(() -> {
  try (var scope = StructuredTaskScope.open()) {
    scope.fork(() -> loadProfile());   // sees CURRENT_USER.get() == user
    scope.fork(() -> loadOrders());    // also sees it
    scope.join();
  }
});

7 · If you're on Java 21–24

The Joiner-based API shown above is the Java 25 rework (JEP 505). If you're on 21–24 LTS-adjacent previews, you'll see (and may still maintain) the older shape based on ShutdownOnFailure/ShutdownOnSuccess subclasses instead of a Joiner parameter. Both compile and run — this is what changed:

Java 21–24 preview — ShutdownOnFailure
try (var scope = new StructuredTaskScope.ShutdownOnFailure()) {
  var sa = scope.fork(() -> a());
  var sb = scope.fork(() -> b());
  scope.join();            // wait for all or first failure
  scope.throwIfFailed();   // rethrow if any subtask failed
  System.out.println(sa.get() + sb.get());
}   // verified: compiles & runs with --enable-preview --source 21
Java 25+ — Joiner
try (var scope = StructuredTaskScope.open(Joiner.allSuccessfulOrThrow())) {
  var sa = scope.fork(() -> a());
  var sb = scope.fork(() -> b());
  scope.join();             // throwing IS the failure signal — no separate throwIfFailed()
  System.out.println(sa.get() + sb.get());
}

The concept — fork, join, fail-fast, no leaks — never changed across any preview. Only the surface API was reworked once, in 25, to make the completion policy pluggable via Joiner instead of baked into a fixed set of scope subclasses.

8 · Pitfalls

PitfallReality
Reading subtask.get() before join()Throws IllegalStateException — always join first.
Forking from another threadThe scope is confined to the thread that opened it.
Depending on exact method namesPreview API is still moving — the concept is stable, the surface is not.
Treating it like a thread poolIt's per-request/task, not a long-lived shared pool.
Forgetting --enable-previewWon't compile/run without it.
Catching java.util.concurrent.TimeoutException around join() Verified: the wrong class. A timed-out scope throws StructuredTaskScope.TimeoutException — a different, unchecked class with the same simple name. See §4.4.
Sharing one Joiner instance across scopes, or reusing it after close Explicitly against Oracle's own guidance — create a fresh one per scope, every time.
A non-thread-safe custom onCompleteIt can be invoked concurrently by multiple subtask threads at once — use a concurrent collection, not a plain ArrayList/HashMap.

Worked example — aggregate a product page with a 2s SLA

Legacy — futures, manual timeout & cancel
var pool = Executors.newFixedThreadPool(3);
try {
  var pf = pool.submit(() -> productSvc.get(id));
  var rf = pool.submit(() -> reviewSvc.list(id));
  var sf = pool.submit(() -> stockSvc.check(id));
  // enforce a 2s budget across three gets... by hand
  var page = new ProductPage(
      pf.get(2, SECONDS), rf.get(2, SECONDS), sf.get(2, SECONDS));
  return page;
} catch (Exception e) {
  // cancel whatever is still running — easy to miss one
  throw e;
} finally { pool.shutdownNow(); }
Structured concurrency
try (var scope = StructuredTaskScope.open(
        Joiner.allSuccessfulOrThrow(),
        cf -> cf.withTimeout(Duration.ofSeconds(2)))) {

  var product = scope.fork(() -> productSvc.get(id));
  var reviews = scope.fork(() -> reviewSvc.list(id));
  var stock   = scope.fork(() -> stockSvc.check(id));

  scope.join();   // 2s budget for the whole group; failures cancel siblings
  return new ProductPage(product.get(), reviews.get(), stock.get());
}

10 · Cheat sheet

Structured concurrency in one glance

  • try (var scope = StructuredTaskScope.open(joiner)) { scope.fork(...); scope.join(); }
  • 5 built-in joiners: allSuccessfulOrThrow (→ List<T> in 26+), anySuccessfulOrThrow, awaitAllSuccessfulOrThrow, awaitAll (no cancel-on-failure), allUntil(Predicate) (general-purpose).
  • Custom Joiner: implement onFork/onComplete (return true to cancel), onTimeout (26), and result() — new instance per scope, must be thread-safe.
  • Timeout throws StructuredTaskScope.TimeoutException — not java.util.concurrent.TimeoutException; failed result() surfaces as StructuredTaskScope.FailedException.
  • Read subtask.get() only after join().
  • All subtasks complete or are cancelled before the block exits — no leaks.
  • One virtual thread per subtask; add withTimeout for a group deadline.
  • Combine with scoped values to pass context; needs --enable-preview.

⚠ Breaking API change between Java 21–24 and Java 25+. The Java 21–24 preview used new StructuredTaskScope.ShutdownOnFailure() (subclass instantiation) with explicit scope.throwIfFailed(). Java 25+ replaces this with StructuredTaskScope.open(Joiner.allSuccessfulOrThrow()) where join() itself throws. These APIs are incompatible — upgrading from Java 21–24 to Java 25 requires refactoring any code using the old subclass-based API.

Advanced Topics

StructuredTaskScope.Config

In the new Java 25+ API, scopes can be customized via StructuredTaskScope.Config. You can set timeouts and thread factories directly on the configuration, providing a cleaner way to apply constraints without subclassing.

Structural Confinement Rule

Structured tasks enforce strict structural confinement. A child subtask cannot outlive the lexical scope of its parent StructuredTaskScope. If a parent exits its scope while subtasks are still running, those subtasks are automatically cancelled (interrupted), preventing orphaned threads.
