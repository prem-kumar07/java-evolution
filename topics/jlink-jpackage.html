Custom Runtimes & Native Packaging Java 9 & 14

Modern Java deployment has shifted away from relying on users to install system-wide JREs. Instead, applications now ship as self-contained bundles. The pipeline consists of three tools: jdeps (dependency discovery), jlink (custom runtime creation), and jpackage (native installer generation).

1 · jdeps: Discovering Dependencies

To build a custom JVM, you need to know exactly which standard modules your application relies on. If you have a non-modular legacy JAR (a "fat JAR"), jdeps can inspect its bytecode and print out the required JDK modules.

$ jdeps --multi-release 21 --ignore-missing-deps --print-module-deps target/myapp-fat.jar
java.base,java.desktop,java.logging,java.sql
Warning: jdeps cannot detect modules loaded dynamically via reflection or ServiceLoader (e.g., JDBC drivers or crypto providers). You may need to manually append modules like jdk.crypto.ec or jdk.unsupported.

2 · jlink: Building the Custom Runtime

Introduced in Java 9, jlink takes the module list and strips the JDK down to exactly what you need. This typically reduces the JVM footprint by 85-90% (from ~300MB down to ~35MB).

$ jlink \
  --module-path "$JAVA_HOME/jmods" \
  --add-modules java.base,java.desktop,java.logging,java.sql,jdk.crypto.ec \
  --output custom-jre \
  --compress zip-9 \
  --no-header-files \
  --no-man-pages \
  --strip-debug

You can now distribute this custom-jre folder alongside your JAR file. Users run your app using ./custom-jre/bin/java -jar myapp.jar.

3 · Does jlink require a modular project?

No — but there's one hard restriction worth knowing before you build a release pipeline around it. jlink links two different things, and only one of them actually needs JPMS:

What's being linkedNeeds module-info.java?
The JDK's own platform modules (java.base, java.sql, …) into a trimmed-down runtime — what §1/§2 above just did No. Works for any project, modular or not — this is the normal path.
Your own application code, linked directly into the image as a module Yes. jlink refuses a plain, non-modular JAR outright.

Verified: pointing jlink at an ordinary classpath JAR (no module-info.class inside it) fails immediately, even though the exact same JAR works fine as an automatic module (JPMS's name for a plain JAR on the module path) everywhere else:

$ jar --describe-module --file app.jar
No module descriptor found. Derived automatic module.
app automatic
requires java.base mandated
contains com.example

$ jlink --module-path "app.jar:$JAVA_HOME/jmods" --add-modules app --output image
Error: automatic module cannot be used with jlink: app from file:///.../app.jar
jlink flatly refuses automatic modules — there is no flag to force it through. To link your own code into the image as a module, it must be a real, explicit module with its own module-info.java.

Running the image once your module is linked in

If your app has a real module-info.java, jlink will link it straight into the image alongside the JDK modules — no separate JAR to ship, no classpath at all:

$ jlink \
  --module-path "app.jar:$JAVA_HOME/jmods" \
  --add-modules com.example.app \
  --output image
$ ./image/bin/java --list-modules | grep com.example
com.example.app                    # verified — it's genuinely baked into image/lib/modules

Three verified, equivalent ways to launch it — no -cp/-jar anywhere, because the module is already inside the image:

# 1. explicit module/class — works on any image, no extra jlink flags needed
$ ./image/bin/java -m com.example.app/com.example.Main
hello from a real modular app, module=com.example.app

# 2. module name alone — works when the module jar's manifest/module-info
#    already points at a main class (jar --create --main-class ... at build time)
$ ./image/bin/java -m com.example.app
hello from a real modular app, module=com.example.app

The third way skips java -m entirely — add --launcher at jlink time and it bakes the whole invocation into a ready-to-ship script:

$ jlink \
  --module-path "app.jar:$JAVA_HOME/jmods" \
  --add-modules com.example.app \
  --launcher run=com.example.app/com.example.Main \
  --output image
$ ./image/bin/run                       # just this — no -m, no module name to remember
hello from a real modular app, module=com.example.app
--launcher is what jpackage (§4) uses under the hood to turn a linked image into a native, double-click-able app — the generated launcher script/binary is the executable the installer ships.

Quick reference — the java launcher flags themselves differ

This is the root of every difference above: a non-modular jar and a modular jar aren't launched with the same flags at all — -cp/-jar vs. -p/-m, never mixed for the same artifact:

Non-modular jarModular jar
Where to look for code -cp / -classpath (a flat bag of classes) -p / --module-path (a directory of modules/modular jars)
What to run -jar app.jar (main class read from the jar's Main-Class manifest attribute) — or name the class explicitly with -cp -m / --module module[/Main] (main class read from module-info/the module's declared main class if omitted)
Full command java -cp app.jar com.example.Main java -p mods -m com.example.app/com.example.Main
Inside a jlink image ./image/bin/java -cp app.jar com.example.Main — app.jar ships alongside the image, isn't linked in (§3, non-modular path above) ./image/bin/java -m com.example.app/com.example.Main — no jar needed; the module is already inside image/lib/modules
The two flag families don't compose: -cp puts a jar on the classpath as the unnamed module (erasing any module-info.class it has), while -p puts it on the module path as a real or automatic module. Same jar, two different runtime identities, depending entirely on which flag you launch it with.

That restriction only applies to linking your code in. Building the slimmed-down runtime and running your existing non-modular JAR on top of it is unaffected — this is the real-world pattern almost every non-modular project actually uses, verified end-to-end:

# 1. jdeps works fine against an ordinary classpath jar (no module-info needed)
$ jdeps --print-module-deps app.jar
java.base

# 2. jlink a minimal runtime with ONLY those JDK modules — no app code inside the image at all
$ jlink --module-path "$JAVA_HOME/jmods" --add-modules java.base --output image
# ~45MB vs ~300MB for a full JDK install — verified

# 3. run your unmodified, non-modular jar on the classpath, same as always
$ ./image/bin/java -cp app.jar com.example.Main
hello from a non-modular app, in a real package        # verified output
This is exactly why jdeps in §1 is described as working against a "non-modular legacy JAR" — it exists specifically so you can build a custom runtime without ever modularizing your project. jlink only trims the JDK's modules here; your app keeps running on the classpath, entirely outside JPMS.

In practice, most non-modular projects skip calling jlink by hand and reach for jpackage (§4) instead — it runs jdeps and jlink for you internally and accepts a plain classpath JAR directly via --main-jar/--main-class, exactly as shown below.

4 · jpackage: Building Native Installers

Introduced in Java 14 (finalized in Java 16), jpackage wraps a runtime image and your app into a native, double-click-able package: .exe/.msi for Windows, .dmg/.pkg for macOS, and .deb/.rpm for Linux.

Modular vs. non-modular — the invocation itself changes, not just a flag

jpackage --help states this as two different command shapes outright: "For a modular application: jpackage -n name -p modulePath -m moduleName/className" vs. "For a non-modular application: jpackage -i inputDir -n name --main-class className --main-jar myJar.jar". Verified end-to-end below by actually building and running both:

Non-modular — --input + --main-jar/--main-class
$ jpackage \
  --type app-image \
  --name NonModApp \
  --input dist/input \
  --main-jar app.jar \
  --main-class NonModMain
$ ./NonModApp.app/Contents/MacOS/NonModApp
non-modular app running        # verified
Modular — --module-path + --module (no --input at all)
$ jpackage \
  --type app-image \
  --name ModApp \
  --module-path mods \
  --module com.example.app/com.example.Main
$ ./ModApp.app/Contents/MacOS/ModApp
modular app running             # verified

The structural difference from §3 carries all the way through to what jpackage actually ships — verified by inspecting both built bundles' contents:

$ ls NonModApp.app/Contents/app/
app.jar   NonModApp.cfg          # your jar, shipped as-is, run on the classpath

$ ls ModApp.app/Contents/app/
ModApp.cfg                       # no jar here at all —
# com.example.app was linked straight into Contents/runtime by the jlink step jpackage ran internally
Both forms accept --runtime-image to reuse a runtime you already built yourself with jlink (§2/§3), instead of letting jpackage invoke jlink internally.

Quick reference — the jpackage flags themselves differ

Same split as the java launcher table in §3, one level up the toolchain:

Non-modular jarModular jar
Where the app lives -i / --input (a directory whose contents are copied wholesale) -p / --module-path (a directory of modules/modular jars)
What to run --main-jar + --main-class -m / --module module[/Main]
Full command jpackage -n MyApp -i dist/input --main-jar app.jar --main-class com.example.Main jpackage -n MyApp -p mods -m com.example.app/com.example.Main
What ends up inside the package Your jar, copied as-is into Contents/app, run on the classpath — verified above No jar at all — linked straight into Contents/runtime by jpackage's internal jlink call — verified above
--main-jar and --module are mutually exclusive, straight from jpackage --help: "Either --module or --main-jar option can be specified but not both." There's no combined form — pick the row that matches your jar.

Same two commands, flag-by-flag:

Non-modular
jpackage \
  --input input-dir \           # 1. directory containing all JARs
  --main-jar "my-app.jar" \     # 2. the main target JAR file
  --main-class "com.foo.Main"   # 3. entry point class name
Modular
jpackage \
  --module-path mods/ \                          # 1. directory containing modules
  --module com.myapp.core/com.myapp.core.Main    # 2. Module/MainClass syntax

Three inputs collapse to two: the module path replaces --input, and --module carries both "which jar" and "which class" in one module/Class argument — there's no separate --main-class to pair it with.

Both stripped-down commands above are the real minimum — verified by actually running them as-is, with no --name, --type, --app-version, or --icon at all. Both exited 0 and produced a real installer. jpackage fills in defaults for everything else: --name falls back to the bare main-class name (Main, not com.foo.Main), and --type falls back to the host OS's default installer format (dmg on macOS) — so the result was a working Main-1.0.dmg in both cases, not an error. Add the cosmetic flags (--name, --app-version, --icon, the per-OS flags below) when you want control over the output; they're not required to make jpackage run.

Per-OS installer types & flags

--type's valid values are platform-dependent — jpackage --help only lists the types the host OS can actually build. Run on macOS, it reports {"app-image", "dmg", "pkg"} — verified; the equivalent flag sets for the other two platforms come from Oracle's jpackage tool reference, since each only builds on its own OS (see the cross-compilation note below):

Host OS--type valuesOS-specific flagsIcon format
Windowsexe, msi --win-shortcut, --win-menu, --win-dir-chooser, --win-per-user-install, --win-console.ico
macOSdmg, pkg --mac-package-name, --mac-app-category, --mac-sign, --mac-package-identifier.icns
Linuxdeb, rpm --linux-shortcut, --linux-menu-group, --linux-app-category, --linux-package-name.png

Windows:

$ jpackage \
  --type exe \
  --name "MyApp" \
  --app-version "1.0.0" \
  --input dist/input \
  --main-jar myapp-fat.jar \
  --main-class com.example.AppMain \
  --runtime-image custom-jre \
  --icon assets/app.ico \
  --win-shortcut \
  --win-menu

macOS — flags verified against jpackage --help on macOS:

$ jpackage \
  --type dmg \
  --name "MyApp" \
  --app-version "1.0.0" \
  --input dist/input \
  --main-jar myapp-fat.jar \
  --main-class com.example.AppMain \
  --runtime-image custom-jre \
  --icon assets/app.icns \
  --mac-package-name "MyApp" \
  --mac-app-category "utilities"

Linux:

$ jpackage \
  --type deb \
  --name "MyApp" \
  --app-version "1.0.0" \
  --input dist/input \
  --main-jar myapp-fat.jar \
  --main-class com.example.AppMain \
  --runtime-image custom-jre \
  --icon assets/app.png \
  --linux-shortcut \
  --linux-menu-group "Utility" \
  --linux-app-category "utils"
Cross-compilation: jpackage is not a cross-compiler. You must run it on Windows to generate Windows installers, on macOS to generate macOS installers, and on Linux to generate .deb/.rpm — each command above only runs on its matching host OS.
