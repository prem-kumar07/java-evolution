Generics

Generics let types be parameters, the same way method parameters let values be parameters. Box<T> is one class that works for Box<String>, Box<Integer>, or any type — with the compiler checking every use, and zero runtime cost.

0runtime overhead — erased at compile time
0casts needed with generic APIs
compile-timetype safety instead of runtime surprises
PECSProducer Extends, Consumer Super
Java 5introduced (2004)
The problem it solves Before generics, a collection held Object — anything could go in, so anything could come out, and the compiler couldn't stop you from putting a String into a list of Integers. The bug surfaced later as a ClassCastException, often far from where the mistake was made. Generics move that check from a runtime surprise to a compile-time error.

1 · Why generics — before & after

Before generics (pre-Java 5) — casts everywhere
List names = new ArrayList();     // holds Object
names.add("Ada");
names.add(42);                    // compiles fine — no error yet!

String s = (String) names.get(0); // manual cast, could fail
String s2 = (String) names.get(1); // ClassCastException AT RUNTIME, far from the bug
After — the compiler catches it immediately
List<String> names = new ArrayList<>();
names.add("Ada");
names.add(42);                    // COMPILE ERROR right here — caught immediately

String s = names.get(0);          // no cast needed at all

Three concrete benefits, straight from Oracle's own generics tutorial: stronger compile-time checks, elimination of casts, and the ability to write one algorithm that works across many types safely.

2 · Generic classes & methods

A non-generic box — only safe with Object
public class Box {
  private Object content;
  public void set(Object content) { this.content = content; }
  public Object get() { return content; }
}
Box b = new Box();
b.set("hello");
String s = (String) b.get();   // cast required, and nothing stops b.set(42)
A generic box — one class, every type, type-safe
public class Box<T> {
  private T content;
  public void set(T content) { this.content = content; }
  public T get() { return content; }
}
Box<String> b = new Box<>();
b.set("hello");
String s = b.get();            // no cast; b.set(42) would not compile

Naming convention — verified from Oracle's own tutorial

LetterMeans
EElement (used extensively by the Collections Framework)
K, VKey, Value (maps)
NNumber
TType
S, U, V...2nd, 3rd, 4th type, when you need more than one

Single uppercase letters are a convention, not a rule — but stray from it and readers will assume you meant something else, since every JDK generic type follows it.

Generic methods — the type parameter belongs to the method, not the class

// a static generic method: <U> is declared right before the return type
public static <U> void addBox(U u, List<Box<U>> boxes) {
  boxes.add(new Box<>(u));
}

// the compiler infers U from the arguments — no need to specify it
List<Box<Integer>> boxes = new ArrayList<>();
BoxDemo.<Integer>addBox(10, boxes);   // explicit type witness — rarely needed
BoxDemo.addBox(10, boxes);            // inferred automatically — the usual way

3 · Type inference & the diamond

Before Java 7 — repeat the type on both sides
Map<String, List<String>> map = new HashMap<String, List<String>>();
The diamond <> — let the compiler infer it
Map<String, List<String>> map = new HashMap<>();
// the compiler infers <String, List<String>> from the declared variable type
Gotcha: new HashMap() with no diamond at all uses the raw type — you lose type checking silently (an unchecked-conversion warning, not an error). Always use either the full parameterization or the empty diamond <>, never bare new HashMap() when assigning to a parameterized variable.

4 · Bounded, multiple, and recursive bounds

By default a type parameter accepts anything. extends narrows it to a specific hierarchy — and despite the keyword, it also means "implements" for interfaces.

// simple bound: T must be a Number (or subtype)
static double sumOf(List<? extends Number> nums) { ... }

// multiple bounds: at most ONE class, then any number of interfaces —
// the class (if any) must be listed first
static <T extends Number & Comparable<T>> T max(T a, T b) {
  return a.compareTo(b) >= 0 ? a : b;
}
// verified: max(3, 7) -> 7

// recursive bound: T must be comparable to itself — this is exactly
// how Collections.max() and Comparable-based sorting are declared in the JDK
  // Using PECS (Producer Extends, Consumer Super) for maximum compatibility
static <T extends Comparable<? super T>> T maxOf(T a, T b) {
  return a.compareTo(b) >= 0 ? a : b;
}
// verified: maxOf("apple", "banana") -> "banana"
Recursive bounds look strange the first time (T extends Comparable<T> — "T is comparable to itself") but they're everywhere in the JDK once you know to look: Enum<E extends Enum<E>> is declared exactly this way.

5 · Wildcards & PECS

A wildcard (?) represents an unknown type — used at the call site, not in a declaration, when you need flexibility a plain type parameter can't give you.

Too restrictive — only accepts List<Number> exactly
static double sum(List<Number> nums) { ... }
sum(List.of(1, 2, 3));       // ✗ compile error — List<Integer> is NOT a List<Number>
Upper-bounded wildcard — accepts any subtype
static double sum(List<? extends Number> nums) {
  double total = 0;
  for (Number n : nums) total += n.doubleValue();   // read-only access as Number
  return total;
}
sum(List.of(1, 2, 3));        // ✓ works — verified: 6.0
sum(List.of(1.5, 2.5));       // ✓ works — verified: 4.0
// lower-bounded wildcard: write Integers into anything that can hold them
static void addIntegers(List<? super Integer> list) {
  list.add(1);
  list.add(2);
}
List<Number> dest = new ArrayList<>();
addIntegers(dest);             // verified: dest == [1, 2]

// unbounded wildcard: List — you can read as Object, but can only WRITE null
List<?> unknown = List.of(1, 2, 3);
Object o = unknown.get(0);     // fine — verified
// unknown.add("x");           // would NOT compile — the element type is truly unknown

6 · Type erasure — verified with real bytecode

Generics are a compile-time feature. The compiler checks your types, then erases them: T becomes Object (or its first bound), and inserts casts where needed to keep the illusion of type safety at runtime.

class Node<T> { T data; void setData(T data) { this.data = data; } }

// after erasure, the compiler actually generates:
class Node { Object data; void setData(Object data) { this.data = data; } }

Bridge methods — verified with real javap output

Erasure creates a real, observable side effect when a subclass narrows a generic method's type. Here's the exact scenario, run and disassembled for real:

class Node<T> {
  T data;
  Node(T data) { this.data = data; }
  void setData(T data) { System.out.println("Node.setData"); this.data = data; }
}
class MyNode extends Node<Integer> {
  MyNode(Integer data) { super(data); }
  @Override void setData(Integer data) {           // looks like an override...
    System.out.println("MyNode.setData");
    super.setData(data);
  }
}

MyNode mn = new MyNode(5);
Node n = mn;              // raw type reference
n.setData("Hello");       // compiles (with an unchecked warning) — erased to setData(Object)
Verified real output: 
Exception in thread "main" java.lang.ClassCastException:
  class java.lang.String cannot be cast to class java.lang.Integer
    at MyNode.setData(BridgeDemo.java:12)
    at BridgeDemo.main(BridgeDemo.java:24)
After erasure, Node.setData(T) becomes Node.setData(Object) — so MyNode.setData(Integer) no longer overrides it by signature. To preserve polymorphism, the compiler silently generates a synthetic bridge method. Verified with javap -p MyNode: 
void setData(java.lang.Integer);   // your real method
void setData(java.lang.Object);    // compiler-generated bridge — casts, then delegates
javap only prints the two signatures — translated back into the Java syntax it's equivalent to (not legal to write by hand: a class can't declare two methods that erase to the same signature), the generated bridge looks like this: 
class MyNode extends Node {   // erased: Node -> raw Node

  // your real method, exactly as you wrote it — untouched by erasure
  void setData(Integer data) {
    System.out.println("MyNode.setData");
    super.setData(data);
  }

  // compiler-generated bridge — same erased signature as Node.setData(Object),
  // so it's the one that actually overrides Node's method and gets called virtually
  /* bridge, synthetic */ void setData(Object data) {
    setData((Integer) data);   // <- the cast: throws ClassCastException here, then
  }                            //    delegates to your real setData(Integer) above
}
The bridge method is what actually gets called, casts its argument to Integer, and that cast is where the ClassCastException is thrown — not inside your code at all. Its full bytecode, verified with javap -p -c -v MyNode, shows exactly that: 
void setData(java.lang.Object);
  descriptor: (Ljava/lang/Object;)V
  flags: (0x1040) ACC_BRIDGE, ACC_SYNTHETIC     // marked bridge + compiler-generated, invisible to reflection by default
  Code:
     0: aload_0
     1: aload_1
     2: checkcast     #24     // class java/lang/Integer   <- the cast that throws
     5: invokevirtual #26     // Method setData:(Ljava/lang/Integer;)V   <- delegates to your real method
     8: return
Two flags on the method, both set by the compiler, never by you: ACC_BRIDGE marks it as a bridge so tools (and the JVM's own overload resolution) know it's not source-level code, and ACC_SYNTHETIC hides it from normal reflection — Class.getMethods() and getDeclaredMethods() return it, but Method.isBridge() and Method.isSynthetic() both report true so you can filter it out.
Looking ahead — Project Valhalla: Valhalla aims to bring primitive specialization for generics to Java, enabling List<int> instead of List<Integer> without boxing overhead. This would fundamentally change the erasure model for specialized types and is expected to ship in a future Java LTS.

7 · What you cannot do with generics

All seven of these are direct, real consequences of erasure — verified against Oracle's own "Restrictions on Generics" reference.

RestrictionWhy (and the workaround)
Cannot instantiate with primitives: Pair<int, char>Only reference types — use Pair<Integer, Character> (autoboxed).
Cannot create an instance of a type parameter: new T()The compiler can't know what T is at runtime. Workaround: pass a Supplier<T> or a Class<T> and use reflection.
Cannot declare static fields of a type parameterA static field is shared by all instances, but each instantiation could have a different T — there's no single answer for what type it would be.
Cannot use instanceof or cast against a parameterized type: x instanceof List<String>Erased at runtime — the JVM can't tell List<Integer> from List<String>. You can check x instanceof List<?> instead.
Cannot create arrays of a parameterized type: new List<String>[10]Arrays check their element type at runtime (ArrayStoreException); erasure would silently defeat that safety check, so it's forbidden outright.
A generic class cannot extend ThrowableException types must be resolvable at both compile and catch time — erasure would make catch clauses ambiguous.

Clarification: Under JLS §8.1.2, it is a compile-time error if a generic class directly or indirectly subclasses Throwable. You cannot define class MyException<T> extends RuntimeException. However, type parameters are allowed in a method's throws clause (e.g., <T extends Throwable> void doIt() throws T).

Cannot overload two methods that erase to the same signaturevoid m(List<String> x) and void m(List<Integer> x) both erase to m(List) — a duplicate-method compile error.

8 · Pitfalls

PitfallReality
Using a raw type (List with no <> at all)Compiles with an unchecked warning and disables generic type checking for that variable entirely — always parameterize.
Assuming generics add runtime type safety to arraysArrays are reified (checked at runtime); generics are erased. Mixing the two is exactly why List<T>[] is forbidden.
Expecting List<Object> and List<?> to behave the sameYou can insert anything into a List<Object>. Into a List<?> you can only insert null — the element type is truly unknown to the compiler.
Suppressing an unchecked-cast warning without understanding why@SuppressWarnings("unchecked") silences the compiler, not the risk. Only use it when you've manually verified type safety (e.g. wrapping a known-safe reflective call).
Trying to overload by generic parameter type aloneErasure makes the overloads identical — a real compile error, not a subtle bug, so at least you find out immediately.

10 · Advanced generics

Four topics that go past the everyday PECS/erasure material above — each verified by actually compiling and running it, and cross-checked against dev.java's generics tutorial and Oracle's "Non-Reifiable Types" reference for wording.

Wildcard capture — the "capture helper" pattern

dev.java's own definition: a list may be declared as List<?>, but "when evaluating an expression, the compiler infers a particular type from the code" — that inferred, unnamed type is the capture (printed by javac as CAP#1). You hit its limits the moment you try to both read and write a List<?> in the same method:

Doesn't compile — two "?" uses aren't provably the same capture
static void swapFirstTwo(List<?> list) {
  Object tmp = list.get(0);
  list.set(0, list.get(1));   // compile error
  list.set(1, tmp);           // compile error
}
// javap/javac's real message:
// error: incompatible types: Object cannot be converted to CAP#1
//   where CAP#1 is a fresh type-variable:
//     CAP#1 extends Object from capture of ?
Fixed — a private generic helper method captures the wildcard
static void swapFirstTwo(List<?> list) {
  swapHelper(list);          // capture happens on THIS call
}

private static <T> void swapHelper(List<T> list) {
  T tmp = list.get(0);       // now get()/set() both agree on the same T
  list.set(0, list.get(1));
  list.set(1, tmp);
}

List<String> names = new ArrayList<>(List.of("Ada", "Grace", "Barbara"));
swapFirstTwo(names);
System.out.println(names);   // verified: [Grace, Ada, Barbara]
The helper method doesn't change behavior — it changes what the compiler can prove. Calling swapHelper(list) from inside swapFirstTwo lets the compiler bind the unknown ? to one concrete, if unnameable, type parameter T for the duration of that call. dev.java's convention: name it <originalMethodName>Helper.

Heap pollution & @SafeVarargs

Oracle's exact definition: heap pollution "occurs when a variable of a parameterized type refers to an object that is not of that parameterized type" — and it becomes possible specifically because a varargs parameter of a non-reifiable type (like List<String>) is compiled down to a plain Object[], which happily accepts any array store:

static void faultyMethod(List<String>... l) {   // no @SafeVarargs — and rightly so
  Object[] objectArray = l;             // fine: T[] "is-a" Object[]
  objectArray[0] = Arrays.asList(42);   // heap pollution: an Integer list, disguised as List<String>
  String s = l[0].get(0);               // ClassCastException — thrown HERE, not where the lie was told
}

faultyMethod(List.of("x"), List.of("y"));
// verified: java.lang.ClassCastException: class java.lang.Integer cannot be cast to class java.lang.String

@SafeVarargs is how you tell the compiler (and readers) "I checked — this method never does that." It's legal only on static/final/private methods and constructors, because those can't be overridden with a less careful body:

@SafeVarargs   // legal: static, and the body only ever reads `items`, never stores into it
static <T> List<T> listOf(T... items) {
  List<T> result = new ArrayList<>();
  for (T item : items) result.add(item);
  return result;
}
listOf("a", "b", "c");   // verified: [a, b, c] — compiles with ZERO warnings under -Xlint:all
Reifiable vs. non-reifiable, precisely (Oracle's wording): a reifiable type has all its information available at runtime — primitives, non-generic types, raw types, and unbounded-wildcard invocations like List<?> all qualify. Non-reifiable types — List<String>, List<Number> — have had information erased, and it's exactly those types that make a varargs parameter dangerous.

Intersection types — bounds that require more than one interface

An intersection type shows up in two places: as a type-parameter bound with & joining several types, and as an explicit cast. Both require the argument to satisfy every listed type simultaneously — at most one class, then any number of interfaces:

// bound form: T must be Comparable AND Serializable at once
static <T extends Comparable<T> & Serializable> T max(T a, T b) {
  return a.compareTo(b) >= 0 ? a : b;
}
max(3, 7);   // verified: 7 — Integer already implements both

// cast form: force a lambda to implement two interfaces at once
Comparator<String> byLength =
    (Comparator<String> & Serializable) (a, b) -> a.length() - b.length();

try (ObjectOutputStream oos = new ObjectOutputStream(byteStream)) {
  oos.writeObject(byLength);   // only compiles/works because of the & Serializable half of the cast
}
// verified: serializes successfully; writeObject(byLength) alone (no cast) would not compile —
// Comparator itself isn't Serializable
Same ordering rule as bounded type parameters everywhere else on this page: if one of the intersected types is a class, it must come first — (Serializable & Comparator<String>) reversed would be a compile error.

Super type tokens — reifying a generic type at runtime

Erasure destroys T on the class holding it — but it does not erase a subclass's extends TypeToken<List<String>> clause, because that's part of the subclass's own class-file signature, not the generic class's runtime representation. Neal Gafter's "super type token" trick (the pattern behind Guice's TypeLiteral, Jackson's TypeReference, and Gson's TypeToken) exploits exactly that gap:

abstract class TypeToken<T> {
  private final Type type;

  protected TypeToken() {
    Type superclass = getClass().getGenericSuperclass();   // e.g. TypeToken<List<String>>
    this.type = ((ParameterizedType) superclass).getActualTypeArguments()[0];
  }

  public Type getType() { return type; }
}

// the anonymous subclass "{}" is what makes this work — it's a real class file whose
// generic superclass is permanently TypeToken>, unaffected by T's own erasure
TypeToken<List<String>> token = new TypeToken<List<String>>() {};
System.out.println(token.getType());
// verified: java.util.List<java.lang.String>
Without the anonymous {} subclass, this doesn't work — a plain new TypeToken<List<String>>() has nothing for getGenericSuperclass() to read, because TypeToken itself has no superclass carrying that information. The empty braces are the whole trick.

11 · Cheat sheet

Generics in one glance

  • class Box<T> { T value; } — one type parameter, works for any reference type.
  • Naming: E element, K/V key/value, N number, T type.
  • Diamond: new HashMap<>() — never bare new HashMap() when the variable is parameterized.
  • Bounds: <T extends Number>; multiple: <T extends Number & Comparable<T>> (class first).
  • PECS: ? extends to read (producer), ? super to write (consumer).
  • Erasure: T → Object/bound at compile time — zero runtime cost, but no runtime type info either.
  • Can't: new T(), static fields of T, instanceof List<String>, arrays of parameterized types, extend Throwable generically.
