Java Management Extensions (JMX) & JConsole Java 5

JMX is the JVM's built-in framework for exposing an application's internals — configuration, statistics, operations — as manageable objects called MBeans, reachable both in-process and over the network. Every JVM has been running a management agent since Java 5, whether you've ever touched it or not: java.lang.management's MemoryMXBean, ThreadMXBean, and friends are JMX, already wired up, with zero configuration.

MBeanthe unit of manageability

The problem it solves Before JMX, "managing" a running Java application meant something different in every codebase — a telnet admin port here, a properties file polled on a timer there, a custom socket protocol somewhere else. Application servers like early WebLogic bolted on their own JMX 1.0 implementation for exactly this reason, years before it shipped in the JDK. JMX standardized it: one API to expose an attribute or an operation, one protocol to reach it locally or remotely, and one set of tools (jconsole, JMC, any JMX client) that work against any compliant application without knowing anything about it in advance.

1 · What JMX Is, and Why It Was Added

JMX (Java Management Extensions) predates its place in the JDK. The core specification — JMX 1.0, then 1.2 — was published by Sun as a standalone download, and application servers of the era adopted it independently for their own admin consoles; WebLogic Server, for instance, implemented the JMX 1.0 spec for its management services well before JMX shipped in any JDK. Every vendor building "manage my running server" tooling was solving the same problem separately.

That changed with J2SE 5.0 (2004), which bundled three related JSRs directly into the platform:

JSRWhat it defined
JSR 3 — Java Management ExtensionsThe core javax.management API: MBeans, the MBeanServer, ObjectName — JMX 1.2.
JSR 160 — JMX Remote APIHow to reach an MBeanServer from outside the process: connectors, the RMI transport, service:jmx:... URLs.
JSR 174 — Monitoring and Management for the JVMThe java.lang.management package: a standard set of platform MBeans (memory, threads, GC, class loading, …) every JVM exposes automatically.

jconsole shipped alongside as the reference GUI client. The result: instead of every app inventing its own admin protocol, a Java application gets a standard, remotely-reachable management surface the instant it starts — for the JVM itself, and for anything the application chooses to expose the same way.

2 · Platform MXBeans — Built In, Zero Setup

Before writing a single line of JMX code yourself, every JVM already exposes a standard set of MBeans through java.lang.management.ManagementFactory — no flags, no registration, no network setup. This is the same data jconsole's "VM Summary" tab and JMC's overview pull from.

import java.lang.management.*;
import java.util.List;

public class PlatformMXBeanDemo {
  public static void main(String[] args) {
    RuntimeMXBean runtime = ManagementFactory.getRuntimeMXBean();
    System.out.println("JVM name: " + runtime.getVmName());
    System.out.println("Uptime: " + runtime.getUptime() + "ms");

    MemoryMXBean memory = ManagementFactory.getMemoryMXBean();
    MemoryUsage heap = memory.getHeapMemoryUsage();
    System.out.printf("Heap used: %.1f MB / max %.1f MB%n",
        heap.getUsed() / 1_048_576.0, heap.getMax() / 1_048_576.0);

    ThreadMXBean threads = ManagementFactory.getThreadMXBean();
    System.out.println("Live threads: " + threads.getThreadCount());
    System.out.println("Peak threads: " + threads.getPeakThreadCount());

    List<GarbageCollectorMXBean> gcs = ManagementFactory.getGarbageCollectorMXBeans();
    for (GarbageCollectorMXBean gc : gcs) {
      System.out.println("GC[" + gc.getName() + "] collections=" + gc.getCollectionCount()
          + " time=" + gc.getCollectionTime() + "ms");
    }

    OperatingSystemMXBean os = ManagementFactory.getOperatingSystemMXBean();
    System.out.println("Available processors: " + os.getAvailableProcessors());
  }
}

4 · Writing Your Own MBean — Complete Example

There are two ways to make your own class manageable, both verified below with the same CacheStats example — a hit/miss counter you might attach to an actual cache.

4.1 · The Standard MBean pattern — naming-convention based

The interface's name must be the implementing class's name with MBean appended — this is a compile-time-invisible convention the JMX runtime checks by reflection, not an annotation. Every public getter/setter/method on the interface becomes an attribute or operation.

// CacheStatsMBean.java — MUST be named "<ClassName>MBean" exactly
public interface CacheStatsMBean {
  long getHitCount();
  long getMissCount();
  double getHitRatio();
  void reset();
}

// CacheStats.java
import java.util.concurrent.atomic.AtomicLong;

public class CacheStats implements CacheStatsMBean {
  private final AtomicLong hits = new AtomicLong();
  private final AtomicLong misses = new AtomicLong();

  public void recordHit() { hits.incrementAndGet(); }
  public void recordMiss() { misses.incrementAndGet(); }

  @Override public long getHitCount() { return hits.get(); }
  @Override public long getMissCount() { return misses.get(); }
  @Override public double getHitRatio() {
    long total = hits.get() + misses.get();
    return total == 0 ? 0.0 : (double) hits.get() / total;
  }
  @Override public void reset() { hits.set(0); misses.set(0); }
}

Registering it puts it on the same MBeanServer platform MXBeans live on — one ObjectName namespace for everything:

import javax.management.*;
import java.lang.management.ManagementFactory;

public class MBeanDemo {
  public static void main(String[] args) throws Exception {
    MBeanServer server = ManagementFactory.getPlatformMBeanServer();
    ObjectName name = new ObjectName("com.example:type=CacheStats,name=OrderCache");

    CacheStats cache = new CacheStats();
    server.registerMBean(cache, name);

    cache.recordHit(); cache.recordHit(); cache.recordHit(); cache.recordMiss();

    // read it back purely through the MBeanServer, exactly as jconsole/a remote client would
    long hits = (long) server.getAttribute(name, "HitCount");
    long misses = (long) server.getAttribute(name, "MissCount");
    double ratio = (double) server.getAttribute(name, "HitRatio");
    System.out.printf("via MBeanServer -> hits=%d misses=%d ratio=%.2f%n", hits, misses, ratio);

    server.invoke(name, "reset", new Object[0], new String[0]);
    System.out.println("after reset, hits=" + server.getAttribute(name, "HitCount"));
  }
}
$ javac CacheStatsMBean.java CacheStats.java MBeanDemo.java
$ java -cp . MBeanDemo
Verified real output: 
via MBeanServer -> hits=3 misses=1 ratio=0.75
after reset, hits=0
The naming convention is strictly enforced. Rename the interface to anything other than CacheStatsMBean (with no @MXBean, below) and registration fails immediately — verified: 
javax.management.NotCompliantMBeanException:
  Class CacheStats is not a JMX compliant Standard MBean

4.2 · The @MXBean pattern — no naming convention required

The simpler, more modern alternative: annotate the interface with @MXBean and name it whatever you like. @MXBean also auto-converts complex return types (records, custom classes) into CompositeData for you — this is the pattern every platform MXBean (MemoryMXBean, ThreadMXBean) itself uses.

import javax.management.MXBean;

@MXBean
public interface Stats {   // any name at all — no "MBean" suffix required
  long getHitCount();
}

public class StatsImpl implements Stats {
  public long getHitCount() { return 42; }
}
$ javac Stats.java StatsImpl.java ArbitraryNameTest.java
$ java -cp . ArbitraryNameTest
Verified real output — registers and reads back fine, despite the interface name matching neither the class name nor "MBean": 
registered with @MXBean, arbitrary interface name -> 42

5 · DynamicMBean, Operations, Attributes & Descriptors

Both patterns in §4 are static: JMX reflects over your interface once, at registration time, and derives the attribute/operation list from its method signatures. A DynamicMBean is the third pattern — you implement the introspection yourself, so the set of attributes and operations can be decided at runtime (config-driven MBeans, plugin systems, proxies over something that isn't a Java interface at all), and so you can attach rich metadata — descriptors — that the naming-convention patterns have no way to express.

5.1 · The DynamicMBean interface

Six methods, straight from the javax.management.DynamicMBean Javadoc — implement all six and any object becomes manageable, with no naming convention and no annotation at all:

MethodWhat it's for
Object getAttribute(String)"Obtain the value of a specific attribute of the Dynamic MBean."
void setAttribute(Attribute)"Set the value of a specific attribute of the Dynamic MBean."
AttributeList getAttributes(String[])"Get the values of several attributes" in one round trip — what jconsole actually calls to refresh its whole attribute table at once.
AttributeList setAttributes(AttributeList)"Sets the values of several attributes" — the bulk counterpart to setAttribute.
Object invoke(String, Object[], String[])"Allows an action to be invoked on the Dynamic MBean" — the operation name, its arguments, and their type signature, all passed as plain data.
MBeanInfo getMBeanInfo()"Provides the exposed attributes and actions of the Dynamic MBean using an MBeanInfo object" — the metadata every other method above must stay consistent with.
Nothing here is checked against real fields or methods at compile time. getAttribute("Typo") compiles fine and only fails at runtime, by contract, with AttributeNotFoundException — the trade-off for runtime flexibility is that the compiler can no longer catch a mismatch between what getMBeanInfo() advertises and what getAttribute/invoke actually handle. Keeping those in sync is entirely on you.

5.2 · MBeanAttributeInfo & MBeanOperationInfo — what metadata actually declares

These are the building blocks getMBeanInfo() hands back. An attribute's constructor takes three booleans that together describe its shape:

FlagMeans
isReadableHas a getter — appears when a client reads the attribute.
isWritableHas a setter — appears when a client calls setAttribute.
isIsIt's a boolean using the JavaBeans is convention (isEnabled() rather than getEnabled()) — must be paired with isReadable=true and a boolean/Boolean type, or JMX throws IllegalArgumentException immediately.

An operation's constructor takes an impact flag — purely descriptive metadata for tools (nothing enforces it), but it's what lets jconsole decide whether to show a confirmation dialog before invoking something:

Impact constantMeans
MBeanOperationInfo.INFO"Read-like: it returns information but does not change any state" — safe to call without asking.
MBeanOperationInfo.ACTION"Write-like: it has an effect but does not return any information" — e.g. reset().
MBeanOperationInfo.ACTION_INFO"Both read-like and write-like: it has an effect, and it also returns information" — e.g. tryAcquire() below, which mutates a counter and returns whether the request was granted.
MBeanOperationInfo.UNKNOWN"The impact... is unknown or cannot be expressed using one of the other values."

5.3 · Descriptors — attaching metadata beyond name and type

A Descriptor is a simple name→value bag attached to an MBeanInfo, MBeanAttributeInfo, MBeanOperationInfo, or even a single MBeanParameterInfo — the Javadoc's own words: "additional metadata for a JMX element... a collection of fields. A field is a name and an associated value." JMX pre-defines a set of "well-known" field names tools already know how to render; anything else you invent is fine too, as long as it contains a period so it can't collide with a future standard one.

Well-known fieldMeaning
units"The units in which an attribute, parameter, or operation return value is measured" — e.g. "bytes", "requests/sec".
minValue / maxValue"Minimum/maximum legal value for an attribute or parameter" — advisory; nothing in the API enforces it for you (your setAttribute still has to check).
defaultValue"Default value for an attribute or parameter."
since"The version of the information model in which this element was introduced."
deprecatedConvention: version first deprecated, a space, then an explanation — e.g. "1.3 Replaced by the Capacity attribute".
immutableInfo"true"/"false" — whether this MBean's whole MBeanInfo is guaranteed never to change over its lifetime; lets a client cache it instead of re-fetching every time.

The simplest way to build one is ImmutableDescriptor, taking "field=value" strings — and descriptors attach at every level: the whole MBean, one attribute, one operation, or one parameter of an operation, verified for all four below.

Descriptor limitDescriptor = new ImmutableDescriptor(new String[] {
    "units=requests/sec", "minValue=1", "defaultValue=100", "since=1.0"
});
MBeanAttributeInfo limitInfo = new MBeanAttributeInfo(
    "Limit", "int", "Maximum requests allowed per window",
    true, true, false, limitDescriptor);   // descriptor is the 7th constructor argument
Reading one back is just as direct — attributeInfo.getDescriptor().getFieldValue("units") — which is exactly how a generic tool like jconsole renders a tooltip or a unit suffix next to a value it has never seen the Java type of before.
Descriptors are not a DynamicMBean-exclusive feature — §4's Standard MBean and @MXBean patterns can carry them too, via the @DescriptorKey meta-annotation. Define a small custom annotation once, tag it @DescriptorKey("fieldName"), then use that annotation on any interface method — JMX folds its value straight into the reflection-derived Descriptor, no DynamicMBean, no hand-built MBeanInfo, required: 
// define once — a reusable, typed wrapper around one descriptor field
@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
public @interface Units {
  @DescriptorKey("units")
  String value();
}

// then use it directly on an ordinary Standard MBean interface
public interface CacheControlMBean {
  @Units("bytes")
  long getCacheSize();
}

public class CacheControl implements CacheControlMBean {
  public long getCacheSize() { return 1024; }
}
server.registerMBean(new CacheControl(), name);   // plain Standard MBean registration — nothing special
MBeanInfo info = server.getMBeanInfo(name);
for (MBeanAttributeInfo attr : info.getAttributes())
  System.out.println(attr.getName() + " units=" + attr.getDescriptor().getFieldValue("units"));
// verified real output: CacheSize units=bytes
Verified identically on an @MXBean interface too — @DescriptorKey doesn't care which of the two static patterns it's attached to. The only real difference from §5.1–§5.2 is who builds the Descriptor: you, by hand, for a DynamicMBean; JMX itself, by reading your annotations, for a Standard MBean or @MXBean.

5.4 · Complete example — a hand-rolled rate limiter, all four pieces together

Everything above, in one working MBean: a DynamicMBean with a writable attribute (Limit, carrying a descriptor with units/minValue/defaultValue), two read-only attributes, and two operations with different impact flags — registered and driven purely through the MBeanServer, exactly as a remote JMX client or jconsole would.

import javax.management.*;
import java.util.concurrent.atomic.AtomicLong;
import java.util.concurrent.atomic.AtomicInteger;

public class RateLimiterDynamicMBean implements DynamicMBean {
  private final AtomicInteger limit = new AtomicInteger(100);
  private final AtomicLong allowed = new AtomicLong();
  private final AtomicLong rejected = new AtomicLong();

  // ---- application logic the MBean is wrapping ----
  boolean tryAcquire() {
    if (allowed.get() < limit.get()) { allowed.incrementAndGet(); return true; }
    rejected.incrementAndGet();
    return false;
  }

  // ---- DynamicMBean: attribute reads ----
  @Override
  public Object getAttribute(String attribute) throws AttributeNotFoundException {
    return switch (attribute) {
      case "Limit" -> limit.get();
      case "Allowed" -> allowed.get();
      case "Rejected" -> rejected.get();
      default -> throw new AttributeNotFoundException(attribute);
    };
  }

  // ---- DynamicMBean: attribute writes (only "Limit" is writable) ----
  @Override
  public void setAttribute(Attribute attribute) throws AttributeNotFoundException, InvalidAttributeValueException {
    if (!attribute.getName().equals("Limit"))
      throw new AttributeNotFoundException(attribute.getName() + " is not writable");
    if (!(attribute.getValue() instanceof Integer v) || v < 1)
      throw new InvalidAttributeValueException("Limit must be a positive Integer");
    limit.set(v);
  }

  @Override
  public AttributeList getAttributes(String[] names) {
    AttributeList list = new AttributeList();
    for (String n : names) {
      try { list.add(new Attribute(n, getAttribute(n))); }
      catch (AttributeNotFoundException ignored) { }
    }
    return list;
  }

  @Override
  public AttributeList setAttributes(AttributeList attributes) {
    AttributeList done = new AttributeList();
    for (Object o : attributes) {
      Attribute a = (Attribute) o;
      try { setAttribute(a); done.add(a); } catch (Exception ignored) { }
    }
    return done;
  }

  // ---- DynamicMBean: operations ----
  @Override
  public Object invoke(String actionName, Object[] params, String[] signature) throws MBeanException {
    if (actionName.equals("reset")) {
      allowed.set(0); rejected.set(0);
      return null;
    }
    if (actionName.equals("tryAcquire")) {
      return tryAcquire();
    }
    throw new MBeanException(new IllegalArgumentException("no such operation: " + actionName));
  }

  // ---- DynamicMBean: metadata, built by hand with Descriptors ----
  @Override
  public MBeanInfo getMBeanInfo() {
    Descriptor limitDescriptor = new ImmutableDescriptor(new String[] {
        "units=requests/sec", "minValue=1", "defaultValue=100", "since=1.0"
    });

    MBeanAttributeInfo limitInfo = new MBeanAttributeInfo(
        "Limit", "int", "Maximum requests allowed per window",
        true, true, false, limitDescriptor);
    MBeanAttributeInfo allowedInfo = new MBeanAttributeInfo(
        "Allowed", "long", "Total requests allowed so far", true, false, false);
    MBeanAttributeInfo rejectedInfo = new MBeanAttributeInfo(
        "Rejected", "long", "Total requests rejected so far", true, false, false);

    MBeanOperationInfo resetOp = new MBeanOperationInfo(
        "reset", "Reset the allowed/rejected counters to zero",
        new MBeanParameterInfo[0], "void", MBeanOperationInfo.ACTION);

    MBeanOperationInfo tryAcquireOp = new MBeanOperationInfo(
        "tryAcquire", "Attempt to acquire one permit; returns whether it was granted",
        new MBeanParameterInfo[0], "boolean", MBeanOperationInfo.ACTION_INFO);

    Descriptor mbeanDescriptor = new ImmutableDescriptor(new String[] {
        "immutableInfo=false", "since=1.0"
    });

    return new MBeanInfo(
        this.getClass().getName(),
        "A hand-rolled DynamicMBean rate limiter",
        new MBeanAttributeInfo[] { limitInfo, allowedInfo, rejectedInfo },
        null,   // no custom constructors exposed
        new MBeanOperationInfo[] { resetOp, tryAcquireOp },
        null,   // no notifications
        mbeanDescriptor);
  }
}

Driving it purely through the MBeanServer — the same calls a remote client or jconsole would make, none of them touching the class directly:

import javax.management.*;
import java.lang.management.ManagementFactory;

public class DynamicMBeanDemo {
  public static void main(String[] args) throws Exception {
    MBeanServer server = ManagementFactory.getPlatformMBeanServer();
    ObjectName name = new ObjectName("com.example:type=RateLimiter,name=OrdersApi");

    RateLimiterDynamicMBean limiter = new RateLimiterDynamicMBean();
    server.registerMBean(limiter, name);

    // read the descriptor on the "Limit" attribute, exactly as jconsole would to render a tooltip
    MBeanInfo info = server.getMBeanInfo(name);
    for (MBeanAttributeInfo attr : info.getAttributes()) {
      if (attr.getName().equals("Limit")) {
        Descriptor d = attr.getDescriptor();
        System.out.println("Limit descriptor: units=" + d.getFieldValue("units")
            + " minValue=" + d.getFieldValue("minValue")
            + " defaultValue=" + d.getFieldValue("defaultValue"));
      }
    }

    // exercise it purely through the MBeanServer -- attributes AND operations
    System.out.println("initial Limit = " + server.getAttribute(name, "Limit"));
    server.setAttribute(name, new Attribute("Limit", 3));
    System.out.println("after setAttribute, Limit = " + server.getAttribute(name, "Limit"));

    int granted = 0, denied = 0;
    for (int i = 0; i < 5; i++) {
      boolean ok = (boolean) server.invoke(name, "tryAcquire", new Object[0], new String[0]);
      if (ok) granted++; else denied++;
    }
    System.out.println("granted=" + granted + " denied=" + denied);
    System.out.println("Allowed=" + server.getAttribute(name, "Allowed")
        + " Rejected=" + server.getAttribute(name, "Rejected"));

    server.invoke(name, "reset", new Object[0], new String[0]);
    System.out.println("after reset, Allowed=" + server.getAttribute(name, "Allowed"));

    // rejected write: bad value type/range must throw, verified
    try {
      server.setAttribute(name, new Attribute("Limit", -5));
      System.out.println("BUG: should have thrown");
    } catch (InvalidAttributeValueException e) {
      System.out.println("rejected bad value as expected: " + e.getMessage());
    }
  }
}

$ java -cp . DynamicMBeanDemo

6 · Remote JMX — Complete Example

The whole point of JSR 160: reach an MBeanServer running in a different JVM, potentially on a different machine. Below, a server process registers the same CacheStats MBean and exposes JMX remotely; a completely separate client process connects and reads it — real two-process, real network round trip on this machine.

Server — three system properties turn on the remote agent at launch:

$ java -Dcom.sun.management.jmxremote \
       -Dcom.sun.management.jmxremote.port=19099 \
       -Dcom.sun.management.jmxremote.authenticate=false \
       -Dcom.sun.management.jmxremote.ssl=false \
       -Djava.rmi.server.hostname=127.0.0.1 \
       -cp . RemoteServer &
server up, pid=30378

Client — a separate process, separate JVM, using JMXConnectorFactory and a service:jmx:rmi:... URL:

import javax.management.*;
import javax.management.remote.*;
import java.util.Map;

public class RemoteClient {
  public static void main(String[] args) throws Exception {
    String url = "service:jmx:rmi:///jndi/rmi://127.0.0.1:19099/jmxrmi";
    JMXServiceURL serviceUrl = new JMXServiceURL(url);
    try (JMXConnector connector = JMXConnectorFactory.connect(serviceUrl, Map.of())) {
      MBeanServerConnection conn = connector.getMBeanServerConnection();
      ObjectName name = new ObjectName("com.example:type=CacheStats,name=OrderCache");

      long hits = (long) conn.getAttribute(name, "HitCount");
      long misses = (long) conn.getAttribute(name, "MissCount");
      System.out.println("REMOTE read -> hits=" + hits + " misses=" + misses);

      // platform MXBeans are reachable remotely too — no extra work
      ObjectName memName = new ObjectName("java.lang:type=Memory");
      System.out.println("REMOTE Memory MBean reachable: " +
          (conn.getAttribute(memName, "HeapMemoryUsage") != null));
    }
  }
}
$ javac RemoteClient.java
$ java -cp . RemoteClient
Verified real output — genuinely two separate JVM processes: 
REMOTE read -> hits=2 misses=1
REMOTE Memory MBean reachable: true
service:jmx:rmi:///jndi/rmi://host:port/jmxrmi is the default RMI connector URL form — the same one jconsole builds internally when you type host:port into its connect dialog. Production setups typically add ssl=true and a password/access file instead of the authenticate=false shortcut used here for a local demo.

7 · Notifications — Complete Example

MBeans aren't purely poll-based — an MBean that implements NotificationEmitter/NotificationBroadcaster can push events to listeners. The platform's own MemoryMXBean does exactly this for heap usage thresholds, which is how tools show a live "memory pressure" alert without polling in a loop:

import java.lang.management.*;
import javax.management.*;
import javax.management.openmbean.CompositeData;
import java.util.*;
import java.util.concurrent.CountDownLatch;
import java.util.concurrent.TimeUnit;

public class MemoryThresholdDemo {
  public static void main(String[] args) throws Exception {
    List<MemoryPoolMXBean> pools = ManagementFactory.getMemoryPoolMXBeans();
    MemoryPoolMXBean targetPool = null;
    for (MemoryPoolMXBean p : pools) {
      if (p.isUsageThresholdSupported() && p.getType() == MemoryType.HEAP) {
        targetPool = p;
        break;
      }
    }
    if (targetPool == null) { System.out.println("no supported pool found"); return; }

    long threshold = targetPool.getUsage().getUsed() + 1;   // trips almost immediately, for the demo
    targetPool.setUsageThreshold(threshold);
    System.out.println("watching pool: " + targetPool.getName());

    CountDownLatch latch = new CountDownLatch(1);
    MemoryMXBean memBean = ManagementFactory.getMemoryMXBean();
    NotificationEmitter emitter = (NotificationEmitter) memBean;
    emitter.addNotificationListener((Notification notif, Object handback) -> {
      if (notif.getType().equals(MemoryNotificationInfo.MEMORY_THRESHOLD_EXCEEDED)) {
        MemoryNotificationInfo info = MemoryNotificationInfo.from((CompositeData) notif.getUserData());
        System.out.println("NOTIFICATION: pool=" + info.getPoolName()
            + " used=" + info.getUsage().getUsed());
        latch.countDown();
      }
    }, null, null);

    // allocate until the threshold trips
    List<byte[]> garbage = new ArrayList<>();
    for (int i = 0; i < 2000 && latch.getCount() > 0; i++) {
      garbage.add(new byte[10_000]);
    }
    latch.await(5, TimeUnit.SECONDS);
    System.out.println("done, notified=" + (latch.getCount() == 0));
  }
}
$ javac MemoryThresholdDemo.java
$ java -cp . MemoryThresholdDemo
Verified real output — a push notification, not a poll: 
watching pool: G1 Old Gen
NOTIFICATION: pool=G1 Old Gen used=1177912
done, notified=true
This is exactly the mechanism behind production "heap usage > 90%" alerting agents — set setUsageThreshold to something meaningful (e.g. 90% of max) instead of "used + 1", and the notification fires once, asynchronously, the moment the JVM crosses it — no polling loop burning CPU.

8 · JMX + JFR — Controlling Recordings Over JMX

This is the direct answer to "how do JMX and JFR relate": since Java 8, every jcmd diagnostic command — including all of JFR's — is also exposed as an MBean, com.sun.management:type=DiagnosticCommand. That means you can start, check, dump, and stop a JFR recording purely through JMX: no shell access to the target host at all, which matters a great deal for a JVM inside a locked-down container where only a JMX port is reachable.

First, proof the operations are really there — inspecting the MBean's own metadata, filtered to the JFR-related ones:

import javax.management.*;
import java.lang.management.ManagementFactory;

public class DiagCommandInspect {
  public static void main(String[] args) throws Exception {
    MBeanServer server = ManagementFactory.getPlatformMBeanServer();
    ObjectName name = new ObjectName("com.sun.management:type=DiagnosticCommand");
    MBeanInfo info = server.getMBeanInfo(name);
    for (MBeanOperationInfo op : info.getOperations()) {
      if (op.getName().toLowerCase().contains("jfr")) {
        System.out.println(op.getName() + " -> " + op.getDescription());
      }
    }
  }
}
Verified real output — the exact same commands jcmd <PID> JFR.* exposes, listed straight off the running JVM's own MBean: 
jfrCheck -> Checks running JFR recording(s)
jfrConfigure -> Configure JFR
jfrDump -> Copies contents of a JFR recording to file. Either the name or the recording id must be specified.
jfrStart -> Starts a new JFR recording
jfrStop -> Stops a JFR recording
jfrView -> Display event data in predefined views

Now actually driving a full start → check → stop cycle — purely over JMX, invoking each operation with a String[] of the same arguments you'd type after jcmd <PID> JFR.start:

import javax.management.*;
import java.lang.management.ManagementFactory;

public class DiagCommandJfr {
  public static void main(String[] args) throws Exception {
    MBeanServer server = ManagementFactory.getPlatformMBeanServer();
    ObjectName name = new ObjectName("com.sun.management:type=DiagnosticCommand");

    String startResult = (String) server.invoke(name, "jfrStart",
        new Object[]{ new String[]{ "name=jmxdemo", "settings=profile", "filename=/tmp/jmx-triggered.jfr" } },
        new String[]{ String[].class.getName() });
    System.out.println("jfrStart -> " + startResult.trim());

    long x = 0;
    for (int i = 0; i < 100_000_000; i++) x += i;   // give the recording something to capture
    System.out.println("work done, x=" + x);

    String checkResult = (String) server.invoke(name, "jfrCheck",
        new Object[]{ (Object) null }, new String[]{ String[].class.getName() });
    System.out.println("jfrCheck -> " + checkResult.trim());

    String stopResult = (String) server.invoke(name, "jfrStop",
        new Object[]{ new String[]{ "name=jmxdemo" } },
        new String[]{ String[].class.getName() });
    System.out.println("jfrStop -> " + stopResult.trim());
  }
}
$ javac DiagCommandJfr.java
$ java -cp . DiagCommandJfr
Verified real output — every line below is a real String returned from an MBean operation call, and the recording it produced was then read back with jfr summary to confirm the file is genuine: 
jfrStart -> Started recording 1. No limit specified, using maxsize=250MB as default.
work done, x=4999999950000000
jfrCheck -> Recording 1: name=jmxdemo maxsize=250.0MB (running)
jfrStop -> Stopped recording "jmxdemo", 373.1 kB written to:
/tmp/jmx-triggered.jfr

Combine this with §5's remote connector and you can trigger the exact same sequence against a JVM on another host — the recipe production incident tooling actually uses: connect over JMX, call jfrDump to pull a snapshot without stopping anything, then read the resulting .jfr file with the jfr CLI or JMC, as covered in the JFR & Mission Control deep dive.

Two independent things are true at once here: JFR events themselves are not delivered over JMX (they're a separate, purpose-built binary format and streaming API — see JFR Event Streaming) — but JFR's control plane (start/stop/dump/configure) is fully reachable through JMX, because it rides on the same general-purpose DiagnosticCommand bridge every jcmd command uses.

9 · Cheat Sheet

JMX in one glance

  • History: JSR 3 (core API) + JSR 160 (remote) + JSR 174 (platform MXBeans), all bundled starting J2SE 5.0 (2004) — JMX itself predates that as a standalone spec app servers adopted on their own.
  • Zero-setup data: ManagementFactory.getMemoryMXBean(), getThreadMXBean(), getGarbageCollectorMXBeans(), etc. — no flags needed.
  • Custom MBean, three ways: Standard MBean (interface must be named <Class>MBean exactly), @MXBean (any interface name, richer type conversion), or DynamicMBean (attributes/operations decided at runtime, no convention at all) — register all three with MBeanServer.registerMBean(obj, ObjectName).
  • Descriptors: a name→value bag on an MBeanInfo, MBeanAttributeInfo, MBeanOperationInfo, or MBeanParameterInfo — not DynamicMBean-only: build one directly with new ImmutableDescriptor("field=value", ...), or attach one to a Standard MBean/ @MXBean via a custom @DescriptorKey-annotated annotation. Well-known fields include units, minValue/maxValue, defaultValue, since, deprecated.
  • Enable remotely: -Dcom.sun.management.jmxremote.port=... at launch, or jcmd <PID> ManagementAgent.start ... on an already-running JVM.
  • Connect remotely: JMXConnectorFactory.connect(new JMXServiceURL("service:jmx:rmi:///jndi/rmi://host:port/jmxrmi")).
  • Push, not poll: NotificationEmitter + addNotificationListener — MemoryMXBean's usage-threshold notifications are the built-in example.
  • JMX ↔ JFR: com.sun.management:type=DiagnosticCommand exposes every jcmd JFR.* command as an MBean operation (since Java 8) — start/check/dump/stop a recording with no shell access to the target host at all.
  • Tools: jconsole (bundled since Java 5), JDK Mission Control (modern successor, also does JFR).
