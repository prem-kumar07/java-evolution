Sealed classes & interfaces Final in Java 17

A sealed type declares exactly which classes may extend or implement it. That gives you a closed, known set of subtypes — the foundation for exhaustive pattern matching and for modelling "a value is one of a fixed set of shapes".

The problem it solves Before, a type was either final (no subtypes) or completely open (anyone, anywhere could subclass). There was no way to say "these three types and no others", so the compiler could never know a hierarchy was complete — every switch needed a default and could silently miss a newly added case at runtime. Sealed types close the hierarchy so the compiler can reason about it.

1 · What & why

Legacy — open hierarchy, compiler can't help
public abstract class Shape { }
// Any code anywhere can do:  class Blob extends Shape {}
// so every switch over Shape must have a default and
// can silently miss new subtypes → runtime surprises.
Sealed — the set is fixed and known
public sealed interface Shape
    permits Circle, Square, Rectangle { }

public record Circle(double r)              implements Shape { }
public record Square(double side)           implements Shape { }
public record Rectangle(double w, double h) implements Shape { }

2 · The three choices each subtype must make

Every permitted subtype must declare how its own hierarchy continues — this keeps the whole tree closed and intentional.

ModifierMeaning
finalLeaf — cannot be extended further.
sealedContinues the closed hierarchy with its own permits.
non-sealedDeliberately re-opens the type to unrestricted extension.

3 · Rules

  • Permitted subtypes must be accessible to the sealed type and, unless in the same source file, in the same module (same package for the unnamed module).
  • permits is optional if all subtypes live in the same file — the compiler infers the list: 
    sealed interface Expr { }              // permits inferred below
record Num(int v) implements Expr { }
record Add(Expr l, Expr r) implements Expr { }
  • Every permitted subtype must directly extend/implement the sealed type.
  • Records are implicitly final, so they slot into permits lists perfectly.
  • Enums work too — an enum with constant bodies is implicitly sealed (otherwise implicitly final), so it satisfies a sealed interface's requirement with no extra modifier, and mixes with record subtypes in the same hierarchy: 
    sealed interface Status permits Active, Suspended, Closed {}
enum Active     implements Status { INSTANCE }
enum Suspended  implements Status { INSTANCE }
record Closed(String reason) implements Status {}

String describe(Status s) {
  return switch (s) {                          // exhaustive — verified
    case Active a       -> "active";
    case Suspended sp    -> "suspended";
    case Closed(var why) -> "closed: " + why;
  };
}
Requires Java 21+ — Record deconstruction patterns in switch (JEP 440, final in Java 21). Sealed classes themselves are available since Java 17 (JEP 409), but deconstruction syntax inside switch requires Java 21.
Forget a modifier and the compiler tells you exactly what's missing — verified real error: 
sealed interface Shape permits Circle {}
class Circle implements Shape {}   // missing final/sealed/non-sealed

// Shape.java:2: error: sealed, non-sealed or final modifiers expected
//     class Circle implements Shape {}
//           ^

4 · The payoff: exhaustive switch

Because the compiler knows every subtype, a switch needs no default. Add a new subtype later and every non-exhaustive switch fails to compile — a compile-time to-do list instead of a production incident.

Legacy — default + runtime failure
double area(Shape s) {
  if (s instanceof Circle c)  return Math.PI*c.r()*c.r();
  if (s instanceof Square sq) return sq.side()*sq.side();
  // forgot Rectangle...
  throw new IllegalStateException("unknown shape");  // 💥 at runtime
}
Sealed — exhaustive, checked at compile time
double area(Shape s) {
  return switch (s) {                 // no default
    case Circle c    -> Math.PI * c.r() * c.r();
    case Square sq   -> sq.side() * sq.side();
    case Rectangle r -> r.w() * r.h();
  };
  // add a new Shape → this won't compile until you handle it
}

5 · Sealed + records = algebraic data types

The killer combination: model a closed set of cases as sealed records, then switch over them with destructuring. This is the modern, type-safe replacement for the Visitor pattern.

Legacy — Visitor pattern (lots of ceremony)
interface Node { <R> R accept(Visitor<R> v); }
interface Visitor<R> { R visitNum(Num n); R visitAdd(Add a); }
final class Num implements Node {
  final int v; Num(int v){this.v=v;}
  public <R> R accept(Visitor<R> v){ return v.visitNum(this); }
}
// ...Add, plus a Visitor impl per operation. Verbose.
Sealed records + switch
sealed interface Node permits Num, Add {}
record Num(int v)          implements Node {}
record Add(Node l, Node r) implements Node {}

int eval(Node n) {
  return switch (n) {
    case Num(int v)          -> v;
    case Add(Node l, Node r) -> eval(l) + eval(r);
  };
}

6 · Sealed vs enum vs abstract class

enumSealed hierarchyOpen abstract
Fixed set of…singleton constantstypes (each with its own data)nothing fixed
Per-case datasame shape for alldifferent fields per subtypefree
Exhaustive switchYesYesNo
Use whena small enumeration of valuesa closed set of variant shapesan extensible framework type
Think of a sealed hierarchy as an "enum of types": like an enum it's a closed set the compiler can exhaustively check, but each member can be a distinct record with its own fields.

7 · Pitfalls

PitfallReality
Subtype in another module/packageNot allowed unless same module (same package for unnamed module).
Forgetting each subtype needs a modifierEvery permitted subtype must be final, sealed, or non-sealed — the compiler enforces it.
Adding default "just in case"Kills the exhaustiveness safety net — omit it so new subtypes force a compile error.
Guards & exhaustivenessA when-guarded case doesn't count toward covering a subtype; keep an unguarded fallback for that type.
Public API sealingSealing a public type is an API contract — third parties can't extend it. Intended, but be deliberate.

Worked example — a typed Result instead of exceptions

Legacy — exceptions as control flow
User find(String id) {           // throws if missing
  User u = repo.get(id);
  if (u == null) throw new NotFoundException(id);
  return u;
}
try { use(find(id)); }
catch (NotFoundException e) { showError(e.getMessage()); }
Sealed Result — errors are values
sealed interface Result<T> permits Ok, Err {}
record Ok<T>(T value)     implements Result<T> {}
record Err<T>(String msg) implements Result<T> {}

Result<User> find(String id) {
  User u = repo.get(id);
  return u != null ? new Ok<>(u) : new Err<>("no user " + id);
}
switch (find(id)) {              // compiler enforces both cases
  case null -> throw new NullPointerException();
  case Ok<User>(var user) -> use(user);
  case Err<User>(var msg) -> showError(msg);
}

9 · Cheat sheet

Sealed classes in one glance

  • sealed interface X permits A, B { } — closed subtype set.
  • Each subtype is final, sealed, or non-sealed.
  • permits optional when subtypes share the file; same module/package otherwise.
  • Enables switch with no default + compile-time exhaustiveness.
  • Sealed + records + patterns = algebraic data types (replaces Visitor).
  • Great for Result types, state machines, ASTs, closed message sets.
