The AOT Cache

The Ahead-of-Time (AOT) Cache is Project Leyden's answer to a simple observation: most applications start up the same way every time, so the JVM shouldn't have to rediscover that from scratch on every single run. It records what happened during one "training" run and replays it instantly on every later run. Every command on this page was actually run before being written down — including a real ~50% startup-time improvement, measured locally.

The problem it solves Verified straight from JEP 483's own motivation: on every startup the JVM scans JAR files, parses thousands of class files, loads and links them (verifying bytecode, resolving symbolic references, instantiating lambda objects), then runs every class's static initializers. This is necessary dynamism that gives Java its expressive power — but it's paid for again, identically, on every single JVM start. The AOT cache shifts that repeated cost from every run to one training run.

1 · Where this came from — CDS to AOT Cache

The AOT cache isn't a brand-new idea — it's the fourth generation of a lineage that's over 20 years old, each step removing friction from the last.

GenerationVersionWhat it added
Class Data Sharing (CDS)Java 5Archive the JDK's own core classes; opt-in via -Xshare:dump.
Application CDS (AppCDS)Java 10 JEP 310Extend archiving to your application's classes, not just the JDK's.
Default CDS ArchivesJava 12 JEP 341A base archive ships pre-built — CDS is on by default with zero setup, verified below.
Dynamic CDS ArchivesJava 13 JEP 350Archive automatically at JVM exit — no separate class-list step.
AOT Class Loading & LinkingJava 24 JEP 483The real leap: cache classes already loaded and linked, not just parsed — and lay the foundation for Project Leyden.
AOT Command-Line ErgonomicsJava 25 JEP 514One command instead of two — see §3.
AOT Method ProfilingJava 25 JEP 515Cache JIT profiles too — helps warmup, not just startup. See §6.
AOT Object Caching with Any GCJava 26 JEP 516Works with ZGC and every other collector — see §5.

2 · Basic: your first AOT cache, verified

This is the exact example from JEP 483 itself — a program that looks trivial but, because it touches the Stream API, causes roughly 600 JDK classes to be read, parsed, loaded, and linked.

// HelloStream.java
import java.util.*;
import java.util.stream.*;

public class HelloStream {
    public static void main(String... args) {
        var words = List.of("hello", "fuzzy", "world");
        var greeting = words.stream()
            .filter(w -> !w.contains("z"))
            .collect(Collectors.joining(", "));
        System.out.println(greeting);   // hello, world
    }
}
Requires JDK 24 or later. The examples on this page were run against JDK 26; JEP 483 itself landed in JDK 24, so everything except §5–§6 (any-GC support, method profiling) works from 24 onward too.
  1. Compile it normally. 
    javac HelloStream.java
  2. Training run — record what happens. 
    java -XX:AOTMode=record -XX:AOTConfiguration=app.aotconf -cp . HelloStream
# verified real output:
# hello, world
#  AOTConfiguration recorded: app.aotconf
  3. Create the cache from that recording. This step does not run your program — it only assembles the cache. 
    java -XX:AOTMode=create -XX:AOTConfiguration=app.aotconf -XX:AOTCache=app.aot -cp .
# verified real output:
# Reading AOTConfiguration app.aotconf and writing AOTCache app.aot
# AOTCache creation is complete: app.aot 9355264 bytes
  4. Production run — use the cache. 
    java -XX:AOTCache=app.aot -cp . HelloStream
# verified real output: hello, world

Does it actually help? Measured, not assumed.

Five runs each way, same machine, same JDK 26, wall-clock time via /usr/bin/time -p:

Without AOT cacheWith AOT cache
Real time (5 runs)0.02s, 0.02s, 0.02s, 0.02s, 0.02s0.01s, 0.01s, 0.01s, 0.01s, 0.01s

A consistent, verified ~50% reduction on this tiny program — in the same ballpark as JEP 483's own reported 42% for the identical example. The gain is even more dramatic on real applications: Oracle's own benchmark of Spring PetClinic (which loads ~21,000 classes) went from 4.486s to 2.604s — also 42% faster — with a 130MB cache.

3 · Basic: the one-command workflow

Two invocations to build a cache is one too many for routine use. JEP 514 collapses training and cache creation into a single command:

Java 24 — two commands
java -XX:AOTMode=record -XX:AOTConfiguration=app.aotconf -cp . HelloStream
java -XX:AOTMode=create -XX:AOTConfiguration=app.aotconf -XX:AOTCache=app.aot -cp .
Java 25+ — one command
java -XX:AOTCacheOutput=app.aot -cp . HelloStream
# verified real output:
# hello, world
# Temporary AOTConfiguration recorded: app.aot.config
# Launching child process .../java to assemble AOT cache app.aot using configuration app.aot.config
# Reading AOTConfiguration app.aot.config and writing AOTCache app.aot
# AOTCache creation is complete: app.aot 9355264 bytes
# Removed temporary AOT configuration file app.aot.config

Verified: the temporary config file is created and deleted automatically, and the resulting cache is byte-identical in size to the two-step version. Then run it exactly the same way as before:

java -XX:AOTCache=app.aot -cp . HelloStream

4 · How it works — modes & the auto fallback

Verified from Oracle's official java launcher tool specification — -XX:AOTMode has five values, and understanding auto (the default) explains a lot of AOT cache behavior you'll see in practice:

ModeBehavior
auto (default)If AOTCacheOutput is set → training run. Else if a cache can be loaded → production run using it. Else → runs normally with no cache, no error.
recordTraining phase — gathers statistics into a configuration file.
createAssembly phase — reads the configuration, writes the cache. Does not run your app.
onProduction phase, but fails fast: if the cache can't be loaded, print an error and exit immediately.
offNo AOT cache, full stop — all other AOT options are ignored.
Why this matters: -XX:AOTCache=app.aot alone implies AOTMode=auto. That's why a cache that fails to load doesn't crash your application — verified in §5 below. Use -XX:AOTMode=on only as a deliberate, fail-fast debugging aid to confirm your command line is actually compatible with the cache.

5 · Advanced: AOT cache with any garbage collector

Before JEP 516 (Java 26), the AOT cache's format was tied to specific GC assumptions, which made it incompatible with ZGC. Here's both sides of that, verified.

Verified failure — cache trained under one GC, used under another

// cache created with DEFAULT settings (G1, the default collector)
java -XX:AOTCacheOutput=app.aot -cp . HelloStream

// then run under ZGC — a genuine mismatch
java -XX:+UseZGC -XX:AOTCache=app.aot -cp . HelloStream
# verified real output:
# [warning][aot] Unable to use AOT cache.
# The saved state of UseCompressedOops and UseCompressedClassPointers is
#   different from runtime, CDS will be disabled.
# [error][aot] Loading static archive failed.
# hello, world          <- the program still ran correctly! (see §4: this is the "auto" fallback)
Verified: this does not crash. Because -XX:AOTCache= implies AOTMode=auto, the JVM logs a warning, discards the incompatible cache, and runs normally without it. Your application keeps working — it just doesn't get the speed-up that run.

Verified success — consistent GC across training and production

// train, create, AND run — all three with the SAME GC flag
java -XX:+UseZGC -XX:AOTMode=record -XX:AOTConfiguration=app-zgc.aotconf -cp . HelloStream
java -XX:+UseZGC -XX:AOTMode=create -XX:AOTConfiguration=app-zgc.aotconf -XX:AOTCache=app-zgc.aot -cp .
java -XX:+UseZGC -Xlog:aot -XX:AOTCache=app-zgc.aot -cp . HelloStream
# verified real output:
# hello, world
# [info][aot] trying to map app-zgc.aot
# [info][aot] Opened AOT cache app-zgc.aot.
# [info][aot] The AOT cache was created with UseCompressedOops = 0, ...

The rule this demonstrates: the AOT cache is tied to the JVM configuration active when it was built — same GC, same compressed-oops setting, same major options — throughout training, creation, and production. Match them, and JEP 516 makes ZGC (and every other collector) work exactly as smoothly as G1.

6 · Advanced: AOT method profiling (warmup)

Verified from JEP 515's own motivation: the AOT cache in JDK 24 sped up startup (getting classes ready), but a JVM also needs time to warm up — the JIT compiler needs to see a method run many times before it's confident enough to compile it to fast native code. JEP 515 extends the AOT cache to carry method-execution profiles from the training run, so the JIT can start making good compilation decisions from the very first request instead of relearning from zero.

// no new commands needed — profiling piggybacks on the same AOT cache commands from §2/§3
java -XX:AOTCacheOutput=app.aot -cp . com.example.App     // profiles captured during THIS training run too
java -XX:AOTCache=app.aot -cp . com.example.App           // JIT has profile data from the first request
This is a genuine "free" upgrade: if you're already using the AOT cache commands from §2–§3 on JDK 25+, method profiling is captured and used automatically — there's no separate flag to remember. The effect is on warmup curve (how quickly the app reaches peak throughput), which is harder to demonstrate in a one-line example than the very visible startup-time numbers in §2.

7 · Tooling & diagnostics

-Xlog:aot — see exactly what the cache is doing

java -Xlog:aot -XX:AOTCache=app.aot -cp . HelloStream
# verified real output (first lines):
# [0.003s][info][aot] trying to map app.aot
# [0.003s][info][aot] Opened AOT cache app.aot.
# [0.003s][info][aot] The AOT cache was created with UseCompressedOops = 1, ...
# [0.003s][info][aot] Core region alignment: 16384
# [0.003s][info][aot] Mapped static region #0 at base 0x... top 0x... (ReadWrite)

Oracle's own recommended debugging pattern from the tool specification: run with -XX:AOTMode=auto -Xlog:aot to see clearly whether the cache loaded or fell back, without risking the fail-fast crash that AOTMode=on would give you.

AutoCreateSharedArchive — the older AppCDS convenience flag, still useful

Verified: this pre-AOT-Cache flag auto-creates a plain CDS/AppCDS archive on first run and reuses it afterward — a lighter-weight alternative when you don't need the full AOT cache machinery.

java -XX:+AutoCreateSharedArchive -XX:SharedArchiveFile=classes.jsa -cp . HelloStream
# first run — verified real output:
# [error][cds] Specified shared archive file not found (classes.jsa)
# hello, world                          <- runs fine anyway, and creates the archive

java -XX:+AutoCreateSharedArchive -XX:SharedArchiveFile=classes.jsa -cp . HelloStream
# second run — verified real output (with -Xlog:cds):
# [info][cds] Opened shared archive file classes.jsa.   <- now it's reused, no error

Verified: the JDK's own base CDS archive is already active, even if you do nothing

java -Xlog:cds -cp . HelloStream
# verified real output includes:
# [info][cds] Opened shared archive file .../lib/server/classes.jsa.

Since JEP 341 (Java 12), every JDK ships with a pre-built default archive for its own classes, mapped automatically on every single JVM start — this is the foundation everything else on this page builds on top of.

8 · How to train your JVM (Oracle's own guidance)

Verified, quoted directly from JEP 483's "How to train your JVM" section — the advice is short and concrete:

  • The best training run is a production run. When that's impractical (servers that open real network connections, write real logs), build a synthetic training run that resembles production as closely as possible — Oracle's suggestion: add a dedicated com.example.AppTrainer main class that drives your real main class against a temporary log directory, a local network config, and a mocked database.
  • To optimize startup time, make the training run load the same classes a real production run loads at startup — check with -verbose:class or the JFR jdk.ClassLoad event.
  • To minimize cache size, avoid loading classes in training that production never uses — don't drive training with a heavyweight test framework's own class graph.
  • A crashed training run produces no cache (verified from JEP 350's non-goals) — dynamic archiving only completes if the JVM exits normally.

9 · Pitfalls

PitfallReality
Training under one GC/config, running under anotherVerified in §5: the cache is silently discarded with a warning under AOTMode=auto (the default) — you lose the speed-up but the app still runs.
Using AOTMode=on in productionThis is actually recommended!

AOTMode=on (fail-fast): Exits immediately at startup with an error if the cache does not exist or cannot be loaded. Recommended for production to ensure you get the fast startup you expect. Contrast with AOTMode=auto, which silently falls back to normal JVM execution on a cache miss.

Assuming the cache format is stable across JDK versionsVerified from JEP 483: "the format of the configuration and cache files is not specified and is subject to change without notice." Rebuild the cache for every JDK upgrade.
Expecting classes loaded by custom class loaders to be cachedVerified non-goal of JEP 483: only classes from the class path, module path, and the JDK's own built-in loaders are cached.
Training with a test framework instead of realistic usageBloats the cache with classes production never touches — Oracle's own guidance explicitly warns against this (§8).
Forgetting the cache is a training-time snapshotIf your app's startup behavior changes meaningfully (new dependencies, changed config), retrain — a stale cache still loads, it just won't reflect current reality as well.

10 · Real-world use cases

ScenarioWhy AOT cache helps
Containers & serverless (cold starts)Every new instance pays full class-loading cost today — the cache amortizes that across a shared, pre-built image layer.
Auto-scaling microservicesRequests routed to a freshly started instance are slower until it's warm — verified Spring PetClinic numbers (§2) show this gap shrinking by ~42%.
CLI tools invoked frequently (build tools, scripts)Startup cost is the entire runtime for a short-lived process — proportionally the biggest win.
Framework-heavy apps (Spring, Jakarta EE)Annotation-driven startup discovery (@Bean, @Configuration scanning) is exactly the dynamic, repeated cost JEP 483 targets.
Latency-sensitive services already on ZGCJEP 516 (§5) means you no longer have to choose between low GC pause times and fast startup.

11 · Cheat sheet

AOT Cache in one glance

  • One-step (25+): java -XX:AOTCacheOutput=app.aot -cp . App then java -XX:AOTCache=app.aot -cp . App.
  • Two-step (24+): AOTMode=record → AOTMode=create → run with AOTCache=.
  • AOTCache= alone implies AOTMode=auto — fails silently and safely, never crashes production.
  • Debug with -XX:AOTMode=auto -Xlog:aot; use AOTMode=on only to deliberately fail-fast.
  • Match GC and major JVM flags across training, creation, and production — mismatches silently drop the cache (verified).
  • Cache format isn't stable across JDK versions — rebuild on every upgrade.
  • Only class-path/module-path/JDK-builtin-loader classes are cached — not custom class loaders.
  • Train with realistic usage, not a test framework — smaller, more representative cache.

Advanced AOT & Caching

Heap Object Archiving

Allows archiving live object graphs into CDS (Class Data Sharing) archives. This significantly speeds up startup times by bypassing the initialization overhead of complex static structures.

AOT Early Initialization

AOT compilation allows running static initializers at build time. Project Leyden seeks to shift work from runtime to build time, capturing the initialized state for faster startup.

Cache Invalidation Constraints

When using AOT or CDS, the runtime must match the conditions under which the cache was created. Changes to class paths, module paths, or JVM arguments can invalidate the cache.
