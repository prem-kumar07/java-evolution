A Gatherer is a custom intermediate stream operation — the long-missing counterpart to a custom Collector. Where collect ends a stream, gather transforms it mid-pipeline: windowing, running totals, dedup-by-key, bounded-concurrency mapping and more.

The problem it solves Streams shipped with a fixed set of intermediate ops (map, filter, limit…). Anything stateful across elements — sliding windows, running averages, "stop after N distinct", batching — meant leaving the stream for manual loops. Collector let you customise the end; Gatherer finally lets you customise the middle.

1 · Gatherer vs Collector — where each one sits

A stream pipeline is source → zero or more intermediate ops → one terminal op. map/filter/gather are all intermediate — the stream stays lazy and un-consumed. collect/toList/forEach are terminal — that's what actually pulls elements through and produces a result.

CollectorGatherer
Position in pipelineTerminal (ends the stream)Intermediate (stream stays open)
CardinalityMany elements → 1 resultMany elements → many elements (0..N per input)
Composable furtherNo — the stream is consumedYes — map, filter, another gather, then collect
Built-in factoryCollectors.*Gatherers.*
Custom factoryCollector.of(...)Gatherer.ofSequential(...) / Gatherer.of(...)

2 · The 5 built-in gatherers, in detail

java.util.stream.Gatherers ships five ready-made gatherers. Each is a small, precise tool — know their edge cases and you rarely need a custom one.

2.1 · windowFixed(n) — non-overlapping batches

Behaviour: groups elements into consecutive, non-overlapping chunks of size n. The last window may be shorter if the stream doesn't divide evenly — nothing is dropped.

Stream.of(1,2,3,4,5,6,7,8).gather(Gatherers.windowFixed(3)).toList();
// [[1, 2, 3], [4, 5, 6], [7, 8]]     ← last window has only 2 elements
Memory note: for efficiency, windows may be allocated eagerly, so very large window sizes on huge streams can use significant memory — size windows for your data, not "big for safety".

2.2 · windowSliding(n) — overlapping windows

Behaviour: a moving window of size n that advances one element at a time — every window after the first shares n-1 elements with its predecessor.

Stream.of(1,2,3,4).gather(Gatherers.windowSliding(2)).toList();
// [[1, 2], [2, 3], [3, 4]]     ← 3 windows from 4 elements (n - windowSize + 1)

2.3 · scan(seed, accumulator) — running (prefix) accumulation

Behaviour: starts from a seed value, then for each input element applies the accumulator to (current value, element) and emits the new running value — one output per input, the seed itself is never emitted separately.

Stream.of(1,2,3,4).gather(Gatherers.scan(() -> 0, Integer::sum)).toList();
// [1, 3, 6, 10]      ← running sum after consuming each element
Stream.of(1,2,3).gather(Gatherers.scan(() -> "", (acc, n) -> acc + n)).toList();
// ["1", "12", "123"]  ← running string concatenation

2.4 · fold(seed, folder) — reduce to exactly one element

Behaviour: like scan, but only the final accumulated value is emitted — always exactly one output element, unlike a plain reduce this works even when the operation is inherently order-dependent (no combiner needed).

Optional<String> result = Stream.of(1,2,3,4,5,6,7,8,9)
    .gather(Gatherers.fold(() -> "", (acc, n) -> acc + n))
    .findFirst();
// Optional["123456789"]

fold vs reduce: fold emits exactly one final element after the entire stream is consumed, and supports an arbitrary accumulator type R that differs from the element type T. Stream.reduce() returns an Optional and requires the accumulated type to match the element type. Use fold when you need type transformation during accumulation.

2.5 · mapConcurrent(n, mapper) — bounded concurrent mapping

Behaviour: maps up to n elements concurrently (backed by virtual threads), while still emitting results in original encounter order. Full breakdown → §6.

var bodies = urls.stream()
    .gather(Gatherers.mapConcurrent(10, this::fetch))
    .toList();   // ≤10 in flight, order preserved

Implementation note: mapConcurrent(n, fn) internally runs tasks on virtual threads, bounded by a semaphore of size n. It reorders outputs to match input encounter order regardless of task completion order, making it safe and deterministic for I/O-bound operations.

Before & after — replacing a manual windowing loop

Legacy — manual index loop, breaks the pipeline
List<List<Integer>> windows = new ArrayList<>();
for (int i = 0; i + 3 <= xs.size(); i++) {
  windows.add(List.copyOf(xs.subList(i, i + 3)));
}
Gatherer — stays lazy & composable
var windows = xs.stream()
    .gather(Gatherers.windowSliding(3))
    .toList();

3 · Anatomy of a gatherer

A gatherer has up to four parts. Only the integrator is required.

4 · Writing your own

4.1 · "Distinct by key"

Legacy — stateful lambda hack (fragile)
Set<String> seen = ConcurrentHashMap.newKeySet();
var out = people.stream()
    .filter(p -> seen.add(p.city()))   // side-effecting filter 😬
    .toList();
Reusable gatherer
static <T,K> Gatherer<T,?,T> distinctBy(Function<T,K> key) {
  return Gatherer.ofSequential(
    HashSet::new,                             // initializer
    (seen, item, downstream) -> {             // integrator
      if (seen.add(key.apply(item)))
        return downstream.push(item);         // emit first per key
      return true;                            // true = keep going
    });
}
var out = people.stream().gather(distinctBy(Person::city)).toList();

Returning false from the integrator short-circuits the upstream — that's how a gatherer can implement limit-like behaviour.

4.2 · "Group consecutive equal elements" (run-length grouping)

A gatherer that tracks the previous element to decide whether to start a new group — something Collectors.groupingBy can't express, because it groups by key across the whole stream, not by adjacency.

static <T> Gatherer<T,?,List<T>> groupRuns() {
  return Gatherer.<T, List<T>, List<T>>ofSequential(
    ArrayList::new,                                    // initializer: current run
    (run, item, downstream) -> {                       // integrator
      if (!run.isEmpty() && !run.get(run.size() - 1).equals(item)) {
        if (!downstream.push(List.copyOf(run))) return false;
        run.clear();
      }
      run.add(item);
      return true;
    },
    (run, downstream) -> {                              // finisher: flush the last run
      if (!run.isEmpty()) downstream.push(List.copyOf(run));
    });
}

Stream.of("A","A","B","B","B","A","C")
    .gather(groupRuns())
    .toList();
// [[A, A], [B, B, B], [A], [C]]
Why this needed a finisher: the very last run is still sitting in state when the stream runs out of elements — only the finisher gets a chance to flush it.

5 · Composing gatherers with andThen

Gatherers chain like any intermediate operation — either by calling .gather() twice, or by fusing two gatherers into one reusable unit with andThen.

Two separate .gather()/.map() steps, repeated everywhere
var result = readings.stream()
    .gather(Gatherers.windowFixed(3))     // batch into 3s
    .map(GathererCompose::average)        // average each batch
    .toList();
// every pipeline that needs this has to repeat both lines
Fused into one named, reusable Gatherer
// turn a plain mapping function into a (stateless) Gatherer
static <T, R> Gatherer<T, ?, R> mapping(Function<T, R> f) {
  return Gatherer.ofSequential((state, element, downstream) -> downstream.push(f.apply(element)));
}

// fuse "batch into 3s" + "average each batch" into one Gatherer
Gatherer<Reading, ?, Double> batchAverage =
    Gatherers.<Reading>windowFixed(3).andThen(mapping(GathererCompose::average));

var result = readings.stream().gather(batchAverage).toList();
// readings 1..7  →  [2.0, 5.0, 7.0]

andThen is most valuable when you want to name and reuse a multi-step transformation (e.g. "batch, then average, then rate-limit") across several pipelines, instead of repeating the same chain of .gather().map() calls everywhere.

6 · mapConcurrent deep dive

Backed by virtual threads, it runs up to N mappings at once and preserves encounter order — ideal for concurrent I/O without managing a thread pool.

Legacy — executor + futures + ordering
var pool = Executors.newFixedThreadPool(10);
var futures = urls.stream()
    .map(u -> pool.submit(() -> fetch(u)))
    .toList();
var bodies = futures.stream().map(f -> get(f)).toList();
pool.shutdown();
Gatherer
var bodies = urls.stream()
    .gather(Gatherers.mapConcurrent(10, this::fetch))
    .toList();   // ≤10 in flight, order preserved
It's for I/O, not CPU. Because each mapping runs on a virtual thread, mapConcurrent only helps when fetch spends most of its time blocked (network, disk, DB). CPU-bound mappers gain nothing and just add overhead.

8 · Pitfalls

PitfallReality
Adding a combiner that doesn't merge correctlyBreaks parallel streams — use Gatherer.ofSequential(...) if state isn't mergeable.
Expecting eager executionGatherers are intermediate & lazy — nothing runs until a terminal op.
Huge windows on huge streamsWindows may be allocated eagerly — mind memory on large window sizes.
Overusing mapConcurrent for CPU workIt's for I/O; CPU-bound work won't speed up.
Side-effecting filter for dedupWorks but is fragile/unclear — a gatherer states intent.
Forgetting a finisher for "flush what's left"State still held when the stream ends is lost unless the finisher pushes it (see run-length example).
Confusing scan and foldscan emits one output per input (running values); fold emits exactly one output total.

Worked example — batch records for a bulk insert

Legacy — manual batching loop
List<Record> batch = new ArrayList<>(500);
for (Record r : records) {
  batch.add(r);
  if (batch.size() == 500) { repo.insertAll(batch); batch.clear(); }
}
if (!batch.isEmpty()) repo.insertAll(batch);   // don't forget the tail!
windowFixed
records.stream()
    .gather(Gatherers.windowFixed(500))
    .forEach(repo::insertAll);   // tail handled automatically

10 · Cheat sheet

Gatherers in one glance

  • Built-ins: windowFixed(n), windowSliding(n), scan(seed, fn), fold(seed, fn), mapConcurrent(n, fn).
  • windowFixed: last window may be short. scan: one output per input. fold: exactly one output, total.
  • Custom: Gatherer.ofSequential(init, integrator[, finisher]).
  • Integrator return false to short-circuit; use a finisher to flush leftover state.
  • Chain with .andThen(...) to name & reuse a multi-step transform.
  • Intermediate & lazy; add a combiner only for safe parallel merges.
  • mapConcurrent(n, fn) = bounded concurrent I/O, order preserved — not for CPU work.
