The Stream API Java 8

A Stream is a pipeline of operations over a sequence of data — you declare what to do (filter, transform, aggregate) instead of writing the loop yourself. Every example on this page is written to be pasted into a file and run as-is.

lazynothing runs until a terminal op
1xuse — a stream can't be replayed
.parallel()one word for multi-core
20+built-in Collectors
Java 8(2014) — the biggest API since generics
The problem it solves Filtering, transforming and aggregating collections used to mean a mutable accumulator and a hand-written for loop every single time — correct but repetitive, and impossible to parallelise without rewriting it with threads. Streams let you describe the transformation declaratively; the same pipeline runs sequentially or across every CPU core by adding .parallel().

1 · Mental model & creating streams

A pipeline is always source → zero or more intermediate ops → one terminal op. Intermediate ops (map, filter...) are lazy — they just describe the pipeline. Nothing executes until a terminal op (collect, forEach, reduce...) pulls elements through it.

Creating a stream — every common source

Legacy — manual loops per source
List<String> out = new ArrayList<>();
for (String s : list) out.add(s.toUpperCase());

int[] arr = {1, 2, 3};
int sum = 0;
for (int x : arr) sum += x;

List<String> lines = new ArrayList<>();
try (var r = Files.newBufferedReader(path)) {
  String line;
  while ((line = r.readLine()) != null) lines.add(line);
}
Streams — one shape for every source
list.stream();                       // from a Collection
Stream.of("a", "b", "c");             // from varargs
Arrays.stream(new int[]{1, 2, 3});    // from an array -> IntStream
Stream.generate(Math::random);        // infinite; must limit()
Stream.iterate(1, n -> n * 2);         // infinite; must limit() or use bounded form
IntStream.range(0, 10);                // 0..9
IntStream.rangeClosed(1, 10);          // 1..10
Files.lines(path);                     // lazy, one line per element (try-with-resources!)
map.entrySet().stream();               // from a Map
A stream can only be consumed once. Calling a terminal operation twice on the same stream throws IllegalStateException. Re-create it from the source (or wrap creation in a Supplier<Stream<T>>) if you need to run the pipeline again.

2 · Intermediate operations

Each returns a new stream, so they chain. All are lazy.

OperationDoes
map(Function)Transform each element 1-to-1.
filter(Predicate)Keep elements matching a condition.
flatMap(Function)Transform each element into a stream, then flatten (1-to-many).
distinct()Remove duplicates (via equals).
sorted() / sorted(Comparator)Sort (natural order, or custom).
peek(Consumer)Look at elements without changing the stream — debugging only.
limit(n) / skip(n)Truncate, or drop the first n.
takeWhile / dropWhile 9Leading-run slicing by predicate.
Legacy — nested loop for flatten + filter + sort
List<String> result = new ArrayList<>();
for (List<String> group : groups) {
  for (String s : group) {
    if (s.length() > 3) result.add(s.toUpperCase());
  }
}
Collections.sort(result);
result = new ArrayList<>(new LinkedHashSet<>(result));  // dedupe, keep order
Streams — one readable chain
List<String> result = groups.stream()
    .flatMap(List::stream)
    .filter(s -> s.length() > 3)
    .map(String::toUpperCase)
    .distinct()
    .sorted()
    .toList();

Multi-key sorting with Comparator chaining

Sorting by more than one field is where Comparator's static/default methods (comparing, thenComparing, reversed) pay off — no manual compareTo chains.

Legacy — hand-written compareTo chain
emps.sort((a, b) -> {
  int byDept = a.dept().compareTo(b.dept());
  if (byDept != 0) return byDept;
  return Double.compare(b.salary(), a.salary());   // descending
});
Comparator chaining
var sorted = emps.stream()
    .sorted(Comparator.comparing(Employee::dept)
        .thenComparing(Comparator.comparing(Employee::salary).reversed()))
    .map(Employee::name)
    .toList();
// verified: dept ascending, then salary descending within each dept

3 · Terminal operations

Exactly one per pipeline — it triggers execution and produces a result (or a side effect).

OperationReturns
forEach(Consumer)void — a side effect per element.
collect(Collector)Whatever the collector builds (List, Map, String…).
reduce(...)A single aggregated value.
count()long — element count.
anyMatch/allMatch/noneMatch(Predicate)boolean, short-circuits.
findFirst() / findAny()Optional<T>, short-circuits.
min/max(Comparator)Optional<T>.
toArray()Object[] or typed array.
toList() 16Unmodifiable List<T> — shorthand for collect(toList()).
boolean anyExpensive = orders.stream().anyMatch(o -> o.total() > 1000);   // stops at first match
Optional<Order> first = orders.stream().filter(o -> o.total() > 1000).findFirst();
long count = orders.stream().filter(Order::isPaid).count();

4 · reduce() — identity, accumulator, combiner

reduce is the most general terminal operation — it folds a stream down to one value. It comes in three overloads, and the difference between them is exactly the part most people find confusing: what happens to the combiner in parallel.

4.1 · One-arg — no identity, returns Optional

Optional<Integer> max = Stream.of(3, 1, 4, 1, 5).reduce(Integer::max);
// empty stream -> Optional.empty() (no identity to fall back on)

4.2 · Two-arg — identity + accumulator, same type

Legacy — manual loop
int sum = 0;
for (int n : numbers) sum += n;
reduce(identity, accumulator)
int sum = numbers.stream().reduce(0, Integer::sum);
// identity = 0 (returned for an empty stream, and the starting value)
// accumulator = (partial, next) -> partial + next

4.3 · Three-arg — identity + accumulator + combiner, different types

Use this when the accumulated type (U) differs from the element type (T) — e.g. reducing a stream of Strings down to a total int length. This is the only form that lets U != T, and it's the one that makes parallel execution correct.

List<String> words = List.of("foo", "bars", "bazzz");   // lengths: 3, 4, 5

int totalLen = words.stream().reduce(
    0,                                    // identity: U (int)
    (partial, word) -> partial + word.length(),   // accumulator: (U, T) -> U
    Integer::sum                          // combiner: (U, U) -> U
);
// totalLen == 12

Why the combiner exists — sequential vs parallel

Common mistake: writing a 3-arg reduce where the combiner doesn't correctly represent "merge two partial results of the accumulation" — e.g. a combiner with side effects, or one that isn't associative. It'll work by luck sequentially and produce wrong answers only when run in parallel.

5 · Collectors, in depth

Collectors is a factory of ready-made terminal strategies for collect(...) — from a plain list to a fully grouped, aggregated report.

5.1 · The basics — toList, toSet, toMap, joining

Legacy
List<String> names = new ArrayList<>();
for (Employee e : emps) names.add(e.name());
StringBuilder sb = new StringBuilder();
for (int i = 0; i < names.size(); i++) {
  sb.append(names.get(i));
  if (i < names.size() - 1) sb.append(", ");
}
Collectors
List<String> names = emps.stream().map(Employee::name).toList();
String csv = emps.stream().map(Employee::name).collect(joining(", "));
String csv2 = emps.stream().map(Employee::name).collect(joining(", ", "[", "]"));  // "[Ada, Bob]"

Map<String, Double> salaryByName = emps.stream()
    .collect(toMap(Employee::name, Employee::salary));
// duplicate keys THROW by default — see 5.2 for the fix

5.2 · toMap with a merge function — handling duplicate keys

// two employees could share a department; keep the HIGHEST salary per dept
Map<String, Double> maxSalaryByDept = emps.stream()
    .collect(toMap(Employee::dept, Employee::salary, Double::max));
// toMap(keyFn, valueFn, mergeFn) — mergeFn resolves collisions instead of throwing

5.3 · groupingBy — the workhorse

Groups elements by a classifier function. Pair it with a downstream collector to do more than just collect the raw group into a list.

// simplest form: group into List per dept
Map<String, List<Employee>> byDept = emps.stream()
    .collect(groupingBy(Employee::dept));

// + downstream collector: average salary per dept, instead of the raw list
Map<String, Double> avgByDept = emps.stream()
    .collect(groupingBy(Employee::dept, averagingDouble(Employee::salary)));

// + a Map supplier: sorted keys via TreeMap instead of HashMap
Map<String, Double> avgByDeptSorted = emps.stream()
    .collect(groupingBy(Employee::dept, TreeMap::new, averagingDouble(Employee::salary)));

// nesting groupingBy inside groupingBy: dept -> salary-bucket -> names
Map<String, Map<Boolean, List<String>>> nested = emps.stream()
    .collect(groupingBy(Employee::dept,
             groupingBy(e -> e.salary() > 70_000,
             mapping(Employee::name, toList()))));
// verified: {Sales={false=[Cy, Dee]}, Eng={true=[Ada, Bob]}}
// the downstream collector of one groupingBy can be another groupingBy —
// this is how you build a two-level report in a single pass

5.4 · partitioningBy — grouping by true/false

Map<Boolean, List<Employee>> highLow = emps.stream()
    .collect(partitioningBy(e -> e.salary() > 80_000));
List<Employee> highEarners = highLow.get(true);
// always has BOTH keys present, even if one group is empty

5.5 · Numeric downstream collectors

long total   = emps.stream().collect(counting());                          // same as .count()
double sum   = emps.stream().collect(summingDouble(Employee::salary));
double avg   = emps.stream().collect(averagingDouble(Employee::salary));
DoubleSummaryStatistics stats = emps.stream()
    .collect(summarizingDouble(Employee::salary));
// stats.getMin() / getMax() / getAverage() / getSum() / getCount() — all in one pass

5.6 · teeing — two collectors, one pass 12

Why it matters: without teeing, computing "sum AND count" in one pass meant either two separate stream traversals or a hand-rolled combined accumulator.

Legacy — two passes over the stream
double sum = emps.stream().mapToDouble(Employee::salary).sum();
long count = emps.stream().count();
String stats = "sum=" + sum + " count=" + count;
teeing — one pass
String stats = emps.stream().collect(teeing(
    summingDouble(Employee::salary),
    counting(),
    (sum, count) -> "sum=" + sum + " count=" + count));
// "sum=425000.0 count=5"

6 · Writing a custom Collector

A Collector<T, A, R> has the same four moving parts as a Gatherer, but they build a single final result instead of emitting elements downstream.

Legacy — build a joined string by hand
StringJoiner sj = new StringJoiner(", ", "[", "]");
for (Employee e : emps) sj.add(e.name());
String joined = sj.toString();
// works, but isn't a reusable, composable Collector
Custom Collector.of — reusable & composable
Collector<Employee, StringJoiner, String> joinNames = Collector.of(
    () -> new StringJoiner(", ", "[", "]"),   // supplier
    (sj, e) -> sj.add(e.name()),              // accumulator
    StringJoiner::merge,                      // combiner (parallel streams)
    StringJoiner::toString);                  // finisher

String joined = emps.stream().collect(joinNames);
// "[Ada, Bob, Cy, Dee, Eve]" — and joinNames can be reused anywhere

StringJoiner already has a merge method built for exactly this purpose — a nice illustration of how the combiner should genuinely represent "merge two partial containers".

7 · Primitive streams — avoiding boxing

IntStream, LongStream, DoubleStream avoid boxing every element into an Integer/Long/Double — faster, and come with numeric-only operations like sum() and summaryStatistics().

Legacy — boxed, manual sum
List<Integer> nums = List.of(1, 2, 3, 4, 5);
int sum = 0;
for (int n : nums) sum += n;   // unboxing on every read
IntStream — unboxed, built-in sum
int sum = IntStream.rangeClosed(1, 5).sum();
IntSummaryStatistics stats = emps.stream()
    .mapToInt(e -> (int) e.salary())
    .summaryStatistics();
// stats.getMin() / getMax() / getAverage() — no manual loop
Stream<Integer> boxedAgain = IntStream.range(0, 5).boxed();   // back to Integer if needed

Convert with mapToInt/mapToLong/mapToDouble (object → primitive) and .boxed() (primitive → object).

8 · Parallel streams

Adding .parallel() splits the source (via its Spliterator) into chunks, processes them concurrently on the shared common ForkJoinPool, and merges results with each collector/reducer's combiner.

Sequential
long count = hugeList.stream()
    .filter(Item::isExpensive)
    .count();
Parallel — one word
long count = hugeList.parallelStream()   // or .stream().parallel()
    .filter(Item::isExpensive)
    .count();

When it actually helps

HelpsDoesn't help / hurts
Large data sets (roughly 10,000+ elements)Small collections — splitting overhead exceeds the work
CPU-bound work per elementI/O-bound work (use virtual threads or Gatherers.mapConcurrent instead)
Easily splittable sources: arrays, ArrayList, IntStream.rangePoorly splittable sources: LinkedList, Iterator-based streams
Stateless, associative operationsOrder-sensitive or stateful operations (see pitfalls)

Verified pitfall — shared mutable state is not thread-safe

This is the #1 real bug with parallel streams: calling a non-thread-safe collection's add from inside forEach.

Broken — throws or silently corrupts
List<Integer> unsafe = new ArrayList<>();
IntStream.range(0, 100_000).parallel().forEach(unsafe::add);
// multiple threads call ArrayList.add() concurrently —
// on a real run this throws ArrayIndexOutOfBoundsException
// (verified: reproduces on the very first attempt)
Correct — let collect() do the merging
List<Integer> safe = IntStream.range(0, 100_000).parallel()
    .boxed()
    .collect(Collectors.toList());
// each chunk accumulates independently; the Collector's
// combiner merges them safely — no shared mutable state
Rule of thumb: never mutate a shared collection from inside a parallel stream. Always finish with collect(...) or reduce(...) and let the combiner do the merging.

Custom thread pool (advanced, use sparingly)

Parallel streams always use the shared common ForkJoinPool — sized to your CPU count and shared with everything else in the JVM that uses it. To isolate a parallel stream in its own pool (e.g. to avoid starving other parallel work), submit the whole pipeline as a task:

ForkJoinPool customPool = new ForkJoinPool(4);
long result = customPool.submit(() ->
    hugeList.parallelStream().filter(Item::isExpensive).count()
).get();
customPool.shutdown();

9 · Putting it all together — a sales report

A single pipeline combining groupingBy, a downstream collector, sorting, and a LinkedHashMap to preserve that order — the kind of thing Stream API replaces a whole page of manual code for.

record Sale(String region, String product, double amount) {}

List<Sale> sales = List.of(
    new Sale("West", "Widget", 120),
    new Sale("East", "Gadget", 300),
    new Sale("West", "Gadget", 80),
    new Sale("East", "Widget", 200),
    new Sale("West", "Widget", 60)
);

// total sales per region, sorted by total descending
Map<String, Double> totalsByRegionSorted = sales.stream()
    .collect(groupingBy(Sale::region, summingDouble(Sale::amount)))
    .entrySet().stream()
    .sorted(Map.Entry.<String, Double>comparingByValue().reversed())
    .collect(toMap(Map.Entry::getKey, Map.Entry::getValue,
             (a, b) -> a, LinkedHashMap::new));   // (a,b)->a: unused, keys are unique here

System.out.println(totalsByRegionSorted);
// {East=500.0, West=260.0}   — sorted descending by total, order preserved by LinkedHashMap

10 · Pitfalls

PitfallReality
Reusing a consumed streamThrows IllegalStateException — streams are one-shot; re-create from the source.
Mutating shared state inside forEach/mapNot thread-safe under .parallel() — verified to throw/corrupt (see §8).
Using peek for side effects/logicMeant for debugging only — its execution isn't guaranteed the way you'd expect on a lazy pipeline.
Assuming .parallel() is always fasterOverhead can exceed the win on small collections or I/O-bound work.
A non-associative 3-arg reduce combinerWorks sequentially, gives wrong answers in parallel — see §4.
Infinite streams without limit()Stream.generate/iterate never terminate unless bounded.
toMap with duplicate keys, no merge functionThrows IllegalStateException at the colliding key — always pass a merge function if duplicates are possible.

12 · Cheat sheet

Stream API in one glance

  • Pipeline: source → map/filter/flatMap/sorted/distinct → collect/reduce/forEach.
  • reduce(id, acc) — same type. reduce(id, acc, combiner) — different type, and what makes parallel correct.
  • groupingBy(fn, downstream) and partitioningBy(pred) for reports.
  • toMap(k, v, mergeFn) — always pass a merge function if keys can collide.
  • Custom collector: Collector.of(supplier, accumulator, combiner, finisher).
  • Primitive streams (IntStream...) avoid boxing; .summaryStatistics() gets min/max/avg/sum/count in one pass.
  • .parallel() for large, CPU-bound, easily-splittable work — never mutate shared state inside it.
  • A stream is one-shot — re-create it from the source to run again.
Beyond Java 8: the core API above hasn't changed shape since Java 8 — only additions. takeWhile/dropWhile (9), toList()/ mapMulti (16), and teeing (12) are covered above. For custom intermediate operations (the missing piece Collectors couldn't do), see Stream Gatherers (final in 24).
