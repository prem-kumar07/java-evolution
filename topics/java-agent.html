Java Agents & the Instrumentation API Java 5

A Java agent is ordinary Java code the JVM runs before — or, for a dynamic agent, during — your application, with one extra superpower: a live handle on the JVM's own class-loading pipeline. Through java.lang.instrument.Instrumentation, an agent can inspect every loaded class, rewrite a class's bytecode as it loads, or even swap the bytecode of a class that's already running — all without touching a single line of the application's source. This is the mechanism underneath every APM tool, every code-coverage tool, every mocking framework, and every JVM profiler that claims "zero code changes required."

The problem it solves Before java.lang.instrument, adding profiling, tracing, or mocking behavior to code you didn't own meant one of two bad options: hand-edit or subclass everything you wanted to observe, or ship a native (JVMTI/JVMPI) agent written in C. JSR 163 gave the JVM a standard, pure-Java hook into class loading itself — any jar can declare itself an agent, ask to see (and rewrite) the bytecode of every class as it loads, and the JDK's own -javaagent flag wires it up with no native code, no build-tool integration, and no changes to the target application at all.

1 · What a Java Agent Is, and Why It Exists

JSR 163 added the whole mechanism in Java 5: the java.lang.instrument package, the -javaagent launch flag, and a new manifest attribute JAR files can carry. An "agent" is just a plain class with a specially-named static method — no interface to implement, no special base class. What makes it an agent is entirely how it's declared (a manifest attribute) and how it's launched (a JVM flag, or a dynamic attach).

Two independent axes define every agent:

AxisOptions
When it attachesStatic — bundled via -javaagent at JVM launch, runs premain() before main() even starts. Dynamic — attached to an already-running JVM from another process, runs agentmain() mid-execution.
What it does once attachedRegisters a ClassFileTransformer to rewrite bytecode as classes load, calls retransformClasses/redefineClasses to rewrite classes that are already loaded, or simply reads JVM state (getAllLoadedClasses, getObjectSize) without changing anything.
Every example on this page was compiled and actually run against a real JDK 25 install (Temurin 25.0.4) — including the exact warning text JDK 21+ prints for dynamic agent loading, and a genuine two-process dynamic-attach scenario. Nothing here is quoted from memory.

2 · Static Agents — premain() and -javaagent

A static agent is just a class with a premain method, packaged as a JAR whose manifest names that class. The JDK looks for the two-argument form first, and falls back to the one-argument form if that's all the class defines — both verified below:

SignatureWhen used
public static void premain(String agentArgs, Instrumentation inst) Preferred — the JDK looks for this first. Gives the agent the Instrumentation handle it needs to actually transform bytecode.
public static void premain(String agentArgs) Fallback, tried only if the two-argument form isn't found. Useful for an agent that only reads agentArgs and never touches bytecode — a JSR 163 holdover from before Instrumentation existed as a concept.
// BasicAgent.java
import java.lang.instrument.Instrumentation;

public class BasicAgent {
  public static void premain(String agentArgs, Instrumentation inst) {
    System.out.println("premain called, agentArgs=" + agentArgs);
    System.out.println("isRetransformClassesSupported=" + inst.isRetransformClassesSupported());
    System.out.println("isRedefineClassesSupported=" + inst.isRedefineClassesSupported());
    System.out.println("loaded class count at premain time=" + inst.getAllLoadedClasses().length);
  }
}

The manifest — not a command-line flag — is what tells the JDK which class has premain, and what capabilities the agent needs:

$ cat MANIFEST.MF
Premain-Class: BasicAgent
Can-Retransform-Classes: true
Can-Redefine-Classes: true

$ javac BasicAgent.java Main.java
$ jar cfm agent.jar MANIFEST.MF BasicAgent.class
$ java -javaagent:agent.jar -cp . Main
Verified real output — premain runs to completion, printing 888 already-bootstrapped JDK classes, before Main.main ever starts: 
premain called, agentArgs=null
isRetransformClassesSupported=true
isRedefineClassesSupported=true
loaded class count at premain time=888
main running

Passing arguments to an agent is done with = after the jar path — everything after the = arrives verbatim as agentArgs, and multiple -javaagent flags can be stacked to load several independent agents into the same JVM:

$ java -javaagent:agent.jar=myArgs -javaagent:other-agent.jar -cp . Main
Order matters when multiple agents are stacked: premain methods run in the same left-to-right order the -javaagent flags appear on the command line, all of them finishing before main() starts.

3 · The Instrumentation Interface — All 17 Methods

Everything an agent can do funnels through the single Instrumentation object handed to premain/agentmain. Confirmed against the live interface with javap java.lang.instrument.Instrumentation — every method that exists, nothing more:

MethodWhat it does
addTransformer(ClassFileTransformer, boolean canRetransform)Registers a transformer to run on every future class load. canRetransform=true lets this transformer also participate in later retransformClasses calls (§5).
addTransformer(ClassFileTransformer)Same, with canRetransform defaulted to false.
removeTransformer(ClassFileTransformer)Unregisters a previously added transformer; returns whether it was actually registered.
isRetransformClassesSupported()Whether this JVM allows re-running the transformer chain against already-loaded classes.
retransformClasses(Class<?>...)Re-invokes every registered, retransform-capable transformer against classes that are already loaded — verified live in §5.
isRedefineClassesSupported()Whether this JVM allows wholesale class redefinition.
redefineClasses(ClassDefinition...)Replaces an already-loaded class's bytecode with caller-supplied bytes directly — bypasses the transformer chain entirely, verified in §5.
isModifiableClass(Class<?>)Whether a specific class can be transformed/redefined at all — some core bootstrap classes can't be.
getAllLoadedClasses()Every class currently loaded anywhere in the JVM.
getInitiatedClasses(ClassLoader)Classes a specific class loader has initiated loading of.
getObjectSize(Object)Shallow size, in bytes, of a given object instance — verified with real numbers below.
appendToBootstrapClassLoaderSearch(JarFile)Makes a jar's classes visible to the bootstrap class loader — used when an agent's own support classes must be reachable from java.* code.
appendToSystemClassLoaderSearch(JarFile)Makes a jar's classes visible to the system (application) class loader at runtime — verified below.
isNativeMethodPrefixSupported()Whether this transformer's native-method-prefix trick is supported.
setNativeMethodPrefix(ClassFileTransformer, String)Lets a transformer wrap a native method by renaming the original and generating a prefixed non-native stub in its place — how native-call interception agents work.
redefineModule(...)Adds reads/exports/opens/uses/provides to an already-defined JPMS module at runtime (Java 9+) — verified below, opening java.lang for reflection without --add-opens.
isModifiableModule(Module)Whether a given module can be redefined.

redefineModule is the one that looks the most like magic: it lets an agent grant itself reflective access to a module's internals without the target JVM ever having been launched with --add-opens. This is exactly how tools like Mockito's inline mock maker avoid making every test run depend on JVM flags — verified end to end, opening java.lang to read String's private backing array:

Field valueField = String.class.getDeclaredField("value");
try {
  valueField.setAccessible(true);           // fails -- java.lang isn't open by default
} catch (InaccessibleObjectException e) {
  System.out.println("before redefineModule, blocked: " + e.getMessage());
}

Module javaBase = String.class.getModule();
Module unnamed  = OpenMain.class.getModule();
inst.redefineModule(
    javaBase,
    Set.of(),                                    // extraReads
    Map.of(),                                     // extraExports
    Map.of("java.lang", Set.of(unnamed)),         // extraOpens -- open java.lang to us
    Set.of(), Map.of());                          // extraUses, extraProvides

valueField.setAccessible(true);                   // now succeeds
System.out.println("after redefineModule, setAccessible succeeded: " + valueField);
Verified real output — genuinely blocked, then genuinely opened, in the same JVM, with no launch flags at all:

4 · ClassFileTransformer — Rewriting Bytecode as Classes Load

addTransformer is where an agent actually gets to change code, not just observe it. Confirmed via javap — two overloads, both default methods so an agent only needs to implement the one it cares about:

MethodSinceNotes
byte[] transform(ClassLoader, String className, Class<?> classBeingRedefined, ProtectionDomain, byte[] classfileBuffer)Java 5The original signature. Return the (possibly modified) bytecode, or null to leave the class unchanged.
byte[] transform(Module, ClassLoader, String, Class<?>, ProtectionDomain, byte[])Java 9Module-aware overload. Its default implementation just delegates to the 5-arg one, so every pre-9 agent keeps compiling and running unmodified.

The bytecode itself can be rewritten with any bytecode library — ASM and Byte Buddy are the ecosystem's usual choices. Since Java 24, the JDK ships its own, no extra dependency required: the Class-File API (JEP 484), confirmed finalized on this JDK 25 install (no --enable-preview needed) by java --describe-module java.base exporting java.lang.classfile unconditionally. Below, a transformer that injects a single static call at the very start of one target method — a minimal, real method-entry probe, the same primitive every bytecode-based profiler and APM agent builds on:

public class CountingTransformer implements ClassFileTransformer {
  private final String targetClassNameSlash;   // e.g. "Worker"
  private final String targetMethodName;       // e.g. "work"

  public CountingTransformer(String targetClassNameSlash, String targetMethodName) {
    this.targetClassNameSlash = targetClassNameSlash;
    this.targetMethodName = targetMethodName;
  }

  @Override
  public byte[] transform(ClassLoader loader, String className, Class<?> classBeingRedefined,
                           ProtectionDomain protectionDomain, byte[] classfileBuffer) {
    if (!targetClassNameSlash.equals(className)) return null;   // null = leave this class unchanged

    ClassFile cf = ClassFile.of();
    ClassModel model = cf.parse(classfileBuffer);

    CodeTransform injectProbe = new CodeTransform() {
      @Override public void atStart(CodeBuilder builder) {
        builder.ldc(targetMethodName);
        builder.invokestatic(ClassDesc.of("Probe"), "hit",
            MethodTypeDesc.of(CD_void, CD_String));
      }
      @Override public void accept(CodeBuilder builder, CodeElement element) {
        builder.with(element);   // forward everything else unchanged
      }
    };

    ClassTransform xform = ClassTransform.transformingMethods(
        mm -> mm.methodName().equalsString(targetMethodName),
        MethodTransform.transformingCode(injectProbe));

    return cf.transformClass(model, xform);
  }
}

Installed in premain, before Worker is ever loaded — the injection happens transparently the first time the class-loading pipeline touches it:

public static void premain(String agentArgs, Instrumentation inst) {
  inst.addTransformer(new CountingTransformer("Worker", "work"), true);
}
$ java -javaagent:agent.jar -cp . Main
Verified real output — Worker.work()'s own source was never touched; the probe call was injected purely at the bytecode level, and the class genuinely grew by 35 bytes: 
[agent] instrumented Worker.work() -- 404 bytes -> 439 bytes
[probe] entered work (total calls=1)
  ...doing real work...
[probe] entered work (total calls=2)
  ...doing real work...
main done, Probe.CALLS=2

5 · retransformClasses vs redefineClasses — Modifying a Live Class

Both methods change the bytecode of a class the JVM has already loaded — the capability that makes hot-swap tooling and "turn on profiling without restarting" possible — but they work in genuinely different ways, verified separately below.

retransformClassesredefineClasses
Source of new bytecodeRe-runs every registered, retransform-capable ClassFileTransformer against the class's original bytecodeBytes supplied directly by the caller in a ClassDefinition — no transformer involved at all
NeedsCan-Retransform-Classes: true + addTransformer(t, true)Can-Redefine-Classes: true
Typical useTurning instrumentation on/off for classes already running (feature-flag a profiler mid-session)Hot-swapping a method body you've computed yourself — the IDE "apply code changes" primitive

5.1 · retransformClasses — turning on instrumentation mid-run

The agent attaches and does nothing at first; only later — driven by application code in this demo, in practice often a JMX operation or a signal — does it install the transformer and retransform an already-loaded, already-executing class:

// -- Main.java --
Worker w = new Worker();
w.work();                                  // BEFORE: plain, un-instrumented
w.work();

TimingAgent.instrumentNow(Worker.class, "work");   // agent decides, mid-run, to instrument

w.work();                                  // AFTER: same object, same class, now instrumented
w.work();

// -- TimingAgent.java --
public static void instrumentNow(Class<?> target, String method) throws Exception {
  inst.addTransformer(new CountingTransformer(target.getName(), method), true);
  inst.retransformClasses(target);   // re-runs the transform chain on an ALREADY-LOADED class
}
Verified real output — the exact same Worker instance, same class, instrumented with zero restart, mid-execution: 
-- before instrumentation --
  ...doing real work...
  ...doing real work...
[agent] instrumented Worker.work() -- 404 bytes -> 439 bytes
[agent] retransformClasses(Worker) complete
-- after retransformClasses --
[probe] entered work (total calls=1)
  ...doing real work...
[probe] entered work (total calls=2)
  ...doing real work...

5.2 · redefineClasses — supplying bytecode directly, no transformer chain

Here the agent registers no transformer at all — the caller builds the new bytecode itself (again with the Class-File API) and hands it straight to redefineClasses via a ClassDefinition:

byte[] original = Files.readAllBytes(Path.of("Worker.class"));
ClassModel model = ClassFile.of().parse(original);
byte[] redefined = ClassFile.of().transformClass(model, /* ...inject a println call... */);

inst.redefineClasses(new ClassDefinition(Worker.class, redefined));
w.work();   // runs the new bytecode immediately
Verified real output — no transformer was ever registered on this agent; the new behavior came entirely from the bytes passed to redefineClasses: 
  ...doing real work...
-- after redefineClasses --
  ...REDEFINED body ran instead...
  ...doing real work...
Both calls fail with UnmodifiableClassException for a class that isModifiableClass reports false for, and both are checked exceptions — the API deliberately forces every caller to think about the "this class can't be touched" case.

6 · Dynamic Agents — agentmain(), the Attach API & Launcher-Agent-Class

Static agents need to be known about at JVM launch. Java 6 added a second path: the Attach API (com.sun.tools.attach, in the jdk.attach module) lets a completely separate process reach into an already-running JVM by PID and load a jar as an agent on the fly — no restart, and the target didn't need -javaagent at all.

MethodNotes
public static void agentmain(String agentArgs, Instrumentation inst) The dynamic counterpart to premain — same two-arg/one-arg fallback rule applies.
VirtualMachine.attach(String pid)From the attaching process — opens a connection to a target JVM by process ID.
vm.loadAgent(String jarPath, String args)Tells the target JVM to load the named jar as an agent and invoke its agentmain, passing args through.

Verified as a genuine two-process scenario on this machine — a long-running TargetApp started with no agent flags at all, and a completely separate Attacher process reaching in by PID:

// Attacher.java -- a totally separate process
VirtualMachine vm = VirtualMachine.attach(pid);
vm.loadAgent(agentJarPath, "hello-from-attacher");
vm.detach();
$ java -cp . TargetApp &          # started with NO -javaagent flag
TargetApp pid=19070
$ java -cp . Attacher 19070 dyn-agent.jar
Attacher: loadAgent completed
Verified real output — printed by agentmain, inside the target process, after being loaded entirely from the outside (warning text discussed in §7): 
[dyn-agent] agentmain called, args=hello-from-attacher canRetransform=true

6.1 · Launcher-Agent-Class — an agent from java -jar, no -javaagent flag

A third, less-known path since Java 9: a runnable jar's own manifest can name an agent class that the launcher loads automatically before calling main — useful for a self-contained tool (e.g. one that needs to open JDK-internal packages to itself) that shouldn't require its users to remember a separate -javaagent flag.

Non-obvious, verified the hard way: Launcher-Agent-Class invokes agentmain, not premain — even though nothing attached from another process. Naming the entry-point method premain here fails at launch with a native-level assertion, not a clean Java exception: 
$ java -jar launcher-app.jar
Exception in thread "main" java.lang.NoSuchMethodException:
  LauncherApp.agentmain(java.lang.String,java.lang.instrument.Instrumentation)
*** java.lang.instrument ASSERTION FAILED ***: "!errorOutstanding" ...

Fixed and verified working — same manifest, method renamed to agentmain:

$ cat MANIFEST.MF
Main-Class: LauncherApp
Launcher-Agent-Class: LauncherApp

$ java -jar launcher-app.jar
Verified real output — the agent runs before main, from a plain java -jar invocation, no -javaagent anywhere on the command line: 
[launcher-agent-class] agentmain ran BEFORE main(), via plain 'java -jar', no -javaagent flag
main() running

7 · Java 21+ — the Dynamic-Loading Warning (JEP 451)

JEP 451, "Prepare to Disallow the Dynamic Loading of Agents," shipped in Java 21 as the first step toward closing off §6's dynamic-attach path by default — the rationale being that a process silently injecting bytecode into another running JVM is a serious integrity concern for security-sensitive deployments, and static -javaagent agents (visible on the launch command line) don't carry the same risk.

As of this JDK 25 install, the dynamic loadAgent call from §6 still succeeds — but now prints a warning to the target process's own output, straight from the JVM itself, unedited:

Verified real output — captured on the target JVM's stdout the moment Attacher loaded dyn-agent.jar into it: 
WARNING: A Java agent has been loaded dynamically (/.../dyn-agent.jar)
WARNING: If a serviceability tool is in use, please run with -XX:+EnableDynamicAgentLoading to hide this warning
WARNING: If a serviceability tool is not in use, please run with -Djdk.instrument.traceUsage for more information
WARNING: Dynamic loading of agents will be disallowed by default in a future release

Suppressing the warning is exactly what it suggests — launch the target JVM (not the attacher) with the flag, verified to fully silence it while dynamic attach keeps working:

$ java -XX:+EnableDynamicAgentLoading -cp . TargetApp &
$ java -cp . Attacher <pid> dyn-agent.jar
Verified real output — no warning lines at all this time: 
TargetApp pid=19131
[dyn-agent] agentmain called, args=hello-from-attacher canRetransform=true
Two things worth being precise about: (1) this affects only the dynamic path (§6) — a static agent loaded via -javaagent at launch is completely unaffected, warning or not; (2) as of this JDK 25 install it is still just a warning, not an error — the JVM's own text says enforcement is planned for "a future release," so check the release notes of whatever JDK you're actually deploying to rather than assuming this page's JDK 25 behavior still holds.
This is precisely why tools like IntelliJ's debugger-attach, Mockito's inline mock maker, and Byte Buddy's ByteBuddyAgent.install() — all dynamic-attach users — started needing -XX:+EnableDynamicAgentLoading on the JVMs they attach to, starting with Java 21.

9 · Real-World Use Cases, and a Combined Instrumentation + JFR + JMX Example

APM / tracing agents (OpenTelemetry Java auto-instrumentation, Datadog, New Relic, Elastic APM)Static -javaagent + addTransformer wrapping known framework/library methods with timing and span-propagation code — exactly §4's pattern, just with a much larger library of "which class/method to instrument" rules.

9.1 · Capstone — one agent, three integrations at once

Everything above, combined into a single premain that a real monitoring agent would actually ship: Instrumentation injects a probe at the target method's entry point (§4), the probe emits a custom JFR event on every call (see the JFR deep dive), and the running counters are exposed live as a JMX MBean (see the JMX deep dive) — all three wired up with zero changes to the target application:

// MethodTimingEvent.java -- a custom JFR event
@Label("Method Timing")
@Category({"Demo", "Agent"})
public class MethodTimingEvent extends Event {
  @Label("Method") String method;
  @Label("Call Number") long callNumber;
}

// AgentStatsMBean.java / AgentStats.java -- a plain Standard MBean (see the JMX deep dive, §4.1)
public interface AgentStatsMBean { long getMethodCallCount(); }
public class AgentStats implements AgentStatsMBean {
  public long getMethodCallCount() { return Probe2.calls.get(); }
}

// Probe2.java -- what the injected bytecode calls into
public class Probe2 {
  static final AtomicLong calls = new AtomicLong();
  public static void hit(String label) {
    long n = calls.incrementAndGet();
    MethodTimingEvent evt = new MethodTimingEvent();
    if (evt.isEnabled() || evt.shouldCommit()) {
      evt.method = label;
      evt.callNumber = n;
      evt.commit();
    }
  }
}

// CapstoneAgent.java
public static void premain(String agentArgs, Instrumentation inst) throws Exception {
  String[] parts = (agentArgs == null ? "Worker:work" : agentArgs).split(":");

  // 1) Instrumentation: inject a probe at the target method's entry point
  inst.addTransformer(new CountingTransformer2(parts[0], parts[1]));

  // 2) JMX: expose the running counters as a standard MBean
  ObjectName name = new ObjectName("com.example.agent:type=AgentStats");
  ManagementFactory.getPlatformMBeanServer().registerMBean(new AgentStats(), name);

  // 3) JFR: start an in-process recording so MethodTimingEvent instances land in a .jfr file
  Recording recording = new Recording();
  recording.enable("MethodTimingEvent");
  recording.setDestination(Path.of("/tmp/capstone-agent.jfr"));
  recording.start();
  Runtime.getRuntime().addShutdownHook(new Thread(recording::stop));
}
// Main3.java -- the "application", completely unaware it's instrumented
Worker w = new Worker();
for (int i = 0; i < 5; i++) w.work();

ObjectName name = new ObjectName("com.example.agent:type=AgentStats");
long count = (long) ManagementFactory.getPlatformMBeanServer().getAttribute(name, "MethodCallCount");
System.out.println("via JMX -> MethodCallCount=" + count);
$ java -javaagent:capstone-agent.jar=Worker:work -cp . Main3
$ jfr print --events MethodTimingEvent /tmp/capstone-agent.jfr
Verified real output — all three integrations firing from one agent, one JVM, zero application changes: 
[capstone-agent] watching Worker.work()
[capstone-agent] registered MBean com.example.agent:type=AgentStats
[capstone-agent] JFR recording started -> /tmp/capstone-agent.jfr
  ...doing real work... (x5)
via JMX -> MethodCallCount=5

MethodTimingEvent {
  startTime = 12:14:00.449 (2026-09-02)
  method = "Worker.work"
  callNumber = 1
  eventThread = "main" (javaThreadId = 3)
  stackTrace = [
    Probe2.hit(String) line: 22

Note what came for free: JFR captured a full stack trace for every event without the agent doing anything to collect one — exactly the mechanism a real profiler leans on instead of hand- rolling stack walking. And the MBean reads live counters straight out of the same AtomicLong the injected bytecode increments — jconsole pointed at this JVM would show MethodCallCount ticking up in real time as Worker.work() gets called.

Java agents in one glance

  • Static agent: Premain-Class in the manifest + a premain(String, Instrumentation) method, loaded with -javaagent:agent.jar[=args] — runs before main().
  • Dynamic agent: Agent-Class in the manifest + agentmain(String, Instrumentation), loaded from another process via VirtualMachine.attach(pid).loadAgent(jarPath) — runs mid-execution, and since Java 21 prints a JEP 451 warning unless the target ran with -XX:+EnableDynamicAgentLoading.
  • From java -jar, no flag at all: Launcher-Agent-Class (Java 9+) — but it calls agentmain, not premain, verified the hard way in §6.1.
  • Rewrite bytecode as it loads: inst.addTransformer(new MyTransformer(), canRetransform) — implement ClassFileTransformer.transform(...), return modified bytes or null to leave a class unchanged.
  • Rewrite a class that's already loaded: retransformClasses (re-runs the registered transformer chain) or redefineClasses (caller supplies the new bytes directly, no transformer chain) — both need the matching Can-Re(de|trans)form-Classes: true manifest attribute.
  • No bytecode library needed since Java 25: the JDK's own Class-File API (java.lang.classfile, JEP 484) — ClassFile.of().parse(bytes), ClassTransform/CodeTransform, transformClass(...).
  • Open a module's internals at runtime, no --add-opens: inst.redefineModule(module, Set.of(), Map.of(), Map.of(pkg, Set.of(reader)), Set.of(), Map.of()).
  • Cheap object size: inst.getObjectSize(obj) — shallow, in bytes.
  • Pair it with JFR/JMX: emit a custom jdk.jfr.Event from the injected probe for structured, stack-trace-carrying telemetry; register a plain MBeanServer.registerMBean(...) to expose the agent's own live counters — both verified together in §9.1.
