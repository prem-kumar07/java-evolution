Java Flight Recorder (JFR) & JMC Java 11

Java Flight Recorder (JFR) is an event-driven diagnostic and profiling framework built directly into the HotSpot JVM. It captures low-level JVM internals (GC, threads, memory, CPU) with negligible runtime overhead (< 1–2%), making it the standard for production profiling.

<2%production overhead
JMCmission control GUI
Java 14event streaming API
Opensourced in Java 11
The problem it solves Profiling Java applications in production historically required attaching heavyweight agents that skewed performance metrics and slowed down the application. JFR is deeply embedded into the JVM, allowing continuous, always-on "black box" flight recording without impacting user latencies.

1 · Starting Recordings

You can start JFR at launch using JVM flags, or dynamically at runtime using the jcmd CLI.

Via JVM Flags

# Start a continuous recording with a rolling 1-hour buffer
$ java -XX:StartFlightRecording=disk=true,maxage=1h,settings=default -jar app.jar

# Start a highly detailed 60-second profile
$ java -XX:StartFlightRecording=filename=startup.jfr,duration=60s,settings=profile -jar app.jar

Via jcmd (Dynamically) — verified end-to-end on a live process

The whole point of jcmd is that you don't restart anything — you attach to a JVM that's already running in production and turn recording on and off from the outside. Find your Java PID with jcmd -l (or jps), then issue commands to it. Run below against a real long-lived process, output unedited:

$ java -cp . LongRunner &
[1] 9496

$ jcmd 9496 JFR.check
9496:
No available recordings.
Use jcmd 9496 JFR.start to start a recording.

$ jcmd 9496 JFR.start name=demo settings=profile duration=60s filename=/tmp/jcmd-demo.jfr
9496:
Started recording 1. The result will be written to:
/tmp/jcmd-demo.jfr

$ jcmd 9496 JFR.check
9496:
Recording 1: name=demo duration=1m (running)

$ jcmd 9496 JFR.dump name=demo filename=/tmp/jcmd-snapshot.jfr
9496:
Dumped recording "demo", 406.9 kB written to:
/tmp/jcmd-snapshot.jfr

$ jcmd 9496 JFR.stop name=demo
9496:
Stopped recording "demo", 792.4 kB written to:
/tmp/jcmd-demo.jfr
JFR.dump doesn't stop the recording — it copies everything captured so far to a file while the recording keeps running. This is what lets you pull a snapshot from a production JVM mid-incident without losing the rest of the recording window.

2 · The jfr Command-Line Tool

Once you have a .jfr file, you don't need JMC's GUI to read it — the jfr CLI (bundled with the JDK since Java 8u, standardized alongside JFR's open-sourcing in Java 11) can print, summarize, and query it directly from a terminal or a CI pipeline. Every command below is jfr <subcommand> --help's real output, condensed:

CommandWhat it's for
jfr summary file.jfrFast overview: recording duration, and every event type present with its count & size — your first stop on any unfamiliar recording.
jfr view <view-name> file.jfrPretty-printed, pre-aggregated tables for ~70 built-in questions (hot methods, GC pauses, contention, allocation pressure, …) — jfr view all-views file.jfr lists every one.
jfr print --events <name> file.jfrRaw, per-event dump (text/XML/ JSON) with full field values and stack traces — use once view has pointed you at a specific event type.
jfr metadata --events <name> file.jfrShows an event type's field layout, labels, and description — works on any .jfr file or the running JDK, useful when you don't remember a custom event's exact field names.
jfr configure [options] --output custom.jfcBuilds a reusable .jfc settings file — e.g. turn on full (non-throttled) exception capture or maximum allocation profiling — instead of a long inline settings=... flag string.
jfr scrub --exclude-categories '...' in.jfr out.jfrStrips events matching a filter and writes a smaller file — handy for sharing a recording without, say, system properties or thread dumps.
jfr assemble <repository-dir> out.jfrStitches together the raw chunk files JFR writes when a JVM crashes mid-recording (found under -XX:FlightRecorderOptions=repository=...) into one loadable .jfr.
jfr disassemble file.jfrThe inverse — splits one recording into its per-chunk files, useful for isolating a time window from a very large recording.

jfr view — every category, verified against a real JDK 25 install

jfr view all-views file.jfr lists every available view; running it here groups into three real categories:

CategorySample views
JVM internalsgc, gc-pauses, heap-configuration, safepoints, compiler-statistics, tlabs
Environmentcpu-load, system-information, jvm-flags, active-recordings, native-library-failures

$ jfr view all-views recording.jfr

3 · Detecting Real Problems — Worked Examples

Four scenarios below, each with a small self-contained Java program you can compile and run locally, plus the actual jfr command output that JFR captured from it — unedited, on this machine, JDK 25. This is the workflow: record with settings=profile, then let jfr view's pre-built aggregations point you straight at the offending method/site instead of reading thousands of raw events by hand.

3.1 · Finding a CPU hotspot

The program below deliberately builds a string with += in a loop (quadratic — a classic accidental hotspot) alongside two cheaper helper methods, so hot-methods has to actually pick the right one out:

import java.util.*;
import java.util.concurrent.*;

public class BuggyApp {
  static final Object LOCK = new Object();
  static long sharedCounter = 0;

  // deliberately inefficient CPU hotspot: string concatenation in a loop
  static String buildReport(int n) {
    String s = "";
    for (int i = 0; i < n; i++) {
      s += "row-" + i + ";";   // hot: quadratic string building
    }
    return s;
  }

  // deliberately generates a lot of short-lived garbage
  static void churnGarbage(int iterations) {
    List<byte[]> junk = new ArrayList<>();
    for (int i = 0; i < iterations; i++) {
      junk.add(new byte[1024]);
      if (junk.size() > 500) junk.clear();
    }
  }

  // deliberately contended lock, held too long
  static void contendedIncrement() {
    synchronized (LOCK) {
      sharedCounter++;
      try { Thread.sleep(2); } catch (InterruptedException ignored) {}
    }
  }

  public static void main(String[] args) throws Exception {
    ExecutorService pool = Executors.newFixedThreadPool(8);
    List<Future<?>> futures = new ArrayList<>();
    for (int t = 0; t < 8; t++) {
      futures.add(pool.submit(() -> {
        for (int i = 0; i < 40; i++) {
          buildReport(3000);
          churnGarbage(2000);
          contendedIncrement();
        }
      }));
    }
    for (Future<?> f : futures) f.get();
    pool.shutdown();
    System.out.println("done, counter=" + sharedCounter);
  }
}
$ javac BuggyApp.java
$ java -XX:StartFlightRecording=filename=demo.jfr,settings=profile -cp . BuggyApp
done, counter=320

$ jfr view --width 140 hot-methods demo.jfr
Verified real output — the deliberately-bad method is identified immediately, no manual code reading required:

3.4 · Finding an exception storm — and the throttling gotcha

This one has a sharp edge worth knowing before you trust a raw count. The program below throws (and catches) a NumberFormatException on exactly 1 in 3 of 50,000 iterations — 16,667 real exceptions:

public class ExceptionStorm {
  public static void main(String[] args) {
    int caught = 0;
    for (int i = 0; i < 50000; i++) {
      try {
        parseMaybeBad(i);
      } catch (NumberFormatException e) {
        caught++;
      }
    }
    System.out.println("caught=" + caught);
  }
  static int parseMaybeBad(int i) {
    String s = (i % 3 == 0) ? "not-a-number" : String.valueOf(i);
    return Integer.parseInt(s);
  }
}
$ java -XX:StartFlightRecording=filename=ex.jfr,settings=profile -cp . ExceptionStorm
caught=16667
$ jfr view --width 140 exception-by-type ex.jfr
Verified real output — the count is wrong on purpose: 
                                Exceptions by Type

Class                                                                 Count
---------------------------------------------------------------------------
java.lang.NumberFormatException                                         60
60, not 16,667. profile.jfc throttles jdk.JavaExceptionThrow to 300/s by default (verified in the JDK's own lib/jfr/profile.jfc) — a deliberate trade-off so a genuine exception storm can't flood the recording buffer and drown out everything else. The view still correctly identifies which exception type and site are the problem; just don't read the number as a literal count under load.

To capture the real count when you need it, override the throttle explicitly:

$ java -XX:StartFlightRecording=filename=ex2.jfr,settings=profile,exceptions=all -cp . ExceptionStorm
caught=16667
$ jfr summary ex2.jfr | grep JavaExceptionThrow
 jdk.JavaExceptionThrow                  16667        216703        # verified — all 16,667 captured

4 · JDK Mission Control (JMC)

JDK Mission Control (JMC) is the official desktop GUI for analyzing .jfr dump files. It provides:

  • Automated Analysis: Rule-based scorecard with tuning recommendations (e.g., GC pauses, memory leaks).
  • Flame Graphs: Visualizes call trees and hotspot methods.
  • Thread & Lock Contention: Swimlanes for thread states, lock wait times, and deadlocks.
  • Memory Profiling: Allocation pressure, object lifetimes, and heap fragmentation.

5 · Custom Application Events — complete example

You can emit your own application telemetry directly into the JFR pipeline, right alongside JVM events — same file, same jfr print/jfr view tooling. Two files, both compiled and run for real below.

1. The event class — extend jdk.jfr.Event; every public field becomes a captured value:

import jdk.jfr.*;

@Name("com.example.OrderProcessed")
@Label("Order Processed")
@Category({"Demo", "Orders"})
@Description("Fired whenever an order finishes processing")
@StackTrace(false)                 // this event doesn't need a stack trace — cheaper to record
public class OrderEvent extends Event {
  @Label("Order ID")
  public String orderId;

  @Label("Amount")
  public double amount;

  @Label("Item Count")
  public int itemCount;
}

2. Emitting it — begin()/end() capture a duration automatically; commit() writes the event only if JFR is actually recording (near-zero cost when it isn't):

import java.util.Random;

public class OrderDemo {
  public static void main(String[] args) throws Exception {
    Random rnd = new Random(42);
    for (int i = 0; i < 5; i++) {
      processOrder("ORD-" + (1000 + i), rnd.nextDouble() * 200, rnd.nextInt(5) + 1);
    }
    System.out.println("processed 5 orders");
  }

  static void processOrder(String id, double amount, int items) throws InterruptedException {
    OrderEvent event = new OrderEvent();
    event.begin();
    Thread.sleep(10 + (long) (Math.random() * 40));   // simulate work
    event.end();
    event.orderId = id;
    event.amount = amount;
    event.itemCount = items;
    event.commit();
  }
}
$ javac OrderEvent.java OrderDemo.java
$ java -XX:StartFlightRecording=filename=orders.jfr -cp . OrderDemo
processed 5 orders

$ jfr print --events com.example.OrderProcessed orders.jfr

6 · JFR Event Streaming — complete example Java 14

Introduced in Java 14 (JEP 349), Event Streaming lets an application consume JFR events continuously, in-process, in real time — completely bypassing the need to dump .jfr files to disk. This is the mechanism behind live dashboards and self-monitoring alerts that react to JVM behavior as it happens.

Below is the complete, compilable program — it starts a live RecordingStream, does a bit of real CPU work so jdk.CPULoad has something to report, and waits (via a CountDownLatch, not a guess-and-sleep) until it has actually received two events before shutting down cleanly:

import jdk.jfr.consumer.RecordingStream;
import java.time.Duration;
import java.util.concurrent.CountDownLatch;

public class StreamDemo {
  public static void main(String[] args) throws Exception {
    CountDownLatch seenCpu = new CountDownLatch(2);

    try (RecordingStream rs = new RecordingStream()) {
      rs.enable("jdk.CPULoad").withPeriod(Duration.ofMillis(500));

      rs.onEvent("jdk.CPULoad", event -> {
        float jvmCpu = event.getFloat("jvmUser") + event.getFloat("jvmSystem");
        System.out.printf("[stream] jvmCpu=%.1f%% machineTotal=%.1f%%%n",
            jvmCpu * 100, event.getFloat("machineTotal") * 100);
        seenCpu.countDown();
      });

      rs.startAsync();

      // simulate a bit of CPU work so CPULoad has something to report
      long x = 0;
      for (int i = 0; i < 200_000_000; i++) x += i;
      System.out.println("busy-work result=" + x);

      seenCpu.await();   // wait until we've actually received 2 CPULoad events
      rs.close();
    }
    System.out.println("stream closed cleanly");
  }
}
$ javac StreamDemo.java
$ java -cp . StreamDemo
Verified real output: 
busy-work result=19999999900000000
[stream] jvmCpu=0.7% machineTotal=16.4%
[stream] jvmCpu=0.0% machineTotal=19.0%
stream closed cleanly
RecordingStream is a new, temporary, in-memory recording, not a view into one you started elsewhere. To tap into an already-running -XX:StartFlightRecording session's live events instead, use EventStream.openRepository(), which reads the same on-disk repository files the running recording is already writing.

7 · Complete example: streaming your own custom events live

The natural next step: combine §5 and §6 — stream your own event type the instant it's committed, instead of writing it to a file and reading it back later. Reuses the exact OrderEvent class from §5, unchanged:

import jdk.jfr.consumer.RecordingStream;
import java.util.Random;
import java.util.concurrent.CountDownLatch;

public class OrderStreamDemo {
  public static void main(String[] args) throws Exception {
    CountDownLatch latch = new CountDownLatch(5);

    try (RecordingStream rs = new RecordingStream()) {
      rs.enable("com.example.OrderProcessed");   // our own event, enabled by name

      rs.onEvent("com.example.OrderProcessed", event -> {
        System.out.printf("[live] order=%s amount=$%.2f items=%d took=%dms%n",
            event.getString("orderId"),
            event.getDouble("amount"),
            event.getInt("itemCount"),
            event.getDuration().toMillis());
        latch.countDown();
      });

      rs.startAsync();

      Random rnd = new Random(7);
      for (int i = 0; i < 5; i++) {
        processOrder("LIVE-" + (2000 + i), rnd.nextDouble() * 300, rnd.nextInt(5) + 1);
      }

      latch.await();   // block until all 5 orders have actually streamed through
    }
    System.out.println("all 5 orders observed live");
  }

  static void processOrder(String id, double amount, int items) throws InterruptedException {
    OrderEvent event = new OrderEvent();
    event.begin();
    Thread.sleep(10 + (long) (Math.random() * 30));
    event.end();
    event.orderId = id;
    event.amount = amount;
    event.itemCount = items;
    event.commit();
  }
}
$ javac OrderStreamDemo.java   # OrderEvent.class from §5 must be on the classpath
$ java -cp . OrderStreamDemo
Verified real output — each order shows up the moment commit() runs, not after the program exits: 
[live] order=LIVE-2000 amount=$219.21 items=1 took=34ms
[live] order=LIVE-2001 amount=$2.89 items=5 took=39ms
[live] order=LIVE-2002 amount=$269.18 items=1 took=22ms
[live] order=LIVE-2003 amount=$170.74 items=3 took=36ms
[live] order=LIVE-2004 amount=$36.22 items=1 took=40ms
all 5 orders observed live
Notice rs.enable("com.example.OrderProcessed") needed no settings=profile flag, no -XX:StartFlightRecording, nothing on the command line at all — RecordingStream creates and controls its own recording purely from Java code, which is exactly what makes it usable for an in-app health dashboard or alerting hook.

8 · Cheat sheet

JFR in one glance

  • Start: -XX:StartFlightRecording=... at launch, or jcmd <PID> JFR.start on a running JVM — no restart needed.
  • Snapshot without stopping: jcmd <PID> JFR.dump copies what's captured so far; the recording keeps running.
  • Read a file fast: jfr summary (overview) → jfr view <name> (pre-built tables: hot-methods, contention-by-site, allocation-by-class, gc, exception-by-type, …) → jfr print --events <name> (raw events).
  • Don't know a field name? jfr metadata --events <name>.
  • Custom events: extend jdk.jfr.Event, annotate fields, begin()/end()/commit() — same tooling reads them.
  • Live, in-process: RecordingStream — enable() + onEvent() + startAsync(), zero files, zero JVM flags.
  • Gotcha: settings=profile throttles noisy events like jdk.JavaExceptionThrow (300/s default) — override with exceptions=all when you need the exact count.
