The Java Platform Module System (JPMS) Java 9

A module is a named, self-describing group of packages that declares what it needs (requires) and what it exposes (exports). It adds strong encapsulation and reliable configuration on top of the old flat classpath.

~90modules the JDK is split into
strongencapsulation (hidden = truly hidden)
startupmissing deps fail early, not deep in a run
jlinkship only the modules you use
Java 9introduced (Project Jigsaw)
The problem it solves The classpath is a flat bag of JARs: every public class is reachable by everyone ("nothing is really private"), missing or duplicate JARs blow up deep into a run ("JAR hell"), and you always ship the whole JRE. Modules make dependencies explicit and checked at startup, let libraries hide internals, and let tools assemble a minimal runtime.

1 · What & why

  • Strong encapsulation — packages you don't export are hidden, even from reflection.
  • Reliable configuration — missing/duplicate/cyclic dependencies are caught at startup.
  • A scalable platform — the JDK is ~90 modules, so jlink can ship only what you use.

2 · A module in one file: module-info.java

// src/com.myapp/module-info.java
module com.myapp {
  requires java.net.http;            // I depend on this module
  requires transitive com.mylib;     // and my consumers get com.mylib too

  exports com.myapp.api;             // this package is public API
  exports com.myapp.internal to com.myapp.tests;   // qualified export

  uses    com.myapp.spi.Plugin;                     // I consume this service
  provides com.myapp.spi.Plugin
      with com.myapp.plugins.DefaultPlugin;          // I provide an implementation

  opens   com.myapp.model;           // allow deep reflection (frameworks)
}

3 · Directives at a glance

DirectiveMeaning
requires MDepend on module M's exported packages.
requires transitive MRe-export M to your consumers (implied readability).
requires static MCompile-time only (optional at runtime).
exports PMake package P readable by all modules.
exports P to M1, M2Qualified export — only to named modules.
opens P / opens P to MAllow deep reflection into P at runtime.
uses S / provides S with ImplConsume / provide a ServiceLoader service.

3b · Advanced Directives: transitive and static

Two modifiers on the requires directive give you fine-grained control over visibility and runtime footprint:

requires transitive
module my.data.layer {
  // Anyone who requires my.data.layer ALSO gets java.sql automatically.
  // Use this when your public API exposes types from another module
  // (e.g., your public methods return a java.sql.Connection).
  requires transitive java.sql;
}
requires static
module my.utils {
  // Compile-time only dependency. 
  // Required to compile, but completely optional at runtime.
  // Perfect for annotations like Lombok or JMH that aren't 
  // needed by the JVM when actually running the app.
  requires static lombok;
}

5 · exports vs opens — the key distinction

exports
exports com.myapp.api;
// Compile against & call public types normally.
// Deep reflection (setAccessible on privates) is STILL blocked.
opens
opens com.myapp.model;
// Reflection frameworks (Jackson, Hibernate, Spring)
// can access members at runtime.
// No compile-time access to non-public types.

opens com.myapp.model to com.fasterxml.jackson.databind;
// qualified opens — only THAT module gets deep reflection,
// everyone else is still blocked

The dreaded error: If you use a reflection-based library (like Gson, Jackson, or Spring) to inspect a class in a module that is not opened, Java will throw a strict exception at runtime instead of silently failing:

java.lang.reflect.InaccessibleObjectException: 
  Unable to make field private java.lang.String com.myapp.model.User.name 
  accessible: module com.myapp does not "opens com.myapp.model" to unnamed module...

To fix this, you must either add an opens directive to your module-info.java or use the --add-opens command-line escape hatch.

5b · open module — opening everything at once

Why it matters: writing opens on every single package that a reflection-heavy framework (Spring, Hibernate, Jackson) might touch gets tedious fast — and it's easy to miss one. Prefixing the whole module declaration with open opens every package in it to deep reflection at once, while exports still controls what's compile-time visible.

Opening each package individually
module com.acme.app {
  requires spring.core;
  exports com.acme.app.api;
  opens com.acme.app.model;
  opens com.acme.app.entities;
  opens com.acme.app.config;   // forget one and Spring throws
                                // InaccessibleObjectException at runtime
}
One open module declaration
open module com.acme.app {
  requires spring.core;
  exports com.acme.app.api;   // exports still applies — this is compile-time API
  // every package in this module is open to reflection — verified:
  // Class.getDeclaredField(...).setAccessible(true) works from anywhere
}

This is exactly why many Spring Boot / Jakarta EE applications declare their main module as open module — those frameworks reflectively construct and inject into almost every class, and enumerating every package individually isn't worth the ceremony for an application module (as opposed to a published library, where you'd want the tighter, explicit package-by-package opens).

6 · Classpath vs module path & legacy JARs

The JPMS introduces the module path (-p), but the legacy classpath (-cp) still fully works. How the JVM treats a JAR depends entirely on where you put it and whether it has a module-info.class.

JAR TypePlaced on Classpath (-cp)Placed on Module Path (-p)
Legacy JAR
(No module-info)		Becomes part of the Unnamed Module.
Reads everything, exports everything.		Becomes an Automatic Module.
Name derived from filename (e.g. gson-2.8.jar → gson). Reads everything, exports everything. Can be required by strict modules!
Modular JAR
(Has module-info)		module-info is ignored! Treated exactly like a legacy JAR in the unnamed module.Becomes a Named Module.
Strict encapsulation applies.

How to run with legacy code

1. Pure legacy (Java 8 style)
# Everything goes on the classpath. No modules exist.
java -cp "my-app.jar:lib/*" com.myapp.Main
2. Mixing modules & legacy
# Put strict modules on module path, legacy on classpath
# Note: Named modules CANNOT require the unnamed module.
java -p my-app.jar -cp "legacy-libs/*" -m com.myapp/com.myapp.Main

# Better: Put legacy JARs on the module path!
# They become "Automatic Modules" so your strict code can require them.
java -p "my-app.jar:legacy-libs/*" -m com.myapp/com.myapp.Main

7 · Services (ServiceLoader) — complete example

Modules formalise the plugin pattern. Instead of hard-coding dependencies on implementation classes, a module provides an implementation, another uses the interface, and the JVM's ServiceLoader wires them together at runtime. This completely replaces the old META-INF/services text files.

Step 1: The API module (defines the contract)

// module-info.java
module com.myapp.api {
  exports com.myapp.spi;
}

// com/myapp/spi/Plugin.java
package com.myapp.spi;
public interface Plugin {
    void run();
}

Step 2: The Provider module (implements the contract)

// module-info.java
module com.acme.impl {
  requires com.myapp.api;
  // We do NOT export the implementation package! It remains hidden.
  provides com.myapp.spi.Plugin with com.acme.impl.FancyPlugin; 
}

// com/acme/impl/FancyPlugin.java
package com.acme.impl;
import com.myapp.spi.Plugin;
public class FancyPlugin implements Plugin {
    public void run() { System.out.println("Running fancy plugin!"); }
}

Step 3: The Consumer module (uses the contract)

// module-info.java
module com.myapp.app {
  requires com.myapp.api;
  uses com.myapp.spi.Plugin; // Declares intent to load this service
}

// com/myapp/app/Main.java
package com.myapp.app;
import com.myapp.spi.Plugin;
import java.util.ServiceLoader;

public class Main {
    public static void main(String[] args) {
        // The JVM automatically discovers FancyPlugin on the module path!
        // Notice: we do NOT require com.acme.impl anywhere.
        Iterable<Plugin> plugins = ServiceLoader.load(Plugin.class);
        for (Plugin p : plugins) {
            p.run(); 
        }
    }
}

8 · Migration & escape hatches

  • You don't have to modularise to run on Java 9+. The classpath still works; the "unnamed module" reads everything. Many apps stay on the classpath for years.
  • Automatic modules bridge non-modular JARs: put a plain JAR on the module path and it gets a name from the filename (or its Automatic-Module-Name manifest entry).
  • Command-line escape hatches for legacy code: 
    --add-modules  --add-exports  --add-opens  --add-reads

9 · Tooling: jdeps, jlink, and jpackage

The module system enabled the creation of three powerful tools that completely change how Java apps are distributed: you no longer tell users to "install Java"; you just hand them an installer.

1. jdeps (Dependency Analysis)

Scans your JARs to find exactly which JDK modules your code actually requires, and flags any illegal usage of internal JDK APIs (like sun.misc.Unsafe).

# What JDK modules does my app need? (Output might be: java.base, java.desktop)
jdeps --module-path libs -summary my-app.jar

# Am I using any hidden/removed JDK internal APIs?
jdeps --jdk-internals my-app.jar

2. jlink (Custom Runtime Generator)

Why ship a 250MB JRE if your app only uses java.base? jlink strips away unused JDK modules (like Swing or CORBA) to build a minimal, custom JVM just for your app.

# Create a tiny custom JVM containing only your app's required modules
jlink --module-path $JAVA_HOME/jmods:./libs \
      --add-modules java.base,com.myapp \
      --strip-debug --no-man-pages --no-header-files --compress zip-9 \
      --output my-custom-jre
# Result: my-custom-jre/bin/java is a fully functional, ~30MB runtime!

3. jpackage (Native Installer Builder) Java 16

Takes your JARs and your custom jlink runtime, and wraps them into a native installer (.exe, .dmg, .deb). The user just double-clicks the installer — they don't even know it's a Java app.

# Build a Windows MSI installer (must be run on Windows)
jpackage --type msi \
         --name "MyApp" \
         --input ./libs \
         --main-jar my-app.jar \
         --main-class com.myapp.Main \
         --runtime-image ./my-custom-jre \
         --win-shortcut --win-menu

10 · Pitfalls

PitfallReality
InaccessibleObjectException after upgradeA reflection framework needs opens (or --add-opens). #1 migration snag.
Split packagesSame package in two modules is forbidden — common with older libs.
Reflecting into JDK internalsStrongly encapsulated since 16/17 — use supported APIs or --add-exports.
Assuming you must modulariseOptional — the classpath still works on any modern JDK.
Cyclic requiresModule dependencies must be acyclic; the module system rejects cycles.

12 · Cheat sheet

Modules in one glance

  • module M { requires …; exports …; } in module-info.java.
  • exports = compile/call; opens = runtime deep reflection.
  • requires transitive re-exports a dependency; requires static = compile-only.
  • Module path -p vs classpath -cp; plain JARs → automatic modules.
  • Framework broke after upgrade? You likely need opens / --add-opens.
  • jlink for minimal runtimes; jdeps --jdk-internals before upgrading.
