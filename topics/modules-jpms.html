The Java Platform Module System (JPMS) Java 9

A module is a named, self-describing group of packages that declares what it needs (requires) and what it exposes (exports). It adds strong encapsulation and reliable configuration above the old flat classpath.

Why it exists

  • Strong encapsulation — packages not exported are truly hidden, even from reflection.
  • Reliable configuration — missing/duplicate/cyclic dependencies are caught at startup, not deep into a run ("JAR hell").
  • A scalable platform — the JDK itself is ~90 modules, so tools like jlink can ship only what you use.

A module in one file: module-info.java

// src/com.myapp/module-info.java
module com.myapp {
  requires java.net.http;            // I depend on this module
  requires transitive com.mylib;     // and anyone who requires me also gets com.mylib

  exports com.myapp.api;             // this package is public API
  exports com.myapp.internal to com.myapp.tests;   // qualified: only to that module

  uses   com.myapp.spi.Plugin;                     // I consume this service
  provides com.myapp.spi.Plugin
      with com.myapp.plugins.DefaultPlugin;        // I supply an implementation

  opens  com.myapp.model;            // allow deep reflection (e.g. for frameworks)
}

Directives at a glance

DirectiveMeaning
requires MDepend on module M's exported packages.
requires transitive MRe-export M to your consumers (implied readability).
requires static MCompile-time only (optional at runtime).
exports PMake package P readable by all modules.
exports P to M1, M2Qualified export — only to named modules.
opens P / opens P to MAllow deep reflection into P at runtime (frameworks).
uses S / provides S with ImplConsume / provide a ServiceLoader service.

exports vs. opens — the key distinction

exports
exports com.myapp.api;
// Compile & call public types normally.
// Deep reflection (setAccessible on privates) is STILL blocked.
opens
opens com.myapp.model;
// Reflection frameworks (Jackson, Hibernate, Spring)
// can access private members at runtime.
// No compile-time access to non-public types.

Practical guidance & gotchas

  • You don't have to modularise your app to run on Java 9+. The classpath still works; the "unnamed module" reads everything. Many apps stay on the classpath for years.
  • Automatic modules bridge non-modular JARs: put a plain JAR on the module path and it gets a module name derived from the filename (or its Automatic-Module-Name manifest entry).
  • Reflection frameworks need opens (or --add-opens on the command line) — the #1 source of InaccessibleObjectException after migration.
  • Split packages (the same package in two modules) are forbidden — a common migration snag with older libraries.
  • Escape hatches for legacy code: --add-modules, --add-exports, --add-opens, --add-reads.

Related tooling

  • jdeps --jdk-internals app.jar — find uses of encapsulated internals before upgrading.
  • jlink — build a minimal runtime image from your modules.
  • Module import declarations (Java 25) — import module java.base; imports everything a module exports; see Java 25.

Cheat card

  • module M { requires …; exports …; } in module-info.java.
  • exports = compile/call; opens = runtime deep reflection.
  • requires transitive re-exports a dependency; requires static = compile-only.
  • Module path -p vs classpath -cp; plain JARs → automatic modules.
  • Framework broke after upgrade? You probably need opens / --add-opens.
