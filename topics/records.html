Records Final in Java 16

A record is a concise, immutable, transparent carrier for a fixed set of values. You declare the components; the compiler generates the constructor, accessors, equals, hashCode and toString — correctly, every time.

The problem it solves "Data classes" (DTOs, value objects, tuples) were almost all boilerplate — and hand-written equals/hashCode are easy to get subtly wrong (forget a field and you get silent bugs). Records make that boilerplate automatic and correct, and clearly signal intent: this type is just its data.

1 · What is a record?

You write the shape of the data in the header — the record components — and that's it. The record is implicitly final, its fields are final, and it carries no hidden state beyond those components.

Legacy — a hand-written value class
public final class Point {
  private final int x, y;
  public Point(int x, int y) { this.x = x; this.y = y; }
  public int x() { return x; }
  public int y() { return y; }
  @Override public boolean equals(Object o) {
    if (!(o instanceof Point p)) return false;
    return x == p.x && y == p.y;
  }
  @Override public int hashCode() { return Objects.hash(x, y); }
  @Override public String toString() {
    return "Point[x=" + x + ", y=" + y + "]";
  }
}
Record — same thing
public record Point(int x, int y) { }
Easy way to think about it: a record is to a data class what enum is to a set of constants — a special, purpose-built shorthand the compiler fills in for you.

2 · What the compiler generates

  • Canonical constructor taking all components in order.
  • Accessors named exactly like the component: x(), y().
  • equals/hashCode comparing all components by value.
  • toString like Point[x=1, y=2].
  • A private final field per component; the class extends java.lang.Record and is final.

3 · Customising records

Compact canonical constructor — validate / normalise

Omit the parameter list and the field assignments; write only the checks. The fields are assigned for you afterwards.

Legacy — validation in a full constructor
public Range(int lo, int hi) {
  if (lo > hi) throw new IllegalArgumentException();
  this.lo = lo;
  this.hi = hi;
}
Record — compact constructor
public record Range(int lo, int hi) {
  public Range {                       // no params, no assignments
    if (lo > hi) throw new IllegalArgumentException();
  }
}

Extra members that are allowed

public record Point(int x, int y) {
  static final Point ORIGIN = new Point(0, 0);     // static fields: OK
  public Point(int v) { this(v, v); }              // extra constructors: OK (must delegate)
  public double distanceTo(Point o) {              // instance methods: OK
    return Math.hypot(x - o.x, y - o.y);
  }
  public static Point of(int x, int y) {           // static factory: OK
    return new Point(x, y);
  }
}
Not allowed: extra instance fields (all state must be a component), and you cannot extend another class (records already extend Record). You can implements interfaces.

Generic records & local records

Records can take type parameters like any other type, and — since they're just a kind of class — can be declared locally inside a method, scoped to exactly where you need a throwaway data shape:

record Pair<A, B>(A first, B second) {}
var p = new Pair<>("x", 42);
System.out.println(p);   // Pair[first=x, second=42] — verified

List<Order> topByScore(List<Order> orders) {
  record Scored(Order order, double score) {}   // local record — only exists in this method
  return orders.stream()
      .map(o -> new Scored(o, rank(o)))
      .sorted(comparingDouble(Scored::score).reversed())
      .map(Scored::order)
      .toList();
}

4 · Immutability & defensive copies

Records are shallowly immutable: the component references can't change, but if a component is itself mutable (a List, array, Date), callers can still mutate what it points to. Copy in the compact constructor for real immutability.

Leaky — shares the caller's list
public record Team(String name, List<String> members) { }

var list = new ArrayList<>(List.of("Ada"));
var team = new Team("A", list);
list.add("Bob");             // 😱 mutates the record's list too
Safe — defensive copy
public record Team(String name, List<String> members) {
  public Team {
    members = List.copyOf(members);   // immutable snapshot
  }
}
// now external mutation of the original list has no effect

5 · Records + pattern matching

Records were co-designed with pattern matching: because their shape is transparent, they can be destructured directly (record patterns, Java 21).

Legacy — accessor soup
if (obj instanceof Line l) {
  Point a = l.start(), b = l.end();
  int x1 = a.x(), y1 = a.y();
  int x2 = b.x(), y2 = b.y();
}
Record patterns
if (obj instanceof Line(Point(var x1, var y1),
                        Point(var x2, var y2))) {
  // all four bound at once
}
// Sealed + records + switch = type-safe "algebraic data types"
sealed interface Expr permits Num, Add {}
record Num(int v)            implements Expr {}
record Add(Expr l, Expr r)   implements Expr {}

int eval(Expr e) {
  return switch (e) {
    case Num(int v)          -> v;
    case Add(Expr l, Expr r) -> eval(l) + eval(r);
  };   // exhaustive — no default needed
}

See Pattern matching and Sealed classes.

The record-vs-enum choice comes down to one question: is the set of values fixed and known at compile time? Days of the week, HTTP methods, and status codes are enums — there will only ever be exactly those constants. A Point, a Money amount, or a row from a database has unlimited possible values with the same shape — that's a record. (Enums can carry fields too — MONDAY(1), TUESDAY(2) — but every constant is still one specific, pre-declared singleton, never a fresh instance built from runtime data.)
If a type is mostly data and immutable, reach for a record. If it needs mutability, inheritance, or lots of behaviour, use a class. Records largely remove the need for Lombok's @Value/@Data on Java 16+.

7 · Serialization

Records serialize based on their components, and deserialization goes through the canonical constructor — so your validation runs on the way in. That's a real safety improvement over normal serialization, which bypasses constructors.

public record Money(String currency, long cents) implements Serializable {
  public Money {                       // runs on deserialize too
    if (cents < 0) throw new IllegalArgumentException("negative");
  }
}

8 · Pitfalls

PitfallReality
"Records are fully immutable"Only shallowly — defensively copy mutable components.
Expecting getX()Accessors have no get prefix: it's x(). Watch frameworks that assume JavaBeans naming.
Adding instance fieldsNot allowed — all state is components.
Big records as JPA @EntityEntities need mutability & a no-arg ctor; records suit projections/DTOs, not entities.
Reordering components laterChanges the canonical constructor signature & serialized form — it's part of the API.
An array-typed componentGenerated equals/hashCode/toString use identity for arrays (like Object[], not Arrays.equals) — verified: two records holding content-equal byte[] arrays are equals() false, and toString() prints [B@hash, not the contents. Use a List instead of an array in a record.

Worked example — DTO + multiple return values

Legacy — a class for a JSON response, array for two values
// response DTO: 30+ lines of a manual class (omitted)
public final class UserResponse { /* fields, ctor, getters, equals... */ }

// "return two things" via an Object[] — untyped and fragile
Object[] minMax(int[] xs) {
  return new Object[]{ min(xs), max(xs) };
}
Object[] r = minMax(data);
int lo = (int) r[0], hi = (int) r[1];   // casts everywhere
Records
public record UserResponse(String id, String name, boolean active) { }

// typed, self-documenting multiple return
record MinMax(int min, int max) { }
MinMax minMax(int[] xs) {
  return new MinMax(min(xs), max(xs));
}
var mm = minMax(data);
int lo = mm.min(), hi = mm.max();       // no casts, clear names

10 · Cheat sheet

Records in one glance

  • record Point(int x, int y) {} → ctor + x()/y() + equals/hashCode/toString.
  • Immutable & final; extends Record; can implement interfaces, not extend classes.
  • Validate/normalise in the compact constructor; defensively copy mutable components.
  • Accessors have no get prefix.
  • Destructure with record patterns; pair with sealed types for ADTs.
  • Use for DTOs / value objects / multiple returns — not JPA entities.
