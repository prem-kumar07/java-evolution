1 · JVM runtime memory areas

The JVM specification divides runtime memory into five areas. Only one of them — the heap — is what the garbage collector manages.

AreaScopeHoldsReclaimed by
HeapShared (whole JVM)Every object, arrayGarbage collector
MetaspaceSharedClass metadata (methods, fields, constant pools)Class unloading (rare) / native OS memory
Thread stackPer-threadMethod frames, local variables, object referencesAutomatic — pops on method return
PC registerPer-threadAddress of the current bytecode instructionN/A — just a pointer
Native method stackPer-threadState for JNI / native code callsManual (native code's own rules)
PermGen is gone. Before Java 8, class metadata lived in a fixed-size "Permanent Generation" inside the heap — a notorious source of OutOfMemoryError: PermGen space. Java 8 replaced it with Metaspace, which lives in native memory and grows automatically (bounded by -XX:MaxMetaspaceSize if you set it).

2 · The Java Memory Model

Multiple threads reading and writing the heap raises a question the type system can't answer: if thread A writes a field, when is thread B guaranteed to see it? The Java Memory Model (JLS Chapter 17) answers this with one core relationship: happens-before.

"If one action happens-before another, then the first is visible to and ordered before the second." — JLS §17.4.5, verified from the current spec

What creates a happens-before edge

Program order within one thread always happens-before itself, but across threads you need one of these — verified straight from JLS §17.4.4 (synchronizes-with):

  • An unlock on a monitor happens-before every subsequent lock on that same monitor.
  • A write to a volatile field happens-before every subsequent read of that field.
  • Starting a thread happens-before the first action inside it; a thread's last action happens-before code that observes it via join() or isAlive().
  • Writing a default value (0/null/false) to every field of an object happens-before any action in the program — fields are never "uninitialized garbage" in Java.
  • The completion of a constructor for an object with final fields happens-before any read of those fields (the "freeze" action — see §2e below).
  • An action that interrupts a thread (t.interrupt()) happens-before the point where the target detects the interrupt (InterruptedException / Thread.interrupted()).
  • Happens-before is transitive: if A hb B and B hb C, then A hb C.

Concrete reordering example — why this matters

Without a happens-before edge the compiler/CPU may freely reorder independent writes. Consider two shared variables x and y initially 0:

// Thread 1           // Thread 2
x = 1;                int r1 = y;
y = 1;                int r2 = x;
// Surprisingly legal result: r1 == 1 AND r2 == 0
// Thread 1 reordered y=1 before x=1; Thread 2 saw the reordered state

Making y volatile would prevent this: the write y = 1 would carry a memory barrier that forces x = 1 to be visible before y's write completes.

Verified: a real visibility bug, and the one-word fix

Without a happens-before edge, the compiler and JIT are free to assume a field never changes and cache it — this is not theoretical. Run this yourself:

Without volatile — hangs forever, verified
public class VisibilityDemo {
  static boolean stopRequested = false;   // plain field

  public static void main(String[] args) throws Exception {
    Thread worker = new Thread(() -> {
      while (!stopRequested) { /* spin */ }
      System.out.println("worker stopped");
    });
    worker.start();
    Thread.sleep(1000);
    stopRequested = true;              // main thread's write...
    worker.join(3000);
    System.out.println(worker.isAlive()
        ? "worker STILL RUNNING after 3s"   // ...never seen by worker
        : "worker exited normally");
  }
}
// verified real output: "worker STILL RUNNING after 3s"
// the JIT hoisted the field read out of the loop — no happens-before edge exists
With volatile — fixed, verified
public class VisibilityFixed {
  static volatile boolean stopRequested = false;   // ONE keyword

  public static void main(String[] args) throws Exception {
    Thread worker = new Thread(() -> {
      while (!stopRequested) { /* spin */ }
      System.out.println("worker stopped");
    });
    worker.start();
    Thread.sleep(1000);
    stopRequested = true;
    worker.join(3000);
    System.out.println(worker.isAlive() ? "still running" : "exited normally");
  }
}
// verified real output: "worker exited normally — volatile fixed it"
Why this matters for GC too: the JMM is the same contract the garbage collector itself relies on internally (safepoints, card-marking writes) — and it's exactly why virtual threads needed scoped values rather than ad hoc shared mutable state.

Advanced JMM: Instruction Reordering & the "As-If-Serial" Illusion

To maximize performance, the compiler, JIT, and CPU are legally allowed to reorder your instructions (e.g., delaying a memory write or hoisting a read) as long as single-threaded execution isn't broken (the "as-if-serial" guarantee). But across threads, this breaks instantly without a happens-before edge.

Advanced JMM: The Double-Checked Locking Bug

The classic Singleton lazy-initialization pattern is the most famous victim of instruction reordering. Without volatile, this code is fatally broken:

public class Singleton {
  private static Singleton instance; // BUG: missing 'volatile'
  public static Singleton getInstance() {
    if (instance == null) {
      synchronized (Singleton.class) {
        if (instance == null) instance = new Singleton(); // The danger zone
      }
    }
    return instance;
  }
}

Why it fails: The JVM performs three steps for new Singleton(): (1) allocate memory, (2) initialize the object (call constructor), and (3) assign the reference to instance. The JMM allows the CPU to reorder these as 1 → 3 → 2. Another thread calling getInstance() could see instance != null (step 3) and return a partially initialized object because the constructor hasn't finished yet (step 2)!
The Fix: Adding volatile to instance establishes a memory barrier. It strictly prevents the write of the reference from being reordered ahead of the object's initialization.

Advanced JMM: final Field Semantics (Initialization Safety)

The JMM provides a special guarantee for final fields. At the end of a constructor, the JMM issues a "freeze" action on all final fields. This creates a happens-before relationship ensuring that any thread that sees the object reference will always see the fully initialized values of those final fields.

  • No Locks Needed: You don't need volatile or synchronized to safely read a final field across threads.
  • The Catch (No Leaking): This guarantee is completely voided if you let the this reference "escape" during construction (e.g., publishing this to a listener or a static field inside the constructor). If this escapes, other threads might see the object before the freeze action occurs.

Advanced JMM: Safe Publication Patterns

"Publication" means making an object reference visible to another thread. Unsafe publication is the #1 source of subtle concurrency bugs — thread B sees the reference but reads partially initialized fields. The JMM defines exactly four safe ways to publish an object:

Safe Publication TechniqueHow it works
static initializerJVM class-loading guarantees the object is fully initialized before any thread can access it. Simplest and safest.
volatile fieldWriting the reference to a volatile field establishes a happens-before edge — all prior writes (including the constructor) are visible to readers.
final fieldThe JMM "freeze" action (§2e) guarantees visibility of final fields without any synchronization — the basis of safe immutable objects.
synchronized / LockAcquiring a lock that was released by the publishing thread creates a happens-before edge. Also applies to concurrent collections (ConcurrentHashMap.put, BlockingQueue.offer).
The Initialization-on-Demand Holder idiom — the preferred lazy singleton in modern Java: 
public class Registry {
  private static class Holder { // Loaded only on first call to getInstance()
    static final Registry INSTANCE = new Registry();
  }
  public static Registry getInstance() { return Holder.INSTANCE; }
}
// Thread-safe, lazy, no volatile needed — relies on JVM class-loading guarantee.

Advanced JMM: Atomics and Compare-And-Swap (CAS)

volatile gives you visibility but not atomicity for compound operations. count++ on a volatile field is still a race (read → increment → write). The java.util.concurrent.atomic package solves this with hardware-level Compare-And-Swap (CAS) instructions:

AtomicInteger counter = new AtomicInteger(0);
counter.incrementAndGet(); // Thread-safe, lock-free, uses CPU CAS instruction

// Under the hood, incrementAndGet does this:
// for (;;) {
//     int current = get();
//     int next = current + 1;
//     if (compareAndSet(current, next)) return next; // retry on contention
// }
ClassUse case
AtomicInteger / AtomicLongLock-free counters, sequence generators.
AtomicReference<V>Lock-free updates to a shared object reference.
AtomicBooleanOne-shot flags (e.g., "initialized?").
LongAdder / LongAccumulatorHigh-contention counters — internally stripes across cells to reduce CAS retries. Prefer over AtomicLong for statistics/metrics.

Advanced JMM: VarHandle Memory Ordering Modes Java 9

java.lang.invoke.VarHandle (JEP 193) replaced the internal sun.misc.Unsafe API with a standard, type-safe mechanism for fine-grained memory access. It exposes four ordering modes, from weakest to strongest:

ModeMethodsGuaranteeUse case
Plainget(), set()No ordering guarantee across threads (same as a normal field).Single-threaded hot paths.
OpaquegetOpaque(), setOpaque()Coherence order for this variable only — no reordering of accesses to this var, but no barrier for other vars.Progress indicators, spin-loops.
Acquire/ReleasegetAcquire(), setRelease()Release writes are visible to subsequent acquire reads. All prior writes become visible (one-way fence).Lock-free data structures, message passing.
VolatilegetVolatile(), setVolatile()Full acquire + release + total ordering across all volatile accesses (same as volatile keyword).When total order is essential.
Rule of thumb: Use java.util.concurrent classes first (AtomicLong, ConcurrentHashMap). Reach for VarHandle only in performance-critical library code where you need acquire/release or opaque semantics — most application code never needs it.

4 · How garbage collection actually works

A collector needs to answer one question — is this object still reachable? — then act on the answer. Every collector on this page is built from combinations of these phases:

PhaseWhat it does
MarkWalk the object graph from GC roots (stack frames, static fields, JNI handles) and mark everything reachable.
SweepReclaim memory occupied by anything not marked.
CompactSlide live objects together to eliminate fragmentation, so large contiguous allocations stay possible.
Evacuate / copyCopy live objects out of the region being collected into a fresh one — compaction and reclamation in one step (G1, ZGC, Shenandoah all do this).

The other axis is who does the work, and does the application keep running while they do it:

  • Stop-the-world (STW): application threads are paused for the phase. Serial and Parallel do almost everything this way.
  • Parallel: multiple GC threads work simultaneously during a stop-the-world pause — shortens the pause, doesn't remove it.
  • Concurrent: GC threads run alongside application threads with only brief STW pauses for bookkeeping — this is what makes G1, ZGC and Shenandoah low-pause.

Minor GC collects the young generation only (fast, frequent). Major GC collects the old generation. A Full GC collects the entire heap — the one you actually want to avoid, since it's typically the longest stop-the-world pause a JVM will take.

5 · The collectors, one by one

Serial — -XX:+UseSerialGC

One thread does everything, stop-the-world. Verified default choice on small/single-CPU machines. Best for tiny heaps, containers, and CLI tools where startup and footprint matter more than pause time.

Parallel (the "throughput" collector) — -XX:+UseParallelGC

Same generational design as Serial, but multiple threads split the STW work. Oracle's own guide: on machines with 8+ hardware threads, it uses roughly 5/8 of them as GC threads by default. Best for batch jobs and throughput-sensitive workloads that can tolerate occasional pauses.

CMS (Concurrent Mark Sweep) — Removed in 14 JEP 363

The first mainstream concurrent, low-pause collector. Deprecated in Java 9, removed in Java 14 — G1 replaced it entirely. If you inherit code with -XX:+UseConcMarkSweepGC, it won't even start on a modern JDK; migrate to G1.

G1 (Garbage-First) — default, -XX:+UseG1GC JEP 248

Default since Java 9. Verified from Oracle's own docs: "generational, incremental, parallel, mostly concurrent, stop-the-world, and evacuating." Splits the heap into equal-sized regions (not one contiguous young/old block) and prioritizes collecting the regions with the most garbage first — hence the name. Full deep dive → §7.

ZGC (Z Garbage Collector) — -XX:+UseZGC

A scalable, low-latency concurrent collector. Verified from Oracle's docs: pause times independent of heap size, "without stopping application threads for more than a millisecond," scales from a few hundred MB to 16 TB. Verified: as of JDK 24, ZGC is generational by default JEP 474 — the old -XX:+ZGenerational and non-generational ZGC have been removed entirely JEP 490.

Shenandoah — -XX:+UseShenandoahGC

Verified from the OpenJDK wiki: "the low pause time garbage collector... pause times are no longer directly proportional to the size of the heap. Garbage collecting a 200 GB heap or a 2 GB heap should have the similar low pause behavior." A Red Hat-led alternative to ZGC with a similar goal, using concurrent compaction rather than ZGC's colored-pointer approach.

Oracle JDK note: JEP 189 was merged into OpenJDK 12, but Oracle JDK did not include Shenandoah until Java 17. If using Oracle-branded JDK builds (not OpenJDK), Shenandoah is available starting from Java 17.

Epsilon (No-Op) — -XX:+UnlockExperimentalVMOptions -XX:+UseEpsilonGC

Allocates memory and never collects it. Verified: it requires unlocking experimental options first, or the JVM refuses to start with a clear error. Useful for performance-testing allocation cost with GC removed from the equation, ultra-short-lived jobs, and memory-pressure testing (it will happily run until it hits -Xmx and then throw OOM).

7 · G1 deep dive — region-based heap

Unlike Serial/Parallel's contiguous young/old blocks, G1 divides the whole heap into many equal-sized regions — each one independently labeled Eden, Survivor, Old, or Humongous (for objects larger than half a region).

Verified live region breakdown — run any program and inspect it with jcmd:

jcmd <pid> GC.heap_info
// verified real output:
// garbage-first heap   total reserved 65536K, committed 65536K, used 58320K
//  region size 1M, 10 eden (10M), 3 survivor (3M), 44 old (44M), 0 humongous (0M), 7 free (7M)

10 · Hands-on lab — try it yourself

One program, five collectors, real differences you can see on your own machine. Save this and run it exactly as shown:

// GcLab.java
import java.util.*;

public class GcLab {
  public static void main(String[] args) throws Exception {
    List<byte[]> garbage = new ArrayList<>();
    for (int i = 0; i < 2000; i++) {
      garbage.add(new byte[100_000]);     // steady allocation, ~200MB churn
      if (i % 500 == 0) garbage.clear();  // let most of it die young
    }
    System.out.println("done, list size=" + garbage.size());
  }
}
java -Xmx64m -XX:+UseSerialGC   -Xlog:gc GcLab.java   # single-threaded pauses
java -Xmx64m -XX:+UseParallelGC -Xlog:gc GcLab.java   # multi-threaded, still full-STW
java -Xmx64m -XX:+UseG1GC       -Xlog:gc GcLab.java   # young + concurrent-mark + mixed
java -Xmx64m -XX:+UseZGC        -Xlog:gc GcLab.java   # Minor/Major, sub-ms pauses
java -Xmx64m -Xlog:gc+age=trace GcLab.java            # watch the age table climb

Then compare region occupancy live while it runs:

java -Xmx64m GcLab.java &
jcmd $! GC.heap_info      # run this a few times while it's executing
What to look for: Serial's pauses are longer but the log is simplest. G1 shows distinct "Concurrent Start" / "Concurrent Mark Cycle" / "Mixed" phases you won't see in Serial or Parallel. ZGC's pause times (the trailing 0.00Xs) barely move even as the heap grows — that's the whole point of a concurrent collector.

11 · Advanced concepts

ConceptWhat it means
TLAB (Thread-Local Allocation Buffer)Each thread gets a private chunk of Eden to allocate from without synchronizing with other threads — this is why object allocation in Java is typically faster than a generic malloc.
Escape analysisThe JIT can prove an object never "escapes" a method (no reference survives it) and may allocate it on the stack or in registers instead of the heap — entirely a JIT decision, not something your code controls or can force.
SafepointA point where every thread's state is consistent enough to pause it — the JVM brings all threads to a safepoint before a stop-the-world GC phase can begin.
Card markingInstead of rescanning the whole old generation to find references into the young generation, the JVM marks small "cards" of memory that were written to, so a minor GC only rechecks those.
Compressed oopsOn 64-bit JVMs with heaps under ~32GB, object references are stored as 32-bit offsets instead of full 64-bit pointers — halves reference size, is on by default (-XX:+UseCompressedOops).
Colored pointers (ZGC)ZGC steals unused bits in a 64-bit pointer to store GC metadata directly in the reference, letting it relocate objects concurrently without a separate forwarding table.

12 · Pitfalls

PitfallReality
Catching OutOfMemoryError and immediately logging/concatenating a stringVerified real bug: if the offending reference is still held, the heap is still full — building the log string can throw a second, uncaught OOM. Release the reference (leak = null;) before doing anything else in the catch block.
Static collections / listener registries that only growThe #1 real-world "memory leak" in Java — nothing is technically unreachable, so the GC (correctly) never frees it. Always pair a registration with a matching removal.
"GC overhead limit exceeded"The JVM detected it's spending >98% of time collecting for <2% heap recovered — not a bug, a real signal to raise -Xmx or fix a leak.
Assuming a bigger heap is always betterBigger heaps mean longer full-GC pauses on STW collectors. Pick a collector suited to your latency budget first, then size the heap.
Tuning young-generation size manually with G1Oracle's own guidance: avoid -Xmn/-XX:NewRatio with G1 — fixing the young size overrides and disables G1's pause-time control entirely.
Expecting System.gc() to force a GCIt's only a hint — the JVM is free to ignore it, and often does under production flags.

14 · Cheat sheet

JVM memory & GC in one glance

  • Memory areas: heap (GC'd) + metaspace (shared) + stack/PC/native-stack (per-thread, not GC'd).
  • JMM: volatile write → happens-before → subsequent read by any thread. No edge = no visibility guarantee.
  • Generational hypothesis: most objects die young — Eden → Survivor (age++) → Old (tenured).
  • Collectors: Serial (simple) → Parallel (throughput) → G1 (default, balanced) → ZGC/Shenandoah (lowest latency) → Epsilon (none, benchmarking).
  • See it live: -Xlog:gc, jstat -gcutil <pid>, jcmd <pid> GC.heap_info.
  • Verified gotcha: release references before logging inside an OutOfMemoryError catch block.
  • Never manually tune G1's young size — it disables pause-time control.
